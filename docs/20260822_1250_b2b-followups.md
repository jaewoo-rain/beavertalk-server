## 1. 항목 4 — 반 이탈 시 익명화

### 문제

`11_개인정보방침_개정안.md` §3.4 ⑤ 가 「지체 없이 파기」를 약속한다.
현행 `remove_from_class` 는 `left_at` 만 세우는 소프트 삭제다.
`roster_name`·`student_no`·`member_id` 가 그대로 남아 **방침이 거짓이 된다.**

### 방침

**삭제가 아니라 익명화다.** 두 요구를 동시에 만족해야 한다.

| 요구 | 근거 |
|---|---|
| 개인 식별 정보 소멸 | §3.4 ⑤ · §3.5 ⑤ |
| 반 단위 통계값 유지 | §3.4 ⑤ 단서 |

`submission` 행을 지우면 `assignment_stats` 의 분모가 소급 변동한다.
행은 남기고 **사람으로 되짚을 통로를 끊는다.**

### 변경

| 필드 | 이탈 시 |
|---|---|
| `roster_name` | `NULL` |
| `student_no` | `NULL` |
| `teacher_alias` | `NULL` |
| `member_id` | `NULL` — 사람으로 가는 유일한 링크 |
| `left_at` | 현재 시각 |
| `submission` 행 | **유지** |

- `roster_name`·`member_id` 를 nullable 로 바꾸는 마이그레이션 1건이 필요하다.
- `uq_classroom_member(classroom_id, member_id)` 는 Postgres 에서 NULL 을 서로 다르게 보므로
  익명화 행이 여러 개여도 충돌하지 않는다.
- 재참여는 **새 행**이 된다. 기존 되살리기 경로(`existing.left_at = None`)는 `member_id`
  조회로 찾으므로 익명화된 행에는 걸리지 않는다. **새 동의 = 새 행이 옳다.**

### 검증

- 이탈 후 명단 조회에 안 뜬다.
- 이탈 후 `assignment_stats` 의 `total`·`completed` 가 변하지 않는다.
- 이탈 후 같은 회원이 재참여하면 새 `classroom_member_id` 를 받는다.

## 2. 항목 5 — 제출 배선

### 현행

`submission` 행은 과제 생성 시 전원분이 `not_started` 로 깔린다. **아무도 채우지 않는다.**

### 두 활동의 성격이 다르다

| 활동 | 서버가 이미 아는가 | 배선 방법 |
|---|---|---|
| **회화** | **안다.** `item_evidence` 가 통화별로 쌓인다 | **서버 단독 자동 배선** |
| **발음** | **모른다.** `learning_item` 예문을 채점하는 경로가 없다 | **엔드포인트 계약만 제공** |

### 2.1 회화 — 자동 배선

`_apply_call_mastery` 가 증거를 적립한 직후에 접는다.

```
통화 분석 종료
  → item_evidence 적립 (기존)
  → [신설] 이 회원의 진행 중 과제를 찾는다
       assignment.closed_at IS NULL
       AND 'conversation' IN activities
       AND classroom_member.left_at IS NULL
  → 과제의 target_item_ids ∩ 이 통화의 E2·E3 증거 item_id
  → submission.conversation_met = 교집합 크기
     submission.call_id = call_id
     submission.status  = 'done' (증거가 1건이라도 있으면)
     submission.completed_at = now
```

- **시간·턴 임계를 만들지 않는다.** `06` §6.1 · D15 확정 — 증거 유무가 기준이다.
- E1(모방)은 세지 않는다. `06` §4.
- 같은 통화가 두 번 분석돼도 `has_call_evidence` 가드가 앞단에서 막는다. 멱등.
- **한 통화가 여러 과제를 동시에 만족시킬 수 있다.** 반 2곳에 속한 학습자가 그렇다.
  전부 갱신한다 — 통화 1건을 과제 1건에 귀속시킬 근거가 없다.

### 2.2 발음 — 엔드포인트 계약

앱이 결과를 보내야 한다. 서버가 만들 수 없다.

```
POST /classroom/enrollment/assignments/{assignment_id}/speaking
  { passed: int, total: int, failed_item_ids: [int] }
  → submission.speaking_passed/speaking_total/failed_item_ids/status/completed_at
```

- ⛔ **호출자가 아직 없다.** Flutter 쪽 `/learning/intro` 완료 훅이 붙어야 동작한다.
  이 사실을 숨기지 않는다 — 배선했다고 말하면 거짓이다.
- 이 엔드포인트가 채우는 `failed_item_ids` 가 `weak_items()`(다시 가르칠 문장)의 유일한 재료다.

### 검증

- 목표 항목을 쓴 통화 1건 → 해당 과제 `status='done'`, `conversation_met` 일치.
- 목표와 무관한 통화 → 과제 미변동.
- E1 만 있는 통화 → 세지 않는다.
- 닫힌 과제·이탈 회원 → 갱신 대상 아님.

## 3. 항목 6 — `meanings` 병합

### 사실

| | 값 |
|---|---|
| 앱 어휘 `meanings` 보유 | **0 / 10,636** (`assets/level/curriculum_v2/vocab.json` 실측) |
| 워크북 보유 | `meaning`(영문 뜻) · `rom`(로마자) — `06_인쇄물디자인_하네스/_workspace/topik{1..6}.json` |
| 소비 형식 | `{"en": "...", "roman": "..."}` — `normalcall_service._study_des` · `_study_roman` |

### 조인 키

`surface` 직접 매칭이 아니라 **`source_key`(`v:{surface}{접미|00}`)** 로 간다.
시드 멱등 키이므로 재실행에 안전하다.

1. `vocab.json` 에서 `(topik_grade, surface) → source_key` 색인
2. 워크북 `(level, term)` 을 그 색인에 붙인다
3. **한 (급수, 표면형)에 행이 2개 이상이면 건너뛴다** — 동형이의어에 한 뜻을 덮어씌우면
   틀린 데이터가 된다. 건너뛴 건수를 보고한다

### 산출

- `scripts/merge_vocab_meanings.py` — 기본 **dry-run**. `--apply` 로만 DB 를 쓴다.
- 병합본 JSON 을 파일로 떨어뜨려 DB 없이도 결과를 셀 수 있게 한다.

⛔ **DB UPDATE 는 이번에 실행하지 않는다.** `.env` 부재.

## 4. 항목 7 — 파일럿 첫 주 수치

**할 수 없다.** 파일럿이 없고 dev DB 에도 붙을 수 없다.
원 질문은 「회화 사용 판정(E2·E3만 셈)이 초급 반에서 어떤 숫자를 내는가」였다.
실통화 증거가 있어야 답이 나온다.

**데이터로 답할 수 있는 절반만 한다** — 분모 실측.
과제의 회화 분모는 챕터의 **핵심(`is_core`) 어휘 수**다. 이것이 급수·챕터별로 얼마인지는
`vocab.json` 만으로 셀 수 있다. 분모가 20을 넘으면 초급 반에서 달성률이 구조적으로 낮게 나온다.

산출 = 급수별 챕터당 핵심 수 분포(최소·중앙·최대). 판단 재료로 남긴다.
