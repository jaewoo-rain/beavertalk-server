## 0. P1이 붙이는 것

```
P0 (완료)   마이크 → STT v2 → [턴 감지] → user_turn_end(텍스트)
P1 (이 문서)                              ↓
                        [LLM 텍스트 스트리밍] → [문장 분할] → [TTS 스트리밍]
                                              ↓
                        [페이서 + 원장] → PCM24k → 클라   (+ barge-in 취소)
```

이미 확정돼 있어 **다시 정하지 않는 것**: 송출 불변식 I1~I5, `audio_cancel` 계약,
`played_server_bytes` 원장, 페이서(100ms 고정 간격 + 무음 패딩), 에코 2차 방어.
전부 `BeaverOutput`에 이미 들어가 있고 테스트로 고정돼 있다.

## 1. LLM 단계

### 1-1. 모델

| 후보 | 15분 통화 비용(저밀도/고밀도) | 선택 |
|---|---|---|
| `gemini-2.5-flash` | $0.098 / $0.234 | **기본값** |
| `gemini-2.5-flash-lite` | $0.032 / $0.075 | 품질 비교 후 후보 |

차이는 통화당 **$0.066**. 캐스케이드 총원가($0.41)의 16%라 **품질을 먼저 보고 정해도 되는
규모**다. 기본은 2.5 Flash로 시작하고 `CASCADE_LLM_MODEL` env로 교체 가능하게 둔다.

> 암묵 캐싱이 이 항을 최대 90% 깎을 수 있다(지시문 4,700 tok가 최소 캐시 단위를 넘는다).
> 적중률 미확인이라 원가 계산에는 넣지 않되, **프롬프트 앞부분을 통화 내내 고정**해
> 프리픽스가 깨지지 않게 짠다(= 시스템 지시문 뒤에 대화 이력을 append만 한다).

### 1-2. 프롬프트 — 새로 만들지 않는다

`core/persona_prompt.build_system_instruction(...)`을 **그대로 재사용**한다. LLM 생성 0,
순수 문자열 조립이라 Live/캐스케이드 어느 쪽이든 같은 입력을 만든다. 레벨테스트는
`build_leveltest_instruction`. **이 파일은 수정하지 않는다** — 두 엔진이 같은 페르소나를
쓰는 것이 비교의 전제다(품질 차이가 프롬프트 차이로 오염되면 안 된다).

⚠ 단 하나 다른 점: Live는 오디오를 직접 듣지만 캐스케이드는 **STT 전사만** 본다. 발음·억양
정보가 사라지므로 발음 교정 지시는 캐스케이드에서 근거가 약해진다. P1에서는 그대로 두고,
통화후 분석(기존 경로)이 발음을 맡는다.

### 1-3. 이력 관리 — 여기가 캐스케이드의 급소

```python
history = [
  {"role": "user",  "text": user_turn_end.text},          # STT 최종 전사
  {"role": "model", "text": beaver.spoken_text(turn_id)},  # ⭐ 실제로 들린 데까지만
  ...
]
```

- 중간에 잘린 비버 턴은 **생성 전체가 아니라 `spoken_text`**를 넣는다(설계 §5).
  뒤에 `…(사용자가 끼어들어 여기서 끊김)`을 붙여 LLM이 문맥을 이해하게 한다.
- 생성 전체(`generated_text`)는 **감사·분석용으로 따로** 보관한다. 두 값을 섞지 않는다.
- `playback_progress`가 안 오면 서버 추정으로 폴백하되 짧은 쪽 편향(§5-3).

### 1-4. 스트리밍 + 문장 분할

LLM 출력을 **스트리밍으로 받아 문장 단위로 즉시 TTS에 흘린다.** 첫 소리까지의 지연이
여기서 결정된다.

```
분할 기준: 종결부호(. ? ! 。) / 줄바꿈 / 길이 상한(120자)
           + 최소 길이(12자) — 너무 잘게 쪼개면 TTS 요청 수가 늘고 운율이 끊긴다
```

⚠ **Cloud TTS 스트리밍 요청은 5,000 bytes 상한**이고 한국어는 UTF-8 3바이트라 **약 1,600자**다.
문장 단위면 절대 안 닿지만, 상한 체크는 코드에 남긴다(모델이 폭주 출력할 때의 방어).

## 2. TTS 스트리밍 배관

### 2-1. `core/tts.py`에 **덧붙인다** (기존 `synthesize()` 무손상)

```python
async def synthesize_stream(text_chunks: AsyncIterator[str], *, voice: str,
                            language: str = "ko") -> AsyncIterator[bytes]:
    """Chirp3-HD streaming_synthesize → PCM16/24kHz 청크."""
```

| | 기존 `synthesize()` | 신규 `synthesize_stream()` |
|---|---|---|
| 용도 | 통화후 분석의 표현 오디오 | **통화 중 비버 발화** |
| 호출 | `synthesize_speech`(단발) | `streaming_synthesize`(양방향) |
| 포맷 | MP3 | **LINEAR16 / 24,000Hz** |
| 끊겼을 때 | 문장 전액 과금 | **안 보낸 문장은 과금 없음** |

D5(기존 무접촉) 준수 — 기존 함수는 한 줄도 안 건드린다.

### 2-2. 확인이 남은 것 하나

`streaming_audio_config.sample_rate_hertz=24000`이 실제로 24k를 내는지 **1회 실측**이 필요하다
(문서에 네이티브 레이트 명시가 없다). 재는 법: 합성 결과 바이트 수 ÷ 48,000 = 초. 예상과
맞으면 앱 재생 경로(PCM24k)에 그대로 꽂힌다 = **앱 수정 0**. 안 맞으면 리샘플 한 단이 붙을 뿐
페이서 설계는 그대로다.

### 2-3. 음색

`_CHIRP3_HD_VOICES`에 Gemini Live 캐릭터 voice와 **같은 이름**이 있다(Fenrir 등). 통화 캐릭터의
voice를 그대로 넘기면 같은 목소리가 난다 — Live에서 캐스케이드로 옮겨도 **비버 목소리가 안 바뀐다.**
이건 이미 `core/tts.py`가 하고 있는 일이고 스트리밍 경로도 같은 `_resolve_voice`를 쓴다.

### 2-4. 스케일 한계 (아키텍처 노트)

| 한계 | 값 | 대응 |
|---|---|---|
| `Chirp3RequestsPerMinutePerProject` | 200/분 | **통화당 TTS 스트림 1개 유지**(턴마다 새로 열지 않는다) |
| `ConcurrentStreamingSessionsPerProject` | 100 | 동시 통화 100건 상한 → 스케일 전 쿼터 증설 신청 |
| SSML | 스트리밍 미지원 | 프롬프트에서 SSML 지시 금지 |

## 3. 상태기계 확장 (P0 골격 그대로)

```
USER_SPEAKING ──(침묵 타이머 만료)──▶ THINKING ──(첫 TTS 청크)──▶ BEAVER_SPEAKING
                                        │                              │
                                        │                    (speech_begin + 2차 방어 통과)
                                        ▼                              ▼
                                    LLM 스트리밍                    CANCELLING
                                                                       │
                                                                 ①합성 cancel
                                                                 ②송신 큐 drain
                                                                 ③audio_cancel
                                                                       ▼
                                                                 USER_SPEAKING
```

P0에서 이미 만들어 둔 것: `TurnState` enum, `_on_barge_in()` 훅, `_bargein_allowed()` 관문,
`BeaverOutput.begin/send/end/cancel`. **P1은 훅의 몸통만 채운다.**

### 3-1. 통화 종료 규약

normalcall의 규약을 그대로 가져온다 — **종료 시점은 서버만 정한다.**
플랜별 통화 길이 경과 → 종료 시드 주입("[시스템] …") → 비버의 작별 발화 → `call_ended`.
캐스케이드에서 달라지는 것은 하나: 작별 발화도 TTS를 타므로 **마지막 바이트를 보낸 뒤**에
`call_ended`를 낸다(I5와 같은 이유).

## 4. 지연 예산 — 사용자가 말을 멈춘 뒤 첫 소리까지

| 단계 | 예산 | 근거 |
|---|---|---|
| 턴 종료 판정(침묵 임계) | **800ms** | 설계 확정값(Live와 동일) |
| STT 최종 전사 대기 | 0~200ms | 대개 침묵 창 안에 도착(§3-1) |
| 파이프라인(리전 왕복+인식) | **?** | ⚠ **P0가 답한다.** 400ms 이하 기대 |
| LLM 첫 토큰(TTFT) | 300~600ms | Flash 계열 추정 |
| 문장 1개 완성 | 100~300ms | 첫 문장만 기다린다(그다음은 겹친다) |
| TTS 첫 청크 | 100~300ms | 스트리밍 합성이라 문장 전체를 안 기다린다 |
| 페이서 선행버퍼 | **200ms** | `CASCADE_TTS_LEAD_MS` |
| 네트워크(서버→클라) | 20~50ms | |
| **합계** | **약 1.5~2.5초** | |

Live의 체감(~1초 내외)보다 **느리다.** 이건 캐스케이드의 구조적 비용이고, 줄일 수 있는 자리는
셋뿐이다: ①침묵 임계 ②리전 ③선행버퍼. 셋 다 env라 실측 후 조정한다.

> ⚠ **원가만 보고 캐스케이드를 고르는 게 아니라, 이 지연을 감수할 수 있는지도 같이 판단해야
> 한다.** 사장님께 보고할 때 "65% 싸다"와 "0.5~1.5초 느리다"를 **같이** 놓아야 한다.

## 5. 취소 배관 실행 상세 (계약은 §4에서 확정됨)

```python
async def _on_barge_in(self, event):
    self.state = TurnState.CANCELLING
    self._llm_task.cancel()          # ① LLM 스트리밍 중단(안 그러면 계속 생성돼 과금)
    self._tts_task.cancel()          # ① TTS 합성 중단(안 보낸 문장은 과금 0)
    self._send_queue.clear()         # ② 송신 큐 비우기
    await self.beaver.cancel()       # ③ audio_cancel(turn_id, epoch) — turn_end 는 안 낸다
    # played_server_bytes 회신은 기다리지 않는다(다음 턴을 막지 않기 위해).
    # 이력 절단은 다음 LLM 호출 **전에만** 확정되면 된다.
```

경합 주의: `_llm_task`/`_tts_task` 취소는 **await 하지 않는다**(취소 완료를 기다리면 그만큼
비버가 더 말한다). 대신 취소된 태스크가 `BeaverOutput.send()`를 호출하면 턴이 이미 닫혀
`InvariantError`가 난다 — 그건 잡아서 로그만 남긴다(정상 경로다).

## 6. 원가 계측 — ⚠ 2026-08-07 갱신: **이미 구현됐다. 이 절의 옛 형식을 쓰지 마라**

계측은 bt-back 확정 계약으로 **P0 단계에서 먼저 붙었다**(`domains/learning/realtime/cascade_usage.py`,
설계 `docs/20260807_0030_캐스케이드-원가계측-설계.md`). 아래 초안의 `est_usd=…` 형식은
**폐기**다 — 달러는 로그에 박지 않는다(단가는 벤더가 바꾼다, 산식은 한 곳에만).

실제 나가는 줄(`cascade usage: engine=… stt_audio_s=… llm_in=… tts_chars=… tts_unheard=…`)은
STT 만 채워진 상태로 이미 돌고 있다. **P1 이 할 일은 형식을 새로 만드는 게 아니라 두 구간을
채우는 것**이다:

| 채울 자리 | 호출 | 넘길 것 |
|---|---|---|
| LLM 응답 1건마다 | `usage.record_llm(resp.usage_metadata, vendor="gemini-2.5-flash")` | 응답 원본의 usage_metadata |
| TTS 합성 1건마다 | `usage.record_tts(text, vendor="cloud-tts-chirp3-hd")` | **API 에 실제로 넘긴 문자열**(strip 후) |
| TTS 실패 | `usage.record_tts(text, failed=True)` | 문자엔 안 더하고 건수만 |
| barge-in 취소 | `usage.record_tts_unheard(chars)` | 합성했지만 못 들려준 문자 수 |

- 마지막 항목이 옛 초안의 `tts_wasted_chars` 다(로그 키는 `tts_unheard`). 이 값이 크면
  문장 분할을 더 잘게 해야 한다는 신호라는 해석은 그대로다.
- `key=value` 라 Cloud Logging 메트릭이 코드 변경 0줄로 붙는다(`normalcall usage:` 와 같은 규율).

## 7. P0 결과가 이 설계를 바꾸는 지점

| P0 결과 | P1에 미치는 영향 |
|---|---|
| 감지지연 ≤ 1.2s, B 시나리오 통과 | **이 설계 그대로 착수** |
| B에서 3초 침묵에 말이 잘림 | 침묵 임계 상향 → §4 지연 예산이 그만큼 늘어난다. 첫 소리 2.5초를 넘으면 선행버퍼·리전을 함께 손봐야 한다 |
| 파이프라인 > 700ms | 리전/모델 실험이 먼저다. 해결 안 되면 **P1 착수 자체를 재검토**(지연이 원가 이득을 상쇄) |
| 전사 품질이 나쁨 | LLM 입력이 오염된다 → 모델 교체(`chirp_3`) 또는 캐스케이드 재검토 |
| 롤오버가 말을 삼킴 | `STT_V2_STREAM_MAX_S` 조정 + 선개통(pre-warm) 도입 검토(이중 과금 감수) |

## 8. 미확정 (P1 착수 시 닫을 것)

1. Chirp3-HD `sample_rate_hertz=24000` 실동작 — 1회 실측(§2-2)
2. LLM 모델 확정 — 품질 비교 후(2.5 Flash vs Lite)
3. 암묵 캐싱 적중률 — 통화 1건의 `cached_content_token_count`로 확인
4. 종료 시드 문구 — normalcall과 동일하게 갈지, 캐스케이드용으로 다듬을지
5. barge-in 실기기 판정 — 브라우저 데모로는 판정 불가(AEC가 공짜라서). Android 4점 세트
   머지 + 에코 리그 실측 후에만 `CASCADE_MIC_ALWAYS_OPEN=true`
