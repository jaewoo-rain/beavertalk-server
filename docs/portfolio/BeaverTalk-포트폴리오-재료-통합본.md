## 이 프로젝트를 관통하는 한 문장

> **측정할 수 없으면 고칠 수 없다.**

계측을 먼저 만들었고, **그 계측이 실제로 결함을 잡았다.** 대표 사례:

| 계측 | 잡아낸 것 |
|---|---|
| 벤더 값의 의미를 모를 때 `sum`·`max`·건수를 **셋 다** 기록 | STT 과금이 누적값임을 실측으로 판별 — **4배 과대계상 방지** |
| `첫소리=-1ms` 판별식 | TTS 무음 사고 — **엔드포인트 200, ERROR 로그 0건**이던 것 |
| 폴백을 **시끄럽게** (모델 ID 포함 WARNING) | Cloud TTS 인데 Vertex 권한이 없던 403 — **1분에 규명** |
| 언어 마커 관측 로그 | **"실험이 성립하지 않았다"** — 소리는 정상이라 귀로는 못 가림 |
| 로거 설정에 `core` 추가 | 실패가 **이름표 없이** 흘러가던 것 |

### 1. 원가를 측정 가능하게 만든 것

#### 무엇을 했나
Gemini Live 네이티브 오디오로 도는 음성통화의 **원가를 아무도 몰랐다.** 서버가 `usage_metadata`를
한 번도 읽지 않았다 — 가장 비싼 항목이 가장 안 보이는 상태였다.

계기판을 3단계로 지었다:
1. 로그 (`normalcall usage:` — `key=value` 고정 형식, Cloud Logging 메트릭이 코드 변경 0으로 뽑아감)
2. DB 영속화 (`call.usage_*` 8컬럼 + `usage_json`) — Cloud Logging 보존이 30일이라
3. 엔진 구분 (`call.usage_engine`) — Live 와 캐스케이드를 갈라 봐야 비교가 된다

#### 숫자 (전부 실측)
| | 값 | 출처 |
|---|---|---|
| Live 15분 통화 원가 | **$1.8724** | `call_id=909`, 902초, Cloud Logging `usage trace` 72건 |
| 입력 오디오 비중 | **78.7%** ($1.4734) | 같은 통화. 모달리티 4항 분해 |
| 압축 발동 | 5회 (15,900↔11,300 톱니) | 같은 통화 시계열 |
| 세션 재연결 | 1회 (480.5s) | `SESSION_ROTATE_AT_S=480` 설계값과 일치 |
| 캐스케이드 실측 | **분당 $0.0296 → 15분 $0.44** | 104초 통화, 6턴 |
| 절감 | **−76%** | 위 둘의 비 |

#### ⭐ 설계 판단 — 달러 컬럼을 만들지 않았다
`call` 테이블에 **원가(달러) 컬럼을 일부러 안 만들었다.** 단가는 벤더가 바꾸는 값이라,
달러를 박아 두면 단가가 바뀐 순간 **과거와 현재를 같은 잣대로 못 본다.**
→ **토큰은 사실, 원가는 파생 계산.** 산식은 코드 한 곳(`estimate_call_cost_usd`)에만 둔다.

#### ⭐ 설계 판단 — NULL 과 0 을 구분했다
기존 796행을 백필하지 않았다. **NULL = "계측 안 됨", 0 = "정말 0 토큰"** 이라야 표본을 믿을 수 있다.
같은 원칙을 산식에도 적용 — **모르는 벤더는 0원으로 먹지 않고 "미상 목록"으로 드러낸다.**
0원으로 처리하면 "캐스케이드가 공짜"라는 **그럴듯한 거짓말이 통계에 섞인다.**

### 2. 계측이 실제로 결함을 잡은 사례 4건

이 프로젝트의 핵심 주제다. **계측을 먼저 만들었고, 그 계측이 실제로 잡았다.**

#### ① 판정을 미룬 덕에 4배 과대계상을 막았다
Google STT v2 의 `total_billed_duration` 이 **증분인지 누적인지 문서로 안 갈렸다**
(v1 은 "for the stream", v2 는 "for the corresponding request" — 문구가 다르다).

→ **해석하지 않고 `sum`·`max`·건수를 셋 다 수집**했다. 첫 실통화가 갈랐다:
```
실제 오디오       104.5초
billed_max_s      102.0초   ← 실제와 일치
billed_sum_s      419.0초   ← 실제의 4배
```
**누적값이 반복해 실린다.** `sum` 을 썼으면 STT 원가를 **4배 과대계상**했다.

#### ② 폴백을 시끄럽게 만든 덕에 403 을 1분에 규명했다
Gemini-TTS 로 전환했는데 소리가 Chirp 이었다. 폴백 WARNING 에 모델 ID 를 박아둔 덕에:
```
tts 폴백: engine=gemini-tts model=gemini-2.5-flash-tts
  실패사유="403 Permission 'aiplatform.endpoints.predict' denied"
```
→ **Cloud TTS 를 호출했는데 거절은 Vertex 가 했다.** Chirp3-HD 는 `texttospeech` 권한만 필요한데
Gemini-TTS 는 내부적으로 Vertex 로 넘어간다. SA 에 `roles/aiplatform.user` 가 없었다.
⛔ 폴백이 조용했으면 **"제미나이가 Chirp 이랑 똑같네"로 끝났을 것이다.**

#### ③ 판별식 하나가 200 도 ERROR 로그도 못 잡은 것을 잡았다
`cascade 대답: … 첫소리=-1ms 글자=49` — LLM 은 답을 쓰는데 소리가 안 났다.
원인은 `AudioEncoding.LINEAR16`. **비스트리밍에선 유효한 값인데 스트리밍은 지원 안 한다**
(SDK 원문: *"Streaming supports PCM, ALAW, MULAW and OGG_OPUS. All other encodings return an error."*).
엔드포인트는 200, ERROR 로그도 없었다. **잡은 건 `첫소리=-1` 판별식뿐이다.**

#### ④ 관측 로그가 "실험이 성립 안 했다"를 알려줬다
언어 마커(`__타깃__`) 실험에서, 폴백이 **조용해서 소리는 정상**이었다. 귀로는 구별이 안 된다.
관측 로그를 심은 덕에:
```
마커=짝안맞음 8건 / 마커=있음 1건 / 언어구간 전부 '1개 ko'
```
→ **모델이 마커를 반만 지킨다.** 이걸 몰랐으면 "끊김 없네"라는 판단을 그대로 썼을 텐데,
**애초에 안 쪼개져서 끊길 일이 없었던 것**이다. 잘못된 결론으로 갈 뻔했다.

### 3. 실시간 오디오의 타이밍 문제 — "두 시계"

같은 종류의 결함을 **하루에 세 번** 밟았다. 전부 **"측정 시각과 이벤트 시각이 다르다"** 였다.

| # | 증상 | 원인 |
|---|---|---|
| 1 | 한 발화가 턴 2개가 됨 | 침묵 타이머가 VAD 지연(≈300ms)을 빼는데, 기다리는 건 최종 전사(≈800ms) |
| 2 | 말했는데 전사가 빈 채로 닫힘 | 위와 같은 뿌리 + 늦게 온 진짜 전사를 "유령 턴"으로 차단 |
| 3 | 끼어들어도 비버가 안 멈춤 | barge-in 에너지(RMS)는 **지금** 값인데, 이벤트는 **800ms 전** 오디오를 가리킴 |

⭐ 3번의 실측 분포가 가설을 그대로 맞췄다:
```
기각 — 에너지 0.0000 / 0.0001 / 0.0003 / 0.0010 / 0.0017   (임계 0.05)
확정 — 1건뿐
```
**짧게 말하면 이벤트 도착 시점엔 이미 조용하다.**
→ (시각, RMS) 이력을 두고 **이벤트가 가리키는 시각 ±400ms 의 최대 에너지**를 보게 고쳤다.

#### ⭐ 설계 판단 — 임계값이 아니라 "언제 재느냐"를 고쳤다
임계(0.05)를 낮추면 증상은 사라진다. 하지만 그건 **감으로 만든 값**이고, 실기기 에코 측정으로
잡기로 한 값이다. **원인은 값이 아니라 시계였다.** 값을 건드렸으면 진짜 원인이 지하로 들어갔다.

### 4. 두 결정이 겹쳐 만든 데드락 (실사용에서만 드러남)

45분 실통화에서 "말했는데 비버가 대답을 안 한다"는 증상이 나왔다. 로그로 재현:
```
02:32:10  대답 취소됨: turn=b36  들린글자=0  못들려준글자=49
02:32:12  빈 턴: id=u49 — 발화 없음(LLM 호출 금지)
```
**barge-in 이 비버를 죽이고 → 그 턴이 빈 채로 닫히고 → LLM 호출 금지 → 침묵.**
45분에 빈 턴 20건, 취소 14건 중 **7건이 `들린글자=0`**(한 글자도 못 들려주고 죽음).

각각은 옳은 결정이었다:
- barge-in 을 관대하게 → 끼어들기가 잘 먹는다
- 빈 턴엔 LLM 을 안 부른다 → 원가 낭비·헛대답 방지

**조합이 나빴다.** 단위 테스트로는 안 잡힌다 — 두 기능이 각자 맞기 때문이다.

#### ⭐ 내 진단이 절반만 맞았다 (이 항목이 가장 값어치 있다)
나는 `_on_transcript` 가 `state==IDLE` 일 때만 턴을 여는 것을 원인으로 지목했다. **맞았지만
셋 중 하나였다.** 진짜 원인은 `_start_reply` 가 "이미 대답 진행 중"이면 새 발화를 **버리는** 것이었다.
**내 수정만 들어갔으면 턴은 열리는데 여전히 답을 안 했을 것이다.**

### 5. 조용한 실패를 드러낸 설계들

| 자리 | 조용했으면 | 어떻게 드러냈나 |
|---|---|---|
| TTS 폴백 | "제미나이가 느리다"로 오독 | WARNING + 모델 ID + `tts=` 에 **실제로 소리를 낸 엔진** 기록 |
| 원가 벤더 미상 | "캐스케이드가 공짜" | 0원이 아니라 `(원가, 미상목록)` 튜플로 반환 |
| 마커 준수 | 판단이 오염됨 | `마커=있음/없음/짝안맞음` **셋으로** 구분 |
| `core.*` 로그 | 실패가 이름표 없이 흘러감 | 로거 설정에 `core` 추가 |
| Live 사고 토큰 | 원가 과소 계상 | 산식엔 안 넣고 **`sum_thoughts>0` 이면 WARNING** |

⭐ 마지막 것이 특히 — **확인 못 한 것을 "확인 못 했다"고 두면서도 썩지 않게** 만든 사례다.
(Vertex 의 모달리티 분해가 사고 토큰을 품는지 확인 못 함 → 더하면 이중계상 위험 → 안 더하고 경고를 심음)

### 6. "같은 벤더면 같은 규칙일 것" 이 세 번 틀렸다

전부 **실사격으로만** 드러났다. 문서·SDK 정의만으로는 못 잡았다.
```
① LINEAR16    비스트리밍엔 유효, 스트리밍엔 무효
② 모델 ID      Cloud TTS 'gemini-2.5-flash-tts' ≠ Gemini API 'gemini-2.5-flash-preview-tts'
③ 음성명 형식  Chirp 'ko-KR-Chirp3-HD-Sulafat' vs Gemini 'Sulafat'(맨이름)
④ 권한        Cloud TTS 인데 Gemini 모델은 Vertex(aiplatform) 권한을 요구
```
→ **"권한 있나"는 "동작하나"가 아니다.** IAM·API 활성·서비스계정을 다 통과시켜도
**인자 값 하나로 무음**이 났다.

### 7. 멀티 에이전트 오케스트레이션 (2026-08-06 ~ 07, 하루)

#### 구성
```
bt-back        오케스트레이터 (분해·계약 정의·검증·통합)
cascade-impl   서버 구현 (캐스케이드)          — git worktree
call15-polish  서버 구현 (원가·15분 통화)      — git worktree
bt-front       Flutter 클라이언트
bt-cascade     Flutter (barge-in 조사)
bt-deploy      배포·인프라 전담
```

#### 하루 실적
```
배포 12회 · 테스트 529 → 629 (+100) · 결함 12건 발견·수정 · IAM/마이그레이션 각 1건
```

#### ⭐ 교차 검증이 실제로 잡은 것 — 혼자 했으면 못 잡았다
1. **두 탭이 서로 다른 모델 ID 를 갖고 있었다** — 한쪽은 Cloud TTS 문서, 한쪽은 Gemini API
   가격 페이지에서 읽었다. 합치는 자리에서 드러났다
2. **계약 키 불일치** — 한쪽이 내는 요약 키(`in_text`)와 다른 쪽이 읽는 키(`in_mod["TEXT"]`)가
   달랐다. 예외도 로그도 없이 **"저장은 됐는데 토큰만 0"** 이 될 뻔했다
3. **미커밋 코드가 배포에 실릴 뻔했다** — `builds submit` 은 워킹트리를 통째로 올린다.
   내가 "clean" 이라고 브리핑했는데 **그 사이 다른 탭이 편집을 시작**했다

#### ⭐ 규율로 정착시킨 것
- **하위 에이전트의 보고를 검증 없이 올리지 않는다** — 테스트 수 9회를 전부 직접 재실행했다
- **"확인했다"에는 유효기간이 있다** — 워킹트리 상태는 시점 정보라 브리핑에 넣으면 안 된다
  (테스트가 7분 걸리는 동안 dirty 로 바뀐다)
- **한 번에 하나씩 바꾼다** — 코드와 env 를 동시에 바꾸면 무엇 때문에 달라졌는지 못 가린다
- **env 선투입 순서** — `extra="ignore"` 를 확인하고 env 를 먼저 넣어 **다운타임 0초**로 전환

#### 내가 틀렸고 하위 에이전트가 고친 것 (신뢰도의 근거)
| 내 판단 | 실제 |
|---|---|
| "들린글자=0 이면 취소하지 마라" | 원장의 '들린 글자'는 문장 단위 — 2초를 들어도 0 일 수 있다. **오디오 시간**으로 재야 한다 |
| "빈 턴 원인은 IDLE 조건" | 셋 중 하나. 진짜는 `_start_reply` 가 버리는 것 |
| "머지하면 테스트 +2" | +9 (델타를 커밋 시점 기준으로 계산했다) |
| "운영은 풀러(6543)를 탄다" | 5432 세션 모드. 호스트 이름만 보고 포트를 확인 안 했다 |
| "404 니까 라우트가 없다" | WS 라우트는 등록돼도 GET 은 404 |

⭐ **이 표가 포트폴리오에서 가장 값어치 있을 수 있다** — 틀린 것을 기록으로 남기고
교차 검증이 그걸 잡는 구조를 만들었다는 증거다.

# ▍캐스케이드 음성통화 — 서버 구현

## 포트폴리오 재료 — 캐스케이드 음성 통화 (서버)

> 용도: 개발자 취업·이직. 읽는 사람이 면접에서 **캐물을 것**을 전제로 썼다.
> 모든 수치에 출처를 달았고 **실측/추정**을 구분했다. 확인 못 한 것은 그렇게 적었다.
> 관통 주제: **측정할 수 없으면 고칠 수 없다.**

**맥락 한 줄**: 오디오를 그대로 주고받는 통합 모델(Gemini Live)로 돌던 한국어 회화 통화를
**STT → LLM → TTS 세 조각**으로 분해해 재현했다. 목적은 원가 절감 하나였고, 그래서
**"싸졌다"를 증명할 계측**이 기능만큼 중요했다.

---

### 1. 계측을 먼저 만들었고, 그 계측이 실제로 결함을 잡았다

#### 1-1. 벤더 값의 의미를 모를 때 **셋을 다 기록**해 4배 과대계상을 막았다
STT 응답의 과금 초가 증분인지 누적인지 proto 문구로 안 갈렸다(v1 과 표현이 바뀌었다).
한쪽으로 정하지 않고 **sum·max·건수를 다 남기고** 실통화 한 건으로 판정했다.
→ 실제 오디오 **104.5초** / max **102.0초** / sum **419.0초**. **sum 을 썼으면 STT 원가가 4배**였고,
하필 그 숫자가 "캐스케이드가 싼가"의 근거로 쓰였을 것이다. (출처: 실통화 `cascade usage` 로그)

#### 1-2. `첫소리=-1ms` 판별식 하나가 무음 사고를 즉시 잡았다
비버가 한마디도 못 하는데 **HTTP 200 이고 ERROR 로그도 없었다**(합성 실패를 graceful 하게
삼키는 구조라). 대답 로그에 "첫 오디오까지 몇 ms"를 넣어 뒀더니 `-1`(= 소리가 한 조각도 안
나감)로 즉시 드러났다. 원인은 스트리밍이 `LINEAR16` 을 거부한 것.
→ **성공/실패가 아니라 "무엇이 실제로 일어났나"를 재는 값**이 사고를 잡는다.

#### 1-3. 폴백을 **시끄럽게** 만들어 둔 덕에 권한 문제가 1분에 규명됐다
TTS 엔진 A/B 를 붙이며 "실패하면 조용히 폴백"을 금지했다 — 조용하면 *"제미나이가 느리다"* 가
아니라 *"제미나이인 줄 알았는데 다른 엔진이었다"* 가 되기 때문이다. 모델 ID 를 로그에 박았다.
→ 실제로 `403 aiplatform.endpoints.predict denied` 가 그 줄에서 바로 나왔다(코드가 아니라 IAM).

#### 1-4. "실험이 성립하지 않았다"를 알아채게 만들었다
대상 언어를 `__마커__` 로 감싸는 기능을 넣고 **로그를 한 줄도 안 늘렸다**. 그런데 폴백이
조용해서, 모델이 마커를 안 써도 통째로 재생돼 **소리는 정상**이다. 즉 "끊김이 줄었다"는 판단이
마커가 걸린 상태의 결과인지 아닌지 **귀로는 못 가른다.**
→ 마커 상태를 **셋으로** 갈라 찍었다: `없음`(모델이 규칙을 안 지킴) / `있음`(짝 맞음) /
`짝안맞음`(반만 지켜서 폴백). 구간 수만 찍으면 앞의 둘이 뭉개진다.
⛔ 대사 원문은 안 찍는다(통화 내용이 로그에 남는다). "원문이 로그로 새지 않는다"도 테스트로 잠갔다.

#### 1-5. 못 모았을 때 **"못 모았다"를 남긴다**
기존 통합 모델 경로는 사용량 수집 실패를 3중으로 조용히 삼켰다(식별자 없음 / 데이터 0건 /
예외). 원가가 안 남아도 아무도 몰랐다. 새 경로는 **`collected=0 reason=…` 한 줄**을 남긴다.
→ 같은 원칙을 산식에도 적용했다: **모르는 벤더는 0원이 아니라 '미상'**(0원으로 먹으면
"공짜"라는 그럴듯한 거짓말이 나온다).

---

### 2. 가설이 틀렸고 **실측이 뒤집은** 것

#### 2-1. "중복 턴을 막는다" → 진짜 발화를 버리고 있었다
한 발화가 턴 2개로 쪼개지는 결함을 고치며 "늦게 온 전사는 꼬리이므로 차단"을 넣었다.
그랬더니 이번엔 **말했는데 빈 턴**이 됐다(speech 1~4초인데 전사 없음).
분류는 맞았다 — 그건 정말 그 턴의 꼬리다. **버린다는 처리가 틀렸다.**
→ **닫힌 턴이 비어 있었으면 버리지 않는다**(전달한 게 없으니 중복이 생길 수 없다).
한쪽만 고치면 다른 쪽이 되살아나는 관계라 두 성질을 같은 파일에 나란히 테스트로 묶었다.

#### 2-2. "엔진이 v2 로 뜨면 STT 가 붙은 것" → 아니다
운영 문서에 그렇게 적었는데, 클라이언트 생성은 **로컬에서 키 파일만 읽는다.** 권한이 없으면
**첫 전사 시점에야** 실패가 드러난다. 문서를 고쳤다("진짜 확인은 첫 전사가 뜨는 것").

#### 2-3. "음색 이름 체계가 같으니 그대로 넘기면 된다" → 형식이 달랐다
로스터(이름 목록)는 같은데 **API 가 요구하는 문자열이 다르다**:
`ko-KR-Chirp3-HD-Sulafat` vs `Sulafat`. 섞으면 400/404.
→ 주석을 사실로 정정. **문서로 같아 보여도 한 번 쏴봐야 확정된다**를 같이 남겼다.

#### 2-4. 내가 쓴 타이밍 테스트가 원래 깨져 있었다
실패를 내 변경 탓으로 넘기지 않고, 변경을 스태시한 뒤 **5회 재현해 4회 실패**를 확인했다.
기대값이 정확히 임계와 같아 경계에 앉아 있었고(윈도우 이벤트 루프는 clock resolution 만큼
일찍 깨어난다) 임계를 조정했다. **아무도 모를 수 있었지만 먼저 보고했다.**

#### 2-5. "상대 모듈은 아직 문자 기준이다" → 머지 전 옛 코드를 본 것이었다
브랜치가 갈라진 채 상대 코드를 1차 자료로 삼으면 **구조적으로 생기는 착각**이다.
머지 커밋에 그 사실을 남겼다.

---

### 3. 갈림길 — 고른 것과 **버린 것**

#### 3-1. 턴 종료를 벤더 설정으로 하려다 접었다
`voice_activity_timeout` 을 턴 노브로 쓰려 했는데 proto 원문이 **"the server will automatically
close the stream"** 이었다. 800ms 로 뒀으면 **0.8초 쉴 때마다 스트림이 죽었다.**
→ **턴 시작은 엔진 VAD / 턴 종료는 서버 자체 타이머.**
**버린 것**: 벤더 설정 하나로 끝내기(간단하지만 스트림이 죽는다).

#### 3-2. 원인을 모르면 값을 덮지 않았다
계측이 79초로 튀는 결함에서 보정값을 넣지 않고 **판정용 로그 3줄**을 심어 다음 통화로 후보를
갈랐다(롤오버 0회인데 79초 → 기준점이 다르다는 뜻). 확정 후에도 **벤더의 의미를 안다고
가정하지 않고**, "우리가 확실히 아는 것"(흘려보낸 오디오보다 한참 과거는 침묵 계산에 못 쓴다)
만으로 거절 규칙을 만들었다.
**버린 것**: 오프셋 무시(계측이 통째로 죽는다) / 감으로 보정값 빼기.

#### 3-3. 임계값을 만지고 싶은 자리에서 **재는 시점**을 고쳤다
끼어들기가 거의 다 기각됐다(에너지 0.0000~0.0017 < 임계 0.05). 임계를 낮추는 게 제일 쉬웠지만,
그 값은 별도 실측으로 정하기로 되어 있었다.
→ 원인은 **에너지를 '지금' 값으로 재고 판정은 ~800ms 전 오디오로 하고 있었던 것**이라,
(시각, 에너지) 짧은 이력을 두고 **그 이벤트가 가리키는 시각의 에너지**를 보게 했다.
**버린 것**: 임계 하향(증상은 사라지지만 에코 방어가 같이 무너진다).

#### 3-4. 이력 상한을 **턴 수 → 글자 수**로 바꿨다
12턴 상한은 15분 통화(72턴 관측)에서 앞부분을 통째로 잊게 만든다. 그리고 턴 수는 애초에
**잘못된 단위**다 — 긴 발화 몇 개가 짧은 턴 12개보다 크고, 과금은 글자·토큰으로 된다.
→ 정상 통화가 절대 안 걸릴 크기의 **글자 백스톱**. 잘라낸 내용은 **버리지 않고 보관**한다
(통합 모델은 압축으로 날아간 대화를 되살릴 수 없었지만, 여기선 원문이 우리 손에 있다).

#### 3-5. 실험을 오염시키지 않는 **순서**로 냈다
사용자가 "끊김"을 직접 재보겠다고 한 시점에, 끊김에 영향을 주는 두 변경을 같이 내지 않았다.
같이 내면 무엇 때문에 달라졌는지 못 가린다.
**버린 것**: 한 번에 내서 배포 횟수 줄이기.

#### 3-6. 깨진 게이트 **위에** 기능을 얹지 않았다
"dev 전용"이라던 블록이 실서비스에도 열려 있었다(운영 환경 값이 `prod` 가 아니었다).
근본 수정은 같은 조건을 쓰는 다른 블록까지 동시에 닫는다 → 영향 범위 조사가 선행이다.
→ **전용 스위치(기본 꺼짐)로 이 기능만** 막았다. 환경 값이 틀려 있어도 안전한 구조다.
⭐ 그리고 **틀린 주석이 다른 팀의 설계 전제가 됐던 사례**(클라이언트가 "운영에선 소켓이 안
열린다"를 안전장치로 세고 있었다)를 주석에 남겼다.

#### 3-7. 판정 재료를 지시받은 것과 **다르게** 골랐다
"들린 글자 수가 0이면 취소하지 마라"는 지시에서, 글자는 **문장 단위**라 2초를 들었어도 0 일 수
있었다. 그대로 쓰면 진짜 끼어들기를 막는다.
→ **오디오 시간**으로 바꿔 제안하고 그 근거를 같이 냈다.

#### 3-8. 설계 예산보다 **실사용 판정**을 위에 뒀다
첫 소리 3.5초는 설계 예산(1.5~2.5초) 초과였지만 실사용자가 "느리지 않다"고 판정했다.
→ 예산을 합격선에서 내리고 참고값으로 뒀다. 다만 **"실사용자 대다수는 초보라 체감이 다를 수
있다"** 를 남겨, 나중에 다시 볼 자리를 표시했다.

---

### 4. 조용한 실패를 **보이게** 만든 설계

| 무엇이 조용했나 | 어떻게 드러냈나 |
|---|---|
| TTS 합성 실패(200·로그 0) | 대답 로그의 `첫소리=-1ms` 판별식 |
| 엔진 폴백(소리는 정상) | 폴백 WARNING 에 **모델 ID + 실패 사유** |
| 마커 미준수(소리는 정상) | 마커 상태를 3분류로 로깅 |
| 사용량 미수집 | `collected=0 reason=…` 한 줄 |
| 모르는 벤더 단가 | 0원이 아니라 **'미상'** 으로 표시 |
| 스트림 롤오버 | 서버 로그에 한 줄도 없던 것을 추가(그래서 79초 결함 진단이 막혀 있었다) |
| 샘플레이트 불일치 | 클라가 값을 안 보내면 "기본값 가정"을 로그로(조용히 어긋나면 목소리만 이상해진다) |

---

### 5. 동시성·타이밍 (실시간 오디오의 진짜 난점)

#### 5-1. 같은 값처럼 보이는 **시계가 세 번 달랐다**
| 무엇 | 증상 | 실측 |
|---|---|---|
| 파이프라인 지연 vs 침묵 임계 | 한 발화가 턴 2개 | 지연 810~914ms > 임계 800ms |
| VAD 지연 vs 전사 지연 | 말했는데 빈 턴 | VAD 291·338·348 / 전사 723~870 |
| 에너지 측정 시점 vs 이벤트 시점 | 짧게 말하면 끼어들기 안 먹음 | 기각 시 0.0000~0.0017 |
세 번 다 **"두 값이 같은 시계일 것"** 이라는 가정에서 나왔다. 로그의 **분포**가 단서였다
(예: "빈 턴만 유독 지연이 절반").

#### 5-2. 취소 태스크가 세션을 죽이는 문제
`asyncio.TaskGroup` 의 자식을 밖에서 취소하면 **그룹 전체가 무너진다**(실측 확인).
우리가 건 취소를 **태스크가 흡수하고 정상 종료**하게 만들어야 세션이 산다.
→ "취소 뒤에도 세션이 살아 있다"를 테스트로 잠갔다.

#### 5-3. 스트림 교체 중 오디오를 잃지 않기
STT 스트림엔 수명 한도가 있어 통화 중 교체가 필요하다. 교체 중 들어온 오디오를 버퍼에 담았다가
새 스트림에 흘리고, **오프셋 기준점을 다시 잡아** 이벤트 시각이 연속되게 했다.
⭐ 그런데 재생 구간에 **이미 인식이 끝난 부분**이 섞이면 같은 말이 두 번 인식된다(턴 중복 +
그 구간 이중 과금). → 확정된 지점까지는 **잘라내고** 흘린다.

#### 5-4. 순서 보장이 곧 계약이다
서버 출력에 불변식을 두고(턴 시작이 오디오보다 먼저 / 실시간보다 앞서 밀지 않기 / 취소된 턴엔
종료를 내지 않기) **한 클래스에 모아 테스트로 고정**했다. 클라이언트의 "취소 이후 도착분은
버린다" 판별식이 이 순서에 의존하기 때문에, 깨지면 **정상 오디오를 조용히 버린다.**

### 6. 회귀로 **못박은** 것 (다음 사람이 되돌리지 못하게)

- **실측 수치를 테스트에 박았다** — 관측된 지연·오프셋 값을 그대로 넣어, 같은 가정이 되살아나면
  실패하게 했다(예: 지연 900ms > 임계 800ms 조건에서 한 발화는 한 턴).
- **수정이 실제로 필요한지 증명** — 세 겹 방어를 **하나씩 꺼서** 각 테스트가 실패하는 것을
  확인했다(꺼도 통과하면 그 수정은 불필요하다는 뜻이다).
- **스트리밍 인코딩** — 비스트리밍에선 유효한 값이라 "통일하자"며 되돌아오기 쉬운 자리라,
  스트리밍은 PCM / 비스트리밍은 MP3 를 **둘 다** 테스트로 고정했다.
- **엔진별 음성명 형식** — 실사격에서만 드러난 결함이라 테스트가 없으면 다음 리팩터에 돌아온다.
- **로그에 통화 원문이 새지 않는다** — 나중에 "디버깅 편하게" 원문을 얹지 못하게.
- **노출 게이트** — 환경 값이 틀린 상태(운영과 동일 조건)에서도 닫히는지를 테스트에 넣었다.
  ⚠ 처음엔 라우트 목록으로 검사했는데 **서브앱으로 붙은 WS 라우트가 안 보여** "안 열렸다"를
  잘못 통과시킬 뻔했다 → **실제 응답**(연결 종료 코드)으로 바꿨다.

**규모**: 캐스케이드 관련 테스트 **93건**(턴 상태기계 33 / 대답·마커 21 / 원가 16 / 턴 경계 10 /

## 포트폴리오 재료 — 15분 통화 · 원가 계기판

브랜치 `feat/call-15min-polish`(기반 `c12eccb`) · 커밋 17개 · 2026-08-04 ~ 08-07
읽는 사람: 면접관·시니어 개발자 / ⛔ 재료 모음이다. 골라 쓰는 것을 전제로 항목마다 짧게 썼다.

### 0. 맥락 (한 문단)

Gemini Live 네이티브 오디오로 한국어 회화 통화를 하는 서비스. **연결 자체가 ~10분에서 끊기는**
플랫폼 한계 위에서 5분 통화를 15분으로 늘리는 작업, 그리고 **통화 원가를 볼 수 있게 만드는**
작업을 했다. 원가가 중요한 이유: 무제한 요금제를 열려면 통화 1건이 얼마인지 알아야 한다.

---

### 1. 계측을 먼저 만들었고, 그 계측이 결함을 잡았다

#### 1-1. 내가 쓴 결론을 내가 만든 로그가 반증했다
"압축(context window compression)이 한 번도 발동한 적이 없다"고 논증 문서에 썼다.
그 뒤 usage 시계열 로그를 다시 뒤지니 **call 890(901초)에서 prompt 15,844 → 11,695 로 실제
압축이 일어나 있었다.** 문서에 정정 절(§1-A)을 넣고 결론을 다시 계산했다.
- 근거: Cloud Run 로그 직접 조회 / 커밋 `5e31f02`
- 이후: 문서에서 **"실측"과 "모델 계산"을 라벨로 구분**하게 됐다(커밋 `3065365` 는
  "5분 ≈ 9,300 tok" 이 선형 외삽임을 명시한 것).

#### 1-2. Σ와 last 를 **둘 다** 내보낸 덕에 해석을 데이터가 정했다
Live 의 `usage_metadata` 가 "메시지별 증분"인지 "세션 누적"인지 문서로 확정되지 않았다.
해석하고 넘어가는 대신 **원본 그대로 시계열에 쌓고, 종료 로그가 Σ(합)과 last(마지막)를 둘 다**
내도록 했다. 단조증가면 누적, 톱니면 증분 — `monotonic` 플래그 한 칸으로 갈린다.
- 근거: `call_session.py::_usage_summary` / 커밋 `de37312`
- 같은 시계열이 "압축이 실제로 발동하는가"도 함께 답한다(1-1 이 그 결과다).

#### 1-3. peak 를 DB 에 남겼더니 **그 컬럼 자체가 틀렸다는 게 드러났다**
`usage_peak_prompt` 를 컬럼으로 승격했더니, 같은 통화에서 **DB 13,355 vs 로그 시계열 최대
15,904** 로 어긋났다. 원인은 압축을 감지할 때마다 peak 를 바닥값으로 리셋하고 있던 것.
로그와 DB 를 **둘 다** 두지 않았으면 못 잡는다.
- 근거: call 909 / 커밋 `0584dad`
- ⚠ 이 로그 값은 **다른 탭이 전달**한 것이고 내가 직접 조회하지는 않았다.

#### 1-4. 테스트가 0건이던 지대를 먼저 채웠다
압축 설정을 만드는 `build_live_config` 와 `LIVE_CTX_*` 설정에 테스트가 **0건**이었다.
압축 트리거를 건드리는 작업(15분 통화의 핵심 레버)을 하기 전에 **13건을 먼저 깔았다** —
설정값이 실제로 wire 까지 도달하는지, target<trigger 가드가 있는지 등.
- 근거: `tests/test_gemini_live_config.py` / 커밋 `a1ddb8c`

#### 1-5. 압축 관측기는 로그 상한과 **무관하게** 돌게 했다
usage 시계열은 메모리 상한이 있어 일정 개수를 넘으면 적재를 멈춘다. 그런데 상한을 넘길 만큼
긴 통화가 **바로 압축이 가장 활발한 구간**이다. 여기서 같이 끊으면 재접지가 후반부터 눈이 먼다.
→ 압축 관측만 상한 밖에서 계속 돈다.
- 근거: `call_session.py::_record_usage`(주석에 이 이유가 박혀 있다)

### 2. 조용한 실패를 드러나게 만든 설계

#### 2-1. "모르는 벤더는 0원으로 먹지 않는다"
캐스케이드 원가 함수가 `(원가, **미상 벤더 목록**)` 을 반환한다. 모르는 벤더를 0원으로 계산하면
*"캐스케이드가 공짜"* 라는 그럴듯한 거짓말이 통계에 들어가고, 하필 그 통계가
"캐스케이드가 Live 보다 싼가"의 근거가 된다.
- 근거: `normalcall_service.estimate_cascade_cost_usd` / 커밋 `0584dad`

#### 2-2. NULL 과 0 을 구분했다
usage 컬럼 전부 nullable. **NULL = 계측 안 됨**, **0 = 정말 0 토큰**. 둘을 구별할 수 있어야
"표본이 왜 이렇게 적지"에 답할 수 있다. 마이그레이션도 백필 없이 기존 행을 NULL 로 남겼다.
- 근거: `models/call.py` 주석 / 마이그레이션 `b7e1c2d3f4a5`

#### 2-3. 확신이 없는 자리에 **경고를 심었다**
Live 원가 산식에 사고(thinking) 토큰을 더할지 판단이 안 섰다(§3-2). 그냥 두면 전제가 깨지는
순간 조용히 과소계상된다. → `sum_thoughts > 0` 인 통화가 나오면 **WARNING 을 찍는다.**
"모른다"를 주석으로만 남기면 썩는다. 침묵 대신 신호가 나오게 했다.
- 근거: `call_session.py::_log_usage_summary` / 커밋 `d837df0`

#### 2-4. 이름 규칙이 다르다는 사실 자체를 못박았다
같은 TTS 모델인데 Cloud TTS 는 `gemini-2.5-flash-tts`, Gemini API 는
`gemini-2.5-flash-preview-tts`. 가격 페이지 이름만 코드에 남기면 **동작은 하는데 값이 안 잡힌다**
— 예외도 로그도 없이 전부 '미상'이 되고 그 통화가 원가 표본에서 사라진다.
→ 단가표를 두 구획으로 나누고 "이름을 통일하면 원가 계측이 죽는다"를 주석에 박은 뒤,
**실제로 올 수 있는 이름 전량을 상수로 세워 회귀 테스트가 순회**하게 했다.
- 근거: `CLOUD_TTS_GEMINI_MODELS` / 커밋 `a88a7a4`

#### 2-5. 못 잰 이유까지 남긴다
토큰 과금 TTS 에 `audio_s` 가 없으면 미상 목록에
`tts:<모델>(audio_s 없음 — 토큰 과금이라 chars 로 못 잰다)` 를 넣는다. "미상"만 남기면
다음 사람이 원인을 처음부터 다시 찾는다.
- 근거: `estimate_cascade_cost_usd` / 커밋 `a793c19`

### 3. 갈림길 — 버린 선택지와 이유

#### 3-1. 원가(달러) 컬럼을 **만들지 않았다**
- **버린 것**: `cost_usd` 컬럼. 집계가 훨씬 편하다.
- **이유**: 단가는 벤더가 바꾼다. 달러를 행에 박으면 **단가가 바뀐 순간 과거와 현재를 같은
  잣대로 못 본다.** 토큰·초·문자는 사실이고 원가는 파생 계산 → 산식은 코드 한 곳에만 둔다.

#### 3-2. Live 사고 토큰: 더하지 않고 **경고로 남겼다**
- **버린 것**: 캐스케이드와 같은 논리니까 그냥 더하기(한 줄이다).
- **이유**: 확인 못 한 게 둘이었다. ①AI Studio 는 candidates 에 사고 토큰이 포함되고 Vertex 는
  빠지는데, 우리 산식은 모달리티 분해로 계산한다 — 그 분해가 사고 토큰을 품는지 문서로 확인
  못 했다(품으면 이중계상) ②현재 모델이 비-사고 변종이라 값이 구조적으로 0 이다.
  → **지금 더해도 값이 안 변하고, 틀리면 조용히 과대계상**된다. 안 더하고 §2-3 의 경고를 심었다.

#### 3-3. 토큰 과금 TTS 를 **문자로 환산하지 않았다**
- **버린 것**: 평균 글자/초를 가정해 환산(비교표가 채워져 보기 좋다).
- **이유**: Gemini-TTS 는 오디오 1초 = 25토큰 과금이라 **같은 문장도 천천히 읽으면 더 비싸다.**
  환산은 말하는 속도에 따라 배로 틀린다. **"이 엔진은 문자로 못 잰다"가 결론**이고, 대신
  무엇을 수집해야 하는지(`tts.audio_s` = 송출 바이트 ÷ 48,000)를 상대 팀에 넘겼다.

#### 3-4. peak 를 고치는 대신 **하나 더 세웠다**
- **버린 것**: 리셋을 없애기(한 줄).
- **이유**: 압축 감지와 재접지 arm 은 **바로 그 리셋되는 사이클 peak 가 있어야 성립**한다
  (낙차의 기준선이자 "지금 컨텍스트가 트리거에 가까운가"의 입력). 기존 값은 그대로 두고
  통화 전체 최대치를 나란히 세워 DB 에는 그쪽을 보냈다. 관측값을 늘렸지 동작을 안 바꿨다.
- 회귀 테스트로 "압축 감지·arm 은 여전히 사이클 peak 를 쓴다"를 고정했다.

#### 3-5. 시각 트리거를 없애면서 **폴백으로는 남겼다**
재접지 트리거를 "통화의 50%·80% 지점"에서 **압축 신호**로 바꿨다. 그런데 usage 가 안 오는
환경(모킹 세션·필드 미제공)에서는 압축 신호가 영영 안 온다 → 5분 무료 통화가 재접지를
한 번도 못 받게 된다.
- **버린 것**: 시각 트리거 완전 제거(코드가 깔끔하다).
- **선택**: 압축이 주, **시간이 폴백**. 간격은 `clamp(통화길이/2.5, 120s, 240s)` 로 잡아
  5분과 15분의 **분당 재접지 빈도를 같게** 맞췄다(길어졌다고 촘촘해지지 않게).
- 회귀 테스트: "압축이 한 번도 없어도 5분 통화는 재접지된다".

#### 3-6. 로그 줄 형식을 **바꾸지 않았다**
Cloud Logging 의 로그 기반 메트릭이 그 줄을 **코드 변경 0줄로** 파싱하고 있다. DB 영속화를
붙이면서 로그 문자열은 무손상으로 두고, 계산을 순수 함수 하나로 뽑아 **로그와 DB 가 같은
결과**를 쓰게 했다 — "로그엔 이렇게 찍혔는데 DB 엔 다른 값"이 안 나오게.

#### 3-7. 임계값을 **미탐 쪽으로** 기울였다
압축 감지의 오탐(불필요한 재접지 주입)은 비버가 두 번 말하는 위험, 미탐(주입 누락)은 무해.
→ 비율과 절대 낙차를 **둘 다** 만족할 때만 압축으로 친다. 실제로 비율 임계 0.75 는
설정값 16000/12000 이 **정확히 0.75 에 걸려** 감지가 불안정해서 0.85 로 올렸다(절대 낙차가
진짜 방어선이고 비율은 보조라는 판단).

### 4. 동시성 · 타이밍

#### 4-1. `except*` 가 예외를 **다시 묶는다** (PEP 654)
`asyncio.TaskGroup` 안에서 종료 신호 둘이 동시에 발생하면 `except*` 절이 각각 실행된 뒤
**새 ExceptionGroup 으로 재포장돼** 밖으로 나간다. 바깥은 개별 신호를 기다렸으므로
**세션 스왑이 통째로 실패**했다(= 15분 통화가 10분에서 끊긴다).
- **고치기 전에 재현부터 했다**: 최소 스크립트로 `group[A, B]` 가 ExceptionGroup 으로 탈출하는
  것을 눈으로 확인. 문서만 읽고 고쳤으면 "고쳤다고 믿는 코드"가 됐다.
- 해법: `except*` 3절을 없애고 `BaseExceptionGroup` 을 직접 받아 **우선순위로 하나만 고른다**
  (종료 > 클라 끊김 > 스왑). 나머지는 로그로 남긴다.
- 커밋 `a4163d7`

#### 4-2. 세션보다 오래 사는 태스크가 세션을 붙잡고 있었다
종료 판정 사이드카가 TaskGroup **밖에서** 세션 객체를 참조했다. 세션이 갈아끼워지면
그 참조는 **죽은 세션**이다.
- 해법: 사이드카에서 세션 인자를 제거하고 `asyncio.Event`(`close_requested`)로 **의사만 전달**,
  실제 주입은 살아 있는 세대가 한다. 시계 태스크의 `sleep` 폴링을 이벤트 대기로 바꿔
  **종료 요청이 즉시 반영**되게 했다(소유권을 세션 수명 안으로 옮긴 것).
- 커밋 `7b7248c`

#### 4-3. 세대를 건너 살아야 하는 상태를 명시적으로 관리
15분 통화는 세션을 갈아끼우는 **세대 루프**다. 시계·무음·flush 태스크가 세대마다 재생성되므로,
태스크 지역 변수에 둔 값은 스왑 때 통째로 사라진다. → 세대를 건너 사는 값(재개 핸들·세대 번호·
재연결 수·usage 시계열)을 상태 객체 `__slots__` 에 모으고 **주석으로 그 이유를 박았다.**

#### 4-4. 재접지 얹기의 경합
"지금 얹어라"를 통화당 1회 불린으로 관리하던 것을 **pending 소비 방식**으로 바꿨다
(arm → 유저 발화 시작 시점에 소비). 한 턴에 두 리마인더가 겹치면 비버 응답이 장황해지고
유저 발화 하나에 서버 텍스트가 수백 토큰 붙는다 → **최소 간격·통화당 상한**을 함께 뒀다.
종료 진행 중에는 arm 자체를 막는다(마무리 인사가 오염되면 통화가 어색하게 끝난다).

#### 4-5. 오디오 해제는 "누가 나중에 읽는가"를 먼저 찾아야 했다
저장이 끝난 통화 오디오를 안 놓아줘서 15분이면 30~50MB 를 물고 있었다. 그냥 버리면 될 것
같지만 **국적 추론 경로가 사용자 PCM 을 나중에 다시 읽는다.** → 저장된 구간은 놓아주되
**사용자 오디오 앞 60초는 상한을 두고 따로 보관**하는 구조가 됐다.
- 커밋 `d117912`

### 6. 틀렸다가 고친 것

#### 6-1. "압축은 발동한 적 없다" → 로그가 반증 (§1-1)

#### 6-2. 지시가 틀렸음을 **반증하고 멈췄다**
"dev DB 에만 마이그레이션을 적용하라"는 지시를 받았다. `gcloud` 로 각 Cloud Run 서비스의
`SUPABASE_URL` 을 찍어 보니 **dev DB 는 어떤 서비스에도 붙어 있지 않았고**, app/demo/test
세 서비스가 모두 같은 운영 DB 를 공유하고 있었다. 적용하지 않고 근거와 함께 보고했고,
지시가 정정됐다. → "dev 라고 적혀 있는 것"과 "실제로 연결된 것"은 다를 수 있다.

#### 6-3. 가드가 **내 실수로** 걸렸다 — 그래서 가드가 맞았다
마이그레이션 스크립트에서 `alembic history -r <current>:heads` 가 현재 리비전을 **포함**해
pending 을 2건으로 셌고, "pending 이 1건이 아니면 중단" 가드가 스스로 멈췄다. DB 를 건드리기
전에 멈춘 것이라 부작용은 없었다. 판정 로직을 고쳐 다시 돌렸다.

#### 6-4. 원칙을 세워 놓고 **다른 자리에서 스스로 어겼다**
"모르는 벤더는 0원으로 먹지 않는다"(§2-1)를 산식에 세웠는데, **영속화 함수는 못 알아듣는
요약에 0 을 써버린다**는 지적을 받았다 — 상대 팀 요약의 키 모양이 달라 토큰 컬럼이 전부 0 이
될 상황이었다(엔진 이름과 벤더 JSON 은 정상 저장되므로 "저장은 됐는데 토큰만 0"). 같은 파일에서
같은 원칙을 두 번 다르게 쓴 셈이다. → 원칙은 세우는 것보다 **모든 경로에 적용됐는지 확인하는
것**이 어렵다. 수정은 배포 후 대기열.

#### 6-5. 데모가 안 되는 원인을 코드에서 찾다가 **설정에서 찾았다**
데모 페이지가 200 으로 뜨는데 로그인 후 모든 요청이 401/403 이고 **서버 ERROR 로그는 0건**
이었다. 원인은 토큰 **발급처와 검증처가 다른 Supabase 프로젝트**였던 것(페이지 하드코딩
기본값이 3주 전 도그푸딩 시절 값). 인증 단계에서 끊기니 애플리케이션 로그에는 아무것도 안 남는다.
→ 배포 무관함을 세 가지로 증명했다: HTML 바이트 동일 / 리비전 8개에서 `SUPABASE_URL` 불변 /
하드코딩 값의 도입 커밋 날짜.

## I. 계측을 먼저 만들었고, 그 계측이 실제로 결함을 잡았다

> 이 절이 이 프로젝트의 축이다. 순서가 중요하다 — **계측이 먼저였고, 결함은 그다음에 드러났다.**

#### 1. 검사가 0건을 뱉었는데 그게 "깨끗하다"가 아니라 "안 보고 있다"였다
릴리즈 APK 에 디버그 화면이 남았는지 한글 문자열로 검색 → **0건**. 통과로 볼 뻔했다.
**반드시 검출돼야 할 대조군 문자열**을 하나 넣고 다시 검색하니 그것도 0건이었다. 검사 자체가 고장난 것 — 릴리즈 AOT 는 비ASCII 를 **UTF-16LE** 로 저장한다.
방식을 고쳐 다시 재니 **화면이 실제로 릴리즈 바이너리에 있었다.** 진입 버튼만 `kDebugMode` 로 가렸는데, 라우트 테이블에 남으면 화면은 살아 있다. 라우트 등록 자체를 조건부로 바꿔 해결. `[담당보고]`
**교훈**: 음성(negative) 결과를 믿으려면 **그 검사가 양성을 낼 수 있다는 것을 먼저 증명**해야 한다.

#### 2. 돌연변이 하나로 테스트 287건이 아무것도 안 보고 있었음을 증명했다
끼어들기 플래그를 켜고 도는 스위트가 있었다. **그 플래그를 참조하는 테스트가 0건**이라, 플래그와 무관한 테스트를 그대로 다시 돌 뿐이었다.
증명: 통로 결정을 항상 한쪽으로 고정하는 돌연변이를 심었더니 **플래그 끈 쪽은 통과, 켠 쪽만 2건 실패.** 그 **비대칭**이 "이제는 진짜 본다"의 증거다. `[담당보고 · 돌연변이]`
**이건 "테스트를 늘렸다"가 아니라 "지금까지 증명한 게 없었다"를 밝힌 것이다.**

#### 3. 정적분석기가 Riverpod 린트를 한 번도 안 태우고 있었다
`analysis_options.yaml` 에 플러그인이 켜져 있는데 `flutter analyze` 는 그것을 안 태운다. `dart run custom_lint` 로 따로 돌려야 한다.
즉 여러 번 보고된 "정적분석 무이슈"에 그 린트는 **한 번도 포함된 적이 없었다.** 돌려보니 7건. `[실측]`
부수 발견: 그 명령은 `build/` 가 있으면 죽고(경로 길이), 그 폴더는 **260자 초과라 일반 삭제가 안 된다.** 결과적으로 **린트와 빌드의 순서가 강제**된다 — 린트 먼저, 빌드 나중. 거꾸로면 APK 를 두 번 만들게 된다.

#### 4. "5.2초 만에 끝난 검증"이 캐시 재사용이었다
빌드 검증이 5.2초에 끝났다. 컴파일 산출물과 소스의 **수정 시각을 비교**하니 네이티브 코드를 실제로 컴파일한 적이 없었다. 이후 클린 빌드 또는 산출물 시각 확인을 게이트에 넣었다. `[담당보고]`

#### 5. 테스트 232건 전부 통과인데 APK 가 안 나오는 상태
`flutter analyze` 와 `flutter test` 는 **Dart VM 에서 돌아 Android 빌드 경로를 안 탄다.** 설정 파일 하나가 없어 APK 만 실패했는데, 앞의 두 게이트는 전부 초록이었다. **실기기 검증 직전에야 발견된다.** `[실측]`
→ 이후 `flutter build apk --debug` 를 게이트에 필수로 넣었다.

#### 6. 서버 주석과 실행 중인 값이 반대였다
서버 코드에 `if ENV != "prod":` 로 실험 라우트를 등록하고, 바로 위에 **"운영에는 노출하지 않는다 / 마운트조차 하지 않는다(노출 0)"** 라고 적혀 있었다.
`/health` 를 직접 쳐보니 **운영 서버가 `{"env":"test"}`** 를 반환한다. 조건이 참이므로 그 가드는 아무것도 막지 않는다. `[실측]`
같은 파일 80줄 아래에 **팀이 이미 그 사실을 적어둔 곳**이 있었다 — 다른 관리자 도구들은 그걸 알고 2차 방어를 달았고, **이 라우트에만 없었다.**
**교훈**: 주석은 1차 자료가 아니다. **런타임으로 갈리는 조건은 런타임 값을 봐야 한다.**

#### 7. 바이너리 라이브러리 안까지 열어 "진짜 불리는가"를 확인했다
녹음 라이브러리에 `enableEchoCancellation: true` 를 주면 실제로 플랫폼 에코제거기가 생기는지가 **미확인**으로 남아 있었다(구현체가 바이너리 AAR).
AAR 의 클래스 파일을 열어 확인: `FlautoRecorderEngine.class` 가 `AcousticEchoCanceler.create(getAudioSessionId())` 를 **실제로 호출**한다. 빌드된 APK dex 에도 심볼 실재. `[실측]`
**다만 여기서 멈췄다** — "호출된다"와 "기기에서 걸린다"는 다르다. 미지원 기기에서는 조용히 실패한다. 그래서 **실측 전에는 "AEC 가 걸렸다"를 서버에 주장하지 않기로** 했다.

## II. 틀렸다가 실측이 뒤집은 것

> 전부 **1차 자료를 안 보고 남의 말·주석·오래된 코멘트를 옮긴** 경우다.

| 틀린 판단 | 무엇이 뒤집었나 |
|---|---|
| 상수값을 **코드 주석**에서 옮겨 적음(1800ms) | 실제 값 1200ms. 주석이 낡아 있었다. 이걸 근거로 "가장 위험하다"는 판정까지 냈다가 철회 |
| "서버가 이 필드를 안 보낸다"(하위 보고 그대로 상신) | 서버는 **예전부터 필수 필드로 보내고 있었다.** 클라가 안 읽고 있었을 뿐 |
| "운영에 아직 배포 안 됨"(하위 보고 그대로 상신) | 라이브 스키마를 직접 받아보니 **이미 배포돼 있었다** |
| Android 에코제거가 안 되는 원인을 **한 곳**으로 지목 | 실제로는 **세 곳**(재생 속성 / 녹음 소스 / 오디오 모드). 하나만 고쳤으면 **라우팅·볼륨만 바뀌고 에코는 그대로**인 최악의 결과였다 |
| "실험 경로가 운영에 지금 열려 있다" | 조건은 참이지만 **그 코드가 배포된 적이 없었다.** 조건만 보고 배포 상태를 확인 안 함 |
| WS 라우트 404 를 "없다"의 증거로 사용 | **등록된 WS 라우트도 HTTP GET 에는 404 를 준다**(확인: 확실히 등록된 다른 WS 경로도 404). 404 는 아무것도 증명하지 않는다 `[실측]` |

**여기서 나온 규칙 두 개를 프로젝트 규칙 문서에 넣었다:**
- 하위의 **코드 사실 주장**은 1차 자료를 직접 확인한 뒤 올린다. 중계된 오류는 상위에서 안 걸리면 **그대로 설계 결정이 된다**
- 정적분석 게이트에 `dart run custom_lint` 를 추가하고 **순서 강제**를 명시

## III. 버린 선택지

#### 컨트롤러를 두 개로 복제하지 않았다
통신 경로 두 개(기존 실시간 / 신규 캐스케이드)를 다 써야 했다.
- **버림**: 컨트롤러 복제. 서로 간섭이 없어 단순하다
- **이유**: 2,400줄 중 대부분이 오디오 배관이고, **이번에 잡은 어려운 버그가 전부 거기 있었다**(영구 락업, 스레드 경합). 복제하면 오디오 버그를 **영원히 두 번씩** 고쳐야 하고, 한쪽만 고치는 사고가 반드시 난다
- **대신**: 오디오 엔진을 공유하고 프로토콜·마이크 정책만 분기. 통로를 enum 하나로 묶어 **소켓 주소와 마이크 정책이 같이 움직이게** 했다 — 흩어 두면 "주소는 새 경로, 마이크는 옛 정책" 같은 **절반만 전환된 상태**가 만들어진다

#### 소유 플래그를 켜지 않았다 (한 줄이면 되는 해법을 버렸다)
구독 회원에게 캐릭터를 열어주는 가장 짧은 길은 "샀다"고 표시하는 것.
- **이유**: 구독 해지 시 다시 닫혀야 한다. 샀다고 알려준 뒤 뺏는 꼴이고 **되돌릴 수 없다.** 서버도 그래서 일부러 피한 설계였다
- **대신**: "지금 쓸 수 있다"를 별도 축으로 읽고 **소유도 잠김도 아닌 세 번째 상태**를 만들었다. 기존 enum 이 소유 축만 있어 표현할 값 자체가 없었다

#### 환경 기반 게이트를 클라이언트에 넣지 않았다
실험 경로를 운영에서 실수로 켜는 것을 막는 방안 검토.
- **버림**: "운영 서버면 차단"
- **이유 1**: 앱은 붙은 백엔드가 운영인지 알 수 없다. **운영 서버가 스스로 `test` 라고 답한다**(위 I-6). 환경 추측 위의 게이트는 **거짓 확신**을 만든다 — 방금 깨진 게 정확히 그 종류다
- **이유 2**: 진짜 위험은 운영/개발이 아니라 **에코제거가 안 걸린 상태**다. 운영 게이트는 **안전한 경우(개발+AEC)를 막고 위험한 경우(개발−AEC)를 통과시킨다** — 위험과 직교한다
- **대신**: 막지 않고, 그 경로로 붙는 순간 전제조건 상태를 로그에 찍는다. **게이트가 아니라 정보**

#### 린트 지적 4건을 고치지 않았다
아바타 입모양용 알림 객체가 린트에 걸린다.
- **이유**: 일부러 상태에 안 올린 것이다. 올리면 **아바타 프레임마다(초당 10회) 통화 화면 전체가 리빌드**된다. 린트 청소가 아니라 렌더링 파이프라인 변경
- **부수**: 그 파일을 다른 브랜치가 647줄 고치는 중 — 작은 청소로 머지 충돌을 사는 건 손해
- **다만 방치는 아니다**: 머지 후 "알고 남긴 것"임을 코드에 명시한다. 안 그러면 다음 사람이 또 발견하고 또 판단한다

## IV. 조용한 실패를 드러낸 설계

#### 모르는 값을 0 으로 보고하지 않는다
`clear()` 가 반환됐다고 소리가 멎은 게 아니다 — 하드웨어 버퍼에 넘어간 20~60ms 가 남는다. 목표가 50~120ms 라 그 차이가 판정을 뒤집는다.
그래서 **하드웨어 잔량을 실측한 표본과 못 한 표본을 다른 이름으로 보고**한다: `hal_drained`(실측) / `clear_returned`(하한). **기본이 하한이다.** 못 잰 것을 0 으로 채우면 서버가 "즉시 멈췄다"로 오해한다.
같은 이유로 폴백 경로에서는 출처를 `estimate` 로 **정직하게** 보낸다 — 서버가 추정치를 거부하도록.

#### 배관 실패를 타이밍 통계에 섞지 않는다
측정 리그에서 **무응답을 0ms 로 채우면 분포가 좋아 보인다. 그런데 정확히 그 실패가 찾는 것이다.**
그래서 배관 실패(락업·잔여 미폐기·무회신)는 통계에서 분리하고, **하나라도 있으면 타이밍이 아무리 좋아도 판정은 실패**로 못 박았다.

#### 통계가 우리가 찾는 것을 못 보는 구간을 계산해 표시한다
p95 는 정의상(nearest-rank) 상위 `N − ceil(0.95N)` 개를 통째로 건너뛴다. **N=20 이면 딱 1건.**
즉 20번 중 한 번 500ms 가 나와도 p95 는 "60ms, 이상 없음"이라고 말한다. **찾는 게 정확히 그 간헐 1건이다.**
→ 반복을 200회로 잡고, **p95 가 통과여도 최댓값이 목표를 넘으면 판정 줄에 강제로 붙게** 했다. `[담당보고]`

#### 락업 검출을 사람 귀에 맡기지 않았다
취소 후 재생이 영영 안 돌아오는 상태를 자동 판정한다 — 새 턴에 1.2초를 밀어 넣고 **큐가 1.5초 안에 다시 비는지**로 본다.
1.2초인 이유: 재생 쿠션이 900ms 라 그보다 짧으면 **락업인지 쿠션 미달인지 구분이 안 된다.** `[담당보고]`

#### 에코 측정 자극음을 순음으로 만들지 않았다
플랫폼 AEC 는 **입력에 적응하는 필터**다. 정현파는 좁은 대역에만 수렴해 **실제보다 좋은 숫자**를 준다. 그 숫자로 임계를 잡으면 **실사용에서 에코가 임계를 넘는다.**
→ 300~3400Hz 대역제한 + 4Hz 음절변조로 음성에 가까운 신호를 합성. 무음 구간은 일부러 뺐다 — 정지 순간이 무음에 걸리면 **잴 잔향 자체가 없어** 0 으로 나온다.
그리고 **"실제 TTS 가 아니다"라는 사실이 리포트에 자동으로 박히게** 했다.

#### 에너지로 가를 수 없으면 "가를 수 없다"고 판정한다
서버 임계 제안값을 `√(에코_p95 × 발화_p5)` 로 계산하되, **두 분포가 겹치면(에코_p95 ≥ 발화_p5) 임계를 만들어내지 않고 "에너지로는 불가"를 판정으로 출력**한다. 그 경우 전사 확인에 기대야 한다는 뜻이다.

## V. 동시성·타이밍

#### 재생 스레드와 취소의 경합 → 마이크가 영영 안 열림
취소가 재생 스레드의 잔량 갱신과 겹치면 잔량이 부풀려진 채 굳어, 마이크 게이트가 영원히 안 풀린다.
세대(generation) 카운터로 막았고, **취소 시점에 이미 폴링됐지만 아직 쓰이지 않은 바이트**를 따로 세는 경로를 추가했다(어디에도 안 세어지던 구멍).

#### 플래그를 세우는 위치가 한 줄 어긋나 있었다
"쓰기 진행 중"을 알리는 플래그가 **쓰기 직전**에 세워져 있어서, 이미 세대 검사를 통과한 스레드가 취소 쪽에서는 "쓰는 중 아님"으로 보였다.
상호배제(Dekker) 순서대로 **플래그를 먼저 세우고 그다음 세대를 다시 확인**하도록 바로잡고, 다시 옮기지 못하게 **이름까지 바꿨다**(`mInAudioWrite` → `mAudioWritePending`).

#### 세션 상태를 되돌리지 않으면 다음 통화가 오염된다
통로를 통화별 값으로 만들면서, **정리(teardown) 가 통로를 기본값으로 되돌리게** 했다.
없으면 캐스케이드 통화 뒤 **다음 통화가 마이크 게이팅 없이 열린다.** 에코제거 실측 전에는 그게 곧 자기-대화 루프다.

#### 지속 시간을 도착 시각으로 재면 안 된다
끼어들기 최소 지속(200ms) 판정을 **오디오 시각**으로 한다. 도착 시각으로 재면 리전 간 왕복(태평양)이 섞인다. `[코드 · 서버 계약]`

## VI. 회귀로 못 박은 자리

| 무엇을 잠갔나 | 어떻게 |
|---|---|
| 같은 빌드에서 두 통로가 **실제로 다르게 동작**하는가 | 전용 테스트 신설. 돌연변이로 이 테스트가 진짜 보는지 검증 |
| 컴파일타임 상수를 지우면서 **기존 테스트가 의미를 잃는 것** | 상수를 삭제하지 않고 **기본값 출처로 강등** — 플래그 스위트가 계속 동작 |

## VII. 서버 없이 실기기를 재는 법

서버가 취소 신호를 보낼 상황이 안 나와 실기기 검증이 막혀 있었다. 서버를 기다리지 않고 **앱 안에서 프레임을 주입**해 풀었다.

- **소켓이 닿는 유일한 관문**으로만 주입한다. 내부 함수를 직접 부르면 **실제로는 안 도는 경로를 검증한 게 된다.** 관문으로 넣으면 JSON 파싱부터 게이팅·원장·버퍼 폐기·회신 구성까지 한 줄도 우회하지 않는다
- 재는 값(`취소 수신 → 실제 무음`)은 **전부 앱 내부 구간**이라 로컬 주입으로도 진짜 숫자가 나온다. 서버가 기여하는 건 왕복 시간뿐이고 그건 측정 대상이 아니다
- **디버그 전용** 진입점 — 라우트 단위 가드

### 3. 조용한 실패를 드러낸 것 (계측이 실제로 결함을 잡은 사례)

#### 3-1. `첫소리=-1` 판별식 → TTS 무음을 즉시 규명
- 배포 전에 **"200 은 동작한다는 뜻이 아니다"** 를 전제로, LLM·TTS 가 실제로 붙었는지 볼
  판별식을 미리 정해 인계했다: `cascade 대답: … 첫소리=<ms> 글자=<n>` 에서
  **`첫소리=-1` 또는 `글자=0` 이면 실패**.
- 첫 통화에서 정확히 그게 떴다: `첫소리=-1ms 글자=49`.
  원인은 `400 Unsupported audio encoding` — 스트리밍은 `PCM/ALAW/MULAW/OGG_OPUS` 만 받는데
  코드가 `LINEAR16` 을 보냈다(비스트리밍 `synthesize_speech` 에서는 유효한 값이라 헷갈리는 자리).
- **HTTP 200 도, ERROR 로그도 이걸 못 잡았다.** 잡은 건 이 판별식 하나다.

#### 3-2. 폴백을 시끄럽게 만들어 둔 덕에 403 이 1분에 규명됨
`core/tts.py` 의 폴백은 조용하지 않다 — `tts 폴백: engine=… model=… 실패사유='…' → … 로 대체`.
- 그래서 "제미나이인 줄 알았는데 Chirp 이었다"가 **로그 한 줄로** 드러났다.
- 조용한 폴백이었다면: 소리는 정상이므로 **귀로는 구별 불가**, A/B 판단 전체가 오염된다.

#### 3-3. 마커 관측 로그 → "실험이 성립하지 않았다"를 알아냄
언어 마커(`__타깃언어__`) 기능 배포 시, **커밋이 로그를 한 줄도 추가하지 않았다**는 걸 확인하고
(`git diff … | grep '^+.*logger\.'` → 0건) 관측 공백을 보고했다. 근거:
`cascade 대답:` 줄엔 글자 수만 있고, `cascade_usage` 도 TTS 를 언어별로 나누지 않으며,
비버 대사 원문은 어디에도 안 남는다 → **마커 준수 여부를 판정할 수단이 전무**.
- 로그 추가 후 실측(3시간, Cloud Logging 집계): **`마커=짝안맞음` 8건 / `마커=있음` 1건**,
  언어구간은 전부 `1개 ko`(타깃 언어 구간이 한 번도 안 생김).
- 즉 모델은 마커를 **쓰긴 쓰는데 짝을 안 맞춘다**. 폴백이 통째 재생이라 **소리는 정상**이고,
  이 로그가 없었으면 "끊김이 줄었다"는 판단이 *마커가 걸린 상태*에서 나온 건지 아닌지 못 갈랐다.
- ⚠ 이 표본은 프롬프트 자기모순(아래 5-3)이 살아 있던 리비전의 것이다. 정정 후 재측정은 **확인 못 함**.

### 4. 배포 직전에 막은 사고 (사전 발견)

#### 4-1. 스키마가 코드보다 늦어 원가 계기판이 통째로 NULL 될 뻔
- 배포 직전 운영 DB 직접 조회: `alembic_version = b7e1c2d3f4a5`, `call.usage_engine` **부재**.

- 파급: `_persist_usage()`(`call_session.py:831`)가 R5(graceful)로 예외를 삼키므로 **앱은 안 죽고
  경고 한 줄만 남긴 채 usage 8컬럼 + usage_json 이 전부 NULL** 이 된다.
- 범위도 특정했다: 캐스케이드 경로는 DB 를 안 쓰므로 **피해는 Live 통화 한정**.
- 마이그레이션 적용 후 같은 쿼리로 재확인(`c8f3a2b1d704`, `usage_engine text`)하고 배포.

#### 4-2. 커밋되지 않은 남의 작업이 데모에 나갈 뻔 (F13)
- 브리핑은 "워킹트리 clean" 이었으나 실제로는 dirty 2건이었고, 내용이 하필
  **"이번 배포에 없다"고 명시된 진행 중 작업**이었다.
- 근본 사실: `gcloud builds submit` 은 HEAD 가 아니라 **디렉터리 현재 상태**를 올린다.
- 비파괴 우회: 공유 워크트리를 건드리지 않고 `git worktree add --detach <임시> <커밋>` 으로
  **커밋 시점의 클린 트리**를 만들어 거기서 빌드. 나간 이미지에 그 변경이 0건인 것도 grep 으로 확인.
- ⛔ `git stash` 는 쓰지 않았다 — 공유 워크트리에서 **남이 편집 중인 파일을 날린다.**

#### 4-3. 사장님이 듣기 전에 Gemini-TTS 400 을 잡음
env 로 Gemini-TTS 를 켠 직후, **링크가 나가기 전에** 같은 코드 경로를 직접 쐈다.
```
name='ko-KR-Chirp3-HD-Sulafat' + model_name='gemini-2.5-flash-tts'
  → 400 Gemini models cannot be used with non-Gemini voices.
name='Sulafat'                 + model_name='gemini-2.5-flash-tts'
  → OK  bytes=64874  first8=b0 ff af ff …   (RIFF 아님 = raw PCM)
name='ko-KR-Sulafat' / 'ko-KR-Gemini-TTS-Sulafat' → 404 Voice not found
```
- 결론이 둘로 갈렸다: **Gemini-TTS 자체는 된다 / 그런데 코드가 못 간다**
  (`_resolve_voice` 가 항상 `{lang}-Chirp3-HD-{voice}` 접두어를 붙인다 — `core/tts.py:91`).
- **env 로는 못 고치는 것**임도 확인했다: 어떤 값을 넣어도 접두어가 붙고, 로스터에 없는 값은
  언어 기본값으로 떨어진다 → 코드 수정 필요.
- 조치: 사전 승인된 롤백으로 `chirp3-hd` 복귀. 그대로 뒀다면 문장마다 400 → Chirp 폴백이라
  **소리는 나는데 전부 Chirp** 이고, "제미나이 소리"로 오인된 채 제품 판단이 내려졌을 것이다.

### 5. 설계 판단 (갈림길과 버린 선택지)

#### 5-1. 배포 순서를 **케이스마다 반대로** 정했다
같은 "코드 + env" 조합인데 순서가 정반대였고, 각각 이유가 있다.
- **env 먼저** (`CASCADE_ENABLED` 게이트): 코드가 먼저 나가면 env 를 넣을 때까지 데모가 404 다.
  구 배포본에는 무해함을 먼저 확인했다 — `core/config.py:24` 가 `extra="ignore"` 라 모르는 env 를
  무시한다 → 그 단계가 **no-op** 임이 보장된다. → 꺼진 창 **0초**.
- **코드 먼저** (`CASCADE_TTS_ENGINE=gemini-tts`): 기본값이 기존 동작이라 배포만으로는 아무것도
  안 바뀐다. 한 번에 둘을 바꾸면 **깨졌을 때 dead-air 수정 탓인지 TTS 엔진 탓인지 못 가린다.**
- 버린 선택지: "항상 코드 먼저" 같은 고정 규칙. 첫 케이스에서 데모 다운타임이 생긴다.

#### 5-2. 검증을 "200" 에서 멈추지 않기 위해 매번 **한 칸 더** 갔다
- HTTP 200 → 배포된 페이지를 **받아서 md5 로 워크트리 파일과 대조**
  (`89bf76888ca2a95b3e499f08467df9d0`). 200 은 옛 이미지도 낸다.
- 페이지 200 → **WS 라우트를 따로** 찔렀다. 업그레이드 헤더로 붙어 **403**(라우트 있음 + 토큰 거절)
  이면 마운트된 것이고, 404 면 미마운트다. HTML 200 만으로는 갈리지 않는다.
- 로그인 200 → 실제 왕복(가입→로그인→`/api/v1/members/me` 200)까지 하고, **발급 토큰의 `iss`**
  가 서버 `SUPABASE_URL` 과 같은지 디코드해서 확인.

#### 5-3. 검증 주체를 코드와 같게 맞췄다 (그리고 다를 땐 그렇게 적었다)
- 1차 검증은 **내 gcloud 자격증명**으로 했고, 보고에 **"주체가 다른 건 사실"** 이라고 남겼다.
- 실제로 거기서 갈렸다 — 서버 SA 는 `aiplatform` 권한이 없어 403 이었고, 내 계정엔 있었다.
- 2차 검증은 **서버가 쓰는 그 키**로 했다. 단, 키를 디스크에 쓰지 않고
  **stdin → `from_service_account_info` 로 메모리에서만** 로드했다(비밀값을 파일로 남기지 않기 위해).
  결과: `principal = web-stt-pronunciation-challeng@…`, `bytes=214634 audio_s=4.47`, RIFF 아님.
- 버린 선택지: 키를 임시 파일로 떨궈서 테스트. 간단하지만 **비밀값이 디스크에 남는다.**

#### 5-4. env 변경은 **치환이 아니라 병합**으로만
`--set-env-vars` 는 **치환**이라 기존 env 를 통째로 날린다(병합은 `--update-env-vars`).
- 실제 위험: `LIVE_USAGE_TRACE=true` 가 날아가면 **에러 없이 조용히** 계측만 사라진다.
- 그래서 프리플라이트에 규칙으로 넣었다 — **배포 명령에 `--set-env-vars` 가 보이면 멈추고 보고.**
- 그리고 매 배포마다 env 를 **JSON 으로 떠서 이름·값 전후 비교**(추가/삭제/변경 목록을 출력).
  재빌드 배포에서도 손실 0인 것을 반복 확인했다.

#### 5-5. 롤백을 "보고만 할지 / 먼저 되돌릴지" 판단
Gemini-TTS 400 을 발견했을 때 지시는 "즉시 보고"였고, 롤백은 사전 승인돼 있었다.
- 그대로 두는 비용: 사장님이 Chirp 을 제미나이로 듣고 **제품 판단이 통째로 틀어진다.**
- 되돌리는 비용: 코드 수정이 오면 env 한 줄로 1분 내 재개.
- 비대칭이라 **되돌리고 보고**했다. 대신 보고에 "내가 되돌렸다 + 언제든 1분에 재개 가능"을 명시.
- 음색(`CASCADE_TTS_VOICE=Sulafat`)은 **유지**했다 — 같은 30종 로스터라 Chirp 에서도 유효해서,
  롤백해도 "라라 목소리의 Chirp 판"이 되어 A/B 기준선으로 쓸 수 있다.

### 6. 남이 보기엔 사소하지만 실제로 어려웠던 것

#### 6-1. "같은 구글이니 같은 규칙일 것" 이 **세 번** 틀렸다
- `LINEAR16` — 비스트리밍엔 유효, 스트리밍엔 400
- 음성명 형식 — Chirp `ko-KR-Chirp3-HD-Sulafat` vs Gemini **맨이름** `Sulafat`
- 권한 — Cloud TTS 를 부르는데 **거절은 Vertex 가** 한다(`aiplatform.endpoints.predict`)
셋 다 **문서로는 같아 보이고 실사격에서만 드러났다.** 그래서 규칙을 만들었다:
**새 외부 경로는 배포 전에 한 번 쏴보고 확정한다.**

#### 6-2. `--update-env-vars` 는 쉼표가 구분자다 (F15)
스타일 프롬프트 값에 쉼표가 있어 기본 구분자로 치면 **앞부분만 들어가고 뒤는 다른 키로 해석**된다
(조용히 깨진다). gcloud 의 대체 구분자 `^@^` 로 해결:
```bash
--update-env-vars "^@^K1=en@K2=ko@K3=한국어@K4=밝고 다정한 선생님 목소리로, 또박또박 자연스러운 속도로."
```

#### 6-3. 한글 env 값은 **repr 로는 검증이 안 된다**
콘솔 코드페이지 때문에 정상 값도 깨져 보인다. 그래서 **bytes 로 비교**했다:
```
LABEL '한국어' = ed 95 9c ea b5 ad ec 96 b4   (기대값과 일치)
STYLE_PROMPT   len=32, 중간 쉼표 2c · 끝 마침표 2e 보존 → 잘리지 않음
```

#### 6-4. gitignore 된 파일은 워크트리에 안 따라온다 (F3)
`herdr` 워크트리에는 `.env` 가 없어 `pytest` 가 **수집 단계에서 즉사**한다
(`ValidationError: DATABASE_URL_POOL Field required`). 더미 env 주입으로 회피 절차를 만들었다.
같은 부류: 플러터 `google-services.json` 없어 APK 빌드 실패.

#### 6-5. 배포 대상 커밋은 **태그 이름으로 특정하면 안 된다**
이미지 태그는 사람이 붙인 문자열이다. **빌드 시각 ↔ 커밋 시각**을 맞춰 특정했다
(`gcloud builds list` 의 `2026-08-05T12:11:34Z` vs `git log --format='%h %ci'` 의 `12:10:55`).
이 방법으로 브리핑의 "미배포 8커밋"이 실제로는 **9커밋**임을 잡았다.

### 8. 검증 방식

- **테스트**: 매 배포 전 전 스위트 실행(`pytest tests/ -q`). 592→629. 워크트리에 `.env` 가 없어
  더미 env 를 주입하는 고정 절차 사용(F3).
- **배포 후**: 스크립트 기본 헬스체크를 믿지 않고 **이번 배포가 건드린 엔드포인트를 직접** 찌른다
  (`deploy_demo.sh` 헬스체크는 `/__cascadedemo` 를 안 본다 — F8).
- **동일성**: 배포된 정적 자산을 받아 **md5 대조**. WS 는 업그레이드 헤더로 403/404 를 갈라 마운트 확인.
- **env**: 매번 전후 JSON 스냅샷 → 추가/삭제/변경 목록 출력. 한글 값은 **bytes 비교**.
- **스키마**: 배포 직전 운영 DB 에 **read-only 쿼리**로 `alembic_version` + 컬럼 존재 확인.
- **권한**: 로그가 아니라 **IAM 정책 + 시크릿 `client_email` 대조 + 실사격**으로 확정.
