# 결제, 처음 보는 사람을 위한 안내

작성 2026-07-31 · 대상: 이 프로젝트에서 결제를 처음 만지는 사람

이 문서는 "왜 이렇게 만들었는가"를 설명한다. 코드에도 같은 내용이 🧒 주석으로 달려 있다.

---

## 1. 지금 무슨 일이 있었나

### 결제가 결제가 아니었다

`POST /characters/{id}/purchase` 는 이런 일을 했다:

```python
price = 캐릭터_가격_계산()          # $10
member_character 에 소유권 추가      # 캐릭터 지급
payment 행 생성 (card_info 저장)     # "결제됨" 기록
commit
```

문제는 **`card_info` 를 저장만 하고 아무 데도 안 보낸다**는 것이다. 카드사에도, PG사에도,
스토어에도. 그래서 실제로는 이렇게 동작했다:

> **돈은 안 받고 → 캐릭터는 주고 → 결제한 것처럼 기록만 남긴다.**

운영 DB 확인 결과 그렇게 생긴 결제가 **11건**, 전부 `card_info` 가 비어 있었다.

### 그래서 지금은 — 막지 않고 "표시"한다

한때 503 으로 막았다가 되돌렸다. **막아두면 앱이 구매 흐름을 하나도 못 만들기** 때문이다.
대신 응답에 `is_test_grant: true` 를 실어 "이건 실결제가 아니다"를 알리고, 서버 로그에도
경고를 남긴다. 나중에 운영 정산에서 이 지급들을 걸러낼 수 있다.

⛔ **이 상태로 스토어에 출시하면 안 된다.** 실결제는 IAP 로 간다.

---

## 2. 왜 하필 503인가

HTTP 상태 코드는 "무엇이 잘못됐는지"를 앱에 알려주는 숫자다. 아무거나 쓰면 앱이 원인을
오해한다.

| 코드 | 뜻 | 왜 안 맞나 |
|---|---|---|
| 400 | 요청이 잘못됨 | 사용자 잘못이 아니다 |
| 403 | 권한 없음 | 권한 문제가 아니다 |
| 404 | 그런 거 없음 | 캐릭터는 있다 |
| **503** | **서비스가 준비 안 됨** | ✅ 지금 상황 그대로 |

503 을 받은 앱은 "결제 준비 중이에요" 를 띄우면 된다. 사용자 잘못이 아니라는 신호이기도
하다.

응답은 이렇게 나간다:

```json
{ "detail": { "code": "PURCHASE_UNAVAILABLE", "message": "결제 준비 중이에요..." } }
```

**앱은 `message` 가 아니라 `code` 로 분기해야 한다.** 문구는 사람이 읽는 것이라 언제든
바뀌지만 코드는 계약이다.

---

## 3. 무료 캐릭터는 왜 안 막았나

온보딩에서 기본 캐릭터(BABA, 가격 0원)를 주는 경로가 **같은 함수**를 탄다. 싸잡아 막으면
신규 가입이 깨진다. 돈이 오가지 않으니 막을 이유도 없다.

그래서 조건이 `if price > 0` 이다. 1센트라도 있으면 막고, 0원이면 통과.

## 4. IAP가 뭔가 (In-App Purchase)

### 핵심 한 문장

> **앱이 "결제됐어요" 라고 말하는 걸 서버가 믿으면 안 된다.**

앱은 사용자 기기에서 돈다. 마음먹으면 코드를 고쳐 "결제 성공!" 이라고 보낼 수 있다.
그래서 서버는 앱 말을 안 듣고 **애플·구글에 직접 확인한다.**

```
앱  : "BIBI 샀어! 여기 영수증"
서버: (앱한테 대답 안 하고) "애플아, 이 영수증 진짜야?"
애플: "응, 진짜. 상품=bibi, 거래ID=abc123"
서버: "그럼 준다"
```

### 왜 카드결제(Stripe 등)를 못 쓰나

애플·구글 규정상 **앱 안에서 쓰는 디지털 상품은 자사 결제를 강제**한다. 캐릭터·구독이
정확히 그 대상이라, 외부 결제로 팔면 **심사에서 반려**된다. 선택의 문제가 아니다.

수수료가 15~30% 로 비싸지만(카드결제는 2~3%) 스토어에 올릴 거면 다른 길이 없다.
→ $10 팔면 실수령 $7~8.5. **가격표를 다시 봐야 한다.**

### 전체 흐름

```
 [앱]  ① 스토어에 가격 물어봄 → "$10"          (가격은 스토어가 정한다)
       ② 결제창 (Face ID / 지문) → 영수증 받음
              ↓ ③ 영수증만 서버로
 [서버] ④ 애플/구글에 "이거 진짜야?" 물어봄
       ⑤ 이 거래ID 전에 처리했나? → 했으면 재지급 안 함
       ⑥ 캐릭터 지급
       ⑦ 거래ID 저장 (다음에 또 오면 ⑤에서 걸림)
       ⑧ (구글만) "잘 받았다" 확인 전송  ★
```

**⑧ 을 빼먹으면 구글이 3일 뒤 자동 환불한다.** 돈은 돌아가고 캐릭터는 남는 사고가 난다.
애플에는 없는 절차라 놓치기 쉽다.

### 구독은 더 복잡하다 — 앱 밖에서 일이 벌어진다

캐릭터는 한 번 사면 끝이지만 구독은 아니다:

```
구독 시작
  → 한 달 뒤 자동 갱신        ← 앱을 안 켰는데 일어남
  → 카드 한도 초과로 실패      ← 앱을 안 켰는데 일어남
  → iOS 설정에서 해지         ← 우리 앱이 아님
  → 애플 고객센터에서 환불     ← 우리 앱이 아님
```

전부 우리 앱을 안 거치므로 **앱이 알려줄 수가 없다.** 그래서 스토어가 서버로 직접
알려주는 **웹훅** 이 필요하다. 없으면 해지한 사람이 계속 Pro 를 쓰고, 갱신된 사람이
만료로 보인다.

### 역할 분담

| | 앱 | 서버 |
|---|---|---|
| 가격 표시 | ✅ 스토어에서 조회 | ❌ 서버가 안 정함 |
| 결제창·실제 결제 | ✅ | ❌ (스토어가 함) |
| **영수증 검증** | ❌ | ✅ **핵심** |
| 중복 지급 방지 | ❌ | ✅ |
| 소유권 지급 | ❌ | ✅ |
| 갱신·해지·환불 반영 | ❌ | ✅ 웹훅 |
| "이 사람 Pro인가" | ❌ 서버에 물어봄 | ✅ |

**앱은 결제창 띄우고 영수증 넘기는 것까지. 돈·권한은 전부 서버.**

## 5. 자주 헷갈리는 것

**중복 요청은 정상이다.** 네트워크 재시도·앱 재실행·구매 복원으로 **같은 영수증이 여러 번
온다.** 에러로 처리하면 안 되고, "이미 처리했음" 으로 조용히 성공 응답해야 한다.
이걸 **멱등성(idempotency)** 이라고 한다.

**구매 복원(restore)이 필요하다.** 폰을 바꾸거나 앱을 지웠다 깔면 산 캐릭터가 사라진다.
사용자가 "구매 복원" 을 누르면 같은 영수증이 다시 오고, 서버는 **재지급 없이 소유권만
확인**해준다. 캐릭터를 **영구 소유(non-consumable)** 로 정했으므로 이 지원이 필수다.

**테스트 환경이 따로 있다.** 샌드박스 결제는 검증 서버 주소가 다르다. 서버가 구분해서
처리해야 한다.

**웹훅은 유실될 수 있다.** 스토어가 재시도하지만 놓칠 수 있어서, 주기적으로 구독 상태를
다시 조회하는 보정 작업이 보통 함께 필요하다.

## 6. 지금 코드에서 볼 곳

| 파일 | 뭐가 있나 |
|---|---|
| `domains/commerce/service/purchase_gate.py` | 차단 게이트. 🧒 주석에 이유가 전부 |
| `domains/commerce/service/purchase_service.py` | 캐릭터 구매. `if price > 0:` 이 게이트 |
| `domains/commerce/service/subscription_service.py` | 구독 시작. 함수 첫 줄이 게이트 |
| `tests/test_purchase_gate.py` | 유료 차단 / 무료 통과 / 이미보유 우선 검증 |

### IAP 를 붙일 때 지울 곳

`purchase_service.py` 의 `if price > 0: reject_until_iap(...)` 블록과
`subscription_service.py` 의 `reject_until_iap(...)` 한 줄. **그 아래 로직(소유권 지급·
결제기록·트랜잭션)은 IAP 에서도 그대로 재사용된다** — 지우면 안 된다.

## 7. 결정된 것 / 아직 안 정해진 것

**결정**
- 구독 상품: **Pro 월간 1종**
- 캐릭터: **영구 소유**(복원 지원 필요)
- 결제 수단: **IAP**(스토어 출시 전제)

**아직**
- 실제 상품 ID 문자열 (`im.beavertalk.character.bibi` 같은 것)
- 애플 `.p8` 키 / 구글 서비스계정 — 콘솔에서 발급받아야 한다
- 수수료 반영 가격표

**다음 단계**: 서버가 IAP 계약서(경로·요청·응답)를 먼저 확정해 앱팀에 넘긴다. 그래야
앱이 껍데기를 채우며 병렬로 갈 수 있다. 자격증명이 없어도 계약·DB·멱등·지급 로직은
지금 다 만들 수 있고, 키가 오면 검증 어댑터 안쪽만 채우면 된다.
