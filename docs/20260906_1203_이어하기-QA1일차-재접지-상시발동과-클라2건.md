### 1~3. 재접지가 통화 내내 상시 발동한다 (공통 원인)

arm 조건이 `usage_prompt_peak >= LIVE_CTX_TRIGGER_TOKENS × 0.85`
(`call_session.py:3742`, `REGROUND_ARM_RATIO=0.85`). demo·운영 **둘 다 트리거가 8,000** →
**기준선 6,800**. 그런데 이 통화의 **바닥 프롬프트가 6,937~7,444**(지시문 + teaching_plan 30개
+ 표정 도구). ⇒ **첫 턴부터 조건이 참**이고 통화 내내 안 꺼진다.

실측(통화 1310, arm 5회 전부 `근거=compress`):

```
[01:24:54] 1/8회  압축감지=0  peak=6937   ← 통화 시작 8초. covered=0/0, topic=(빈 값)
[01:25:56] 2/8회  압축감지=1  peak=14382
[01:27:02] 3/8회  압축감지=2  peak=15990
[01:28:18] 4/8회  압축감지=5  peak=6845   ← 압축이 아니라 바닥만으로 넘음
[01:29:19] 5/8회  압축감지=6  peak=7444   ← 같음
```

주입은 `자리=마이크`(학습자 발화 시작 시). 브리프가 "학습자가 방금 한 말에 **먼저** 반응하고 /
요청 하나로 이어가라"라서, **미완성 답변 위에 얹히면 비버가 자기 과제를 버린다.**

증거 — 마지막 턴:
```
[01:29:20] BEAVER[t33]: ..."My younger sibling is like that, too." Hurry up!
[01:29:36] 재접지 얹기 5회째
[01:29:39] USER[t34]:   내 동생은                    ← 시킨 문장을 만드는 중
[01:29:39] BEAVER[t35]: Oh, you want to talk about your sibling? Fine.
                        But do you remember how to say 'road' in Korean?
```

반복(#3): `"길 옆에 나무가 있어요"` 를 **t5·t21·t31·t35 네 번** 시켰다. 비버 턴 18개에서 실제로
돈 항목은 4~5개인데 `teaching_plan=30` 이었다. 반복을 막는 게 브리프의 `covered` 인데 값이
`0/0 → 1/1 → 3/3 → 4/4 → 4/5` 로 거의 비어 있다.

⭐ **더 큰 그림**: 임계 8,000 에 바닥이 7,000이면 **대화가 들어갈 자리가 600~1,000토큰뿐**이다.
그래서 **압축이 5분에 7번** 돌았다(`컨텍스트 압축 감지 #7`). 비버가 5분 동안 앞부분을 일곱 번
잊었다는 뜻이고, #3(같은 문장 반복)이 여기서도 설명된다.

⭐ **비용 역설**: Live 는 매 턴 프롬프트 전액 재과금이다. 바닥이 7,000이면 **트리거를 얼마로
내리든 매 턴 최소 7,000은 나간다.** 실측 `sum_prompt=175,172 / 18턴 = 턴당 9,732` ⇒ **비용의
약 72%가 지시문**이다. 진짜 절감은 트리거보다 **바닥(teaching_plan 30개 등)** 을 줄이는 쪽일 수
있다. 아직 안 쟀다.

### 4. 메인스레드 지각 선형 증가

5초 창별 최대 지각(`main_late_ms`)이 통화 시간에 비례해 자란다.

```
  5s=81ms   50s=105ms  100s=305ms  150s=436ms  200s=714ms  250s=1172ms  300s=1688ms
```

- ⭐ **계측 착시가 아니다.** `FlutterPcmSoundPlugin.java:496` 에서 ping 마다 `mainProbeMaxLateMs = 0`
  으로 **리셋한다** ⇒ 누적 최대값이 아니라 **창별 최대값**이다. 실제로 오르내리며 상승한다.
- **기각된 후보**: 영상 디코더 누수(2↔3 오르내리고 매번 회수) · 오디오 적체(큐 거의 항상 0) ·
  감정 반복 재생(재생이 멈춘 120초 뒤 기울기가 **더 가팔라짐** — 2.0 → 7.6ms/s).
- ⛔ **팀이 미리 세운 판정선이 안 먹었다**(`normalcall_controller.dart:2745-2750`).
  "메인지각이 왕복을 따라가면 레코더 유죄 / 메인지각 평평하고 왕복만 자라면 무죄" 인데,
  실측은 **메인지각만 자라고 왕복(`ping_ms`)은 0~4ms 로 평평**했다 — 두 갈래 어디에도 안 든다.
  둘 다 같은 메인 루퍼에서 도는데(`Handler(Looper.getMainLooper())`) 한쪽만 늦었다
  ⇒ **"두 계측이 같은 스레드를 잰다"는 전제 자체가 의심스럽다.**
- ⭐ **사장님 제보**: "영상통화 버벅인다"는 말이 있었다. 이 수치가 그것일 가능성이 높다.
- **다음 수는 정해져 있다**: 통화 중 logcat 에서 `Choreographer: Skipped N frames` 를 잡아
  시각을 다른 이벤트와 대조한다. 폰이 연결돼 있으면 바로 된다.
- 08-23 메모(`[[live-call-fix-in-progress-20260820]]`)는 "메인스레드 홉 수정 넣어뒀고 미검증"
  이라고 돼 있는데, **이 수치는 아직 안 고쳐졌다**고 말한다.

### 5. 감정 클립 반복 재생 (심각도 낮음)

서버는 laugh 마커를 **1번**(seq=2, +52s) 보냈는데 화면엔 **4번** 떴다(+54.1 / 86.0 / 99.5 / 117.8s,
전부 `cached:false` = 매번 새 디코더).

원인: `_stopTalking` → `_freeEmoSlot` 이 `_emo=null`·캐시 비움까지 하는데 부모 위젯의
`widget.emotion` 은 **여전히 laugh**. 다음 발화에서 `_startTalking`(`sync_avatar.dart:520`)이
`_syncEmotionLayer()` 를 부르고 `_emo == null` 갈래(`:863`)에 걸려 **같은 클립을 다시 연다.**
어제 커밋 **`9748eae`**("발화가 끝나면 감정 클립도 끝낸다")가 만든 회귀다. 51.9초 물던 건 고쳤고
그 수정 자체는 옳다.

⚠ **체감은 약하다**(사장님 실통화 확인). 비버가 원래 비웃는 캐릭터라 웃는 얼굴이 안 어색하고,
120초의 neutral 마커에서 멈춰 **영향 구간이 5분 중 66초**였다. 표본 1건.
⛔ **성능 문제(#4)의 원인이 아니다** — 위 기각 근거 참조. 내가 처음에 연결 가능성을 언급했는데 아니다.

### 곁다리 — 오전사를 정답 처리
