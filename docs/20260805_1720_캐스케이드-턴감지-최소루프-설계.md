## 0. 프레임 — 무엇을 만드는가, 무엇을 만들지 않는가

**동기는 원가 하나다.** 캐스케이드(STT→LLM→TTS)의 목표는 **Live보다 나아지는 게 아니라
Live와 같은 동작을 더 싸게 재현**하는 것이다. 현재 Live 통화는 품질이 좋고 잘 돌고 있다 —
그게 기준선(baseline)이고 상한이다.

> ⚠ 원가 기준선 숫자는 이 문서에 **인용하지 않는다.** 5분 실측을 선형 3배 한 값(15분 ≈ $1.65)은
> 신뢰할 수 없고(컨텍스트 누적 때문에 3배가 아니라 4~4.5배),
> `docs/20260804_1930_15분-통화-마스터플랜.md` §1 은 $2.5~2.9 로 본다. 조사 탭이 재확정 중이다.
> 어느 쪽이든 이 설계는 바뀌지 않는다.

추가 요구는 하나: **barge-in**(비버 발화 중 사용자가 말을 시작하면 비버를 끊고 턴을 넘긴다).
이건 Live에서 못 하던 것이라 "재현"이 아니라 신규다.

### 확정 전제 (재논의 대상 아님)

- 턴 감지 = **하이브리드.** 시작 = STT v2 `SPEECH_ACTIVITY_BEGIN` 이벤트 / 종료 = **서버 자체

  그 필드는 스트림을 닫는다(§2-3에서 proto 원문으로 확정).

- 기존 normalcall은 **한 줄도 안 건드린다**(R4: 2펌프·절대 백스톱·barge-in off·종료 규약).

**왜 `protocol.py`에 신규 메시지를 안 넣나.** 신규 메시지 추가는 additive라 normalcall
동작이 바뀌지는 않는다. 그래도 안 넣는 이유는 D5(기존 통화 무접촉)와 R4다 — 통화의 계약
파일을 캐스케이드 실험이 흔들면, 나중에 캐스케이드를 버릴 때 되돌릴 게 생긴다.
`cascade_protocol.py`가 `protocol.py`의 모델을 **import 해서 재사용**하므로(ping·error·pong,
P1에서 turn_start·turn_end·output_transcript) 클라 입장에선 여전히 한 벌의 계약이고,
중복 정의는 없다.

## 2. STT v2 인터페이스 계약

### 2-1. 왜 v2인가

v1(`speech_v1`)에는 **음성 활동 이벤트가 없다.** `is_final`만으로 턴을 판정하면 엔진이 문장을
확정하는 자체 타이밍에 끌려다니고, 무엇보다 **턴 "시작"을 알 수 없다** — barge-in이 불가능하다.
v2의 `enable_voice_activity_events`는 `SPEECH_ACTIVITY_BEGIN` / `SPEECH_ACTIVITY_END`를 준다.
시작은 barge-in 트리거, 종료는 턴 종료 판정이다.

> 인수인계 4-1은 종료(`is_final`)만 봤는데, 그건 barge-in 요구사항이 붙기 전에 쓰인 것이다.
> **둘 다 노출한다.**

### 2-2. 이벤트 타입 (core/stt.py)

v1의 `results() -> (text, is_final)`는 전사만 표현할 수 있어 VAD 이벤트를 담지 못한다.
v2는 **이벤트 스트림**을 낸다:

```python
@dataclass(slots=True)
class SttV2Event:
    kind: str            # 'speech_begin' | 'speech_end' | 'transcript' | 'stream_rollover'
    text: str = ""       # transcript 일 때만
    is_final: bool = False
    at: float = 0.0      # time.monotonic() — 지연 계산용 서버 시각
```

인터페이스(v1과 대칭, 이름만 다름):

```
start()             스트림 개시
push_audio(bytes)   PCM16/16k 청크 투입 (롤오버 중이면 내부 버퍼에 적재)
feed_test(text)     테스트 훅(페이크만 반응)
feed_test_event(kind)  테스트 훅 — speech_begin/speech_end 주입
events()            SttV2Event async iterator
close()             정리
```

구현 3종:
- `GoogleSttV2Stream` — 단일 gRPC 스트림 1개. 스트림이 닫히면 이터레이터가 끝난다.
- `RollingSttV2Stream` — **위를 감싸 롤오버를 숨긴다.** 세션이 보는 건 이것 하나(§5).
- `FakeSttV2Stream` — 크레덴셜 없이 상태기계를 구동(테스트·데모 폴백).

팩토리: `make_stt_v2_stream(sample_rate=16000) -> RollingSttV2Stream | FakeSttV2Stream`.
**v1 심볼(`GoogleSttStream`·`FakeSttStream`·`make_stt_stream`·`get_speech_client`)은 손대지 않는다.**

### 2-3. 인식 설정 — ⛔ **정정(조사 탭 지적 → proto 직접 확인)**

초안은 `speech_end_timeout=800ms`로 턴 종료를 판정하려 했다. **틀렸다.**
`cloud_speech.proto` v2 원문을 직접 확인했다:

```protobuf
// StreamingRecognitionFeatures.voice_activity_timeout
"If set, the server will automatically close the stream after the specified duration
 has elapsed after the last VOICE_ACTIVITY speech event has been sent."

// VoiceActivityTimeout.speech_end_timeout
"Duration to timeout the stream after speech ends. If this is set and no speech is
 detected in this duration after speech was detected, the server will close the stream."
```

**이 필드는 턴 감지 노브가 아니라 스트림을 닫는 값이다.** 800ms를 박으면 사용자가 0.8초
쉴 때마다 스트림이 통째로 죽는다. 조사 탭(§5-5)의 지적이 맞았고, 직접 확인해 확정했다.

☞ **하이브리드로 간다:**

| 무엇 | 누가 판정하나 | 값 |
|---|---|---|
| **턴 시작** | STT v2 `SPEECH_ACTIVITY_BEGIN` 이벤트 | (엔진 내부) |
| **턴 종료** | **서버 자체 타이머** | `CASCADE_TURN_SILENCE_MS` = **800ms**(Live와 같은 출발값, env) |
| 스트림 보호 | `voice_activity_timeout` | **미설정(기본)**. 쓰더라도 턴 판정과 무관하게 크게 |

```python
RecognitionConfig(
  explicit_decoding_config=ExplicitDecodingConfig(
      encoding=LINEAR16, sample_rate_hertz=16000, audio_channel_count=1),
  language_codes=[STT_V2_LANGUAGE],     # 기본 STT_LANGUAGE("ko-KR")
  model=STT_V2_MODEL,                   # 기본 "long"
)
StreamingRecognitionFeatures(
  interim_results=True,
  enable_voice_activity_events=True,
  # voice_activity_timeout: ⛔ 설정하지 않는다(스트림을 닫는 필드)
)
recognizer = f"projects/{project}/locations/{location}/recognizers/_"
```

- `location != "global"`이면 **리전 엔드포인트**(`{loc}-speech.googleapis.com`)로 클라이언트를
  만들어야 한다. 안 하면 NOT_FOUND.
- 오디오 청크 상한 **15 KB/요청**(proto: *"Maximum size for this field is 15 KB per request"*).
  어댑터가 초과분을 잘라 보낸다.

### 2-3-1. ⭐ 침묵을 **오디오 시각**으로 재는 이유

STT v2는 **서울(asia-northeast3)도 도쿄도 지원하지 않는다.** `global`/`us`로 나가므로
태평양 왕복이 고정비로 붙는다. 이벤트 *도착 시각*으로 침묵을 재면 그 왕복 + 인식 지연이
800ms 임계에 **그대로 얹혀** 턴이 그만큼 늦게 끊긴다.

v2 응답은 오디오 타임라인 좌표를 준다:

| 필드 | 뜻 |
|---|---|
| `speech_event_offset` | *"Time offset between the beginning of the audio and event emission"* |
| `result_end_offset` | *"Time offset of the end of this result relative to the beginning of the audio"* |

서버는 자기가 STT로 흘린 오디오 총량(`audio_ms_sent`)을 알고 있으므로:

```
이미 흘러간 침묵 = audio_ms_sent − event.offset_ms
남은 대기        = max(0, CASCADE_TURN_SILENCE_MS − 이미 흘러간 침묵)
```

즉 **임계는 오디오 위에서 800ms로 지켜지고**, 파이프라인 지연은 임계에 더해지지 않는다.
덤으로 `audio_ms_sent − offset_ms`가 곧 **파이프라인 지연(리전 왕복 + 인식)** 계측값이라
`user_turn_end.pipeline_lag_ms`로 내보낸다(§9에서 이 값으로 지연을 분해한다).

오프셋이 없으면(페이크·구버전) 그냥 전체 임계를 기다린다 — 폴백은 항상 있다.

| 키 | 기본 | 의미 |
|---|---|---|
| `CASCADE_TURN_SILENCE_MS` | `800` | ⭐ **턴 종료 침묵 임계(서버 타이머).** Live와 같은 출발값 |
| `CASCADE_TURN_MAX_S` | `60` | END가 영영 안 와도 턴을 강제 종료(안전망) |

## 3. 턴 상태기계

```
        ┌──────────────────────── speech_begin ───────────────────────┐
        ▼                                                             │
   ┌────────┐  speech_begin   ┌───────────────┐  speech_end   ┌───────────┐
   │  IDLE  │ ──────────────▶ │ USER_SPEAKING │ ────────────▶ │ THINKING  │
   └────────┘                 └───────────────┘               └───────────┘
        ▲                                                            │ 첫 TTS 청크
        │ 재생 완료 / 취소 완료                                        ▼
   ┌────────────────┐    speech_begin (=barge-in)          ┌────────────────┐
   │   CANCELLING   │ ◀────────────────────────────────────│ BEAVER_SPEAKING│
   └────────────────┘                                      └────────────────┘
```

| 상태 | 들어오는 오디오 | 나가는 오디오 | 비고 |
|---|---|---|---|
| IDLE | STT로 계속 흘림 | 없음 | 통화 내내 STT는 **항상 켜져 있다**(barge-in 전제) |
| USER_SPEAKING | STT | 없음 | partial 전사를 클라에 중계 |
| THINKING | STT | 없음 | LLM 응답 대기(P1) |
| BEAVER_SPEAKING | STT **계속 흘림** ← Live와 다른 지점 | TTS PCM24k | speech_begin = barge-in |
| CANCELLING | STT | **중단 + 폐기** | §4 |

**P0(이번)에서는 THINKING 이후가 없다.** speech_end 즉시 최종 전사를 텍스트로 에코하고 IDLE로
돌아간다. 상태 enum과 전이 훅은 P1이 그대로 채우도록 미리 만든다.

### 3-1. 턴 종료 판정 — 서버 타이머의 정확한 동작

```
SPEECH_ACTIVITY_BEGIN → speech_active = True,  카운트다운 없음(엔진이 "말하는 중"이라 함)
transcript(부분/최종)  → 텍스트 누적. speech_active 가 아니면 카운트다운 재장전
SPEECH_ACTIVITY_END   → speech_active = False, 카운트다운 장전
                         남은 대기 = 800ms − (audio_ms_sent − event.offset_ms)
카운트다운 만료        → 턴 종료(reason="silence")
만료 전 BEGIN 재발생   → 카운트다운 취소, **같은 턴 계속**   ← 생각하느라 쉬는 구간
턴 상한(60s) 초과      → 강제 종료(reason="max")            ← END를 영영 못 받는 경우 안전망
```

`speech_active` 동안 카운트다운을 걸지 않는 것이 핵심이다. 부분 전사는 인식 지연 때문에
항상 과거를 가리키므로, 그것만 보고 타이머를 걸면 **말하는 중에 턴이 잘린다.**

VAD 이벤트를 아예 안 주는 엔진/설정에서는 `speech_active`가 계속 False라 전사 오프셋이
타이머를 몬다 — 자동으로 폴백이 된다.

> 안전망이 필요한 이유: 문서상 *"If the stream is closed before speech ends, a
> `SPEECH_ACTIVITY_END` event won't be sent."* 발화 중 스트림이 죽으면 END가 영영 안 온다.

### 3-2. barge-in 트리거 정책 — ⭐ 에코 2차 방어는 **선택이 아니라 필수**

클라 조사 결론: **플랫폼 AEC를 제대로 켜도 잔여 에코가 남는다**(스피커폰 최악, 이어폰은
사실상 무해). 게다가 현재 Android 재생은 `USAGE_MEDIA/CONTENT_TYPE_MUSIC`이라 **AEC 기준
경로 밖**이어서 지금은 AEC가 실질적으로 안 걸린다.

☞ 그 상태로 `speech_begin` 하나에 비버를 끊으면 **비버가 자기 목소리에 끊긴다.**
초안의 "즉시 취소 + 클라 AEC에 맡긴다"는 폐기하고, 서버에 관문을 둔다:

| # | 관문 | 값(env) | 왜 |
|---|---|---|---|
| ① | **에너지 임계 상향** | `CASCADE_BARGEIN_RMS`(0=비활성) | 잔여 에코는 대개 원음보다 작다. 비버 발화 중에만 적용 |
| ② | **최소 지속** | `CASCADE_BARGEIN_MIN_MS` = **150ms** | 순간 튐으로 비버를 끊지 않는다 |
| ③ | **전사 확인** | `CASCADE_BARGEIN_CONFIRM=transcript` | 비어있지 않은 전사 `CASCADE_BARGEIN_MIN_CHARS`자 이상. 200~400ms 늦지만 가장 강함 |

- 지속 판정도 **오디오 시각**으로 한다(도착 시각으로 재면 리전 왕복이 섞인다).
- ⚠ ③에는 이 앱 특유의 위험이 있다: **학습자가 비버 말을 따라 하는 것은 정상 학습 행동**이다.
  "방금 합성한 문장과 STT 전사의 유사도"로 에코를 거르면 **따라읽기를 씹는다.** 유사도
  필터는 쓰지 않는다 — ①②③만 쓴다.

**정책은 세션마다 다르다.** AEC는 기기·라우트마다 다르므로 전역 설정 하나로는 표현할 수 없다.
클라가 `start`에 자기진단을 실어 보내고 서버가 세션 정책을 고른다:

```json
{"type":"start","sampleRate":16000,"aec":{"mode":"headset|hw|vpio|none|unknown","route":"speaker"}}
```

| mode | 세션 정책 |
|---|---|
| `headset` | `immediate` — 음향 결합이 없다. 가장 빠르게 반응 |
| `hw` / `vpio` | 전역 기본값 유지 + ①②는 항상 적용 |
| `none` / `unknown` | `transcript` — AEC가 없다. 가장 보수적으로 |

클라의 **에코 측정 리그 실측**이 나오면 ①②의 값만 env로 조정한다(재빌드 없음).

### 3-3. ⭐ 마이크 상시 개방은 **플래그 뒤에 둔다** (`CASCADE_MIC_ALWAYS_OPEN`, 기본 OFF)

barge-in은 "사용자가 아무 때나 말할 수 있다"는 뜻이고, 그러려면 마이크가 항상 열려 있어야
한다. 그런데 **지금 클라의 '비버 발화 중 마이크 닫기' 게이팅이 자기-대화 루프의 유일한
방어선**이다 — Android 재생이 `USAGE_MEDIA`라 플랫폼 AEC 레퍼런스 밖이라서 AEC가 실질적으로
안 걸린다.

> 실측: `call_id=855`(2026-08-01)에서 **유저 턴의 절반이 비버 대사**였다. 게이팅이 켜져
> 있었는데도 타이밍 결함 하나로 그랬다. 게이팅까지 빼면 스피커폰에서 무방비다.

켜는 조건은 **둘 다** 충족된 뒤다: (a) Android AEC 정비 머지 (b) 에코 측정으로 서버 2차 방어
파라미터 확정.

**서버는 두 모드를 모두 견딘다:**

| 모드 | 업링크 | barge-in | 서버 동작 |
|---|---|---|---|
| **OFF**(초기) | 비버 발화 중엔 **안 온다** | 사실상 미발동 | 이 상태에서도 통화가 **정상 성립**해야 한다 |
| **ON** | 전 구간 끊김 없이 온다 | 활성 | 2차 방어(§3-2)를 통과한 것만 취소 |

☞ 구현 규율: **"비버 발화 중 입력이 온다/안 온다"를 어느 쪽으로도 가정하지 않는다.**
상태기계는 들어온 이벤트에만 반응하고, 플래그는 *barge-in을 시도할지*와 `ready` 통지에만 쓴다.
OFF일 때 비버 발화 중 들어오는 음성 활동은 **에코이거나 게이팅 타이밍 결함**일 확률이 높으므로
끼어들지 않는다 — 그게 OFF에서 "견디는" 방법이다.

☞ **이 제약은 P0를 막지 않는다.** `/__cascadedemo`에는 TTS 재생이 아예 없다(턴 감지만 본다).
스피커로 나가는 소리가 없으니 에코 위험이 0이다. 턴 감지 검증은 전속력으로 진행한다.

## 4. 취소 배관 — barge-in 시 **세 곳**을 동시에 멈춘다

비버가 말하는 중 사용자가 끼어들면, 다음 셋이 전부 멈춰야 한다. 하나라도 빠지면 비버가
몇 초 더 말한다.

```
 ① TTS 합성 중단        서버 안: 합성 태스크 cancel + 업스트림 스트림 close
 ② 서버 송신 중단        서버 안: 송신 큐 drain(버린다) + epoch 증가
 ③ 클라 버퍼 폐기        ← 프로토콜에 통로가 없다. 신규 메시지를 만든다.
```

③이 진짜 구멍이다. 클라(브라우저 WebAudio·Flutter PCM 플레이어)는 이미 **수백 ms~수 초
분량을 스케줄/큐에 쌓아둔 상태**다. 서버가 보내기를 멈춰도 클라는 쌓인 걸 끝까지 재생한다.

> 참고: `core/gemini_live.py:304`가 `interrupted` LiveEvent를 만들지만
> `domains/learning/realtime/` 어디서도 소비하지 않는다 — barge-in off라 올 일이 없어서다.
> **캐스케이드는 그 자리를 우리가 채운다.**

### 4-1. 신규 메시지 (cascade_protocol.py)

```python
# 서버 → 클라
class ServerAudioCancel(BaseModel):
    """지금 재생 중/버퍼에 쌓인 이 턴 오디오를 **즉시 버려라**."""
    type: Literal["audio_cancel"] = "audio_cancel"
    turn_id: str                     # ⭐ 필수. 클라 회신을 대조할 유일한 열쇠(§5-5)
    epoch: int                       # 이 값보다 낮은 epoch 의 오디오는 전부 무효
    reason: str = "barge_in"         # 'barge_in' | 'abort' | 'call_end'
    report_progress: bool = True     # 재생 진행도를 되보내 달라(§5 이력 정합성)

# 클라 → 서버
class ClientPlaybackProgress(BaseModel):
    """실제로 재생한 양. audio_cancel 을 받은 직후 1회(또는 턴 종료 시)."""
    type: Literal["playback_progress"] = "playback_progress"
    turn_id: str
    epoch: int
    played_server_bytes: int         # ⭐ 서버발 오디오 중 실제로 스피커로 나간 바이트 수
    source: "native" | "estimate"    # ⛔ estimate 는 서버가 버린다(§5-3)
    sampled_at: "stop" | "cancel"    # stop 권장 — 취소 후 50~120ms 더 들린다
```

### 4-2. 뒤늦게 도착하는 프레임 — 오디오 포맷을 **안 바꾸고** 거른다

취소 메시지와 오디오 프레임은 **같은 소켓의 다른 프레임 종류**다(텍스트 vs 바이너리).
취소를 보낸 뒤에도 이미 write 버퍼에 들어간 오디오 프레임이 클라에 도착한다. 클라가
`turn_id`만 보고 판단하면 "취소된 턴의 뒤늦은 조각"을 새 소리로 재생한다.

**해법: 구간으로 식별한다.** WebSocket은 한 연결 안에서 메시지 순서를 보장한다(텍스트·
바이너리가 섞여도). 그래서

```
audio_cancel 도착  ~  다음 turn_start 도착   ← 이 사이의 바이너리 프레임 = 취소된 턴의 잔여
```

가 **유일하게** 성립한다. 클라 규칙은 두 줄이다:
1. `audio_cancel` → 재생 중지 + 큐 폐기 + `drop=true`
2. 다음 `turn_start` → `drop=false`. 그 사이 도착한 바이너리는 디코드 없이 버린다.

> **초안의 4바이트 epoch 헤더는 폐기했다.** 클라 조사 결과 오디오 규격(입력 PCM16/16k ·
> 출력 PCM24k · 헤더 없음)을 그대로 두는 것이 앱 수정 최소화의 조건이고(제약 #4), 프레임
> 포맷을 바꾸면 **모든 프레임의 파싱 경로**를 건드려야 한다. 순서 보장으로 같은 목적을
> 달성하는데 포맷을 깰 이유가 없다. `epoch`는 JSON 메시지(`audio_cancel`/
> `playback_progress`)에만 남겨 상관관계·로그 대조에 쓴다.

### 4-3. 순서

```
t0  STT: speech_begin (BEAVER_SPEAKING 중)
t0  서버: epoch += 1
t0  서버: TTS 합성 태스크 cancel                    ← ①
t0  서버: 송신 큐 비우기(pending PCM 폐기)           ← ②
t0  서버: audio_cancel(turn_id, epoch) 텍스트 전송   ← ③
t0+ε 클라: 재생 정지 + 버퍼 폐기 + played_server_bytes 계산(네이티브 카운터)
t0+ε 클라: playback_progress(turn_id, epoch, played_server_bytes)
t0+δ 서버: 이력 절단(§5) → 상태 USER_SPEAKING
```

**취소된 턴에는 `turn_end`를 보내지 않는다.** `audio_cancel`이 그 턴의 **종결을 겸한다** —
두 메시지가 경합하면 클라가 "정상 완료"로 처리해 프리버퍼 우회가 걸린다(§8-1). 클라도
`turn_end` 훅 자리에 `audio_cancel`을 같이 건다.

취소는 **동기적으로 셋을 다 친 뒤** 상태를 넘긴다. `playback_progress`를 기다리느라 다음 턴을
막지 않는다 — 이력 절단은 늦게 도착해도 되는 일이다(다음 LLM 호출 전에만 확정되면 된다).

## 5. 대화 이력 정합성 — 중간에 잘린 비버 발화를 이력에 뭐라고 남기나

**문제.** LLM이 생성한 전체 텍스트를 이력에 남기면, 비버는 **사용자가 듣지도 못한 말을 한
것으로 알고** 다음 턴을 잇는다. "아까 말한 것처럼…" 하는데 사용자는 들은 적이 없다.
Live는 이걸 내부에서 처리한다(`interrupted` 이벤트로 자기 이력을 스스로 잘랐다).
캐스케이드는 우리 몫이다.

### 5-1. 재생 원장(playback ledger)

TTS는 **한 덩어리로 합성하지 않는다.** 문장/절 단위로 쪼개 합성하고, 청크마다 원장에 적는다:

```python
@dataclass
class SpokenChunk:
    start_byte: int    # 이 턴에서 송출한 누적 바이트 오프셋(무음 패딩 포함)
    end_byte: int
    text: str = ""     # "" = 페이서가 끼운 무음 패딩
```

⭐ **왜 ms가 아니라 송출 바이트로 키잉하나.** 클라는 **서버가 끼운 무음 패딩과 실제 대사를
구분할 수 없다** — 둘 다 서버발 바이트로 똑같이 도착한다. 클라가 "무음 제외"를 시도하면
자기가 만든 필러만 걸러낼 뿐 **서버 패딩은 대사로 계산돼 절단이 틀어진다.**
그래서 계약을 이렇게 나눈다:

```
클라 → 서버 : played_server_bytes = 서버에서 받은 오디오 중 실제로 스피커로 나간 바이트 수
              (클라 자체 생성 무음 필러는 세지 않는다)
서버        : 대사/무음 분리는 원장이 한다 — 어디에 패딩을 넣었는지 아는 건 서버뿐이다
```

PCM은 **고정 비트레이트**라(24kHz·16bit·mono = 48,000 bytes/s) 바이트 ↔ 밀리초 변환이
정확하다. 추정이 아니라 산수다.

### 5-2. 절단 규칙

```
played_server_bytes 도착
  → 원장에서 end_byte <= played_server_bytes 인 청크까지를 "말한 것"으로 확정
  → 무음 패딩 청크(text="")는 오프셋 계산에만 쓰고 텍스트에서는 제외
  → 걸쳐 있는 청크(start_byte < played < end_byte)는 **버린다**(부분 문장은 안 남긴다)
  → spoken_text = 확정 청크들의 text 이어붙임 + " …"      ← LLM 이력에 남는 값
  → generated_text = LLM 이 만든 전체                      ← 감사/분석용으로 따로 보관
  → 이력 항목: {"role":"model", "text": spoken_text + "(사용자가 끼어들어 여기서 끊김)"}
```

**걸친 청크를 버리는 쪽(짧은 쪽)으로 편향한다.** 두 방향의 실패 비용이 비대칭이기 때문이다:

- 실제보다 **적게** 남기면 → 비버가 이미 한 말을 조금 반복한다. **경미**(사람도 그런다).
- 실제보다 **많이** 남기면 → 사용자가 못 들은 정보를 전제로 대화가 진행된다. **대화가 어긋난다.**
  사장님이 지목한 그 실패다.

문장 경계로 자르므로 "…했습니 …" 같은 반쪼가리가 이력에 들어가지 않는다.

### 5-3. `played_server_bytes`는 **네이티브 카운터만** 받는다 (클라 실측 반영)

클라 실측:

| 소스 | 오차 | 판정 |
|---|---|---|
| Android `getPlaybackHeadPosition` | **±10~20ms** | ✅ 쓴다 |
| iOS 네이티브 카운터 | (신규 구현 필요) | ✅ 쓴다 |
| **Dart/JS 외삽값** | **±50~150ms** | ⛔ **버린다** |

외삽값의 오차는 우리가 자르려는 단위(문장 청크 수백 ms)와 같은 자릿수다. 그걸 받으면
"짧은 쪽 편향" 원칙 자체가 무의미해진다 — 어느 쪽으로 틀릴지 모르는 값이 되기 때문이다.
그래서 `playback_progress.source != "native"`면 **없는 것으로 치고 서버 추정으로 간다**
(`CASCADE_TRUST_ESTIMATED_PROGRESS=true`로 강제 허용은 가능 — 실험용).

**⚠ 취소 후에도 50~120ms 더 들린다.** 클라가 `audio_cancel`을 받고 실제로 소리가 멎기까지
그만큼 걸린다(재생 플러그인에 `clear()`가 없어 신설해야 하고, 그 자체가 4~5일 작업이다).
그래서 샘플 시점을 계약에 넣는다:

```
sampled_at="stop"   ← 권장. 실제로 멎은 뒤 카운터를 읽는다 = 지연이 값에 이미 포함
sampled_at="cancel" ← 취소 수신 순간. 서버가 CASCADE_CANCEL_STOP_MS(120ms)를 더해 보정
```

**서버 추정 폴백**(native가 안 올 때):

```
played_est_ms = max(0, sent_ms − CASCADE_CLIENT_BUFFER_MS)      # 기본 600ms
```

버퍼 상수를 **크게** 잡는 이유는 방향이 비대칭이기 때문이다. 실제 버퍼가 가정보다 크면
(클라 쿠션은 언더런 오인 시 **1200ms까지** 올라간다 — §8-2) 우리 추정은 실제보다 **많이**
말한 것으로 계산한다 = 대화가 어긋나는 쪽. 그래서 보수적으로 크게 잡고, 정지 지연은
폴백에서는 **더하지 않는다**(짧은 쪽 유지).

데모/실기기에서 native 값과 서버 추정을 나란히 찍어 이 상수를 교정한다.

### 5-5. ⭐ 진행도는 **`turn_id`로 대조**한다 — 원장은 턴별로 산다

`playback_progress`는 비동기다. 도착할 즈음 **서버는 이미 다음 턴을 시작했을 수 있다.**
원장을 하나만 들고 있으면 늦게 온 이전 턴 진행도가 **새 턴 원장에 적용돼** 엉뚱한 대사가
잘린다.

그래서:

1. `audio_cancel`은 `turn_id`를 **필수**로 싣는다. (normalcall의 `turn_start`/`turn_end`/
   `output_transcript`가 이미 `turn_id`를 싣는 것과 **같은 규약**이다 — 새 규약이 아니다.)
2. 클라는 그 `turn_id`를 `playback_progress`에 그대로 되보낸다.
3. 서버는 **턴별 원장**(최근 4턴 보관)을 두고 `turn_id`로 찾아 그 턴에만 적용한다.
4. 모르는·이미 밀려난 `turn_id`면 **버린다**(로그만 남긴다). 현재 턴에 적용하지 않는다.
5. `source != "native"`도 버린다(§5-3).

고정 테스트: `test_audio_cancel_carries_turn_id`,
`test_late_progress_applies_to_its_own_turn_not_the_current_one`,
`test_unknown_turn_id_progress_is_ignored`,
`test_session_ignores_estimated_and_stale_progress`.

### 5-4. 합성 전에 취소된 텍스트

LLM이 아직 스트리밍 중이었거나 합성 큐에 있던 텍스트는 **원장에 없다 = 이력에 없다.**
자동으로 올바르다. 별도 처리 불필요.

## 7. 스트림 롤오버 — 왜 필수인가

두 가지 이유로 STT 스트림은 통화보다 짧다:

### 7-1. 턴마다 스트림이 죽지는 않는다 (초안 정정)

초안은 "`speech_end_timeout`이 턴 종료 시 스트림을 닫으므로 턴 하나 = 스트림 하나가 될 수
있다"고 봤다. **그 필드를 안 쓰기로 했으므로(§2-3) 이 시나리오는 사라졌다.**
스트림은 수명 한도(§7-2)에서만 교체된다.

다만 **방어 코드는 남긴다** — 서버가 어떤 이유로든 스트림을 닫으면(쿼터·네트워크·내부 오류)
상위가 이어붙인다. 세션이 보는 이벤트 열은 어느 경우에도 하나로 연속된다. 이게 이 설계의
안전장치다.

### 7-2. 스트림 수명 한도

v1은 ~5분(`core/stt.py:74` 주석). v2 한도는 조사 탭 확인 중이나, **통화 최대 15분보다 짧다고
가정**하고 짓는다. `STT_V2_STREAM_MAX_S`(기본 240초) 경과 시 선제 롤오버.

### 7-3. 롤오버가 턴을 끊지 않게 — 버퍼 리플레이

```
현재 스트림 종료 감지
  → 상태: ROLLING (세션에는 이벤트를 안 낸다, stt_rollover 진단만)
  → 이 사이 들어온 클라 오디오는 링버퍼(최대 CASCADE_ROLLOVER_BUFFER_MS=3000)에 적재
  → 새 스트림 start() 완료
  → 버퍼를 순서대로 push → 이후 실시간 흐름 재개
```

- **오디오 유실 0.** 감지가 갭(gap_ms, 통상 100~300ms)만큼 늦을 뿐이다.
- **말하는 중 롤오버는 미룬다.** 턴을 반토막 내지 않기 위해서만이 아니다 — 문서상
  *"If the stream is closed before speech ends, a `SPEECH_ACTIVITY_END` event won't be sent."*
  발화 중 교체하면 **턴 종료 신호 자체를 잃는다.** 그래서 롤오버는 반드시 END 이후에 한다
  (그래도 못 받으면 §3-1의 턴 상한 안전망이 받는다).
- **오프셋을 재기준한다.** 새 스트림의 오디오 타임라인은 0부터 다시 시작한다. 그대로 쓰면
  롤오버마다 침묵 계산이 0으로 되돌아가 타이머가 오작동한다. 새 스트림의 t=0이 전역
  타임라인의 어디인지(`총 유입량 − 리플레이 버퍼 길이`)를 잡아 모든 오프셋에 더한다.
- 대안인 **선개통(pre-warm, 두 스트림 겹치기)** 은 갭이 0이지만 겹친 구간이 이중 과금이다.
  원가가 동기인 프로젝트에서 기본값으로 삼지 않는다. 갭이 문제로 드러나면 그때 켠다.

## 8. 클라이언트(앱) 제약 4건 — 서버가 지켜야 할 것

bt-front 조사에서 나온 제약이다. **앱을 안 고치는 것이 목표**이므로 전부 서버가 맞춘다.
두 건(#1·#4)은 이 문서 초안의 계약을 뒤집었고, 그에 맞춰 §4-2·§6을 이미 고쳤다.

### 8-1. `turn_end`는 **마지막 TTS 바이트를 보낸 뒤**에 낸다 (확정)

현행 클라 계약은 `turn_end = 이 턴 오디오가 전부 큐에 들어왔다`이고, 클라의 `_turnEnded`가
그 전제로 **지터 프리버퍼를 통째로 우회**한다. 캐스케이드가 **LLM 텍스트 완료 시점**에
`turn_end`를 보내면 TTS 오디오가 아직 흘러오는 중인데 클라는 "다 왔다"고 판단한다 →
**짧은 대사가 끊긴다.**

☞ 계약을 바꾸지 않는 쪽으로 확정. 서버 규칙:

```
LLM 텍스트 완료  ≠  turn_end
마지막 TTS 청크를 소켓에 write 완료  →  그때 turn_end
barge-in 으로 잘린 턴  →  turn_end 대신 audio_cancel (turn_end 를 내지 않는다)
```

취소된 턴에 `turn_end`를 내면 클라가 "정상 완료"로 처리해 프리버퍼 우회가 걸린다. 취소는
취소 메시지로만 끝낸다.

### 8-1-1. ⛔ 서버 출력 불변식 5개 — **테스트로 고정한다**

클라는 `audio_cancel` 이후 ~ 다음 `turn_start` 이전에 도착한 바이너리를 **전부 버린다**(§4-2).
그 판별이 안전하려면 서버가 아래를 어기면 안 된다. 어기면 클라가 **정상 오디오를 조용히
버린다** — 증상이 "가끔 대사가 통째로 안 들린다"라서 추적도 어렵다.

| # | 불변식 | 고정 테스트 |
|---|---|---|
| **I1** | 비버 턴 **밖에서는 오디오를 일절 보내지 않는다** | `test_i1_no_audio_outside_beaver_turn` |
| **I2** | 모든 비버 턴은 `turn_start`로 시작한다 — **오디오 첫 바이트보다 먼저** | `test_i2_turn_start_precedes_first_audio_byte` |
| **I3** | 누적 송출량 ≤ 실시간 레이트 + lead | `test_i3_pacing_never_outruns_realtime` |
| **I4** | 취소된 턴에는 `turn_end`를 보내지 않는다 | `test_i4_cancelled_turn_has_no_turn_end` |
| **I5** | `turn_end`는 마지막 오디오 바이트 **뒤에** 낸다 | I2 테스트에 포함 |

구현상 이 다섯은 **`BeaverOutput` 한 곳을 통과하게** 만들어 강제한다(턴 밖 `send()`는
`InvariantError`로 즉시 터진다 — 조용히 나가는 것보다 낫다). TTS·LLM이 붙어도 송출 경로는
이 클래스 하나다.

### 8-2. ⭐ starve 오인 → 재생 쿠션 1200ms 함정 (제일 위험)

클라에는 언더런 감지 시 재생 쿠션을 키우는 로직이 있고 **최대 1200ms까지 올라간다.**
한 번 올라가면 **그 뒤 모든 턴에 그 지연이 붙는다.**

> 📌 출처(상수 선언 직접 확인):
> `beavertalk-flutter/lib/features/normalcall/presentation/normalcall_controller.dart:455`
> `static const int _cushionMaxBytes = _playbackSampleRate * 2 * 1200 ~/ 1000;`
> (증가 단위 150ms `:454` / 감쇠 300ms `:456`)
>
> ⚠ **초안에 쓴 1800ms는 틀렸다.** 같은 파일 `:1669`의 **주석에 남아 있던 과거 값**이다 —
> 이미 1.8s→1.2s로 낮추는 수정이 들어갔고 그때 실측 지연이 777ms→585ms로 개선됐다.
> **수치는 주석이 아니라 상수 선언에서 딴다**(이 문서의 모든 외부 수치에 출처를 붙이는 이유).
> 방침은 그대로다 — 쿠션 인플레이션은 서버가 흡수한다.

문제의 구조적 차이:

```
Live       한 모델이 오디오를 연속 생성   → 와이어가 고르게 채워진다
캐스케이드  LLM 텍스트 → TTS 문장 단위 합성 → 문장마다 버스트, 사이에 공백
```

클라 코드에 **"5분 통화에서 26회 판정 중 18회가 가짜였다"**는 실측 주석이 이미 달려 있다
(`normalcall_controller.dart:1669` — 그 오탐 때문에 상한을 낮춘 이력). Live에서도 오탐이
있었는데 캐스케이드는 **그 조건을 상시로 만든다.**

☞ **답: 서버가 흡수한다(앱 무수정).** 클라 임계를 바꾸는 쪽은 배포된 앱을 고쳐야 하고,
고쳐도 캐스케이드의 버스트가 사라지는 게 아니라 **감지기를 무디게 만드는 것**뿐이다.
진짜 언더런을 못 잡게 된다.

**비버 턴 페이서(pacer)** — 서버가 TTS 출력을 연속 스트림처럼 내보낸다. 세 가지가 한 몸이다:

| 장치 | 규칙 | 효과 |
|---|---|---|
| **고정 간격 송출** | 비버 턴 동안 `BEAVER_FRAME_INTERVAL_MS`(100ms)마다 프레임 1개 | 와이어 공백이 250ms 임계(§8-3)를 **구조적으로** 넘지 않는다 |
| **무음 패딩** | 낼 실오디오가 없으면 그 슬롯은 **무음 PCM**으로 채운다 | 문장 경계 공백이 와이어에서 사라진다. 어차피 소리는 안 나므로 체감 동일 |
| **선행 버퍼(lead)** | 합성분이 `CASCADE_TTS_LEAD_MS`(**200ms**) 쌓인 뒤 송출 시작, 그 리드를 유지 | TTS가 실시간보다 잠깐 느려도 무음 패딩까지 안 간다 |

비용: 무음도 48,000 bytes/s(24kHz·16bit·mono)를 흘린다 — 통화당 대역폭은 무시 가능하고,
**TTS 과금은 문자 수 기준이라 무음은 공짜다**(합성 안 한다, 0으로 채운 PCM일 뿐).
지연 비용은 리드만큼(첫 소리 +200ms). 이건 감수한다 — 쿠션이 상한(1200ms)까지 차오르는 쪽이
6배 나쁘고, 그건 **한 번 오르면 통화 내내 남는다**(리드는 매 턴 같은 200ms다).

> ✅ **조사 결과 반영: Cloud TTS 스트리밍 합성은 된다.** Chirp3-HD가 `streaming_synthesize`를
> 지원하고 출력에 **PCM/LINEAR16**이 있다(문서상 기본이 LINEAR16). 문장 내부에서도 오디오가
> 조각으로 나오므로 리드를 크게 잡을 필요가 없다 — 초안의 400ms를 **200ms로 내렸다.**
> `sample_rate_hertz=24000`이 실제로 24k를 내는지는 1회 실측이 남아 있다(되면 앱 재생 경로에
> 그대로 꽂혀 **앱 수정 0**). 안 되면 리샘플 한 단이 붙을 뿐 페이서 설계는 그대로다.

**대안(선합성 lookahead)도 같이 쓴다:** 문장 N을 페이싱하는 동안 N+1을 미리 합성해 두면
공백 자체가 줄어 무음 패딩이 거의 안 걸린다. 페이서는 그래도 남긴다 — 마지막 안전망이다.

⭐ **`누적 송출량 ≤ 실시간 레이트` 보장은 전적으로 서버 책임이다(I3).** 페이서가 실시간보다
빨리 밀어내면 클라 버퍼가 무한히 부풀고, 그러면 **barge-in 취소가 늦게 먹히고(사용자가
끊었는데 계속 들린다) 이력 절단도 같이 틀어진다** — §4·§5가 동시에 무너진다.
클라가 넣는 '턴 경계 잔류 백로그' 계측은 **안전망이지 대책이 아니다.**

> 🔗 **조사 탭 직결.** Cloud TTS가 **스트리밍 합성**을 지원하면 문장 내부에서도 오디오가
> 조각조각 나오므로 리드를 훨씬 작게 잡을 수 있다(첫 소리가 빨라진다). 지원 안 하면
> 문장 단위 일괄 합성이라 **페이서와 선합성이 필수**다. 어느 쪽이든 위 설계는 그대로 성립하고,
> `CASCADE_TTS_LEAD_MS` 값만 달라진다.

### 8-3. 서버 공백 감지 임계 250ms

클라는 250ms 이상 공백을 'mid-utterance 서버 공백'으로 판정·로깅한다
(출처: `normalcall_controller.dart:1494` — `nowMs - prevChunkMs >= 250`). §8-2와 같은 뿌리이고,
같은 장치(100ms 고정 간격 + 무음 패딩)로 함께 해결된다. **100ms를 고른 이유가 이것이다** —
임계의 절반 이하로 두면 지터·스케줄링 흔들림이 있어도 250ms를 안 넘는다.

검증: P1 데모에서 **프레임 도착 간격의 최댓값**을 화면에 띄운다. 이 값이 250ms를 넘으면
페이서가 진 것이다.

### 8-4. 오디오 규격은 그대로

```
입력  PCM16 / 16kHz  (클라 → 서버, 헤더 없음)
출력  PCM16 / 24kHz  (서버 → 클라, 헤더 없음)
WS    바이너리 = 오디오, 텍스트 = JSON 제어
```

☞ 초안의 **4바이트 epoch 헤더를 폐기**한 근거다(§4-2). 순서 보장만으로 같은 목적을 이룬다.

### 8-5. 그래서 앱이 P1에서 고쳐야 하는 것 (최소)

barge-in 자체가 신규 기능이라 이것만은 앱이 받아야 한다:

1. `audio_cancel` 수신 → 재생 중지 + 큐 폐기 + `drop=true` (다음 `turn_start`까지).
   `audio_cancel`이 그 턴의 **종결**이므로 `turn_end` 훅 자리에 같이 건다
2. `playback_progress` 회신 — **네이티브 카운터**로 `played_server_bytes`. 안 보내도 서버가
   추정으로 돌아가지만(§5-3) 이력이 덜 정확해진다
3. (조건부) 마이크 상시 개방 — **AEC 정비 + 에코 측정 뒤에** 플래그로 켠다(§3-3)

그 외(오디오 포맷·turn_start/turn_end 의미·프리버퍼)는 **건드릴 필요가 없다.**

## 9. 지연 측정 — 데모가 무엇을 보여줘야 하나

"턴이 제때 끊기나"는 숫자로만 답할 수 있다. 데모 화면에 턴마다 한 줄:

```
#3  시작 12.84s   종료 15.62s   발화 2.78s   감지지연 921ms (엔진오버헤드 +121ms)  "안녕하세요 저는..."
```

- **감지지연** = `turn_end 도착 시각(클라) − 클라 로컬 VAD가 본 마지막 유성 프레임 시각`.
  클라의 RMS 기반 로컬 VAD는 **측정 전용**이다 — 어떤 판정에도 관여하지 않는다(D2: 턴 판정은
  서버만 한다). 사용자가 실제로 입을 다문 순간에 가장 가까운 관측치라 이게 정직한 숫자다.
- **파이프라인 지연** = `audio_ms_sent − event.offset_ms` (서버가 `user_turn_end`에 실어 보낸다).
  = **리전 왕복 + STT 인식 지연**. STT v2는 서울·도쿄가 없어 `global`/`us`로 나가므로 이 항은
  구조적 고정비다. ⚠ 보고할 때 **"리전 왕복 포함"임을 반드시 명시**한다.
- **잔여 오버헤드** = `감지지연 − 침묵임계 − 파이프라인지연`. 이 셋을 분리해야 **무엇을 고칠지**
  안다 — 임계를 줄일 문제인지, 리전을 옮길 문제인지, 우리 코드가 느린 것인지.
- (P1) **barge-in 반응** = `2차 방어 지연(최소 지속 150ms) + 파이프라인 지연 + 취소 왕복 +
  클라 정지 지연(50~120ms)`. 네 항을 따로 찍는다 — 합만 보면 어디가 병목인지 모른다.
- **턴 시작 지연** = `turn_start 도착 − 로컬 VAD 첫 유성 프레임`. barge-in 반응성의 상한이다.
- 롤오버 갭(gap_ms)도 같은 줄에 찍는다 — 롤오버가 턴을 삼키는지 눈으로 본다.

판정 기준(사장님 기준 = "Live만큼"): 외국인 학습자 속도로 말할 때 **생각하느라 쉬는 3초를
말 끊김으로 오인하지 않고**, 감지지연이 1.2초 이내면 통과. 통과하면 P1(LLM+TTS+barge-in)으로
간다. 안 되면 여기서 멈춘다 — 인수인계 4-1의 판단 그대로다.

## 10. graceful degradation (R5)

| 상황 | 동작 |
|---|---|
| `google-cloud-speech` 미설치 | `FakeSttV2Stream` — 데모 페이지는 열리고 dev 훅으로 상태기계 구동 |
| SA 키 부재·인증 실패 | 동일(페이크). 로그 warning 1줄 |
| `STT_V2_FAKE=true` | 강제 페이크(과금 0) |
| v2 스트림 런타임 실패 | 세션에 `error` 이벤트 → 소켓 정리. **서버는 죽지 않는다** |
| `ENV=prod` | 캐스케이드 라우터·데모 **둘 다 마운트 안 함**(노출 0) |

`ready` 이벤트의 `engine` 필드가 `"fake"`면 데모 화면 상단에 **"페이크 STT — 실제 인식 아님"**
배너를 띄운다. 크레덴셜 없이 구조만 검증하는 상태를 사람이 착각하지 않게.

## 11-1. 아키텍처 노트 — 스케일에서 먼저 막히는 것

지금 당장 풀 문제는 아니지만, 설계에 적어 둔다:

| 한계 | 값 | 언제 막히나 |
|---|---|---|
| Cloud TTS `Chirp3RequestsPerMinutePerProject` | **200/분** | 턴마다 스트림을 새로 열면 3.3턴/분 기준 **동시 통화 ~60건** |
| Cloud TTS `ConcurrentStreamingSessionsPerProject` | **100** | 통화당 스트림 1개 유지 시 **동시 통화 100건** |
| STT v2 `Concurrent StreamingRecognize sessions` | 300/리전 | 동시 통화 300건(롤오버 중 순간 겹침 고려하면 더 일찍) |
| 리전 비대칭 | TTS는 도쿄 GA / STT는 서울·도쿄 **없음** | 지연 예산이 한쪽으로 쏠린다 — 원인을 오해하지 않도록 §9에서 분리 계측 |

☞ **통화당 TTS 스트림을 1개로 유지**(턴마다 새로 열지 않기)하면 분당 요청 상한을 피하고
동시 세션 상한(100)만 남는다. 스케일 전에 쿼터 증설을 신청한다.

⚠ 원가 구조가 뒤집힌다는 점도 함께 기억한다: 캐스케이드 원가의 **약 59%가 STT**이고,
**barge-in을 켜면 마이크를 상시 열어야 해서 STT 게이팅으로 아낄 여지가 잠긴다.**
barge-in은 기능이자 원가 항목이다(통화당 약 $0.11).
