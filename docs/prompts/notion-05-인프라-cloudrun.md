## §1. 무슨 일이 있었나 (2026-07-24)

**결론 한 줄**: `test-api`가 매분 스케줄러 + CPU 상시할당(`cpu-throttling=false`)으로 24시간 과금돼 GCP 비용의 76%를 먹고 있었음 → `throttling=true`로 전환해 **월 약 ₩10만 절감**. `app-api`(실통화)는 통화후 분석이 fire-and-forget이라 `false` 유지가 필요. 정석 해법은 Cloud Tasks 오프로드(우선순위 낮음).

### 문제
- call-v2 배포(~7/8) 이후 Cloud Run 비용 약 **+1,654%**. Cloud Run이 전체 청구의 96%(₩69,538 / ₩72,713).
- Monitoring API로 서비스별 billable instance-time 측정 → **`test-api`가 76%** (4일간 4.01 인스턴스-일 = 인스턴스 1개가 24시간 상시).
- 근본 원인 = `cpu-throttling=false` + Cloud Scheduler(`dispatch-calls`, 매분)가 test-api를 계속 깨움 → 24h warm 유지 → **유휴 CPU까지 초당 과금**.

### 해결 (완료)
- `test-api`에 `cpu-throttling=true` 적용 (리비전 `beavertalk-app-test-api-00031`) → 요청기반 과금.
- **안전 근거**: `dispatch-calls`는 **동기(sync) 핸들러** — 요청 안에서 알람 조회·발송을 끝내고 리턴, fire-and-forget이 없음 → `true`로 굶길 작업이 없음.
- `test-api`는 사실상 '스케줄러 전담 서버'. app/demo/test가 **같은 DB를 공유**하므로 크론은 한 서버만 돌리면 전체 커버(중복 발송 방지).
  ⚠ `dogfood`만 별도 DB라 이 크론이 dogfood 알람은 안 챙김(필요 시 dogfood용 크론 별도).
- 효과: 월 ~₩10.4만 → ~₩0.26만(추정). Cloud Run 전체의 ~74% 절감. **되돌리려면 `--no-cpu-throttling` 한 줄.**

### 왜 `app-api`(실통화)는 `false`를 유지해야 하나
통화 종료 시 WS를 닫고 통화후 파이프라인을 **fire-and-forget**(`asyncio.create_task`, `call_session.py` finally 블록)으로 돌린다.

1. **LLM 1콜**: 전사 → 요약 + 피드백 + 문장(표현) 추출 + 항목 검출 → commit → `status=done`.
   프론트 폴링(`analysis_loading.dart`, 1.5s마다·최대 60s)이 기다리는 게 이것.
   **죽으면 통화가 `analyzing`에 멈춤 = 치명적.**
2. 문장별 TTS ×N — 온디맨드 폴백 `POST /sentences/{id}/tts` 있어 죽어도 복구 가능
3. 체크판(mastery)
4. 오디오 MP3 업로드(~9s), 국적 추론

WS(요청)가 닫힌 뒤 = **활성 요청 0** → `throttling=true`면 CPU가 즉시 near-zero로 조여지거나 인스턴스가 회수(SIGTERM→10s→죽임) → 백그라운드 분석이 굶거나 중간에 죽어 결과 유실.
→ `app-api`는 `throttling=false`(CPU 상시)로 소켓 닫힌 뒤에도 뒤처리를 완주시킨다.
단 `app-api`는 통화 없을 때 scale-to-zero → 월 ~₩16k(QA로 부풀려짐)라 실질 낭비 아님. **24/7 낭비는 test-api뿐이었고 이미 해결.**

### 검토했으나 안 되는 우회책
| 시도 | 왜 안 되나 |
|---|---|
| `min-instances=1` + `true` | 콜드스타트만 해결. 살아있어도 유휴 시 CPU는 여전히 조여짐 → 통화후 분석 못 살림 |
| '요청 후 N초만 CPU 유지' 유예 설정 | **Cloud Run에 그런 노브 없음.** CPU 스위치는 타이머가 아니라 '활성 요청 유무'로만 작동 |
| 동기처리(`await` 후 종료) | 모바일 끊김(앱 백그라운드/화면잠금/네트워크전환)에 요청이 끊겨 분석이 죽음 → 지금 구조보다 후퇴 |
| 로컬/집 컴퓨터 배포 | 스로틀 문제는 사라지나 uptime·보안·확장·운영 부담↑. 절충안은 작은 상시 VM(고정비·스로틀 없음). 단 DB·Gemini는 어차피 클라우드라 실익 작음 |

## §2. 개념 정리 — Cloud Run CPU 할당 (오해 → 실제)

**핵심 한 줄**: Cloud Run에서 CPU는 **'활성 인바운드 요청이 있을 때만'** 나온다. 그래서 응답/연결이 끝난 뒤 도는 일(통화후 분석)은 CPU를 못 받아 죽는다 → `false`로 상시 CPU를 주거나, Cloud Tasks로 '나중 요청' 안에서 돌려야 한다.

1. **CPU 상시할당(`false`) ≠ 항상 100% 성능**
   CPU가 인스턴스 생존 내내 '할당/사용가능'하다는 뜻. 실제 사용률(5%든 95%든)과 무관하게 할당된 시간만큼 정액 과금. '최고성능'이 아니라 '항상 켜져있음'.

2. **CPU는 타이머가 아니라 '활성 요청 유무'로 켜진다**
   grace 노브 없음. `false`가 사실상 '스케일다운까지 최대 유예'(대신 유휴 과금).

3. **`min-instances=1` + `true`는 콜드스타트만 해결**
   살아있는 유휴 인스턴스도 요청 없으면 CPU 조여짐.

4. **'요청(request)'의 두 가지 의미**
   Cloud Run이 CPU 주는 '요청' = **들어오는 HTTP/WS(클라→서버)뿐**. DB·Gemini 호출은 그 요청을 처리하는 '도중' 밖으로 나가는 I/O — Cloud Run의 '요청'이 아님. `await`로 기다리는 동안 핸들러가 아직 return 안 했으니 인바운드 요청은 계속 활성 → CPU 유지.

5. **'async(비동기)'의 두 가지 의미**
   (1) `async/await` = 한 요청 **안**에서의 논블로킹 동시성, 요청은 여전히 열려있음.
   (2) fire-and-forget(응답 먼저 주고 나중에) = 일을 요청 **밖**으로 넘김.
   DB `await`는 (1). **단어만 같지 전혀 다름.**

6. **진짜 기준: '가공/저장이냐'가 아니라 '요청 안에서 끝나냐'**
   같은 저장이라도 통화 중(WS 열림)=OK, 통화 후(WS 닫힘)=위험.
   👉 **판단 기준 = 'return 했냐 / WS 닫혔냐'. `await`=요청 안, `create_task`(안 기다림)=요청 밖.**

7. **WebSocket은 '하나의 긴 활성 요청'**
   WS 열려있는 동안은 계속 활성 요청 → 인스턴스 유지 + CPU 있음(`true`여도). **통화 중엔 안 끊김.** 스케일다운/스로틀은 '활성 요청 0'일 때만.

8. **클라(폰)가 끊기면 서버 요청도 torn down**
   폰 끊김 → 그 POST/WS 요청 종료 → 핸들러(코루틴) 취소 + CPU 조임. Gemini가 답을 계산해도 **그걸 받아 저장할 핸들러가 죽어서 유실**. 'LLM이 일하냐'가 아니라 **'결과 받을 요청이 살아있냐'**가 관건.

9. **'통화 끊고 앱 종료'는 예외가 아니라 정상 케이스** ⭐
   유저가 통화를 끝내는 정상적인 방법. 그래서 `true`면 **대부분의** 통화가 분석 실패 → 이게 `app-api`를 `false`로 둬야 하는 **결정적 이유**. (같은 인스턴스에 다른 통화가 동시에 떠있으면 우연히 살 수도 있으나 운에 못 기댐)

10. **전사 vs 분석 분리 → Cloud Tasks**
    전사는 통화 중(활성 WS) 점진 flush로 저장돼 `true`여도 OK. 무거운 분석만 요청 밖이라 문제.
    → **'WS는 전사 저장까지, 분석은 Cloud Tasks 워커'**로 쪼개면 전체 `true` 가능.
    Cloud Tasks = 백그라운드 일을 '나중에 오는 진짜 서버-서버 요청'으로 바꾸는 큐. 폰과 무관하게 완주, 프론트 폴링 그대로. 워커는 별도 서버 or 같은 서버 새 라우트.

11. **비용 모델**: `false` = 인스턴스 생존 내내 과금(유휴 포함) / `true` = 요청 순간만. billable instance-time 메트릭(Monitoring API)으로 서비스별 측정 가능.

12. **로컬/VM 배포**: 스로틀 개념 자체가 없어 백그라운드 완주. 단 프로덕션은 uptime·보안·운영 부담↑. 절충안 = 작은 상시 VM. DB(Supabase)·Gemini는 어차피 클라우드라 그 비용은 안 줄어듦.

## §3. 남은 문제 / 향후 방향

- **(정석 · 우선순위 낮음)** 통화후 분석을 **Cloud Tasks 워커로 오프로드** → 분석이 워커의 '진짜 요청' 안에서 돌아 CPU 확보 → `app-api`도 `true` 가능 → 프론트 폴링 무변경 + 모바일 끊김과 무관하게 안전. 클라 `POST /calls/{id}/analyze`는 '트리거'로만 쓰고 실제 일은 워커가 수행.
- (선택) 안 쓰는 서버 정리: `dogfood`/`web-api`/`web-demo-api` 트래픽 확인 후 정리(비용보다 관리·보안 단순화 목적).
- (선택) `demo-api`: 통화 테스트 안 할 땐 `throttling=true` 가능(테스트 시 다시 `false`).
- (모니터링) test-api 실측으로 추정치(~₩2,589) 갱신 — **2026-07-26~27경 예정이었음. 아직 미확인.**
- (별개·미해결) demo/main 배포 통화 검증이 **Vertex 키(`tta-lingko-rookie`, `gcp_key.json`) 만료로 블록**.
