# 캐스케이드 원가 계측 — 설계 (2026-08-07)

> 담당: cascade-impl · 계약 소유: bt-back(변경 금지) · 반대편 구현: call15-polish(컬럼·마이그레이션)
> 선행: `docs/20260804_2115_통화원가-계기판-Phase0-구현계획.md`, `docs/20260805_1950_원가계기판-2단계-영속화-설계.md`

## §0 왜 — 안 남기면 이 프로젝트를 증명할 수 없다

캐스케이드의 **유일한 동기는 원가**다("Live 와 같은 동작을 더 싸게"). 그런데 지금
`cascade_session.py` 에는 usage/token/cost 문자열이 **0건**이다. 이대로 실사용에 들어가면
Live 는 실측치가 있고(15분 $1.8724 · call 909) 캐스케이드는 비교할 숫자 자체가 안 생긴다.

⚠ 게다가 **조용히** 안 생긴다. Live 경로도 3중으로 삼킨다(`call_session.py:803-830` — call_id
None·usage 0건·예외 전부 조용히 리턴). 그래서 캐스케이드는 **"못 모았다"도 한 줄 남긴다**(§4-3).

## §1 [답] 사용량을 어디서 얻나 — 구간별 출처와 근거

bt-back 이 구현 전에 답하라고 한 항목이다. **추측 없이 1차 자료(proto·설치된 SDK 정의)로만** 적는다.

| 구간 | 벤더가 사용량을 주나 | 근거(1차 자료) |
|---|---|---|
| STT | **준다**(단, "when available") | googleapis `google/cloud/speech/v2/cloud_speech.proto` |
| LLM | **준다** (`usage_metadata`) | Live 경로가 이미 소비 중 — `call_session.py:681 _record_usage` |
| TTS | **안 준다 → 우리가 센다** | 설치된 SDK `google.cloud.texttospeech` 응답 정의 |

### §1-1 STT — 벤더가 과금 초를 알려준다

`cloud_speech.proto`(googleapis master, 2026-08-07 직접 확인) 원문:

```proto
// Metadata about the recognition request and response.
message RecognitionResponseMetadata {
  // When available, billed audio seconds for the corresponding request.
  google.protobuf.Duration total_billed_duration = 6;
```

`StreamingRecognizeResponse` 에 이 메타데이터가 달려 있다:

```proto
message StreamingRecognizeResponse {
  repeated StreamingRecognitionResult results = 6;
  SpeechEventType speech_event_type = 3;
  google.protobuf.Duration speech_event_offset = 7;
  // Metadata about the recognition.
  RecognitionResponseMetadata metadata = 5;
}
```

⚠ **집계 방식이 v1 과 달라졌고, 그 차이가 그대로 위험이다.** v1 같은 필드의 원문은

```proto
// When available, billed audio seconds for the stream.
// Set only if this is the last response in the stream.
google.protobuf.Duration total_billed_time = 5;   // v1 cloud_speech.proto
```

v1 = "**스트림 전체**, 마지막 응답에만". v2 = "**해당 요청**(the corresponding request)".
문구만 보면 v2 는 **응답마다 증분**일 수 있다 — 그러면 합산이 맞고, 반대로 v1 처럼 누적값이
반복해 실리면 합산은 **중복 집계**가 된다. 스트리밍에서 언제 채워지는지 명시한 문장을 공식
레퍼런스에서 못 찾았다(§3 참조).

### ⭐ 판정 완료 (2026-08-07 실통화) — **max 가 정답, sum 은 중복**

```
실제 오디오 104.5s / stt_billed_max_s=102.0 / stt_billed_sum_s=419.0   (4배)
```

`total_billed_duration` 은 **누적값이 반복해 실린다**(응답마다의 증분이 아니다). max 가 실제
오디오 길이와 맞고, sum 은 그 4배다. → **원가 산식이 쓰는 `audio_s` 는 `billed_max` 다.**
sum 을 썼으면 STT 원가를 4배로 과대계상했고, 그 숫자가 "캐스케이드가 Live 보다 싼가"의
근거로 쓰였을 것이다. 아래의 "판정을 미루고 셋 다 든다"가 정확히 이걸 갈랐다.

구현: `cascade_usage.summary()` 가 `billed_msgs>0` 이면 `audio_s=billed_max_s`,
`audio_s_source="vendor_billed_max"`. 벤더가 값을 안 실어 주면 우리 카운터로 폴백한다.

---

(이하는 판정 전 기록 — 왜 셋을 다 들었는지의 근거라 남긴다.)

→ **판정을 미룬다.** 스트림마다 `sum`(전부 더한 값)과 `max`(최댓값)를 **둘 다** 기록하고,
값이 실린 응답 수(`billed_msgs`)도 센다. 첫 실통화 로그 한 줄이면 셋 중 무엇이 맞는지 드러난다
(증분이면 sum ≫ max, 누적 반복이면 sum ≫ max 이지만 max ≈ 스트림 길이 — **max 를 오디오 길이와
대조하면 갈린다**). 확정 전까지 `audio_s` 에는 **우리 카운터**를 넣고 출처를 `sent_audio` 로 찍는다.

### §1-2 TTS — 벤더가 안 준다. 우리가 문자를 센다

설치된 SDK(`google-cloud-texttospeech`, conda env `beavertalk-server`)의 응답 정의를 직접 조회한 결과:

```
SynthesizeSpeechResponse:    ['audio_content']
StreamingSynthesizeResponse: ['audio_content']
과금/사용량 낱말이 든 심볼:   ['SynthesizeLongAudioMetadata']   ← 장문 배치용, 스트리밍과 무관
```

응답에 사용량 필드가 **아예 없다.** 따라서 **우리가 보낸 입력 문자열의 길이**를 센다.
세는 대상은 "합성하려던 텍스트"가 아니라 **실제로 API 에 넘긴 문자열**이다 —
현행 `core/tts.py:116` 은 `SynthesisInput(text=text.strip())` 로 **strip 한 것**을 보낸다.

### §1-3 LLM — Live 와 같은 `usage_metadata`

`prompt_token_count` / `candidates_token_count` / `thoughts_token_count` / `total_token_count`.
캐스케이드 LLM 은 **오디오를 받지 않는다**(입력이 STT 텍스트) → 계약대로
`usage_in_audio = usage_out_audio = 0`.

## §2 [답] 실청구액과 어긋날 여지 — 7건

bt-back 이 요구한 항목. **어긋남을 없앨 수 없으면, 어긋나는 방향과 크기를 남긴다.**

| # | 어긋남 | 방향 | 우리 대응 |
|---|---|---|---|
| 1 | **무음도 과금** — 마이크 오디오를 끊지 않고 흘린다 | 실청구 = 통화 전체 길이 | 설계상 사실로 인정, `sent_audio_s` 가 곧 그 값 |
| 2 | **롤오버 재생 이중 과금** — `_flush()` 가 버퍼를 새 스트림에 다시 흘린다(`core/stt.py:534`) | 우리 카운터가 **과소** | `replay_audio_s` 를 따로 센다 |
| 3 | **요청/스트림 단위 올림** — 스트림마다 올림이면 스트림 수만큼 얹힌다 | 우리 카운터가 **과소** | `streams` 를 센다 |
| 4 | **취소된 비버 발화도 합성했으면 과금** | 실청구에 포함, 사용자는 못 들음 | `chars_cancelled` 를 따로 센다 |
| 5 | **TTS 실패/재시도 호출** 과금 여부 미확인 | 우리 카운터가 **과대일 수 있음** | 문자는 **API 에 넘기는 시점**에 센다(P1 구현) — barge-in 으로 끊긴 문장도 값은 이미 나갔기 때문이다. 실패는 `calls_failed` 로 따로 드러난다 |
| 6 | **LLM thoughts·cached 토큰** 이 `candidates_token_count` 에 없다 | `out_text` 만 보면 **과소** | `usage_json.llm.thoughts`·`cached` 로 남긴다 |
| 7 | **단가(달러)** 를 우리가 안다고 가정 | — | 이 문서에 단가를 **박지 않는다**(§3) |

⭐ #1 은 단순한 오차가 아니라 **캐스케이드 원가 모델의 핵심**이다. barge-in 을 하려면
비버가 말하는 동안에도 마이크를 열어 둬야 하고, 그러면 STT 는 **통화 길이 전체**로 과금된다.
"사용자가 말한 시간만 과금"이 아니다. 이 사실이 Live 대비 절감폭을 좌우하므로, P1 이후
`sent_audio_s ÷ 통화길이` 비율을 로그에서 바로 볼 수 있게 둔다.

## §3 자료 등급 — 무엇이 1차이고 무엇이 아직 아닌가

- **1차(확인 완료)**: STT v2/v1 proto 원문, 설치된 texttospeech SDK 응답 정의, 우리 코드(파일:행).
- **미확보**: 공식 단가 페이지 원문. `cloud.google.com/{speech-to-text,text-to-speech}/pricing` 은
  본문이 잘리거나 404 로 돌아와 **원문 인용을 못 만들었다**. 검색 결과(2차)로는 STT v2 가
  "1초 증분·요청마다 올림", TTS Chirp3-HD 가 "$30/1M 문자, 공백·구두점 포함"이라고 나오지만
  **이 문서에 단가로 못 박지 않는다.** 달러 계산은 기존 단일 산식 자리
  (`normalcall_service.estimate_usage_cost_usd`)에만 두고, 여기서는 **단위(초·토큰·문자)만** 남긴다
  — 모델 `call.usage_*` 주석이 이미 같은 규율이다("단가는 벤더가 바꾼다").

## §4 구현

### §4-1 자리
`domains/learning/realtime/cascade_usage.py` (신규) — 세션·STT·(P1)LLM·TTS 가 여기에 넣고,
**요약은 순수 함수 1개**가 만든다(Live 의 `_usage_summary` 가 참고 모델 — 로그와 DB 의 단일 소스).

핵심 계측 자체는 벤더 응답을 보는 자리에 있어야 하므로 `core/stt.py` 가 스트림별로
누적해 `usage()` 로 노출하고, 세션이 종료 시 **한 번** 흡수한다(오디오 경로에 계측 코드 0줄).

### §4-2 요약 모양 (계약 그대로)

```python
{
  "engine": "cascade:google-stt-v2+gemini-2.5-flash+cloud-tts-chirp3-hd",
  "in_text": 41000, "out_text": 3200, "in_audio": 0, "out_audio": 0, "total": 44200,
  "vendors": {
    "stt": {"vendor": "google-stt-v2", "audio_s": 902.4, "audio_s_source": "sent_audio",
            "sent_audio_s": 902.4, "replay_audio_s": 1.2, "billed_sum_s": …, "billed_max_s": …,
            "billed_msgs": …, "streams": 4},
    "llm": {"vendor": "gemini-2.5-flash", "in_text": 41000, "out_text": 3200,
            "thoughts": 0, "cached": 0, "calls": 12},
    "tts": {"vendor": "cloud-tts-chirp3-hd", "chars": 8400, "chars_cancelled": 320,
            "calls": 12, "calls_failed": 0},
  },
}
```

- `engine` 은 **실제로 돈 구성요소만** 잇는다. 지금(P0)은 STT 뿐이라 `cascade:google-stt-v2`,
  크레덴셜이 없어 페이크로 돈 세션은 `cascade:fake-stt` — 데모 세션이 실통화 원가로 섞이지 않는다.
- `audio_s` 는 계약이 요구한 키다. 값은 §1-1 판정 전까지 **우리 카운터**이며, 어느 쪽을 넣었는지
  `audio_s_source` 가 항상 말한다.

### §4-3 로그 (지금 단계의 유일한 출구)

Live 와 같은 `key=value` 한 줄. Cloud Logging 에서 grep 으로 뽑는다.

```
cascade usage: engine=cascade:google-stt-v2 stt_audio_s=902.4 stt_src=sent_audio
  stt_replay_s=1.2 stt_streams=4 stt_billed_sum_s=… stt_billed_max_s=… stt_billed_msgs=…
  llm_in=0 llm_out=0 llm_calls=0 tts_chars=0 tts_cancelled=0 tts_calls=0 dur_s=… turns=…
```

- 못 모은 경우에도 **한 줄 남긴다**: `cascade usage: engine=… collected=0 reason=…`.
- ⛔ **DB 영속화·call_id 배관은 이번에 붙이지 않는다.** 캐스케이드를 통화 기록 파이프라인에
  올릴지가 미정이고, 컬럼·마이그레이션은 call15-polish 담당이다.

### §4-4 R5 — 계측이 통화를 죽이면 안 된다

3중:
1. **경로 분리** — 오디오 펌프에는 계측 호출이 없다. 스트림이 자기 응답을 보다가 **부수적으로**
   누적하고(try/except 로 감쌈), 세션은 **끝난 뒤에만** 읽는다.
2. **전량 흡수** — 누적·요약·로그 전 구간 `except Exception` → `logger.warning` 후 계속.
3. **없어도 진행** — `usage()` 가 없는 스트림 객체(페이크·미래의 다른 엔진)도 정상 동작.
   계측 실패는 세션 종료 코드·클라 프로토콜에 **아무 영향이 없다**.

## §6 계약에 대한 의견 2건 (반대 아님 — 채택 시 양쪽 동시 반영 필요)

1. **thoughts 토큰**: `usage_out_text = candidates_token_count` 로 두면 사고 토큰이 빠져
   출력 원가가 과소가 된다. Live 와 대칭을 지키려 컬럼은 그대로 두고 `usage_json.llm.thoughts` 에
   남긴다. 달러 산식에서 **out_text + thoughts** 로 계산해야 한다는 뜻이라, 산식 자리에 이 사실이
   같이 가야 한다.
2. **engine 문자열**: 모델명만으로는 STT 리전(현 `global` — 서울·도쿄 없음)·TTS 음성이 안 드러난다.
   문자열 형식은 계약대로 두고, 상세는 `usage_json.vendors.*` 에 키로 넣는다.
