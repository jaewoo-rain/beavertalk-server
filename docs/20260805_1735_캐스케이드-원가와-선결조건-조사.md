## 1. ⭐ Live 15분 기준선 — 실측으로 다시 세움

### 1-1. 데이터 출처 [실측]

```bash
gcloud logging read 'textPayload:"normalcall usage"' --project bt-dev-web-01 --freshness=30d
```

30일 보존 기간 안에 남아 있는 usage 로그는 **총 4건**뿐이다(신 포맷 1건 + 구 포맷 3건).
그중 통화로서 유효한 건 2건:

| call | 시각(UTC) | 통화 길이 | 관측(≈턴) | 최대 컨텍스트 | 압축 | 세션 | 입력 모달리티 합 |
|---|---|---|---|---|---|---|---|
| **890** | 2026-08-04 04:18:36 → 04:33:40 | **15분 04초** | 52 | 15,844 | 1회 | 2개(스왑 1) | `TEXT 245,338 / AUDIO 300,628` |
| 891 | 2026-08-04 09:31:02 → 09:38:09 | 6분 46초 | 43 | 12,555 | 0회 | 1개 | `TEXT 201,810 / AUDIO 192,845` |

⚠ **이 "모달리티" 값은 입력(prompt)만이다.** 방출 코드(`git show d8dd46f:.../call_session.py`
의 `_observe_usage`)가 `event.prompt_modalities` 만 누적한다 — **출력(response) 토큰은
이 포맷에 없다.** 출력은 §1-2에서 별도 추정한다.

`prompt_token_count` 를 합산하는 게 맞는 이유 [실측]: 신 포맷 call 893의 시계열이
`1698 → 1833 → 2048 → 2266 → 2535 → 2730 → 2946 → 3257` 이고 이 8개의 합이 정확히
`sum_prompt=19313`. 즉 **메시지마다의 값 = 그 시점 컨텍스트 크기**이고, Live 는 턴마다
컨텍스트 전체를 재과금하므로 **합이 곧 청구 입력량**이다.

### 1-2. 원가 계산

단가 [문서] — [Gemini API pricing](https://ai.google.dev/gemini-api/docs/pricing),
"Gemini 2.5 Flash Native Audio (Live API)" 항목 원문:
`Input price: $0.50 (text) / $3.00 (audio / video)`,
`Output price (including thinking tokens): $2.00 (text) / $12.00 (audio)`.

**입력 [실측]**

```
AUDIO 300,628 × $3.00 / 1M = $0.9019
TEXT  245,338 × $0.50 / 1M = $0.1227
────────────────────────────────────
입력 소계                    $1.025
```

**출력 [추정]** — 계측 포맷에 없어서 다음 3단으로 추정한다.

1. 비버 발화 글자수 **[실측]**: call 890 의 전사 로그를 전부 긁어 합산 → **2,027자**
   (턴 확정 로그 `🦫 BEAVER[t..]` 49턴 기준) / 2,415자(부분 청크 합).
2. 발화 시간 **[추정]**: 한국어 발화 속도 4.5~5.5자/초 가정 → **370~535초**
   (15분 통화의 41~59%를 비버가 말함 — 교습 통화로 타당한 범위).
3. 오디오 토큰율 **[문서]**: 같은 pricing 페이지 각주 원문 —
   *"Billing is based on total input and output audio token consumption, calculated at
   a rate of **25 tokens per second of audio**"*. (덤: 이 각주가 `$3.00 or $0.005/min`
   같은 "분당" 표기가 **별도 요금제가 아니라 토큰가의 환산**임을 확정한다.)

```
오디오 출력  370~535초 × 25 tok/s = 9,250~13,375 tok × $12/1M = $0.111 ~ $0.161
텍스트 출력  입출력 전사(in_tr+out_tr) ≈ 3,000~4,000 tok × $2/1M = $0.006 ~ $0.008
────────────────────────────────────────────────────────────────────────────
출력 소계                                                        $0.12 ~ $0.17
```

> ⚠ 마스터플랜 §1의 경고("전사도 과금된다")는 사실이나 **금액은 $0.01 미만**이다.
> 원가 서사에서 전사는 무시해도 되는 항이다.

**합계: $1.15 ~ $1.20 → 기준선 $1.16**

### 1-3. ⚠ 그런데 이 값은 "낮은 쪽"이다 — 턴 밀도가 지배 변수

두 통화를 분당으로 환산하면 짧은 통화가 **더 비싸다**:

| call | 길이 | 입력 원가 | 분당 입력 | 턴/분 |
|---|---|---|---|---|
| 890 | 15.1분 | $1.025 | **$0.068** | 3.3 |
| 891 | 6.8분 | $0.679 | **$0.100** | 6.3 |

원인: 턴마다 컨텍스트를 통째로 재과금하므로 **원가 ∝ 턴 수 × 평균 컨텍스트**다.
길이가 아니라 **턴 밀도**가 1차 변수다. call 890은 유저가 자주 침묵한 저밀도 통화였고,
게다가 압축 1회 + 세션 스왑 1회로 컨텍스트가 두 번 깎였다.

**891의 밀도(6.3턴/분)가 15분 내내 유지되면** [추정]:
턴 ≈ 95, 컨텍스트는 12k~16k 사이에서 진동(평균 ≈13,000; 텍스트 4,700 고정 + 오디오 8,300)

```
AUDIO 95 × 8,300 = 788,500 × $3.00/1M = $2.37
TEXT  95 × 4,700 = 446,500 × $0.50/1M = $0.22
출력                                    ≈ $0.15
────────────────────────────────────────────
                                        ≈ $2.74
```

☞ **마스터플랜의 $2.5~2.9는 틀린 게 아니라 "고밀도 통화" 시나리오였다.**
실측 15분 통화는 저밀도라 $1.16으로 나왔다. 정직한 표현은 이것이다:

> **Live 15분 = $1.16 ~ $2.7. 실측 1건은 $1.16(저밀도). 턴 밀도가 2배면 원가도 2배 이상.**

### 1-4. 계측 구멍 (다음에 반드시 닫을 것)

| 구멍 | 영향 | 닫는 법 |
|---|---|---|
| 15분 통화의 **출력 토큰 실측이 0건** | 기준선의 $0.13이 추정 | 신 포맷(`sum_out=AUDIO=..,TEXT=..`)이 이미 배포돼 있다. dev 15분 통화 **1건**이면 끝 |
| 표본 2건 (그중 15분은 1건) | 턴 밀도 분산 미상 | 15분 통화 5건이면 밀도 분포가 나온다 |
| 로그 보존 30일 | 8월 4일 이전 데이터 소실 | 원가 확정 전까지 `LIVE_USAGE_TRACE=true` 유지 |

### 2-0. 계산에 쓴 파라미터 (전부 실측 기반)

| 파라미터 | 값 | 출처 |

| 시스템 지시문 크기 | **2,959자(최소) ~ 4,709자(공부블록 포함)** | [실측] `build_system_instruction()` 을 실제 호출해 측정 |
| 시스템 지시문 토큰 | **≈ 4,700 tok** | [실측] call 890·891의 턴당 TEXT 입력이 4,718 / 4,693 — 지시문 글자수와 일치 |
| **한국어 토큰율** | **≈ 1 토큰 / 1 글자** | [추정, 근거 강함] 위 두 값의 비. 4,709자 ↔ 4,700 tok |
| 비버 발화량 | **2,027자/15분**(저밀도) ~ 4,000자(고밀도) | [실측] call 890 전사 |
| 사용자 발화량 | 비버의 약 50% [추정] | 초보 학습자 특성 |

### 2-1. STT — Google Cloud Speech-to-Text v2

단가 [문서] — [STT pricing](https://cloud.google.com/speech-to-text/pricing) 원문:
V2 Standard recognition, `0 minute to 500,000 minute: $0.016 / 1 minute`.
(볼륨 구간: 50만분↑ $0.010 / 100만분↑ $0.008 / 200만분↑ $0.004)
*"priced based on the amount of audio successfully processed ... measured in increments
of one second"*, *"Each request is rounded up to the nearest increment of 1 seconds"*.

⚠ **V2에는 무료 한도가 없다.** 월 60분 무료는 V1 전용이다(같은 페이지).

| 시나리오 | 전송 오디오 | 원가 |
|---|---|---|
| 상시 스트리밍(15분 내내) | 15.0분 | **$0.240** |
| 서버 VAD 게이팅(발화 구간 + 마진만, 약 8분) | 8.0분 | **$0.128** |

⚠ **barge-in을 켜면 게이팅 여지가 줄어든다.** 비버 발화 중에도 마이크를 열어둬야
끼어들기를 잡으므로, 현실적으로 상시 스트리밍($0.240) 쪽에 가깝다.
스트림 롤오버(5분 한도, §4-3)를 해도 과금은 처리된 오디오 초의 합이라 **동일**하다.

### 2-2. LLM — Gemini Flash 계열 텍스트

단가 [문서] — 같은 pricing 페이지. **오디오가 아니라 텍스트 단가**를 쓴다:

| 모델 | 입력(text) | 출력 | 캐시 적중 입력 |
|---|---|---|---|
| gemini-2.5-flash | **$0.30** /1M | **$2.50** /1M | $0.03 /1M |
| gemini-2.5-flash-lite | **$0.10** /1M | **$0.40** /1M | $0.01 /1M |
| (참고) gemini-3-flash-preview | $0.50 /1M | $3.00 /1M | $0.05 /1M |

**누적 입력 모델링** — Live와 똑같이 매 턴 전체 컨텍스트를 다시 보낸다:

```
턴당 입력 = 시스템 지시문(4,700) + 그 시점까지의 대화 이력(텍스트)
Σ입력    = N × 4,700  +  N × (최종 이력 / 2)      ← 이력은 선형 성장 가정
```

| 시나리오 | N | 최종 이력 | Σ입력 | 출력 | 2.5 Flash | Flash-Lite |
|---|---|---|---|---|---|---|
| 저밀도 | 50 | 3,000 tok | **310,000** | 2,100 | **$0.098** | $0.032 |
| 고밀도 | 95 | 6,000 tok | **731,500** | 6,000 | **$0.234** | $0.075 |

> 💡 **암묵 캐싱(implicit caching)이 이 항을 최대 90% 깎을 수 있다** [문서].
> Gemini 2.5 계열은 프로젝트 기본으로 켜져 있고, 프리픽스가 일치하면 캐시 토큰이
> 표준가의 **10%**로 청구된다. 최소 1,024 토큰(2.5 Flash) 조건을 우리 지시문(4,700 tok)이
> 충족한다. 통화 중 턴 간격이 ~15초라 적중 가능성이 높다.
> 적중 시 저밀도 $0.098 → **약 $0.03**. ([Google Developers Blog](https://developers.googleblog.com/gemini-2-5-models-now-support-implicit-caching/) /
> [Context caching 문서](https://ai.google.dev/gemini-api/docs/caching))
> **본 계산에는 넣지 않았다** — 적중률이 미확인이라 없는 셈 치는 게 안전하다.

### 2-3. TTS — Google **Cloud** TTS Chirp3-HD

단가 [문서] — [TTS pricing](https://cloud.google.com/text-to-speech/pricing) 원문:
`Chirp 3: HD voices — Free usage limit: 0 to 1 million characters —
US$0.00003 per character (US$30 per 1 million characters)`.
과금 단위 원문: *"The total number of characters in the input string are counted for
billing purposes, including spaces and newline characters."*

| 시나리오 | 비버 발화 | 기본 원가 |
|---|---|---|
| 저밀도 [실측 기반] | 2,027자 | $0.061 |
| 고밀도 [추정] | 4,000자 | $0.120 |

**barge-in 낭비율** — 끊긴 TTS도 **서비스에 보낸 글자는 과금된다**:

| 합성 방식 | 낭비 | 근거 |
|---|---|---|
| **스트리밍 합성 + 문장 단위 투입**(권장) | **+5~10%** | 끼어들면 그 시점 이후 문장을 아예 안 보낸다 → 못 낸 소리는 과금도 안 됨 |
| 턴 전체를 한 번에 합성(현행 `core/tts.py` 방식) | **+12~15%** | 끼어들기율 25% × 평균 잔여 50% [추정] |

→ **TTS 총액 $0.064 ~ $0.135.** 게다가 월 100만 자 무료 = 월 **약 490통**(2,027자 기준)이
공짜다. dev 실험 단계에서는 사실상 $0.

|---|---|---|---|

| 최악 대 최선 (Live $1.16 vs 캐스케이드 $0.61) | | **47%** | $0.55 |

> **어떤 조합을 잡아도 절반 이하로 떨어진다. 게이트는 통과다.**

⚠ **원가 구조가 뒤집힌다는 점이 더 중요하다.**

```
Live         : 오디오 입력 88%  ← LLM이 원가의 전부
캐스케이드    : STT 59% / LLM 24% / TTS 16%   ← STT가 최대 항목이 된다
```

- Live에서 원가 레버는 "컨텍스트 압축·턴 밀도"였다.
- 캐스케이드에서 레버는 **"마이크를 언제 STT로 보내느냐"**다. barge-in을 켜면 이 레버가
  잠긴다 — **barge-in은 기능이자 원가 항목**이다. (게이팅으로 $0.24 → $0.128,
  즉 통화당 $0.11 = 총원가의 27%가 여기 걸려 있다.)
- LLM 모델 선택(2.5 Flash vs Flash-Lite)은 통화당 $0.066 차이. **품질을 먼저 보고 정해도
  되는 규모**다.

## 3. 에코 / AEC — barge-in의 선결 조건

> **결론: AEC는 앱(클라이언트)이 한다. 서버는 보완만 가능하다.
> 그리고 지금 앱의 Android 재생 경로는 AEC 기준신호 밖에 있다 — 이대로 barge-in을 켜면 깨진다.**

### 3-1. 누가 하나 — 클라이언트 [문서]

- LiveKit 공식: *"WebRTC cancellation runs in the client only"*
  ([docs.livekit.io](https://docs.livekit.io/transport/media/noise-cancellation/))
- Pipecat도 AEC를 자체 파이프라인이 아니라 WebRTC 트랜스포트(=클라)에 위임
  ([Pipecat Transports](https://docs.pipecat.ai/pipecat/learn/transports))
- 물리적 이유 [추정, 정설]: AEC는 "지금 스피커로 나가는 샘플"을 기준신호로 적응 필터를
  수렴시킨다. 서버는 네트워크 지터 + 클라 재생 버퍼(수백 ms~수 초)만큼 흔들리는 지연을
  모르고, 스피커 비선형 왜곡·기기 AGC도 못 본다.

### 3-2. Android — 4점 세트 [문서]

하나라도 빠지면 대체로 안 돈다:

| # | 항목 | 근거 | 현재 앱 |
|---|---|---|---|
| ① | 캡처 `AudioSource.VOICE_COMMUNICATION` | Android CDD 5.4.4: *"SHOULD implement an Acoustic Echo Canceler (AEC) ... applied to the capture path when capturing using AudioSource.VOICE_COMMUNICATION"* ([CDD 5.4](https://android.googlesource.com/platform/compatibility/cdd/+/refs/tags/platform-tools-31.0.0/5_multimedia/5_4_audio-recording.md)) | ❌ 미지정 |
| ② | 재생 `USAGE_VOICE_COMMUNICATION` / `CONTENT_TYPE_SPEECH` | 구글 WebRTC 레퍼런스 구현이 그렇게 짝지음 ([WebRtcAudioTrack.java](https://chromium.googlesource.com/external/webrtc/+/HEAD/sdk/android/src/java/org/webrtc/audio/WebRtcAudioTrack.java)) | ❌ `USAGE_MEDIA`/`CONTENT_TYPE_MUSIC` |
| ③ | `AudioManager.setMode(MODE_IN_COMMUNICATION)` | 강한 정설이나 1차 문서 명문 없음 [추정] | ❌ `AudioManager` 호출 0건 |
| ④ | `AcousticEchoCanceler.isAvailable()` → `create()` → **`getEnabled()` 확인** | javadoc: *"The application should call getEnable() after creating the AEC to check the default AEC activation state"* | ❌ |

⚠ `isAvailable()==true` 여도 **실제로 못 지우는 기기가 있다**. WebRTC Android가
`setUseHardwareAcousticEchoCanceler(false)` 로 끄고 소프트웨어 AEC로 폴백하는 API를
열어둔 이유이고, Signal-Android는 하드웨어 AEC 블랙리스트를 유지한다.
반대 실패모드도 있다 — AEC가 과하면 **double-talk에서 사용자 목소리까지 지운다**
(= "에코 없음"과 "끼어들기 못 잡음"이 같이 온다).

**24k 재생이 문제인가**: 대체로 아니다 [추정]. 앱이 정하는 건 AudioTrack 입력 레이트일 뿐,
에코 기준신호는 HAL(보통 48k)에서 잡힌다. 진짜 리스크는 레이트가 아니라 **②③이 빠져
재생이 AEC 기준 경로 밖에 있다는 것**이다.

### 3-3. iOS — 카테고리/모드만으론 AEC가 안 돈다 [문서]

Apple 공식 `AVAudioSession.Mode.voiceChat` 문서 원문:

> *"For apps that use one or more chat modes ... but **don't use Audio Unit Voice I/O or
> AVAudioEngine with `setVoiceProcessingEnabled(_:)`, the system reduces the processing**
> it applies to audio signals. Specifically, it doesn't apply voice-specific processing,
> like echo cancellation and automatic gain correction..."*
> ([developer.apple.com](https://developer.apple.com/documentation/avfaudio/avaudiosession/mode-swift.struct/voicechat))

즉 `.playAndRecord + .voiceChat` 은 **필요조건일 뿐**이고, AEC 본체는
`AUVoiceProcessingIO` / `AVAudioEngine.setVoiceProcessingEnabled(true)` 다.
(iOS 18.2+ `setPrefersEchoCancelledInput` 은 2024년 이후 일부 기기 한정이라 주 대책 불가.)

**현재 앱**: 세션은 정확히 잡혀 있으나 **재생이 VPIO가 아닌 별도 RemoteIO 유닛**이다.
실기기 에코가 완전히는 안 잡혔던 이유일 가능성이 크다 [추정].

### 3-4. Flutter 생태계 [문서]

| 패키지 | AEC | 한계 |
|---|---|---|
| flutter_sound (현 캡처) | 부분 | 공식 문서: *"enableNoiseSuppression / enableEchoCancellation are only implemented on Android and just when recording to a PCM dart stream"*. AudioRecord 세션ID 미노출로 외부 AEC 부착 불가([issue #1134](https://github.com/Canardoux/flutter_sound/issues/1134), open) |
| record | 플래그만 | *"if available on the device"*, *"May not be considered on all platforms"* — 베스트에포트 |
| flutter_pcm_sound (현 재생, 자체 포크) | 없음 | **우리가 포크해 쓰는 코드라 여기 손대는 게 가장 값싼 수정** |
| audio_session (이미 의존) | 설정 통로 | Android `setMode(inCommunication)`, `setSpeakerphoneOn`, 라우트 감지 제공 |
| flutter_webrtc / livekit_client | 진짜 AEC | ⛔ **Dart에서 raw PCM을 넣고 빼는 통로가 없다.** "AEC만 빌려 쓰고 WS로 PCM 전송"은 실무에서 안 통한다 — 트랜스포트 자체를 WebRTC로 바꿔야 함(서버 아키텍처 변경) |

### 3-5. 서버 측 보완책 — **완전 해결이 아니다**

서버의 유일한 무기는 "자기가 보낸 TTS 텍스트와 재생 타임라인을 안다"는 것뿐이다.

| 대책 | 한계 |
|---|---|
| ① 재생 구간 + 꼬리 200~400ms 게이팅 | 게이트를 크게 열면 **그게 곧 barge-in off**다. 꼬리만 무시하는 부분 완화만 가능 |
| ② 방금 합성한 문장과 STT partial의 유사도 비교 | ⚠ **이 앱에서 특히 위험**: 학습자가 비버 말을 **따라 하는 게 정상 학습 행동**이다. 따라읽기를 에코로 씹으면 핵심 루프가 깨진다. 게다가 partial을 기다리느라 200~600ms 지연 |
| ③ 최소 발화 길이·에너지 임계 | "네?", "아니요" 같은 짧은 끼어들기를 삼킨다 |
| ④ `CASCADE_BARGEIN_CONFIRM=transcript` (`core/config.py:156`에 이미 있음) | 반응 200~400ms 지연. 에코의 STT 결과도 "비어있지 않은 partial"이라 ②와 결합해야 실효 |
| ⑤ 서버 AEC(진짜 적응 필터) | **비권장.** §3-1의 물리적 이유 그대로 |

☞ **서버 대책은 "AEC가 웬만큼 도는 상태에서 남는 잔향을 거르는 2차 방어"로만 값을 한다.**
AEC가 0이면 ①로 수렴 = half-duplex = barge-in 포기다.

### 3-6. 브라우저 데모 vs 실기기 — ⚠ 설계문서 스코프와 충돌

| | 브라우저 | Flutter 실기기 |
|---|---|---|
| AEC 켜기 | `getUserMedia({audio:{echoCancellation:true}})` **한 줄**, 2020년부터 Baseline ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints/echoCancellation)) | §3-2/§3-3의 조립을 앱이 직접 |
| 기준신호 | **브라우저가 캡처와 재생을 같은 엔진 안에서 소유** → 무엇이 스피커로 나가는지 정확히 앎 | 캡처=flutter_sound, 재생=flutter_pcm_sound. **둘을 잇는 기준신호 경로가 없다** |
| 음향 결합 | 데스크톱: 마이크 멀고 볼륨 낮음 | 폰 스피커폰: 마이크와 수 cm, 볼륨 최대 |

> ⛔ **`/__cascadedemo` 브라우저에서 barge-in이 잘 도는 것은 실기기 barge-in의 근거가

> 에는 타당하지만, **P1(barge-in) 판정 기준으로는 성립하지 않는다.**

### 3-7. AEC 없이 barge-in을 켤 수 있나 — 라우트별 폴백 [추정, 물리 근거]

| 라우트 | 음향 결합 | barge-in |
|---|---|---|
| 유선 이어폰 / BT HFP | 거의 없음 | ✅ 켠다 |
| BT A2DP(출력만, 마이크는 폰 본체) | 있음 | ⚠ 스피커폰과 동일 취급 |
| 내장 스피커 + AEC 확인됨(`getEnabled()==true`) | 큼 | △ 조건부 + `confirm=transcript` |
| 내장 스피커 + AEC 미확인/부재 | 큼 | ❌ half-duplex 유지 |

**제안**: 클라가 통화 시작 시 AEC 자기진단 결과를 `start`에 실어 보내고

정책을 고른다. 라우트는 통화 중에도 바뀌므로(이어폰 뽑기) 런타임 통보 메시지도 필요하다.
현행 `CASCADE_BARGEIN_CONFIRM` 은 **전역 설정**이라 이 요구를 못 받는다 — 세션별 값이어야 한다.

## 4. Cloud TTS 스트리밍 합성 — ✅ 된다

### 4-1. 지원 여부 [문서]

[Chirp 3: HD voices 문서](https://docs.cloud.google.com/text-to-speech/docs/chirp3-hd) 에
`streaming_synthesize` 파이썬 예제가 그대로 실려 있다:

```python
streaming_config = texttospeech.StreamingSynthesizeConfig(
    voice=texttospeech.VoiceSelectionParams(name="ko-KR-Chirp3-HD-Fenrir",
                                            language_code="ko-KR"))
# 첫 요청은 config, 이후 요청마다 텍스트 조각
streaming_responses = client.streaming_synthesize(request_generator())
for response in streaming_responses:
    ...  # response.audio_content
```

문서 원문: *"The first request must contain your config, and then each subsequent request
must contain text."* — **LLM 출력 스트리밍을 그대로 제너레이터로 물릴 수 있다**(문서가
직접 그렇게 권한다: *"Consider using Gemini or another LLM with output streaming as a generator."*)

### 4-2. 출력 포맷 — PCM 가능 [문서]

같은 문서 "Supported output formats" 표 원문:

| API Method | Format |
|---|---|
| **streaming** | **ALAW, MULAW, OGG_OPUS and PCM** |
| batch | ALAW, MULAW, MP3, OGG_OPUS and PCM |

*"The default response format is LINEAR16"* — 그리고 문서의 모든
`StreamingSynthesizeConfig` 예제가 `"audio_encoding": "LINEAR16"` 을 쓴다.

**샘플레이트 24000**: `streaming_audio_config.sample_rate_hertz` 필드가 존재하고
Chirp3 예제에서 24000을 쓰는 것이 확인되나, **[미확인]** — Chirp3-HD의 네이티브 레이트가
24kHz인지, 다른 값을 주면 리샘플되는지는 공식 문서에 명시가 없다.
→ **결정 전 1회 실측**: `sample_rate_hertz=24000, audio_encoding=LINEAR16` 으로 합성해
바이트 길이/초를 재면 끝난다(24k·16bit·mono = 48,000 B/s).

☞ **되면 앱 재생 경로(PCM24k)에 그대로 꽂힌다 → 앱 수정 0.** 이건 원가·지연 양쪽 이득이다.

### 4-3. 제약 [문서]

| 제약 | 값 | 출처 |
|---|---|---|
| 요청당 총 바이트 | **5,000 bytes** | [Quotas](https://docs.cloud.google.com/text-to-speech/quotas). ⚠ *"In some locales a single character is made up of multiple bytes"* — 한국어는 UTF-8 3바이트 → 요청당 약 1,600자 |
| `Chirp3RequestsPerMinutePerProject` | **200** | 동. 턴마다 스트림을 새로 열면 **분당 200턴**이 프로젝트 전체 상한 → 3.3턴/분 기준 **동시 통화 약 60건**에서 막힌다 ⚠ |
| `ConcurrentStreamingSessionsPerProject` | **100** | 동. 통화당 스트림 1개 유지 시 **동시 통화 100건** 상한 |
| SSML | **스트리밍 미지원** | Chirp3-HD 문서: *"SSML tags are not currently supported for streaming requests"* |
| 리전 | `global`, `us`, `eu`, `asia-southeast1`, `europe-west2`, **`asia-northeast1`(도쿄)** 전부 GA | Chirp3-HD 문서 |

☞ 서울은 없지만 **도쿄(asia-northeast1)가 GA**다 — Cloud Run(asia-northeast3)에서 가장 가깝다.

### 4-4. 현행 `core/tts.py`와의 관계

현행은 `synthesize_speech` **한 덩어리 + MP3**다(`core/tts.py:115-121`). 통화후 분석의
표현 오디오용이라 그 자체는 맞는 설계다. 캐스케이드는 **별도 스트리밍 경로**가 필요하다:

| | 현행(표현 TTS) | 캐스케이드에 필요한 것 |
|---|---|---|
| 호출 | `synthesize_speech` (단발) | `streaming_synthesize` (양방향) |
| 포맷 | MP3 | LINEAR16/PCM 24k |
| 첫 소리까지 | 문장 전체 합성 완료 후 [미확인, 수백 ms~수 초 추정] | 첫 오디오 청크 도착 즉시 |
| 낭비 | 끊겨도 문장 전액 과금 | 안 보낸 문장은 과금 없음 |

**D5(기존 무접촉) 준수**: `core/tts.py`에 `synthesize_stream()` 을 **덧붙이고** 기존
`synthesize()` 는 손대지 않는 게 맞다.

## 5. STT v2 실무 가용성

### 5-1. ko-KR × 모델 × 스트리밍 [문서]

| 모델 | 스트리밍 | ko-KR | 근거 |
|---|---|---|---|
| `chirp_3` | ✅ *"Speech.StreamingRecognize — Supported"* | **GA** (`Korean (Korea) | ko-KR | GA`) | [chirp-3 문서](https://docs.cloud.google.com/speech-to-text/docs/models/chirp-3) |
| `chirp_2` | ✅ (언어 한정) | **명시적 포함** — *"StreamingRecognize supports the following languages: … Korean (South Korea)"* | [chirp-2 문서](https://docs.cloud.google.com/speech-to-text/docs/models/chirp-2) |
| `chirp` (원조) | ❌ 미지원 | — | [미확인 — 전용 문서 페이지 404] |
| `long`/`short`/`telephony` | ✅ | **[미확인]** `global` 가용성이 문서 페이지마다 엇갈림(페이지가 커서 fetch가 잘림) | — |

### 5-2. 리전 — **서울(asia-northeast3)에 STT v2가 없다** [문서]

- supported-languages 표에 등장하는 location 전체: `asia-south1, asia-southeast1, eu,
  europe-west2, europe-west3, europe-west4, global, northamerica-northeast1, us, us-central1`
  → **`asia-northeast3`도 `asia-northeast1`도 없다.**
- `chirp_2` 의 `us-central1`/`europe-west4`/`asia-southeast1` 은 **Private GA**(접근 신청
  필요할 수 있음 [미확인]).
- `chirp_3` 은 `us`/`eu` 멀티리전 GA.
- recognizer 는 **선택**: `projects/{P}/locations/global/recognizers/_` 로 인라인 사용 가능.
  단 문서 경고 — *"Reuse recognizers as often as possible. Creating one for each request
  dramatically increases the latency."*

⚠ **지연 세금**: Cloud Run이 서울인데 STT는 `global`/`us`. 태평양 왕복이 캐스케이드
지연 예산에 고정비로 들어온다. `global` 이 실제로 어디로 라우팅되는지는 문서에 없다 [미확인]
→ **실측 필요**.

### 5-3. 스트림 시간 한도 — **v2도 5분. 15분 통화는 롤오버 필수** [문서]

[v2 Quotas and limits](https://docs.cloud.google.com/speech-to-text/v2/quotas) 원문:

> *"Each request in the stream is limited to 25 KB of audio. **A stream can remain open
> for up to 5 minutes**, and the audio must be sent at a rate that approximates real time."*

동 페이지: `Concurrent StreamingRecognize sessions (per region) = 300`.

**청크 크기 상충** ⚠ — 문서마다 다르다:

| 출처 | 값 |
|---|---|
| v2 quotas / v2 streaming 가이드 | 25 KB |
| **`cloud_speech.proto` v2 원문** | *"Maximum size for this field is **15 KB** per request."* |
| voice-activity-events 문서 | 15360 bytes |

→ **15,360 B를 상한으로 잡아라**(2:1로 proto 쪽 우세). PCM16/16k = 32,000 B/s 이므로
15,360 B ≈ 480ms. 20~100ms 청크(640~3,200 B)면 여유.

**롤오버 실무 패턴**: ① 선제 재시작(4분 30초경, 서버가 닫기를 기다리지 말 것)
② **비버가 말하는 동안**(= 무음 구간)에 스왑 ③ 마지막 0.5~1초 오버랩 버퍼로 경계 단어 보호
④ 스트림 경계에서 STT 내부 컨텍스트가 리셋되는 건 불가피.

### 5-4. VAD 이벤트 — proto 원문 [문서]

[cloud_speech.proto v2](https://raw.githubusercontent.com/googleapis/googleapis/master/google/cloud/speech/v2/cloud_speech.proto):

```protobuf
message StreamingRecognitionFeatures {
  message VoiceActivityTimeout {
    // Duration to timeout the stream if no speech begins. ...
    // the server will close the stream.
    google.protobuf.Duration speech_start_timeout = 1;
    // Duration to timeout the stream after speech ends. ...
    // the server will close the stream.
    google.protobuf.Duration speech_end_timeout = 2;
  }
  enum EndpointingSensitivity {
    ENDPOINTING_SENSITIVITY_UNSPECIFIED = 0;   // = STANDARD
    ENDPOINTING_SENSITIVITY_STANDARD    = 1;
    ENDPOINTING_SENSITIVITY_SUPERSHORT  = 2;
    ENDPOINTING_SENSITIVITY_SHORT       = 3;
  }
  bool enable_voice_activity_events = 1;
  bool interim_results = 2;
  VoiceActivityTimeout voice_activity_timeout = 3;
  EndpointingSensitivity endpointing_sensitivity = 8;
}

enum SpeechEventType {
  SPEECH_EVENT_TYPE_UNSPECIFIED = 0;
  END_OF_SINGLE_UTTERANCE = 1;   // latest_short 모델 전용
  SPEECH_ACTIVITY_BEGIN   = 2;   // voice_activity_events=true 일 때만
  SPEECH_ACTIVITY_END     = 3;   // 동. 발화가 반복되면 여러 번 온다
}
```

응답에서 `StreamingRecognizeResponse.speech_event_type` (필드 3) +
`speech_event_offset` (필드 7, *"Time offset between the beginning of the audio and
event emission"*) 로 온다.

| 항목 | 값 |
|---|---|
| 타입 | `google.protobuf.Duration` (파이썬은 `timedelta` 또는 `duration_pb2.Duration`) |
| **범위** | *"Voice activity timeouts must be greater than **500ms** and less than **60s**"* ([voice-activity-events 문서](https://docs.cloud.google.com/speech-to-text/docs/voice-activity-events)) |
| 기본값 | 문서에 명시 없음 — 미설정 = 타임아웃 없음으로 읽힘 [미확인] |
| 시간 기준 | *"Time elapsed is measured by the **bytes of audio sent**, as opposed to server time."* |

### 5-5. ⛔ 가장 중요한 함정 — `voice_activity_timeout` 은 턴 감지 노브가 아니다

문서 원문: *"Cloud STT will automatically **close the stream** if no further speech is
detected within the timeout duration after a `SPEECH_ACTIVITY_END` event."*

즉 `speech_end_timeout=800ms` 로 두면 **사용자가 0.8초 쉴 때마다 스트림이 닫힌다.**
상시 스트림 설계라면:

```
enable_voice_activity_events = True
interim_results              = True
voice_activity_timeout       = ⛔ 설정하지 않는다
endpointing_sensitivity      = STANDARD
```

으로 두고 **`SPEECH_ACTIVITY_END` 이후 몇 ms를 기다릴지는 서버가 자체 타이머로 결정**해야 한다.

또 하나: *"If the stream is closed before speech ends, a `SPEECH_ACTIVITY_END` event
won't be sent."* → **롤오버는 반드시 END 이후에.**

> ⚠ 설계문서(`_1720_*.md`)의 "타임아웃 출발값 800ms"가 `speech_end_timeout` 을 가리키는
> 것이라면 **재검토가 필요하다.** 그 필드는 스트림을 닫는다. 서버 자체 타이머여야 한다.

### 5-6. 엔드포인팅 튜닝의 한계 — 외국인 초보 학습자

| 제약 | 실체 |
|---|---|
| `speech_end_timeout` 상한 60초 | 숫자상 충분하나 **스트림을 닫는 값**이라 턴 노브로 못 씀(§5-5) |
| `endpointing_sensitivity` | STANDARD / SHORT / SUPERSHORT — **전부 "더 빨리 끊는" 방향**. **침묵을 더 참는 값이 없다** |
| `is_final` 확정 지연 | 튜닝 노브 없음. 비공식 실측이지만 chirp_3에서 단어 1개에 2,468ms 보고 ([livekit/agents#4804](https://github.com/livekit/agents/issues/4804), 비공식) |

**평가: STT 엔드포인팅 단독으로는 부족하다.** 침묵 허용을 늘리는 공식 노브가 없고,
`SPEECH_ACTIVITY_END` 이후 대기 시간은 어차피 우리가 정해야 한다.

**권장 구조** [제안]:
- `SPEECH_ACTIVITY_BEGIN` → 사용자 발화 시작(비버 TTS 중이면 barge-in 정책에 따라 분기)
- `SPEECH_ACTIVITY_END` → **서버 타이머 시작**(초보 2.5~3.5s / 상급 1.2s — 레벨 연동 가능)
- 타이머 만료 전 BEGIN 재발생 → 취소(같은 턴 계속)
- 타이머 만료 + 누적 `is_final` 텍스트 존재 → 턴 확정 → LLM
- 보조 [제안, 문서 근거 아님]: interim이 종결어미로 끝나면 타이머 단축, 접속사("그런데",
  "그리고")로 끝나면 연장

### 5-7. v1 → v2 차이 (캐스케이드 영향분) [문서]

| 항목 | v1 | v2 |
|---|---|---|
| `single_utterance` | 있음 | **없음** |
| `interim_results` 위치 | `StreamingRecognitionConfig` 직속 | `streaming_features` 안 |
| `endpointing_sensitivity` | 없음 | **v2 전용** |
| `enable_voice_activity_events` | **v1에도 있음** | 있음 |
| recognizer | 개념 없음 | 필수 필드(단 `_` 허용) |
| 언어 지정 | `language_code`(단수) | `language_codes`(복수) |
| 스트림 한도 | ~5분 | **5분(동일)** |
| 프로토콜 | gRPC | *"Streaming speech recognition is available through gRPC only"* |

☞ **v2로 가는 실익은 `endpointing_sensitivity` + chirp_2/3 정확도뿐이다.**
15분 롤오버 문제는 v1/v2 동일하므로 마이그레이션 사유가 못 된다. 비용은 리전(서울 없음) +
ko-KR 모델 가용성 재검증. **v1으로 P0를 먼저 끝내고 v2는 정확도 비교로 붙이는 선택지도
살아 있다** — `core/stt.py` 의 `make_stt_stream` 팩토리가 이미 그 교체점이다.
