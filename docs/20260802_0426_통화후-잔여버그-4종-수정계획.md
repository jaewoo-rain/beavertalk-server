## A. 레벨테스트 분석중에 통화하기 → 레벨테스트가 또 시작된다

### 원인 (확정)

`domains/learning/realtime/call_session.py:562`

```python
call_type = "level_test" if (spec.leveltest and setup["needs_level_test"]) else "normal"
```

`needs_level_test` 는 `normalcall_service.py:238` 에서

```python
needs_level_test = korean_level is None
```

`korean_level` 을 채우는 건 **통화후 분석**(`analyze_level_test_call`)이다. 분석은 통화 종료 후
fire-and-forget 으로 돌고 13~21초쯤 걸린다. 그 창 안에 통화하기를 누르면 `korean_level` 이
아직 None 이라 서버가 **또 레벨테스트로 라우팅**한다. 일일 한도(`DAILY_CALL_LIMIT`)는
`level_test: 1` 이지만 `has_call_in_window` 는 "유저 발화가 있는 done/analyzing" 을 세므로
직전 통화가 이미 카운트돼 있어도 이 경로를 막지 못한다 — 한도는 **시작 게이트가 아니라 홈
배지 계산용**이다.

### 선택한 방식 — 서버가 판정하고 클라가 기다린다

서버가 진실의 원천이어야 한다: 앱을 껐다 켜도, 다른 기기에서도 똑같이 막힌다.

**서버**

1. `repository/call_repository.py` — `find_pending_level_test(member_id, language, within_min)`
   - `call_type='level_test' AND status='analyzing' AND target_language=:lang`
   - `call_date >= now() - within_min` (기본 10분). **이 시간창이 안전장치다** — 분석이
     크래시해 `analyzing` 으로 영원히 남은 행이 사용자를 영구히 가두면 안 된다.
   - 최신 1건, 순수 SELECT (R3: 커밋하지 않는다).
2. `service/call_service.py` — `pending_level_test(member_id)` → `{"call_id": int|None}`
   - 대상 언어는 member 의 현재 학습 언어. 언어가 다르면 그 언어의 레벨은 별개라 막지 않는다.
3. `routers/call.py` — `GET /calls/level-test/pending`
   - **`/{call_id}` 보다 위에** 선언(정적 경로 우선 — 이 파일의 기존 컨벤션).

**클라**

4. `normalcall_remote_data_source.dart` / `..._repository.dart` / `..._repository_impl.dart`
   — `pendingLevelTestCallId()` 추가.
5. `screens/home/call_loading.dart` `_begin()` 의 `CallPhase.idle` 분기
   - `start()` 전에 조회. null 이면 즉시 기존 경로.
   - non-null 이면 대기 모드: 1.5초마다 `getStatus(callId)` 폴링(분석 로딩 화면과 같은 주기),
     `done`/`failed` 가 되면 `start()`.
   - **상한 45초**. 넘으면 그냥 `start()` 한다 — 분석이 죽었을 때 사용자를 영구히 막는 것보다
     레벨테스트가 한 번 더 도는 게 낫다(원래 버그 수준으로 돌아갈 뿐).
   - 문구는 l10n 신규 키 `levelTestFinishing`("레벨 테스트 결과를 정리하고 있어요").

### 안 하는 것

- WS 시작에서 거부(에러 코드)로 막기 — 사용자에겐 "통화 실패"로 보여 UX 가 나쁘다.
- `needs_level_test` 판정 자체를 바꾸기 — 레벨 시스템 D11 라우팅 규칙은 건드리지 않는다.

## B. 분석 결과에서 스피커 → "생성중"("isn't ready yet")

### 원인 (확정)

서버는 **의도적으로** TTS 전에 결과를 연다 — `normalcall_service.py:1071`

```python
call.status = "done"   # P2.6 — 결과 화면 즉시 해제(요약·표현과 같은 커밋)
#  ... TTS·체크판은 done 이후 후행
```

`analysis_loading.dart` 는 1.5초 폴링이라 `done` 직후 넘어가고, 그때 `sentence.voice_url` 은
아직 NULL 이다. `analysis.dart:166` 는 그 스냅샷을 들고 **다시 안 받아온다**:

```dart
if (url == null || url.isEmpty || !url.startsWith('http')) {
  _snack(l10n.standardAudioNotReady);
  return;
}
```

dev DB 확인: 최근 200문장 `voice_url` **200/200 채워짐**. 서버는 정상, 화면만 옛 값을 본다.

### 수정

서버엔 이미 멱등 온디맨드 엔드포인트가 있다 — `POST /sentences/{id}/tts`
(`sentence_service.synthesize_tts`: `voice_url` 이 있으면 **재합성 없이 그대로 반환**).
클라도 `ReviewRepository.sentenceTtsUrl()` 로 이미 구현돼 있다. 분석 화면만 안 쓴다.

`analysis.dart` `_playSentence` 를 폴백 경로로 바꾼다:

1. `voiceUrl` 이 쓸 만하면 그대로 재생(현행과 동일 — 추가 왕복 0).
2. 없으면 `sentenceTtsUrl(id)` 1회 호출 → 받은 URL 재생 + 로컬 상태에 캐시(같은 카드 재탭 시 재요청 안 함).
3. 그것마저 null/실패면 그때 `standardAudioNotReady`.

서버 변경 없음. 후행 TTS 가 끝났으면 1회 왕복으로 즉시 재생되고, 파이프라인이 실패했던
문장도 이 경로로 복구된다.

## C. "홈으로 가기" 뒤 뒤로가기 하면 홈이 또 나온다

### 원인 (확정)

`main.dart:111` 의 첫 라우트는 `AuthGate` 이고, 온보딩 끝난 사용자에겐 `auth_gate.dart:79`
에서 **`HomeScreen()` 을 직접 렌더**한다. 그런데 앱의 "홈으로"는 전부

```dart
Navigator.pushNamedAndRemoveUntil(context, Routes.home, (r) => r.isFirst);
```

`isFirst`(= AuthGate = 이미 홈) 를 남기고 그 위에 홈을 **또 push** → 스택 `[홈, 홈]`.
뒤로가기 한 번이면 아래 홈이 나온다.

`network_error.dart:81` 에 "AuthGate 를 지우면 세션만료 리다이렉트가 끊긴다(그래서 `=> false`
가 아니라 `=> r.isFirst`)" 는 주석이 있다. 그 판단은 맞다 — 다만 해법이 틀렸다.

### 수정

```dart
Navigator.of(context).popUntil((r) => r.isFirst);
```

AuthGate 를 그대로 남기면서(주석의 요구 충족) 중복도 안 만든다. 대상 8곳:

| `screens/home/call.dart` | 150, 231 |

`auth/`·`onboarding/` 의 `popUntil((r) => r.isFirst)` 들은 **이미 올바르다** — 건드리지 않는다.
`onboarding_reason.dart:63`(→ onboardingDone), `onboarding_done.dart:29`(→ callLoading) 은

## D. 통화가 길어질수록 응답 시작이 느려진다 (4분쯤부터 체감)

### 원인

`normalcall_controller.dart` 적응형 쿠션의 **비대칭**:

```dart
static const int _cushionStepBytes  = ... 300ms;   // 굶은 턴마다 +300
static const int _cushionDecayBytes = ... 150ms;   // 깨끗한 턴마다 −150
static const int _cushionMaxBytes   = ... 2500ms;  // 상한
```

성장이 감쇠의 2배라 통화가 길어질수록 단조 증가하고, `_cushionBytes` 는 **모든 응답의 시작
지연에 그대로 더해진다**(턴 시작 시 이만큼 버퍼링한 뒤 재생 시작).

보조 요인으로 Gemini 컨텍스트 누적이 있으나 이건 서버측·불가피.

### 수정 — 비대칭 완화 (되돌림 아님)

| 상수 | 현재 | 변경 |
|---|---|---|
| `_cushionStepBytes` | +300ms | **+150ms** |
| `_cushionDecayBytes` | −150ms | **−300ms** |
| `_cushionMaxBytes` | 2500ms | **1800ms** |

이제 감쇠가 성장의 2배라 나쁜 구간이 지나면 값이 **되돌아온다**. 끊김 방어(쿠션이 자란다는
성질)는 유지하되 통화 내내 누적되지 않는다. 시작값 `_prebufferBytes`(900ms)는 그대로 —
그건 커밋 2의 재생 안정화 핵심이라 건드리면 끊김이 돌아온다.

**실기기 재검증 필요**: 5분 통화에서 (a) 끊김 없음 (b) 4분 시점 응답 시작이 초반과 비슷.

## 보류 — 에코 되먹음 (별도 작업)

call=851 전사 t24 이후 매 턴, 유저 발화 앞에 비버의 마지막 절이 그대로 붙는다
(`…좋아하는 거 있어?` → `좋아하는 거 있어? 기생충…`). 길이가 0.5초→2초로 커진다.

원인은 벤더링 플러그인 `FlutterPcmSoundPlugin.java:461`:

```java
long remainingFrames = mQueuedBytes.get() / (2 * mNumChannels);
```

**플러그인 자기 큐만** 센다. 이미 `mAudioTrack.write()` 로 넘어간 분량(트랙 버퍼 =
`minBufferSize * 4`)은 빠져 있다. 그래서 `_audioDrained` 가 "다 나갔다"고 볼 때 스피커엔
아직 소리가 남아 있고, `_micHangover`(300ms) 로는 못 덮는다.

제대로 된 수정은 `getPlaybackHeadPosition()` 기반 실제 잔량 보고(플러그인 자바 수정 + 실기기
검증). 전사 오염·레벨 판정 오류의 직접 원인이라 값어치는 크지만, 위 4건과 섞으면 되돌리기가
어려워져 **분리**한다.
