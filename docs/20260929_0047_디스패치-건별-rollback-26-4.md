# §26-④ 디스패치 건별 except 에 rollback (2026-09-29)

## 결함(앱팀 실기기 검증 → bt-back 코드 확인)
`dispatch_service.run` 의 알람 건별 `except` 가 로그만 남기고 `db.rollback()` 을 안 했다. 세션은 루프 전체가 공유한다.

## 재현하며 더 나온 것 — 건너뛰기보다 나쁜 경우가 있었다
- Core `execute` 실패(PG «current transaction is aborted»): 뒤 알람 쿼리가 연달아 실패 → 건별 except 가 잡아 **그 분의 나머지 전부 건너뜀**(bt-back 설명대로, 다음 분 catchup 으로 ~1분 지연).
- **flush 실패**(ORM 쓰기 — 예: `_ring` 의 토큰 무효화 commit): SQLAlchemy 가 세션 객체를 전부 만료시킨다. 그러면 뒤 알람의
  `if a.time is None` 읽기가 DB 를 다시 치는데 그 줄이 **try 밖**이라 `PendingRollbackError` 가 루프를 깨고 **run() 전체가 예외(500)**.
  수정 전 코드로 시험을 돌려 확인했다.

## 수정
1. 건별 `except` 에서 `self.db.rollback()`(그 자체 실패도 삼킴). 로그의 alarm_id 는 `inspect(a).identity`, tz 값은 `a.__dict__` 에서
   — 오염/만료 세션에서 속성을 새로 읽다 except 안에서 또 터지지 않게.
2. `a.time is None` 검사를 try 안으로.

## 함정 — rollback 이 다른 알람의 발송 기록을 되돌리나? → 아니다
rollback 범위는 «마지막 commit 이후»뿐이다. `_claim` 은 INSERT 직후 **그 자리에서 commit**, `_ring` 은 자기 commit/rollback 으로 닫는다 —
알람 사이에 걸친 미커밋 쓰기가 없다. 되돌려지는 건 실패한 그 알람의 미커밋분뿐이다(예: `_claim` 의 commit 자체가 실패했다면 그 클레임은
실제로 없었고 발송도 안 했다 — 남으면 오히려 «보냄»으로 기록돼 catchup 이 못 살린다).
⚠ 기존 동작 그대로: 클레임 commit 후 `_ring` 에서 실패하면 기록은 남고 발송은 안 된 상태가 된다(멱등 키가 재시도를 막음) — 이번 범위 밖.
⚠ rollback 은 세션 객체를 만료시켜 뒤 알람이 속성을 다시 읽는다(정상 동작, 실패가 난 분에만 쿼리 증가).

## 참고 — 앱팀 질문: `PUT /alarms/{id}` 에 `tz` 만 담아도 되나 → **된다**
`AlarmUpdate`(domains/alarm/schemas/alarm.py:43-52) 7필드 전부 Optional(time·character_id·is_activate·days_of_week·call_type·tz·tz_offset_min),
`AlarmService.update` 는 None 이 아닌 필드만 바꾼다(부분 갱신). `{"tz":"America/New_York"}` 만 보내면 tz 만 바뀐다.
⚠ `alarm.tz` 는 저장 시 IANA 유효성 검사가 없다(잘못된 값은 디스패치가 경고 후 다음 폴백). 디스패치는 member.tz 를 먼저 보므로
앱의 재전송은 member.tz 가 아직 없는 회원에게만 실효가 있다.
