# IAP API 계약서 (프론트 공유용)

작성 2026-07-31 · **이 문서는 앱팀에 그대로 전달하는 계약이다.**

서버가 아직 실구현 전이어도 **경로·요청·응답은 이 문서대로 확정**이다. 앱은 이 스펙으로
미리 구현하면 되고, 서버가 붙은 뒤에도 계약은 안 바뀐다.

| 항목 | 값 |

| base URL | `https://beavertalk-app-api-ig4qiawz4q-du.a.run.app/api/v1` |

## 1. 상품 ID 규칙

앱과 서버가 **같은 문자열**을 써야 한다. 스토어 콘솔에도 이대로 등록한다.

```
캐릭터   im.beavertalk.character.<이름소문자>
         im.beavertalk.character.bibi
         im.beavertalk.character.popo
         im.beavertalk.character.rara
         im.beavertalk.character.dudu

구독     im.beavertalk.pro.monthly
```

⚠ `baba` 는 무료 기본 캐릭터라 **IAP 상품이 아니다**(등록하지 않는다).

서버가 이 문자열 ↔ `character_id` / 구독플랜을 매핑한다. 앱은 `character_id` 를 몰라도
되고 상품 ID 만 알면 된다.

## 2. `POST /purchases/verify` — 영수증 검증 (핵심)

앱이 스토어 결제를 마친 **직후** 호출한다. 이 API 하나가 캐릭터·구독을 모두 처리한다.

### 요청

```http
POST /api/v1/purchases/verify
Authorization: Bearer <supabase access token>
Content-Type: application/json
```

```json
{
  "platform": "ios",
  "product_id": "im.beavertalk.character.bibi",
  "transaction_id": "2000000912345678",
  "purchase_token": "<플랫폼별 영수증/토큰 원문>",
  "is_sandbox": false
}
```

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `platform` | `"ios"` \| `"android"` | ✅ | |
| `product_id` | string | ✅ | §1 규칙 |
| `transaction_id` | string | ✅ | iOS: `originalTransactionId` / Android: `orderId` |
| `purchase_token` | string | ✅ | iOS: JWS 서명 영수증 / Android: `purchaseToken` |
| `is_sandbox` | bool | ❌(기본 false) | 테스트 결제 여부 |

> **iOS**: StoreKit2 `Transaction.jwsRepresentation` 을 `purchase_token` 에.
> **Android**: `Purchase.getPurchaseToken()` 을 `purchase_token` 에.

### 응답 200 — 성공 (신규 지급 / 이미 지급 **둘 다 200**)

```json
{
  "status": "granted",
  "already_granted": false,
  "product_id": "im.beavertalk.character.bibi",
  "kind": "character",
  "character_id": 2,
  "entitlement": {
    "is_pro": false,
    "pro_expires_at": null,
    "owned_character_ids": [1, 2]
  }
}
```

구독이면:

```json
{
  "status": "granted",
  "already_granted": false,
  "product_id": "im.beavertalk.pro.monthly",
  "kind": "subscription",
  "character_id": null,
  "entitlement": {
    "is_pro": true,
    "pro_expires_at": "2026-08-31T09:00:00Z",
    "owned_character_ids": [1]
  }
}
```

| 필드 | 설명 |
|---|---|
| `status` | 항상 `"granted"` (실패는 4xx/5xx 로 온다) |
| `already_granted` | **`true` 면 이미 처리된 영수증**(재전송·복원). 에러가 아니다 |
| `kind` | `"character"` \| `"subscription"` |
| `character_id` | 캐릭터일 때만 값. 구독이면 `null` |
| `entitlement` | **호출 후 최신 권한 상태** — 앱은 이걸로 화면을 갱신하면 된다 |

> ⭐ **`already_granted: true` 도 정상 성공이다.** 네트워크 재시도·앱 재실행·구매 복원으로
> 같은 영수증이 여러 번 오는 건 **정상 동작**이다. 앱은 200 이면 성공으로 처리하고,
> `already_granted` 는 토스트 문구를 바꾸는 정도로만 쓰면 된다.

### 에러

에러 바디는 기존 규약과 동일: `{"detail": {"code": ..., "message": ...}}`

| 상태 | `code` | 뜻 | 앱 동작 |
|---|---|---|---|
| 400 | `INVALID_REQUEST` | 필드 누락·형식 오류 | 버그. 재시도 금지 |
| 401 | `HTTP_401` | 토큰 무효 | 재로그인 |
| 422 | `INVALID_RECEIPT` | **스토어가 무효 판정** | 재시도 금지, 문의 안내 |
| 404 | `UNKNOWN_PRODUCT` | 서버가 모르는 상품 ID | 버그. 상품 등록 확인 |
| 409 | `RECEIPT_OWNED_BY_OTHER` | 다른 계정이 이미 쓴 영수증 | 안내 후 중단 |
| 503 | `VERIFY_UNAVAILABLE` | 스토어 서버 응답 없음 | **재시도 가능**(백오프) |

⚠ **422 와 503 을 반드시 구분해야 한다.** 422 는 아무리 재시도해도 안 되고, 503 은
잠시 뒤 되므로 앱은 재시도 큐에 넣어야 한다(영수증은 기기에 남아 있으니 유실 아님).

## 3. `GET /purchases/entitlement` — 현재 권한 조회

앱 시작 시·복원 후·구독 화면 진입 시 호출한다. **"이 사람이 지금 Pro인가"의 단일 진실.**

```http
GET /api/v1/purchases/entitlement
Authorization: Bearer <token>
```

```json
{
  "is_pro": true,
  "pro_expires_at": "2026-08-31T09:00:00Z",
  "owned_character_ids": [1, 2, 9]
}
```

| 필드 | 설명 |
|---|---|
| `is_pro` | 지금 유효한 구독이 있는가 |
| `pro_expires_at` | 만료 시각(UTC ISO 8601). `is_pro=false` 면 `null` |
| `owned_character_ids` | 보유 캐릭터 id 목록 |

> **앱이 자체 판단하지 마라.** 만료 시각을 앱에서 비교해 Pro 여부를 정하면 기기 시계
> 조작·시차로 어긋난다. `is_pro` 를 그대로 쓰고, `pro_expires_at` 은 "언제까지" 표시용으로만.

## 4. `POST /purchases/restore` — 구매 복원

폰 교체·앱 재설치 후 "구매 복원" 버튼에서 호출. 앱이 스토어에서 **과거 영수증 전부**를
꺼내 배열로 보낸다.

```json
{
  "platform": "ios",
  "purchases": [
    { "product_id": "im.beavertalk.character.bibi",
      "transaction_id": "2000000912345678",
      "purchase_token": "..." },
    { "product_id": "im.beavertalk.pro.monthly",
      "transaction_id": "2000000987654321",
      "purchase_token": "..." }
  ],
  "is_sandbox": false
}
```

```json
{
  "restored": 2,
  "failed": 0,
  "entitlement": { "is_pro": true, "pro_expires_at": "...", "owned_character_ids": [1, 2] }
}
```

일부가 무효여도 **200** 이다(`failed` 로 알려준다). 유효한 것만 지급된다.

## 5. 폐기되는 API

| API | 어떻게 되나 |
|---|---|
| `POST /characters/{id}/purchase` | **동작(실결제 없음 — is_test_grant:true)** → IAP 후 폐기 |
| `POST /subscriptions` | **동작(실결제 없음)** → 폐기(가격을 클라가 정하는 구조라 IAP 와 양립 불가) |
| `GET /subscriptions` | 유지(내역 조회) |
| `POST /subscriptions/{id}/cancel` | **폐기** — 해지는 스토어(iOS 설정 / Play)에서만 가능 |

### ⚠ 지금 구매는 실결제가 아니다

서버가 어디에도 청구하지 않고 그냥 지급한다(앱이 흐름을 만들 수 있게). 응답의
**`is_test_grant: true`** 가 그 표시다. IAP 전환 후 이 필드는 사라진다.
이 상태로 스토어 출시 금지.

## 6. 앱이 알아둘 것

**해지·환불은 앱에서 못 한다.** iOS 설정 / Play 구독 화면으로 보내는 링크만 제공한다.
서버는 스토어 웹훅으로 상태를 받아 `entitlement` 에 반영한다.

**구독 상태는 앱 밖에서 바뀐다.** 갱신·결제실패·해지·환불이 앱을 안 거치고 일어나므로,
앱 시작 시 `GET /purchases/entitlement` 를 항상 다시 불러야 한다.

**결제 직후 반드시 `verify` 를 호출해야 한다.** 특히 Android 는 서버가 스토어에
"확인(acknowledge)" 을 보내야 하는데, 그게 `verify` 안에서 일어난다. **3일 안에 안 하면
구글이 자동 환불**한다.

**가격은 스토어에서 받아 표시한다.** 서버는 IAP 상품 가격을 모른다.

## 7. 지금 바로 테스트할 수 있다 (스텁 모드) ⭐

**서버가 이미 배포돼 있고 위 3개 API 가 실제로 동작한다.** 스토어 자격증명이 아직 없어
영수증을 애플·구글에 진짜로 물어보지 않을 뿐, **요청·응답 형태는 실제와 100% 같다.**

즉 앱은 지금 **구매 → 지급 → 화면 갱신 → 복원**까지 전 구간을 만들고 돌려볼 수 있다.
서버가 실검증으로 바뀌어도 **앱은 고칠 게 없다.**

### 성공을 만드는 법

`purchase_token` 에 아무 문자열이나 넣으면 통과한다(형식만 검사).

```json
{ "platform": "ios",
  "product_id": "im.beavertalk.character.bibi",
  "transaction_id": "test-tx-001",
  "purchase_token": "whatever" }
```

`transaction_id` 를 **바꾸면 새 구매**, **같으면 이미 처리됨**(`already_granted: true`)이 된다.
멱등 동작을 이걸로 그대로 확인할 수 있다.

### 실패를 만드는 법 (에러 분기 테스트용)

`purchase_token` 접두어로 원하는 실패를 부른다:

| `purchase_token` | 결과 | 앱이 해야 할 일 |
|---|---|---|
| `invalid...` | **422** `INVALID_RECEIPT` | 재시도 금지, 문의 안내 |
| `unavailable...` | **503** `VERIFY_UNAVAILABLE` | 재시도 큐(백오프) |
| 그 외 | 200 성공 | 지급 완료 |

`product_id` 를 없는 것으로 보내면 **404** `UNKNOWN_PRODUCT` 도 확인할 수 있다.

### 확인용 curl

```bash
TOKEN=<supabase access token>
BASE=https://beavertalk-app-api-ig4qiawz4q-du.a.run.app/api/v1

# 구매
curl -X POST "$BASE/purchases/verify" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"platform":"ios","product_id":"im.beavertalk.character.bibi",
       "transaction_id":"test-1","purchase_token":"ok"}'

# 권한 조회
curl "$BASE/purchases/entitlement" -H "Authorization: Bearer $TOKEN"
```

⚠ 스텁으로 지급된 것은 DB 에 `is_stub=true` 로 표시된다. 운영 정산에서 걸러내니
테스트로 캐릭터를 받아도 문제없다.

| | 상태 |
|---|---|
| 계약(이 문서) | ✅ 확정 |

| 웹훅 수신(갱신·해지·환불) | ⬜ 콘솔 등록 대기 |

**막힌 것 2개**: 애플 App Store Connect API 키(`.p8`), 구글 Play Developer API 서비스계정.
둘 다 콘솔 발급이 필요하다. 들어오면 `core/iap.py` 의 어댑터 안쪽만 채운다 —
**계약·DB·멱등·지급은 이미 완성이라 앱 영향 0.**

웹훅이 붙기 전까지는 구독 갱신·해지·환불이 서버에 자동 반영되지 않는다(수동 확인 필요).
