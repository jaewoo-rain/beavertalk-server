## 1. 🔴 착수 전 관문 — 이게 안 풀리면 PTT 는 성립하지 않는다

`core/openai_stt.py:149-156` (내가 직접 읽음, 실측 기록):

> ⭐ **닫기 전에 무음을 조금 흘린다** — 안 그러면 마지막 발화가 통째로 사라진다.
> 실측(2026-08-10): 같은 오디오를 그냥 끊으면 전사가 2건인데, **꼬리 무음 1.5초**를 붙이면
> 3건째가 온다. **server VAD 가 발화 끝을 못 봐서 마지막 구간을 커밋하지 않는 것이다.**
> ⚠ **통화 중에는 마이크가 상시 열려 무음이 계속 흘러 문제가 안 된다 — 통화 끝에서만 생긴다.**

`core/openai_stt.py:129` — `turn_detection = {"type": "server_vad"}`

⛔ **PTT 는 그 전제를 매 턴 깬다.** 버튼을 떼고 마이크를 닫으면 벤더가 침묵을 못 보고 커밋을 안 한다.
⇒ **지금 통화 끝에서만 나던 「마지막 발화 유실」이 매 턴 난다.**

### 선택지 (셋 다 미검증)
| | 방법 | 이득 | 위험 |
|---|---|---|---|
| (a) | `turn_detection: null` + 릴리즈 시 수동 `input_audio_buffer.commit` | 벤더 침묵창 300ms 통째로 회수. 가장 깨끗 | transcription intent 세션에서 `null` 이 허용되는지 **미확인**. 서버 에이전트가 문서 접근 실패(403) |

| (c) | 클라가 릴리즈 후 300~500ms 더 보낸다 | 가장 단순 | 이득 최소 |

⇒ **구현 전 30분 스파이크로 (a)를 확정할 것.** 여기서 갈리면 이득 추정이 통째로 바뀐다.

## 2. 지연 — 벌어서 도로 쓴다

```
현재 말끝 → 소리                    2,354ms
못 없애는 바닥 (파이프라인 184 + 최종전사 349)   533ms
```

🔴 **그런데 잘림을 막으려면 릴리즈 그레이스가 필요하고, 그 권장값이 300ms 다.**
(사람이 마지막 음절을 발음하는 **중에** 손을 뗀다. 이 폭을 잰 문헌은 없다 — 잠정값)

⚠ 그리고 **사람이 버튼을 떼는 데 걸리는 시간을 아무도 안 쟀다.** 이게 200ms 면 이득이 마이너스가 된다.
**실기기 측정 전에는 이득을 확정하지 마라.**

## 3. 그럼 뭐가 남나 — 진짜 이득 셋

### ① 추측 제거 (가장 큼)
지금 턴 경계·끼어들기를 판정하는 코드가 **주석 포함 약 430줄 · 노브 10개**이고,
전부 "벤더 VAD 가 뭘 말하려는 건지"를 추측한다. PTT 는 그 추측을 버튼 신호 하나로 치환한다.

⚠ **다만 「선택 모드」에서는 그 430줄이 안 사라진다.** VAD 모드가 기본으로 남으므로 코드는 그대로 살고
모드 분기가 얹힌다 — **총 복잡도는 오히려 는다.** 줄어드는 건 "한 통화 안에서 동시에 도는 판정 수"다.

### ② STT 원가
STT 는 흘려보낸 오디오 길이로 계산된다(`core/openai_stt.py:274` → `cascade_usage.py:157`).
지금은 마이크 상시개방이라 **침묵도 전부 흘리고 전부 센다.** PTT 는 hold 시간만 보낸다.
5분 통화에서 실제 발화가 1/3 이면 **STT 오디오가 1/3 로 준다.**
⚠ 벤더가 침묵을 과금하는지는 코드가 스스로 "미확인"이라고 적어 뒀다 — 청구서로 확인 필요.

### ③ 학습 — 계획 시간을 학습자가 통제한다
```
현행 문장 중간 쉼 허용치  약 1,100ms  (벤더 300 + 우리 800)
원어민 "표준 최대 침묵"    약 1,000ms  (Jefferson 1989)
L2 연구가 "쉼"으로 세는 단위  200~350ms
```
⇒ **초보에게 원어민 기준의 인내심을 적용하고 있다.** 그리고 조용히 생각하는 초보는 VAD 가 꺼져
800ms 경로를 탄다 — **가장 도움이 필요한 사용자에게 가장 짧은 인내심**을 준다.

## 4. 🔴 새로 생기는 실패 모드 — 버튼을 일찍 뗀다

확률적 오탐이 아니라 **확정 손실**이다(뗀 뒤엔 오디오가 아예 안 온다).
⇒ "뗌 = 종료"로 구현하면 **지금보다 나빠진다.** 4층 방어가 세트로 붙어야 한다.

| 층 | 무엇 | 값 | 근거 |
|---|---|---|---|
| L1 | 릴리즈 그레이스 | 300ms (잠정) | 문헌 없음. 클라에서 `릴리즈 − 마지막 유성` p95 측정해 확정 |
| L2 | 미완이면 이어말하기 창 | 1,500ms | 기존 상수와 정합(`config.py:223,263`). ⭐ `_looks_unfinished` 가 **이미 있다**(지금은 관측 전용) |
| L3 | 재누름 병합 | 간격 ≤1,500ms | ⛔ **기존 병합 코드를 그대로 쓰면 안 된다** — 아래 |
| L4 | 취소 제스처(위로 밀기) | — | 자기수정(self-repair) 기회. 지금은 잘못 말하면 이미 전송된 뒤다 |

⚠ **L2 의 함정**: 짧은 정답이 미완으로 오판된다. "어디 가요?" → **"학교에."** → `_looks_unfinished`=yes.
⇒ **길이 게이트 필수** — 4어절 또는 1.5초 이상일 때만 연장. 없으면 초보 통화의 절반이 1.5초씩 늦어진다.

### 🔴 L3 — 기존 병합 코드가 PTT 에서 **양방향 다 틀린다** (내가 코드로 확인)
```python
cascade_session.py:1787-1789  "판정은 **오디오 시각**으로만 한다. 도착 시각은 벤더 지연이 섞여 못 쓴다"
cascade_session.py:1531       self._audio_ms += len(inb.audio) / (rate*2) * 1000   ← 받은 바이트만큼만 흐른다
```
- **뗀 동안 마이크를 닫으면** → `_audio_ms` 가 안 흐른다 → gap 이 항상 ≈0 → **5분 뒤 발화까지 앞에 붙는다**
- **뗀 동안 무음을 계속 보내면** → gap 이 실시간으로 흘러 500ms 를 즉시 넘긴다 → **병합이 절대 안 된다**

⇒ PTT 에서는 병합 판정 축을 **오디오 시각 → 릴리즈·재누름 벽시계 간격**으로 바꿔야 한다.

## 5. 앱 — 마이크 제어는 ⓐ (실측 근거)

### startRecorder / stopRecorder 실측 (Android 에뮬, 로그 18건)
```
startRecorder   n=11  최소 21 / 중앙 27 / 최대 37ms
stopRecorder    n=7   89 ~ 490ms      ← 한두 자릿수 느리다
```
⚠ 그리고 둘이 **같은 `_lock`** 을 쓴다 — 뗀 직후 다시 누르면 start 가 stop 뒤에 줄을 서서
**그만큼 첫 음절이 통째로 없어진다.** PTT 는 짧게 여러 번 누르는 조작이라 이 경합이 상시로 온다.

| | ⓐ 계속 녹음 + 버리기 | ⓑ 누를 때 start / 뗄 때 stop |
|---|---|---|
| 첫 음절 | **손실 0** | 21~37ms + lock 경합 시 수백 ms |
| 변경 면적 | `:1909` 한 줄 조건 | 레코더 수명·워치독·재시도 루프 전부 |
| 마이크 워치독 | 영향 없음 | **오작동한다** (`:2038`, 6초 안에 프레임 0이면 재시작) |
| 배터리 | **오늘과 동일** (지금도 상시개방). 업링크만 줄어 **오늘보다 싸다** | 절감량 미측정 |
| pre-roll | 가능 (14프레임 ≈ 10KB) | 구조적으로 불가 |

⇒ **ⓐ 채택.** ⚠ 대가: 마이크 인디케이터가 통화 내내 켜져 있다 — 다만 **오늘과 같은 상태**다.

### 제스처 — `GestureDetector` 가 아니라 `Listener`
```
onTapUp        손가락이 18px 벗어나면 onTapCancel 로 갈린다 (kTouchSlop)
onPanStart     움직여야 인식 → 가만히 누르는 PTT 에서 안 뜬다
onLongPress    deadline 500ms 대기 → 치명적
Listener       아레나·슬롭 없음. onPointerUp 은 위치 조건 없음   ← 채택
```
⇒ 미끄러져도 **마이크가 열린 채 붙잡히는 경우가 구조적으로 없다.**

## 7. 모드 정책 (결정)

1. **모드는 통화 시작 화면에서만 고른다. 통화 중 전환 금지.**
   두 모드의 혼란 비용은 "동시에 존재할 때"만 크다.
2. **자동 전환 금지.** 소음을 감지해도 **제안만** 한다.
   자기 의사와 무관하게 바뀌면 초보는 진단할 수 없고, 그때 앱은 고장난 것으로 인식된다.
3. **기본은 현행 연속 모드.** PTT 는 명시적 선택.
4. **레벨로 자동 결정하지 않는다.** 두 논리가 정면 충돌한다(왕초보가 가장 필요 ↔ 왕초보에게
   조작 규칙 추가가 가장 큰 장벽). ⇒ 대신 **행동 지표**로 제안 — `미완=yes` 비율.
5. ⭐ **통화 레코드에 모드 필드를 반드시 남긴다.**
   ⛔ 안 남기면 통화 품질 지표가 두 분포로 섞여 **앞으로의 모든 판정이 오염된다.**
   이게 이번 결정에서 가장 되돌리기 비싼 부분이다.

## 11. 확인 못 한 것

1. **[최대] `turn_detection: null` + 수동 commit 이 되는가** — 문서 접근 실패(403). 30분 스파이크 필요
2. **Google STT 폴백에서 PTT 가 성립하는가** — 수동 커밋 개념이 없다
3. **사람이 버튼을 떼는 지연(말끝 → 릴리즈)** — 아무 데도 측정치가 없다. 이득 추정에 이 항이 빠져 있다
4. **실기기 startRecorder 지연** — 위 11건은 전부 에뮬레이터. 실기기 로그엔 타임스탬프가 없다
5. **에코가 실제로 사용자 전사를 오염시키는가** — 지금은 취소 경로로만 나타나 데이터가 없다
6. **PTT vs 오픈마이크를 언어학습자 대상으로 비교한 통제 연구** — **없다.** 결정적 근거는 우리 A/B 로만
7. **버튼 유지의 인지 부하** — 직접 측정 연구 없음
8. **`CASCADE_TURN_MAX_S=30` 을 hold 상한으로 써도 되나** — "쉬지 않고 말하는 상한"으로 잡힌 값이다

## 12. 권장 순서

```
0단계 (코드 0줄)   미완=yes 비율 · 빈 턴 비율 뽑기 → PTT 논거가 서는지 확인
1단계 (30분)       turn_detection:null + 수동 commit 스파이크 → 이득 확정
2단계 (앱, 선결)   _clearPlayback 의 _envPlayed 보정 + 회귀
3단계              서버 드라이버 분리(VadTurnDriver / PttTurnDriver) + 프로토콜 2메시지
4단계              앱 Listener 버튼 + _micGated 조건 + 모드 필드
5단계              4층 잘림 방어 (L1~L4)
```
⛔ 0·1단계가 안 끝나면 2단계 이후로 가지 마라.
