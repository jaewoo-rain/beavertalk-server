## 0. 한 줄

**서버가 2,026ms, 앱이 520ms.** 벤더 왕복 2개(LLM 844 + TTS 819 = 1,663ms)가 직렬로 쌓여
전체의 71%다. **"플러터 한계" 가설은 기각**됐고, 앱이 웹보다 늦는 217ms는 쿠션 정책 하나다.

## 1. 실측 — 웹과 앱을 같은 자로

서버가 턴마다 `cascade 클라계기:` 한 줄로 뺄셈을 해서 남긴다
(`cascade_session.py:1909 _on_client_timing`).

```
웹 (쿠션 300 고정 · 4턴)
  b2 들림=2425 서버첫소리=2121 클라몫=304
  b3 들림=2679 서버첫소리=2354 클라몫=325
  b4 들림=1986 서버첫소리=1710 클라몫=276
  b5 들림=2414 서버첫소리=2112 클라몫=302
                     중앙값  들림 2,419 · 클라몫 303

앱 (쿠션 750→1200 자동성장 · 6턴)
  b2 들림=2262 서버첫소리=1868 클라몫=394  (쿠션 750)
  b3 들림=2233 서버첫소리=1821 클라몫=412  (쿠션 1050)
  b4 들림=2757 서버첫소리=2022 클라몫=735  (쿠션 1200)
  b5 들림=2525 서버첫소리=1951 클라몫=574  (쿠션 1200)
  b6 들림=2288 서버첫소리=1795 클라몫=493  (쿠션 1200)
  b7 들림=2419 서버첫소리=1871 클라몫=548  (쿠션 1200)
                     중앙값  들림 2,354 · 클라몫 520
```

**읽는 법 3가지**
1. **총 시간은 앱이 오히려 65ms 빨랐다**(2,354 vs 2,419). 서버가 그날 웹 판에서 246ms 더
   느렸을 뿐 — 대답 길이가 달랐다.
2. **앱만의 몫이 217ms 더 크다**(520 vs 303). ⇒ 이게 유일한 진짜 차이다.
3. ⭐ **웹의 클라몫 303ms ≈ 자기 쿠션 300ms.** 웹은 쿠션 말고 아무것도 안 쓴다.
   앱은 쿠션이 자라는 만큼 그대로 느려진다(394 → 735, 한 통화 안에서 거의 2배).

⚠ 표본이 작다(웹 4턴 / 앱 6턴). 방향은 확실하나 정확한 ms는 흔들린다.

### 🔴 정정 — 내가 낸 틀린 수치
이전에 **"앱 몫 328ms"** 라고 보고했다. 그건 중앙값끼리 뺀 것이라 **서로 다른 턴을 섞었다.**
턴 단위 조인값은 **520ms** 다. 그리고 나는 이 틀린 328ms를 **전수조사의 전제로 넣었다**
⇒ 조사 보고서의 앱 관련 ms 추정은 전부 과소평가다.

## 2. 서버 2,026ms의 분해

`cascade 대답: 첫소리=` 가 분해해서 낸다(`cascade_session.py:640 _ReplyTiming`).
`첫소리` = 대답 시작 → **첫 바이트가 클라로 나간 시각**(`:709`). 최근 20턴 중앙값:

| 구간 | ms | 정체 |
|---|---:|---|
| LLM 첫조각 | 844 | Gemini 2.5 Flash 첫 토큰 |
| 문장 완성 | 206 | 「8자 이상 + 종결부호」 조각이 올 때까지 |
| 묶음 대기 | 82 | 우리 정책 구간 |
| 벤더(TTS) | 819 | Gemini TTS 첫 바이트 |
| 송출 | 16 | WS |
| **소계** | **2,026** | |

⭐ **844 + 819 = 1,663ms가 벤더 왕복 2개 직렬.** 전체 2,354ms의 71%.

## 3. 확정된 결함 — 앱 쿠션 자동성장

**독립된 두 에이전트가 서로 모르고 같은 줄을 짚었다.** 나도 현재 코드로 재확인했다.

`normalcall_controller.dart:2747` — 쿠션을 키울지 정하는 곳
```dart
_turnStarved = true;
_cushionBytes += _cushionStepBytes;      // +150ms
_log('cushion grew → ... (turn starved)');
```
조건에 `_turnFirstAudioFed` 가 **없다.**

`normalcall_controller.dart:2793-2795` — **같은 함수, 48줄 아래**
```dart
// ⛔ 첫 소리 전이면 「턴 시작 대기」다 — **발화 중 구멍이 아니다.**
//   처방이 달라 갈라야 한다(2026-08-13).
if (_turnFirstAudioFed) { 진짜 구멍 } else { 턴 시작 대기 }
```

⇒ **08-13에 "둘은 다르다"고 갈라놓고, 계기에만 적용하고 쿠션 판정에는 안 붙였다.**

**메커니즘**: 서버는 `turn_start`를 첫 오디오보다 **먼저** 보낸다(불변식 I2). 그 사이
`_pump`가 40ms마다 돌며 「큐 빔 + 비버 턴 열림」을 본다 ⇒ **매 턴 가짜 굶주림 확정.**
그리고 `_decayCushion`(`:2988` 부근)이 `if (_turnStarved) return;` 이라 **감쇠가 영영 안 걸린다.**

⚠ **같은 병을 한 번 앓은 기록**이 `:2726-2731` 주석에 있다 — *"판정 26회 중 실제로 들린
끊김은 8회. 나머지 18회가 가짜였고 쿠션은 72초 만에 1800ms 상한에 고정됐다"*(2026-08-02).
그때 `_audioDrained`를 넣어 고쳤는데 **턴 시작 케이스가 아직 샌다.**

## 4. "플러터 한계" 가설 — 기각

| 확인한 것 | 결과 |
|---|---|
| 재생 엔진 언어 | **이미 자바 네이티브** (`packages/flutter_pcm_sound/.../FlutterPcmSoundPlugin.java`). 코틀린 전환으로 안 바뀐다 |
| 음성 라이브러리 | **이미 포크해서 쓰는 중** (`pubspec.yaml:120-122 dependency_overrides`) |
| 재생 스레드 | 전용 스레드 + MAX_PRIORITY + THREAD_PRIORITY_AUDIO |
| 메서드 채널 | 이미 백그라운드 큐 (메인스레드 아님) |
| Dart 이벤트 루프 | `elLagMax 8~69ms, elLagOver50 0~2` — **안 막혀 있다** |
| 실시간 유지 | `PCMSTATS wrote/elapsed=100%`, `gap=0ms`, `take=0ms` |
| `STALL write=120ms` | **정상 페이싱.** 4800B ÷ 48,000B/s = 정확히 100ms 오디오. 로그 임계가 60ms라 매번 찍힐 수밖에 없다 |

⇒ 늦는 건 전부 **Dart 정책**이다. 그리고 산수가 전환을 막는다 —
앱을 통째로 다시 써서 얻는 상한이 **217ms**(웹 수준까지)다.

## 8. ⚠ 검증 실패 — 플랜에서 뺀 것

조사 보고서의 핵심 주장: *"말끝→턴닫힘 1,139ms가 지표 밖에 있다. 진짜 체감은 3,490ms"*

**내 앱 로그로 교차검증하면 안 맞는다.**
```
말시작→첫소리 − 응답 − 발화  =  245 · 88 · 495 · 1327 · 322 ms   (중앙값 322)
보고서 주장                  =  1,139ms
```
서버 `cascade turn:` 줄에 `앵커절약=442~550ms`가 매 턴 찍히는데, 보고서가 이걸 뺐는지
확인이 안 된다. **두 출처가 어긋나므로 확정하지 않는다.**

⇒ 방향(그 구간이 지표 밖에 있다)은 그럴듯하나, **크기를 모른다.** 계측 #3이 붙으면 갈린다.
