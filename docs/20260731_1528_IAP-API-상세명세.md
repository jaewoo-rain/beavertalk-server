**앱은 `message` 가 아니라 `code` 로 분기해야 한다.** `message` 는 사람이 읽는 문구라
언제든 바뀌지만 `code` 는 계약이다.

## 1. `POST /purchases/verify`

스토어 결제 **직후** 호출. 캐릭터·구독 모두 이 API 하나로 처리한다.

### 요청

```json
{
  "platform": "ios",
  "product_id": "im.beavertalk.character.bibi",
  "transaction_id": "2000000912345678",
  "purchase_token": "eyJhbGciOiJFUzI1NiIsIng1YyI6...",
  "is_sandbox": false
}
```

| 필드 | 타입 | 필수 | 제약 | 설명 |
|---|---|---|---|---|
| `platform` | string | ✅ | `"ios"` \| `"android"` | 그 외 값은 422 |
| `product_id` | string | ✅ | 1자 이상 | 위 상품 ID |
| `transaction_id` | string | ✅ | 1자 이상 | **멱등 키**. iOS `originalTransactionId` / Android `orderId` |
| `purchase_token` | string | ✅ | 1자 이상 | iOS JWS 원문 / Android `purchaseToken` |
| `is_sandbox` | bool | ❌ | 기본 `false` | 테스트 결제 여부 |

**플랫폼별로 어디서 꺼내나**

```swift
// iOS — StoreKit2
transaction_id  = transaction.originalID          // String(…)
purchase_token  = verificationResult.jwsRepresentation
```

```kotlin
// Android — Play Billing
transaction_id  = purchase.orderId                // null 가능 → 아래 주의
purchase_token  = purchase.purchaseToken
```

> ⚠ Android 의 `orderId` 는 **프로모션·테스트 결제에서 null 일 수 있다.** null 이면
> `purchaseToken` 을 `transaction_id` 로 대신 넣어라. 서버는 이 값을 멱등 키로만 쓰므로
> **기기·재설치와 무관하게 같은 구매에 대해 같은 값**이기만 하면 된다.

### 응답 200 — 캐릭터

```json
{
  "status": "granted",
  "already_granted": false,
  "product_id": "im.beavertalk.character.bibi",
  "kind": "character",
  "character_id": 2,
  "entitlement": {
    "is_pro": false,
    "pro_expires_at": null,
    "owned_character_ids": [1, 2]
  }
}
```

### 응답 200 — 구독

```json
{
  "status": "granted",
  "already_granted": false,
  "product_id": "im.beavertalk.pro.monthly",
  "kind": "subscription",
  "character_id": null,
  "entitlement": {
    "is_pro": true,
    "pro_expires_at": "2026-08-31T09:00:00Z",
    "owned_character_ids": [1]
  }
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `status` | string | 항상 `"granted"`. 실패는 4xx/5xx 로 온다 |
| `already_granted` | bool | **`true` 여도 성공이다** (§1.2) |
| `product_id` | string | 요청한 상품 ID 그대로 |
| `kind` | string | `"character"` \| `"subscription"` |
| `character_id` | int? | 캐릭터일 때만. 구독이면 `null` |
| `entitlement` | object | **호출 직후 최신 권한** — 앱은 이걸로 화면 갱신 |

> ⭐ `entitlement` 를 응답에 같이 실은 이유: 지급 후 화면을 갱신하려고 앱이 또
> `GET /purchases/entitlement` 를 부르지 않아도 되게. 왕복 1회가 줄고, 지급과 권한이
> **같은 시점의 값**이라 어긋나지 않는다.

### 1.2 `already_granted` — 중복은 정상이다

같은 영수증이 **여러 번 오는 것은 버그가 아니다**:

- 응답을 못 받아 앱이 재시도
- 결제 직후 앱이 죽었다 다시 켜짐 (미완료 트랜잭션 재처리)
- 사용자가 "구매 복원" 실행

이때 서버는 **재지급 없이 200 + `already_granted: true`** 를 준다.

```dart
final res = await verify(...);
if (res.alreadyGranted) {
  // 이미 갖고 있음 — 조용히 화면만 갱신 (에러 토스트 금지)
} else {
  showToast('구매 완료!');
}
// 어느 쪽이든 entitlement 로 화면 갱신
```

### 1.3 에러

| HTTP | `code` | 원인 | **앱이 할 일** |
|---|---|---|---|
| 401 | `HTTP_401` | 토큰 만료·무효 | 토큰 갱신 후 재시도 |
| 404 | `UNKNOWN_PRODUCT` | 서버가 모르는 상품 ID | **버그**. 상품 ID 오타·미등록 |
| 409 | `RECEIPT_OWNED_BY_OTHER` | 다른 계정이 이미 쓴 영수증 | 안내 후 중단. 재시도 금지 |
| 422 | `INVALID_RECEIPT` | 스토어가 무효 판정 | **재시도 금지**. 문의 안내 |
| 422 | `VALIDATION_ERROR` | 필드 누락·형식 오류 | **버그**. 재시도 금지 |
| 503 | `VERIFY_UNAVAILABLE` | 스토어 서버 응답 없음 | **재시도**(지수 백오프) |

> ⚠ **422 와 503 을 반드시 구분하라.** 422 는 몇 번을 보내도 안 되고, 503 은 잠시 뒤
> 된다. 뭉뚱그리면 위조를 무한 재시도하거나 정상 결제를 잃는다.

**503 재시도 지침**

영수증은 기기에 남아 있으므로 유실이 아니다. 앱은 트랜잭션을 **완료 처리하지 말고**
큐에 넣어 재시도한다.

```
1차 즉시 → 실패 시 5초 → 30초 → 2분 → 10분 → 앱 재시작 시 다시
```

성공(200)하기 전까지 iOS `transaction.finish()` / Android `consumeAsync`·`acknowledge`
완료로 넘기지 마라.

### 1.4 ⚠ Android — `verify` 는 선택이 아니다

서버가 구글에 **acknowledge** 를 보내는 일이 이 API 안에서 일어난다.
**결제 후 3일 안에 안 하면 구글이 자동 환불**한다 — 돈은 돌아가고 지급은 남는다.

따라서 Android 는 결제 성공 시 **반드시** `verify` 를 호출하고, 실패하면 §1.3 대로
재시도해야 한다. (애플엔 없는 절차다.)

## 2. `GET /purchases/entitlement`

**"이 회원이 지금 Pro 인가"의 단일 진실.**

### 요청

```http
GET /api/v1/purchases/entitlement
Authorization: Bearer <token>
```

바디 없음.

### 응답 200

```json
{
  "is_pro": true,
  "pro_expires_at": "2026-08-31T09:00:00Z",
  "owned_character_ids": [1, 2, 9]
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `is_pro` | bool | **지금** 유효한 구독이 있는가. 만료 판정은 서버가 한다 |
| `pro_expires_at` | string? | 만료 시각(UTC). `is_pro=false` 면 `null` |
| `owned_character_ids` | int[] | 보유 캐릭터 id 오름차순 |

> ⛔ **앱이 `pro_expires_at` 을 자체 비교해 Pro 여부를 정하지 마라.** 기기 시계는 조작
> 가능하고 시차도 있다. `is_pro` 를 그대로 쓰고, 만료 시각은 "8월 31일까지" 같은
> **표시용**으로만 써라.

### 언제 부르나

| 시점 | 이유 |
|---|---|
| 앱 시작 / 포그라운드 복귀 | 구독이 앱 밖에서 갱신·해지·환불됐을 수 있다 |
| `verify` / `restore` 직후 | 응답에 `entitlement` 가 오므로 **추가 호출 불필요** |
| 구독·아바타 화면 진입 | 최신 상태로 그리기 |

## 3. `POST /purchases/restore`

폰 교체·앱 재설치 후 "구매 복원". 캐릭터가 **영구 소유**라 필수 기능이다.

### 요청

앱이 스토어에서 과거 구매를 전부 꺼내 배열로 보낸다.

```json
{
  "platform": "ios",
  "purchases": [
    { "product_id": "im.beavertalk.character.bibi",
      "transaction_id": "2000000912345678",
      "purchase_token": "..." },
    { "product_id": "im.beavertalk.pro.monthly",
      "transaction_id": "2000000987654321",
      "purchase_token": "..." }
  ],
  "is_sandbox": false
}
```

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `platform` | string | ✅ | `"ios"` \| `"android"` |
| `purchases` | array | ✅ | **1건 이상**. 빈 배열은 422 |
| `purchases[].product_id` | string | ✅ | |
| `purchases[].transaction_id` | string | ✅ | |
| `purchases[].purchase_token` | string | ✅ | |
| `is_sandbox` | bool | ❌ | |

### 응답 200

```json
{
  "restored": 2,
  "failed": 0,
  "entitlement": { "is_pro": true, "pro_expires_at": "...", "owned_character_ids": [1, 2] }
}
```

| 필드 | 설명 |
|---|---|
| `restored` | **새로 지급된** 건수. 이미 갖고 있던 건 포함하지 않는다 |
| `failed` | 무효로 건너뛴 건수 |
| `entitlement` | 복원 후 최신 권한 |

> **일부가 무효여도 200 이다.** 유효한 것만 지급하고 `failed` 로 알린다 — 하나 때문에
> 전체가 실패하면 사용자가 산 것을 못 받는다.
>
> `restored: 0, failed: 0` 은 **"전부 이미 갖고 있었다"** 는 뜻이다(정상). 앱은
> `entitlement` 를 보고 "복원 완료"를 안내하면 된다.

### 에러

| HTTP | `code` | 원인 |
|---|---|---|
| 401 | `HTTP_401` | 토큰 무효 |
| 422 | `VALIDATION_ERROR` | `purchases` 가 비었거나 필드 누락 |

개별 영수증 실패는 에러가 아니라 `failed` 카운트로 나온다.

## 4. 지금 테스트하는 법 (스텁 모드) ⭐

**서버가 배포돼 있고 위 3개 API 가 실제로 동작한다.** 스토어 자격증명이 아직 없어
영수증을 애플·구글에 진짜로 묻지 않을 뿐, **요청·응답은 실제와 100% 동일**하다.

앱은 지금 구매→지급→화면갱신→복원 전 구간을 만들 수 있고, 서버가 실검증으로 바뀌어도
**앱은 고칠 게 없다.**

### 원하는 결과를 만드는 법 — `purchase_token` 접두어

| `purchase_token` | 결과 |
|---|---|
| `invalid...` | **422** `INVALID_RECEIPT` |
| `unavailable...` | **503** `VERIFY_UNAVAILABLE` |
| 그 외 아무 문자열 | **200** 지급 성공 |

`transaction_id` 를 바꾸면 새 구매, 같으면 `already_granted: true`.
없는 `product_id` 로 **404** 도 만들 수 있다.

### curl

```bash
TOKEN=<supabase access token>
BASE=https://beavertalk-app-api-ig4qiawz4q-du.a.run.app/api/v1

# 1) 구매 성공
curl -X POST "$BASE/purchases/verify" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"platform":"ios","product_id":"im.beavertalk.character.bibi",
       "transaction_id":"test-1","purchase_token":"ok"}'

# 2) 같은 영수증 재전송 → already_granted: true
#    (위와 동일하게 한 번 더)

# 3) 무효 영수증 → 422
curl -X POST "$BASE/purchases/verify" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"platform":"ios","product_id":"im.beavertalk.character.popo",
       "transaction_id":"test-2","purchase_token":"invalid-x"}'

# 4) 스토어 불통 → 503 (재시도 로직 테스트)
curl -X POST "$BASE/purchases/verify" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"platform":"ios","product_id":"im.beavertalk.character.rara",
       "transaction_id":"test-3","purchase_token":"unavailable-x"}'

# 5) 권한 조회
curl "$BASE/purchases/entitlement" -H "Authorization: Bearer $TOKEN"

# 6) 복원
curl -X POST "$BASE/purchases/restore" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"platform":"ios","purchases":[
        {"product_id":"im.beavertalk.character.bibi","transaction_id":"test-1","purchase_token":"ok"}]}'
```

⚠ 스텁 지급은 DB 에 `is_stub=true` 로 남아 운영 정산에서 걸러진다. 테스트로 캐릭터를
받아도 문제없다. 초기화가 필요하면 서버에 요청하면 된다.

## 5. 폐기·변경되는 기존 API

| API | 지금 | IAP 후 |
|---|---|---|
| `POST /characters/{id}/purchase` | **동작 — 단 실제 청구 없음**(무료 지급) | 폐기(무료 캐릭터 지급은 유지) |
| `POST /subscriptions` | **동작 — 단 실제 청구 없음** | **폐기** — 클라가 금액을 정하는 구조라 IAP 와 양립 불가 |
| `POST /subscriptions/{id}/cancel` | 동작 | **폐기** — 해지는 스토어에서만 |
| `GET /subscriptions` | 동작 | 유지(내역 조회) |
| `GET /payments` | 동작 | 유지 |

### ⚠ 지금 구매는 **실결제가 아니다**

서버가 카드사·PG·스토어 **어디에도 청구하지 않는다.** 유료 캐릭터도 그냥 지급된다.
앱이 구매 흐름을 지금 만들 수 있게 열어둔 상태다.

응답으로 그 사실을 알려준다:

```json
{
  "member_character": { "member_id": 20, "character_id": 2,
                        "purchase_price": "10.00", "purchase_date": "..." },
  "payment": { "payment_id": 12, "price": "10.00", "payment_date": "...",
               "description": "캐릭터 구매: BIBI" },
  "is_test_grant": true
}
```

| 필드 | 설명 |
|---|---|
| `is_test_grant` | **`true` = 실결제 아님**(테스트 지급). IAP 전환 후 이 필드는 사라진다 |

앱은 이 값으로 "테스트 구매" 배지를 띄우거나 개발 빌드에서만 허용하는 식으로 쓸 수 있다.
서버 로그에도 `⚠ 실결제 아님(IAP 전환 대기)` 경고가 남는다.

⛔ **이 상태로 스토어에 출시하면 안 된다.**

## 6. 앱 구현 체크리스트

- [ ] 상품 ID 를 §0 대로 스토어 콘솔에 등록 (`baba` 제외)
- [ ] 가격은 **스토어에서 조회해 표시** (서버는 IAP 가격을 모른다)
- [ ] 결제 성공 → **즉시 `verify` 호출**
- [ ] `already_granted: true` 를 **성공으로 처리** (에러 토스트 금지)
- [ ] **422 는 재시도 금지 / 503 은 백오프 재시도**
- [ ] `verify` 200 전까지 트랜잭션 완료 처리 보류 (특히 Android)
- [ ] 앱 시작·포그라운드 복귀 시 `GET /purchases/entitlement`
- [ ] `is_pro` 를 그대로 사용 (만료 시각 자체 비교 금지)
- [ ] "구매 복원" 버튼 → `POST /purchases/restore`
- [ ] 해지 안내는 스토어 설정 화면 링크로 (앱에서 해지 불가)
- [ ] 미완료 트랜잭션 재처리 (앱 시작 시 스토어 큐 확인)

| **웹훅**(갱신·해지·환불 수신) | ⬜ 콘솔 등록 대기 | 구독 상태가 자동 반영되지 않음 |
| Pro 혜택(통화 횟수·길이 차등) | ⬜ **미정** | 지금 Pro 를 사도 혜택 없음 |

**웹훅 전까지의 한계**: 사용자가 스토어에서 해지·환불해도 서버가 모른다. 갱신도 앱이
`verify` 를 다시 호출해야 반영된다. 앱은 시작 시 미완료 트랜잭션을 확인해 `verify` 를
보내는 것으로 어느 정도 보완할 수 있다.
