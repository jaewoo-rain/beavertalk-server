## 2. 함정 목록

### F1. `.env` = 운영 / `.env.local` = 개발 — 이름과 반대
`core/config.py` 가 `('.env', '.env.local')` 순으로 읽어 **뒤가 이긴다**.
`.env` 만 읽는 스크립트·도구는 **실서비스 DB 에 붙는다.**

### F2. DB 는 분리돼 있지 않다
`beavertalk-app-api`(실서비스)·`demo-api`·`test-api` 셋 다 같은 Supabase
(`ppllscbfdvebsmdatpnc`) + 같은 시크릿(`beavertalk-app-db-pool`).
→ **demo-api 에서 한 통화·가입·실험은 실서비스 DB 에 남는다.**
→ `/__dev/signup`(신규) 로 만든 데모 계정도 **실 사용자 풀에 생긴다.** 의도된 구성이지만 알고 쓸 것.

### F3. gitignore 된 파일은 워크트리에 안 따라온다 — 그리고 테스트가 죽는다
`herdr` 워크트리(`.herdr/worktrees/...`)에는 `.env`·`.env.local` 이 없다(gitignore).
그래서 워크트리에서 `pytest` 를 돌리면 **수집 단계에서 즉사**한다:
```
ValidationError: 1 validation error for Settings

```
회피(2026-08-06 실행 확인 — `tests/test_cascade_turn.py` 33 passed):
```bash

STT_FAKE=true STT_V2_FAKE=true PYTHONIOENCODING=utf-8 \

```
같은 부류: 플러터 `google-services.json` 이 워크트리에 없어 APK 빌드 실패.

### F4. 데모 페이지가 서버와 다른 Supabase 프로젝트를 본다 → 로그인 후 전부 401/403, **서버 ERROR 로그는 0건**

`WebSocket /api/v1/calls/stream?token=<iss: wbxyhgkmhfbjvqmxlgrh> 403` × 8건.
**전부 `INFO: connection rejected (403 Forbidden)` 라 ERROR 검색으로는 안 잡힌다.**

→ `gcloud builds submit --tag` 로 단일 매니페스트를 만든 뒤 그 태그로 deploy. `scripts/deploy_demo.sh` 가 이 순서다.

### F6. `--set-env-vars` 는 병합이 아니라 **치환**이다
`scripts/deploy_demo.sh:28` 은 `--set-env-vars` 를 쓰지 않는다(이미지 + `--timeout=3600` 만).
그래서 재배포해도 기존 env·시크릿이 **보존된다.**
⚠ 누가 `--set-env-vars` 를 붙이는 순간 **기존 env 가 전부 날아간다**(병합은 `--update-env-vars`).
지금 demo-api 에 걸린 `LIVE_USAGE_TRACE=true` 가 날아가면 15분 실측 통화가
**에러 없이 조용히 무의미해진다**(trace 만 안 찍힘).
→ **프리플라이트 규칙: 배포 명령에 `--set-env-vars` 가 보이면 멈추고 보고.**

### F9. `.gcloudignore` 에 죽은 패턴이 하나 있다 (신규 발견)
```
*service-account*.json# (Cloud Build 업로드 제외 — .dockerignore 와 동일 유지. ...)
```
패턴과 주석이 **같은 줄**에 붙어 있다. gitignore 문법은 줄 중간 `#` 를 주석으로 치지 않으므로
이 줄 전체가 하나의 패턴이 되고 **아무것도 매치하지 않는다** → `*service-account*.json` 은
Cloud Build 업로드에서 **제외되지 않는다.**
현재 워크트리에 해당 이름의 파일이 없어 실피해는 0. 다만 누가 그 이름으로 키를 두면 조용히 빌드에 올라간다.
(`.dockerignore` 쪽은 줄이 분리돼 있어 정상.)
→ 조치: 주석을 다음 줄로 내린다.

### F11. `core/*` 어댑터는 **로그가 안 남는다** (신규 발견 2026-08-06) — 캐스케이드 진단의 함정
`main.py:43 _configure_logging()` 이 INFO 핸들러를 붙이는 로거는 **딱 3개**다:
`domains.learning.realtime` · `domains.learning.service` · `domains.push`.
`core.*` 와 `__main__` 은 목록에 없다 → 루트로 전파되는데 루트에 핸들러가 없다.
- **측정 사실**: `"Vertex genai 클라이언트 생성"`(main), `"tts(gcp): ... ready"`,
  `"[stt-v2] ... ready"` 는 demo-api 14일 · app-api 7일치 로그에 **각 0건**이다.
  그동안 app-api 에서 표현 TTS 는 정상 동작했다 → **고장이 아니라 로그 설정이다.**
- ⚠ 그래서 "`[stt-v2] ready` 가 로그에 없다 = v2 가 안 돈다"는 **틀린 추론**이다.
  (§4 의 옛 항목이 이 오독 위에 서 있었다 — 아래에서 정정한다.)
- **정확한 경계(2026-08-06 19:07 실통화로 확정)**: 파이썬 `logging.lastResort` 의 레벨이
  WARNING 이라 **WARNING 이상만 새어 나가고 INFO 는 통째로 버려진다.**
  - ✅ 나온다: `tts(gcp): 스트리밍 합성 실패(무시) — 400 Unsupported audio encoding.`
    (실제로 이 줄이 TTS 무음 사고를 잡았다. severity 는 비어 있고 `LEVEL:name:` 접두어도
    없다 — 핸들러가 아니라 lastResort 가 stderr 로 쓴 것이라 그렇다.)
  - ⛔ 안 나온다: `core.*` 의 **모든 INFO**. `"tts(gcp): 합성 성공 MP3"` 는 운영 7일치 0건,
    `"Vertex genai 클라이언트 생성"`·`"[stt-v2] ready"` 도 0건이다.
  - ⚠ 그래서 **진단용 로그를 `core/*` 에 `logger.info` 로 넣으면 영영 안 보인다.**
    실제 사례: `core/tts.py:_log_first_bytes` 의 `"스트리밍 첫 조각 앞 8바이트=…"` 는
    `logger.info` 라 통화를 몇 번 해도 안 나온다. `logger.warning` 이어야 보인다.
- **대신 이걸 봐라**(realtime 은 INFO 가 붙어 있어 반드시 남는다):
  ```
  cascade 대답: turn=<id> 첫소리=<ms> 글자=<n> 문장모델=gemini-2.5-flash
  ```
  `첫소리=-1` 또는 `글자=0` 이면 **LLM 또는 TTS 가 실패한 것**이다(200 과 무관).
- 조치안: `_configure_logging` 목록에 `core` 를 추가한다. F4 의 교훈이 반복되고 있다 —
  **실패는 우리가 보는 레벨에 안 찍힌다.**

### F10. `.gcloudignore` 는 `.dockerignore` 와 별개로 유지한다
gitignore 변경이 빌드 업로드를 오염시키지 않게 하기 위해서다.
⛔ `.gitignore` 에 `scripts/` 를 넣지 말 것 — 데모 HTML 이 이미지에서 사라진다.

## 3. 프리플라이트 체크리스트 (배포 요청마다)

1. **대상** — 서비스·리전·프로젝트. prod(`beavertalk-app-api`)면 멈추고 승인 재확인
2. **범위** — `git log <배포본커밋>..HEAD`. 배포본 커밋은 **빌드 시각 ↔ 커밋 시각**으로 특정한다
   (`gcloud builds list` vs `git log --format='%h %ci'`). 태그 이름만 믿지 말 것
3. **env·시크릿** — 새로 요구하는 env 가 있나 / 서비스에 있나 / **명령에 `--set-env-vars` 가 있나(F6)**
4. **gitignore 된 필수 파일** — 이미지에 들어가야 하는데 없는 파일(F7). `git ls-files scripts/` 로 확인
5. **GCP API·권한** — 새로 쓰는 API 활성 여부 + **그 키의 SA 가 실제로 권한이 있나**(활성 ≠ 권한)
6. **스키마 순서** — 코드가 쓰는 컬럼의 마이그레이션이 **먼저** 적용됐나
7. **배포 후 헬스체크** — 스크립트 기본 + **이번 배포가 건드린 엔드포인트 직접**(F8)
8. **실패는 Cloud Logging 원문까지** — 500 이면 예외 문장, 인증이면 **INFO 레벨까지** 훑는다(F4)

  이전 "1.3x" 는 28~44자 짧은 문장 측정이라 **고정 오버헤드(≈1.3초)가 배속을 뭉갠 것**이다.
- 교훈: **여러 지표가 같은 방향을 가리켜도 원인이 확인된 건 아니다.** 두 관측이 같은 교란요인
  (고정 오버헤드·버퍼)을 공유하면 서로를 검증하지 못한다. 원인을 가르려면 **그 요인을 변수로
  바꿔 재는 실험**(길이를 바꿔 배속 측정)이 필요하다 — 이번엔 사장님 지적이 그 방향을 열었다.

#### 🎯 `pcm_24000` 이 정말 PCM16LE 인지 가르는 규칙 (내 실측 바이트에서 도출)
cascade-impl 이 비트 깊이·엔디안을 문서에서 못 찾았다고 했다. 첫 8바이트로 가를 수 있다 —
**PCM16 리틀엔디언은 조용한 구간에서 "매 두 번째 바이트가 `00` 또는 `ff`"** 로 나타난다
(작은 16비트 표본의 상위 바이트 = 부호 확장). 실제로 오늘 잰 값들이 전부 그 패턴이다:
```
Chirp3-HD   01 00 00 00 00 00 00 00   → (01,00)(00,00)(00,00)(00,00)   상위 전부 00
Gemini      b0 ff af ff cc ff f4 ff   → (b0,ff)(af,ff)(cc,ff)(f4,ff)   상위 전부 ff
Gemini(2)   0a 00 f3 ff d7 ff d1 ff   → (0a,00)(f3,ff)(d7,ff)(d1,ff)   상위 00/ff
```
판정:
- **홀수 번째(2,4,6,8번) 바이트가 00/ff** → PCM16 **리틀엔디언** ✅ 그대로 쓰면 된다
- **짝수 번째(1,3,5,7번)가 00/ff** → **빅엔디언**(바이트 스왑 필요) — 안 하면 잡음
- `52 49 46 46`(RIFF) → 헤더 포함(벗겨내야 함)
- 어느 쪽 패턴도 아님 → 16비트가 아닐 가능성(24비트/float) — 그러면 변환 필요
근거 줄: `tts: 스트리밍 첫 조각 engine=eleven_flash_v2_5 앞 8바이트=…`

#### 📌 ElevenLabs 는 **구글이 아니다**
별도 REST API · `xi-api-key` 헤더 · `output_format=pcm_24000`. 오늘 "같은 벤더면 같은 규칙"이
**네 번** 틀렸다(LINEAR16 / 모델 ID / 음성명 형식 / 권한이 Vertex). 아예 다른 벤더면
**같은 규칙일 이유가 애초에 없다** — 첫 호출 로그로 하나씩 확정한다.
