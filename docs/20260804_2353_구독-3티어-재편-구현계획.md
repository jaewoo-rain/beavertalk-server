## 1. 설계 근거

### 1-1. 프론트는 이미 2축이다 — wire 를 그대로 맞춘다

`lib/features/subscription/domain/entities/subscription_state.dart` 첫 문단:

> *"Two axes live here and they are **not** the same thing: `SubscriptionState` — where the
> billing relationship stands. `SubscriptionTier` — which feature set is unlocked."*

그리고 `impliedTier` 가 `grace`·`onHold`·`ending` 에서 **`null`** 을 돌려준다 —
*"those retain whichever plan lapsed, which only the subscription record knows."*

☞ 서버는 제안서의 wire(8종 문자열 + 별도 `plan`)를 그대로 구현하면 되고, **프론트는 안 고친다.**

⛔ **`plan` 은 `grace`·`on_hold`·`ending` 에서 필수다.** 빠지면 클라가
`isPlanInferred=true` 로 **Pro 로 가정**한다(`subscription_status_dto.dart:77`) —
Max 회원이 결제 실패하면 Pro 화면을 보게 된다.

계약(클라 `SubscriptionStatusDto` 기준, 변경 불가):
```
state · plan · subscribe_id · price · start_date · end_date · retrying_until · paused_since
```
`state` 는 8종 snake_case 정확히. 모르는 값이면 클라가 **파싱을 거부하고** 행 목록 추론으로
폴백한다(9번째 상태가 생겨도 유료 회원의 접근권을 빼앗지 않기 위한 설계).

### 1-2. 캐릭터 상품 ID — 이름도 DB id도 안 된다

| 방식 | 문제 |
|---|---|
| 이름 `bt_character_bibi` | 캐릭터 이름은 마케팅 자산이라 바뀔 수 있다. 스토어 상품 ID 는 **영구 불변** |
| DB id `bt_character_2` | **dev/prod 의 character_id 가 다르다**(prod 2·9·10·11 / dev 2·3·4·5 — `iap_catalog.py` 주석). 내부 PK 가 영구 공개 식별자로 샌다 |

→ **불변 슬러그 컬럼 `character.product_key` 신설.** 표시 이름과 DB PK 양쪽에서 분리한다.
- 상품 ID = `bt_character_{product_key}`
- 표시 이름을 바꿔도 상품 ID 불변
- dev/prod 동일 값
- 초기값은 `lower(name)` 백필 → 지금 당장은 동작 변화 0

### 1-3. `product_id` 를 저장한다 (원본 보존)

4종이 되면 `plan`(pro/max)과 주기(monthly/yearly)가 따로 논다. 기획서에 **Pro 연납 마진
3.3%** 이슈가 있어 주기별 집계가 곧 필요하다. 스토어가 준 `product_id` 원본을 그대로
저장하면 둘 다 파생된다 — 이 코드베이스의 *"증거가 원본·나머지는 파생"* 원칙과 같다.

### 1-4. 체험은 **Max** 체험이다

`subscription_state.dart:176` — `SubscriptionState.trial => SubscriptionTier.max`.
프론트가 이미 박아놨다. 스토어 체험은 **Max 상품에 붙여야** 한다. Pro 에 붙이면 앱이
Max 화면을 보여준다. ⚠ 기획서와 교차 확인 필요(§6 미결).

## 2. DB 변경 (Alembic Rev — down_revision `3549a9133f9d`)

### 2-1. `character`
```sql
ALTER TABLE character ADD COLUMN product_key VARCHAR(32);
UPDATE character SET product_key = lower(regexp_replace(name, '[^A-Za-z0-9]', '', 'g'));
-- 백필 검증 후
ALTER TABLE character ALTER COLUMN product_key SET NOT NULL;
CREATE UNIQUE INDEX uq_character_product_key ON character (product_key);
```

### 2-2. `subscribe`
```sql
ALTER TABLE subscribe ADD COLUMN plan           VARCHAR(8)  NOT NULL DEFAULT 'pro';
ALTER TABLE subscribe ADD COLUMN billing_period VARCHAR(8)  NULL;      -- monthly | yearly
ALTER TABLE subscribe ADD COLUMN product_id     TEXT        NULL;      -- 스토어 원본(manual 이면 NULL)
ALTER TABLE subscribe ADD COLUMN source         VARCHAR(8)  NOT NULL DEFAULT 'manual';
ALTER TABLE subscribe ADD COLUMN is_trial       BOOLEAN     NOT NULL DEFAULT FALSE;
ALTER TABLE subscribe ADD COLUMN billing_state  VARCHAR(16) NOT NULL DEFAULT 'ok';
ALTER TABLE subscribe ADD COLUMN retrying_until TIMESTAMPTZ NULL;
ALTER TABLE subscribe ADD COLUMN paused_since   TIMESTAMPTZ NULL;

-- source 백필: IAP 가 만든 행은 price 를 비워 둔다("스토어가 청구한다 — 서버는 금액을
-- 모른다", iap_service._grant_subscription). 레거시 POST /subscriptions 는 항상 금액이 있다.
UPDATE subscribe SET source = 'store' WHERE price IS NULL;
```

**기존 행 소급 해석**: 전부 `pro` · 비체험 · 정상 결제. 현행 판매 상품이 Pro 월납 1종뿐이라
사실과 일치한다.

### 2-3. 하지 않는 것

- **활성 행 부분 UNIQUE 인덱스는 이번에 만들지 않는다.** 기존 데이터에 회원당 활성 행이
  여러 개 있으면 인덱스 생성이 실패한다(레거시 `POST /subscriptions` 가 검사 없이
  만들어 왔다 — 클라 resolver 주석도 이를 전제한다). 데이터 정리는 파괴적 작업이라
  **R6** 대상 → 별도 확인 후 진행. 이번엔 **애플리케이션 레벨 차단**만 건다(§3-4).

## 3. 서버 변경

### 3-1. `iap_catalog.py` — `bt_*` 4종 + product_key

```python
SUBSCRIPTION_PRODUCTS = {
    "bt_pro_monthly":  ("pro", "monthly"),
    "bt_pro_yearly":   ("pro", "yearly"),
    "bt_max_monthly":  ("max", "monthly"),
    "bt_max_yearly":   ("max", "yearly"),
}
PRODUCT_PREFIX_CHARACTER = "bt_character_"
```
`ProductRef` 에 `plan` · `billing_period` 추가. 캐릭터는 `product_key` 로 조회(이름 조회 폐기).

⚠ **구 스킴(`im.beavertalk.*`) 호환은 두지 않는다.** 스토어에 등록된 적이 없어(결제 미연동)
실제 영수증이 존재하지 않는다. 호환을 남기면 두 스킴이 영구히 공존한다.

### 3-2. `GET /subscriptions/status` (신규)

`SubscriptionStatusOut` — §1-1 계약 그대로. 상태 계산은 순수 함수로 분리해 단위 테스트한다.

```
행 없음                                   → free
활성 행(is_activate ∧ end_date 미도래|NULL):
    billing_state == 'on_hold'            → on_hold
    billing_state == 'grace'              → grace
    is_trial                              → trial
    plan == 'max'                         → active_max
    그 외                                  → active_pro
is_activate == False ∧ end_date 미도래     → ending
그 외(행은 있으나 전부 실효)                → expired
```
- 여러 활성 행이면 **가장 최근 것**이 이긴다(클라 resolver 와 같은 규칙 — 두 곳이 어긋나면
  폴백 전후로 화면이 바뀐다).
- `plan` 은 `free`·`expired` 를 뺀 전 상태에서 **반드시** 채운다.

### 3-3. `IapService` — 지급 시 신규 필드 기록

`_grant_subscription(member_id, store_expires_at, ref, product_id)`:
`plan` · `billing_period` · `product_id` · `source='store'` 세팅. 기존 활성 행 연장 시에도
**플랜이 바뀌면 갱신**한다(Pro→Max 업그레이드).

### 3-4. `POST /subscriptions` — 중복 활성 행 차단

기존 활성 행이 있으면 **409**. 레거시 API 지만 살아 있는 동안 상태 모호성의 원천이다.

### 3-5. 티어 배선 — `is_daily_limit_reached`

```python
DAILY_CALL_LIMIT_BY_PLAN = {
    None:  {"normal": 1, "level_test": 1},   # Free
    "pro": {},                                # 무제한
    "max": {},
}
```
회원의 유효 플랜을 조회해 한도를 고른다. **현재 유료 회원이 0명이라 실동작 변화는 없다**
(유료구매 임시차단 중). 결제가 붙는 날 값만 채우면 되도록 배선만 해둔다.

⛔ 유효 플랜 판정은 `grantsPaidAccess` 와 같아야 한다 — **`grace` 는 접근 유지, `on_hold`
는 차단**(프론트 `subscription_state.dart:188`). 두 곳이 어긋나면 "앱은 되는데 서버가 거절".

## 4. 클라 변경 (`beavertalk-flutter`)

### 4-1. 상품 ID 스킴
`IapProductIds.character(characterId)` → `character(productKey)`.

### 4-2. 영수증 서버 검증 연동 (신규)
현재 클라는 서버 IAP 엔드포인트를 **한 번도 부르지 않는다**(호출 0건 확인).
- 구매 성공 → `POST /purchases/verify`
- 복원 → `POST /purchases/restore`

**복원도 반드시 서버를 태운다.** verify 만 태우면 폰 교체 사용자의 복원 기록이 서버에
남지 않아 권한이 유실된다.
