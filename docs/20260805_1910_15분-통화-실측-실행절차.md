```
https://beavertalk-app-demo-api-ig4qiawz4q-du.a.run.app/__levelcalldemo
```

### ⚠미확인 — 배포된 코드의 정확한 커밋

demo-api 최신 리비전 `beavertalk-app-demo-api-00101-pvz`,
이미지 `...:demo-1785885788`, **배포 2026-08-05 06:17 UTC (=15:17 KST)**.
이미지 태그와 배포 시각까지만 확인했고 **어느 커밋인지는 대조하지 못했다.**
다만 오늘 06:35 UTC 통화(call_id=893)의 로그가 `sum_in=` / `sum_out=` 분리 형식으로 찍혀
있어, **최신 계측 코드가 올라가 있는 것은 확실하다**(이 형식이 우리가 필요로 하는 형식이다).

### ✅확인 — 로그인·플랜 조건

- 데모 화면 상단에 이메일/비밀번호가 **미리 채워져 있다**(`test@naver.com` / `11111111`).
  그대로 **[로그인]** 을 누르면 된다.
- **구독(Pro·Max)이 필요 없다.** 통화 길이는 두 경로로 정해지는데,
  ① 구독 플랜(Free 5분 / Pro·Max 15분) ② 데모 화면의 **통화 길이 드롭다운**.
  `ENV=test`(prod 아님)라 ②가 우선하고 서버가 3~15분으로 클램프한다 —
  즉 **드롭다운에서 15분을 고르면 구독과 무관하게 15분이다.**

## 2. 통화 시작 전 — 화면에서 딱 3가지

| # | 항목 | 설정값 | 이유 |
|---|---|---|---|
| 1 | **재측정 강제** 체크박스 | **반드시 끈다(체크 해제)** | ⛔ 켜면 `call_type=level_test` 로 간다. 레벨테스트는 답변 10개에서 자동 종료(하드 턴캡)라 **15분을 못 채우고 실험이 무의미해진다** |
| 2 | **통화 길이** 드롭다운 | **15분** | 3/5/10/15 중 선택. 이게 `duration_min` 으로 서버에 간다 |
| 3 | 학습 언어 / 모국어 | 기본값(한국어 학습) 그대로 | 바꿀 이유 없음 |

⚠ 체크박스를 끈 뒤에도 서버가 레벨테스트로 보낼 수 있다 — **그 계정에 한국어 레벨이 아직
없으면** 자동으로 레벨테스트가 된다. 통화 시작 직후 화면/로그의 `call_type` 이 **`normal`**
인지 확인하고, `level_test` 로 뜨면 그 통화는 버리고 레벨이 있는 계정으로 다시 한다.

## 3. 통화 중에 무엇을 하나 — ⭐ 여기가 실험의 성패다

**쉬지 말고 계속 말해 주셔야 한다.**

이유: 이 실험이 재는 것은 "대화가 쌓여 컨텍스트가 압축 임계(16,000 토큰)에 닿는가"인데,
컨텍스트는 **말한 시간에 비례해** 쌓인다. 실측 증가율은 **초당 18~26 토큰**이다.

| 상황 | 15분 뒤 컨텍스트 | 결과 |
|---|---|---|
| 쉬지 않고 대화 (26 tok/s) | 약 25,000 | 압축 **2회 이상** → 톱니가 뚜렷하게 보인다 ✅ |
| 실측 call 890 수준 (18 tok/s) | 약 17,000 | 압축 1회 → 판정은 되지만 표본이 얇다 |
| 침묵이 많음 | 16,000 미만 | **압축 0회 → 실험 실패, 다시 해야 한다** ❌ |

### 구체적 지침

1. **비버가 말을 마치면 곧바로 대답한다.** 3초 이상 비우지 않는다.
   (10초 넘게 조용하면 서버가 무음 넛지를 넣고, 82초까지 조용하면 통화를 끝내 버린다.)
2. **짧은 대답 금지.** "네", "좋아요" 대신 **두세 문장씩** 말한다. 한국어가 막히면
   모국어로 길게 말해도 된다 — 실험은 내용이 아니라 **말한 양**을 본다.
3. **15분을 끝까지 채운다.** 서버가 먼저 작별을 시작할 때까지 끊지 않는다.
4. **중간에 이걸 관찰해 주셔야 한다(로그로는 안 보인다):**
   - **8분 전후에 목소리가 끊기거나 문장이 잘리는가?** ← 세션 교체(재연결) 지점
   - **재연결 후 비버가 다시 인사하는가?** ("안녕! 오늘은…" 같은 첫인사)
     → 이게 보이면 **15분화 자체를 보류해야 하는 신호**다. 즉시 메모.
   - **재연결 후에도 앞 대화를 기억하는가?** 통화 초반에 "제 강아지 이름은 콩이에요" 같은
     **앵커 3개**를 심어 두고, 12분쯤에 "아까 제 강아지 이름 뭐라고 했죠?" 로 확인.

## 4. 끝난 뒤 — 로그 뽑기

통화가 끝나고 **1분쯤 기다린 뒤**(통화후 저장·분석이 끝나야 요약 줄이 찍힌다) 아래를 그대로 실행한다.

### 4-1. call_id 확인

데모 화면 하단에 통화 결과가 뜨면서 call_id 가 보인다. 안 보이면 아래 명령이 알려준다.

```bash
gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="beavertalk-app-demo-api" AND textPayload:"저장 완료"' \
  --project=bt-dev-web-01 --limit=3 --freshness=1h \
  --format="value(timestamp,textPayload)"
```
→ `normalcall: 저장 완료 call_id=894 segments=97 duration=901s` 처럼 나온다.
**`duration` 이 880 이상이어야 15분을 채운 것이다.**

### 4-2. ⭐ 실험 본체 — 이 한 줄이 전부를 뽑는다

```bash
gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="beavertalk-app-demo-api" AND (textPayload:"normalcall usage" OR textPayload:"세션 스왑" OR textPayload:"세션 재개 핸들" OR textPayload:"GoAway" OR textPayload:"통화 상한" OR textPayload:"저장 완료")' \
  --project=bt-dev-web-01 --limit=100 --freshness=1h \
  --format="value(timestamp,textPayload)" > 15min_call.txt
```

`15min_call.txt` 를 통째로 보내 주시면 된다. 안에 들어 있어야 할 것:

| 줄 | 무엇을 답하나 |
|---|---|
| `normalcall usage: call_id=… sum_in=AUDIO=…,TEXT=… sum_out=AUDIO=…,TEXT=…` | **원가 확정.** 특히 `sum_out` 이 캐스케이드 기준선의 유일한 추정항 |
| `normalcall usage trace: call_id=… t:prompt/total …` | **압축 판정**(톱니 vs 계속 증가). `LIVE_USAGE_TRACE=true` 라 나온다 |
| `normalcall: 세션 스왑 #1 (epoch=1 → 2, handle=있음)` | 재연결이 실제로 일어났는가 |
| `normalcall: 세션 재개 핸들 수신(epoch=…)` | 핸들을 받고 있는가(재연결의 전제) |
| `normalcall: 저장 완료 … duration=…s` | 15분을 채웠는가 |

⚠ **현재 배포 코드에는 "컨텍스트 압축 감지" 로그가 없다.** 그 줄은 이전 버전(call-v2)에
있었고 지금 브랜치에는 빠져 있다(작업2에서 되살리는 중). 그래서 **압축 판정은 아래 §5 의
`trace` 톱니로 한다.**

## 5. 무엇을 보면 판정이 나나 — 숫자 기준

`normalcall usage trace:` 줄은 `경과초:prompt/total` 이 쭉 나열된다. **prompt 값의 모양**만 보면 된다.

```
예) 0.1:1698/1711  4.6:1833/1970  …  610:15702/…  625:11701/…  ← 여기가 톱니(압축)
```

| 관측 | 판정 | 다음 |
|---|---|---|
| prompt 가 **16,000 근처까지 올랐다가 12,000 근처로 뚝 떨어진다**(1회 이상) | **압축이 실제로 자른다 = 레버 실재** | 8k A/B 를 별도 플랜으로 검토(단 **플랜별 트리거**로) |
| prompt 가 16,000 을 **넘어서도 계속 증가**만 한다 | 압축이 안 걸리거나 못 자른다 | **단계 4 폐기** |
| 톱니는 있는데 낙차가 작다(예: 16,000 → 15,000) | 효과 미미 | **단계 4 폐기** |
| prompt 최대가 **16,000 에 못 미친다** | 말수가 부족했다 | **실험 실패 — 다시 통화**(§3 대로 더 많이 말하기) |

참고: 2026-08-04 실측(call 890, 901초)에서는 `15,844 → 11,695` 로 **1회 잘렸다.**
즉 첫 번째 줄(레버 실재)일 가능성이 높고, 이번 통화는 그것을 **더 많은 표본**으로 확인하면서
`sum_in`/`sum_out` 분해를 처음으로 얻는 것이 목적이다.

### 함께 판정되는 것

| 항목 | 보는 곳 | 합격 |
|---|---|---|
| 15분 재연결 안정성 | `세션 스왑` 줄 + 사장님이 들은 것 | 스왑 1~2회 발생 / 갭 1초 미만 / **문장 중간 절단 0회** |
| 재개 후 재인사 | 사장님이 들은 것 | **다시 인사하면 불합격** — 15분화 보류 신호 |
| 재개 후 기억 | 앵커 3개 중 2개 이상 | 3개 중 2개 이상 회상 |
| 캐스케이드 기준선 | `sum_out=AUDIO=…,TEXT=…` | 값이 찍히기만 하면 확정된다 |

## 6. 원가 계산식 (로그를 받으면 이걸로 바로 계산한다)

100만 토큰당 단가(Vertex·AI Studio 동일):

```
cost = sum_in.AUDIO ×$3.00 + sum_in.TEXT ×$0.50
     + sum_out.AUDIO ×$12.00 + sum_out.TEXT ×$2.00     (모두 /1,000,000)
```

## 7. 실패 시 재시도 기준

아래 중 하나면 그 통화는 버리고 다시 한다. (통화 1건 비용은 대략 $1~3)

- `call_type=level_test` 로 갔다 (§2 체크박스)
- `duration` 이 880초 미만이다 (중간에 끊겼거나 무음으로 종료됨)
- `trace` 의 prompt 최대가 16,000 에 못 미친다 (말수 부족)
- `normalcall usage` 요약 줄에 `msgs=0 (usage_metadata 미수신)` 이 찍혔다 (계측 실패)
