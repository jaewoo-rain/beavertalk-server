## 1-A. ⛔ 실측 정정 (2026-08-05 19:10) — 내 §1·§2 에 틀린 것이 둘 있었다

Cloud Run 로그(`beavertalk-app-demo-api`, 30일)를 실제로 조회했더니 **이미 15분 통화 실측이
있었다.** 문서만 보고 "데이터가 없다"고 쓴 것이 첫 번째 잘못이다.

### 실측 원자료 (2026-08-04, demo-api)

| call | 길이 | 세그먼트 | 최대 컨텍스트 | 압축 | 세션 | 모달리티 Σ |
|---|---|---|---|---|---|---|
| **890** | **901s (15분)** | 97 | **15,844 tok** | **1회** | 2개(스왑 1) | TEXT 245,338 / AUDIO 300,628 |
| 891 | 424s (7.1분) | 61 | 12,555 tok | 0회 | 1개 | TEXT 201,810 / AUDIO 192,845 |

```
04:27:10  normalcall: 세션 스왑 #1 (epoch=1 → 2, handle=있음)            ← t+514s
04:31:45  normalcall: 컨텍스트 압축 감지 15844 → 11695 tok (누적 1회)     ← t+789s
```

### 정정 ① — "압축이 한 번도 발동한 적이 없다"는 **틀렸다**

15분 통화(call 890)에서 **실제로 1회 발동했고, 15,844 → 11,695 로 잘랐다.** 낙차 4,149 로
target(12,000) 근처에서 정확히 멈췄다.

☞ 이것이 §3 의 반증 시나리오(커뮤니티 관측 — *슬라이딩 윈도우가 턴 경계에 묶여 target 까지
못 내려간다*)를 **우리 환경에서 기각한다. 압축은 실제로 자른다 = 트리거 레버는 실재한다.**

내 주장이 유효한 범위는 **5분 통화에 한해서**다. 5분 통화의 최대 컨텍스트는 약 9,300 tok 으로
16,000 에 닿지 않는다 — ⚠ **단 이 9,300 은 실측이 아니라 모델 계산이다**(아래 정정 ②).

### 정정 ② — 컨텍스트 증가율이 내 모델(32 tok/s)보다 **느리다**

| 근거 | 계산 | 결과 |
|---|---|---|
| call 890 | (15,844 − 1,428) / 789s | **18.3 tok/s** |
| call 891 | (12,555 − 1,428) / 424s | **26.2 tok/s** |

(지시문 1,428 은 config 메모값. call 891 은 teaching_plan=10 이라 지시문이 더 길 것이므로
실제 증가율은 더 낮다. 보수적으로 **18~26 tok/s**.)

**5분 통화 환산**: 1,428 + 26.2 × 300 ≈ **9,300 tok** → 16,000 미도달 ✓
(§1 의 "5분은 트리거에 안 닿는다"와 `core/config.py` 메모(약 11,000)는 유지된다.)

> ⚠ **9,300 은 실측이 아니라 모델 계산이다.** 5분 통화를 직접 잰 값이 아니라, call 891 에서
> 역산한 증가율(26.2 tok/s)을 300초로 **선형 외삽**한 값이다. 가정 둘이 들어가 있다 —
> ① 컨텍스트 증가가 선형 ② 그 통화의 지시문이 1,428 tok(회원마다 다르다: teaching_plan 3 vs 10).
>
> **확정하는 방법 둘.**
> 1. 15분 실측 통화의 `usage trace` 에서 **t≈300 지점의 prompt 값**을 읽는다 — 외삽 없는
>    직접 측정값이다(세션 스왑은 480~514s 라 300s 판독에 영향 없음).
>    ⚠ 단 그 통화는 절차서대로 쉬지 않고 말하는 통화라 **전형값이 아니라 상한**으로 읽어야 한다.
>    상한이 16k 밑이면 "5분은 압축에 안 닿는다"가 안전하게 확정되고, 넘으면 이 주장을 폐기해야 한다.
> 2. **더 나은 경로** — 계기판 2단계가 배포되면 `call.usage_peak_prompt` 가 통화마다 남는다.
>    `total_time` 이 280~320초인 통화들의 그 값을 집계하면 단발 외삽이 아니라 **실제 분포**가 나온다.
>    peak_prompt 를 JSON 이 아니라 컬럼으로 승격한 이유가 정확히 이 질의다.

### 정정 ③ — "5분 통화 초반 2/3 를 버린다"는 **과장이었다**

압축 1회가 버리는 양은 `trigger − target` = 2,000 tok ≈ **약 77초 분량**이다(26 tok/s 기준).
8k/6k 로 낮추면 5분 통화는 t≈253s 에 압축이 1회 걸려 **가장 오래된 77초**를 잃는다.
통화 초반 2/3 가 사라지는 것이 아니다. §2 표의 정성 서술을 이 값으로 대체한다.

### 실측으로 다시 계산한 8k 하향 효과 (call 890 기준)

| 설정 | 압축 시작 | Σ 입력 토큰(추정) | 비고 |
|---|---|---|---|
| 16k/12k (현행) | t=789s | 약 476,000 | 15분 통화에서 압축이 **단 1회** |
| 8k/6k | t=359s | 약 317,000 | **−33%** |

원가 차이는 모달리티 45:55(TEXT:AUDIO) 가정에서 **통화당 약 −$0.30** — 처음 모델의
−$0.84 의 약 1/3 이다. 그리고 15분 통화 원가 자체도 마스터플랜 추정($2.5~2.9)보다
**낮아 보인다**(모달리티 합 546k 토큰).

⚠ 다만 위 로그의 `모달리티 {...}` 는 **입출력이 합쳐진 한 덩어리**라 원가를 확정할 수 없다.
입력·출력 단가가 4배 차이(오디오 $3 vs $12)라 분해 없이는 곱할 수가 없다.
→ **현재 배포 코드(2026-08-05 06:17 UTC 리비전)는 `sum_in=` / `sum_out=` 을 나눠 찍는다.**
   그래서 실험 1건이 여전히 필요하고, 그 1건이 캐스케이드 원가 기준선의 유일한 추정항
   (Live 15분 **출력** 원가)도 같이 확정한다.

### 결론은 유지, 이유는 교체

- ~~"근거가 없어서"~~ → **"레버는 실재하지만 이익이 통화당 $0.30 수준이고, 원가 구조를
  아직 in/out 으로 못 봤기 때문에"** 지금 적용하지 않는다.
- 그 위에 §2-1 의 비대칭(이익은 장통화, 비용은 전 통화)이 그대로 남는다 → 적용한다면
  **플랜별 트리거**로.

*(아래 §1~§3 은 정정 전 원문이다. 숫자는 위 §1-A 가 우선한다.)*

### ⛔ 여기가 핵심이다

`core/config.py` 의 실측 메모대로, **5분 통화의 최대 컨텍스트는 약 11,000 토큰**이다

> **즉 지금까지의 모든 통화에서 압축은 한 번도 발동한 적이 없다.**
> 우리는 "이 API 의 압축이 실제로 컨텍스트를 자르는가"를 **한 번도 관측한 적이 없다.**

트리거 하향의 절감 효과는 전부 "압축이 발동하면 컨텍스트가 target 까지 실제로 내려간다"는
가정 위에 서 있는데, 그 가정이 우리 환경에서 미검증이다.

## 2. 모델 계산 — 가정이 맞다면 얼마인가

⚠ **아래는 실측이 아니라 모델이다.** 실측으로 읽지 마라. 가정을 명시한다.

| 기호 | 값 | 근거 |
|---|---|---|
| 컨텍스트 성장률 `g` | 32 tok/s | 5분에 오디오+전사로 ~9,600 누적(실측 메모 역산) |
| 턴 간격 `τ` | 13.6 s | 5분 22턴(실측) |
| 시작 컨텍스트 | 1,428 tok | 지시문(실측 메모) |
| 입력 단가(혼합) | $2.625 /1M | 오디오 85%×$3.00 + 텍스트 15%×$0.50 |
| 재과금 모델 | 매 모델 턴마다 컨텍스트 전체가 입력 | Live API 구조 |

압축 후 컨텍스트는 target↔trigger 사이를 톱니로 오간다(평균 `(T+G)/2`).

| 설정 | 압축 시작 | Σ 입력 토큰 | 입력 원가 | 비고 |
|---|---|---|---|---|
| 15분, 압축 없음 | — | 1,047,000 | $2.75 | 참고값 |
| **15분, 16k/12k (현행)** | 455s | **749,000** | **$1.97** | 압축이 이미 28% 깎고 있다(가정대로라면) |
| 15분, 8k/6k | 205s | 429,000 | $1.13 | 현행 대비 **-43%, 통화당 -$0.84** |
| **5분, 16k/12k (현행)** | **미발동** | **137,000** | **$0.36** | 트리거에 닿지 않는다 |
| 5분, 8k/6k | 205s | 120,000 | $0.31 | 현행 대비 **-13%, 통화당 -$0.05** |

*(5분 모델값 137k 는 실측 메모의 209,974 보다 작다. Phase 0 문서가 같은 통화를 재구성해
얻은 Σ 도 142,120 이었고 그 값으로 원가 $0.585 가 실측과 맞았다 — 209,974 의 출처가
무엇인지는 계기판 실측으로만 확정된다. 어느 쪽이든 **아래 결론의 방향은 바뀌지 않는다**.)*

### 2-1. 숫자가 말하는 것 — 전역 하향은 레버의 방향이 틀렸다

```
8k 하향의 이익:   15분 통화 -$0.84   /   5분 통화 -$0.05   (17배 차이)
8k 하향의 비용:   15분 통화 초반 망각  /   5분 통화도 3.4분부터 초반 망각
```

**이익은 장통화(Pro·Max)에 몰려 있는데, 품질 비용은 전 통화(Free 5분 포함)에 걸린다.**
5분 통화는 $0.05 를 아끼자고 통화 초반 2/3의 기억을 버리는 셈이다. 마스터플랜이 단계 4 를
"진짜 위험 지점"이라고 쓴 이유가 정확히 이것이다 — *"15분 기능"인 줄 알았던 변경이 전
일반 통화를 건드린다.*

☞ 설령 §3 실험이 "레버는 실재한다"로 나와도, **전역 env 하향은 채택하면 안 된다.**
  트리거를 **통화 길이(플랜)별로** 갈라야 한다. 구조상 어렵지 않다 —
  `build_live_config` 는 이미 인자를 받고, `call_session` 은 `state.call_duration_s` 를 안다.
  (이건 이번 범위 밖. 실험 결과가 긍정일 때 별도 플랜으로.)

## 3. 반증 — 이 모델이 통째로 틀릴 수 있는 경로

마스터플랜 §1 이 인용한 커뮤니티 실측: **`target_tokens` 를 512 vs 8,000(16배)으로 바꿔도
누적 과금이 거의 같았다**(작은 쪽이 오히려 9% 비쌌다). 추정 원인은 *슬라이딩 윈도우가
USER 턴 경계에서만 자르는데 오디오 턴 하나가 커서 작은 target 에 도달 자체가 불가능*.

그 가설이 맞다면 **trigger 도 같은 이유로 안 들을 수 있다.** 트리거를 낮추면 압축은 더 자주
발동하지만, 한 번에 버릴 수 있는 양이 턴 경계에 묶여 있어 컨텍스트가 target 까지 안 내려간다.
그러면 §2 표의 "톱니 평균 `(T+G)/2`" 전제가 무너지고, 실제 곡선은 **압축을 켜든 안 켜든
계속 자라는 모양**에 가까워진다 — 절감은 0 에 수렴하고, 남는 건 망각뿐이다.

우리 데이터로는 이 갈림길을 **판정할 수 없다.** 5분 통화가 트리거에 닿은 적이 없기 때문이다.

## 4. 결정적 실험 (승인 요청 대상)

**"트리거를 낮추자"가 아니라 "레버가 실재하는지 1통으로 확인하자"** 를 요청한다.

| 항목 | 값 |
|---|---|
| 무엇 | dev 실기기 **15분 통화 1건** |
| 설정 | `LIVE_CTX_TRIGGER_TOKENS=16000` **현행 유지**(하향 없음) + `LIVE_USAGE_TRACE=true` |
| 비용 | 통화 1건 ≈ $2.5~2.9 + 15분 |
| 위험 | 없음 — 설정을 바꾸지 않는다. 로그만 켠다 |

### 판정표 (trace 의 `t:prompt/total` 시계열 한 줄로 끝난다)

| 관측 | 해석 | 다음 행동 |
|---|---|---|
| prompt 가 16k 부근에서 **톱니**(12k 근처까지 낙하) | 압축이 실제로 자른다 = **레버 실재** | 8k A/B 2통으로 진행. 단 §2-1 대로 **플랜별 트리거**로 설계 |
| prompt 가 16k 를 **넘어 계속 증가** | 압축이 안 걸리거나 못 자른다 | **단계 4 폐기.** 절감은 다른 레버(전사 off·프롬프트 축소·캐스케이드)로 |
| 톱니는 있는데 낙차가 작다(예: 16k→15k) | 커뮤니티 관측과 같은 상황 | 하향해도 효과 미미 → **폐기** |

부수 확보(같은 로그 한 줄로): `usage_metadata` 가 증분인지 누적인지(`monotonic`), 15분 통화의
**실제** 원가, GoAway·재연결이 usage 에 어떻게 찍히는지.

### 실험이 곧 싸진다

작업 2(재접지 통합)가 들어가면 `_observe_compression` 이 **모든 통화에서** 압축 감지를
`normalcall: 컨텍스트 압축 감지 #n (prompt A → B)` 로 자동으로 남긴다. 그 뒤로는 이 판정이
전용 실험 없이 평소 로그에서 나온다 — 15분 통화가 dev 에서 돌기 시작하면 자동 축적된다.
