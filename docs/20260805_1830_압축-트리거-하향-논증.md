# 압축 트리거 하향(마스터플랜 단계 4) — 논증 결과: **진행하지 않는다**

작업일시 2026-08-05 18:30 / 브랜치 `feat/call-15min-polish`
상위 계획: `docs/20260804_1930_15분-통화-마스터플랜.md` §2 단계 4 · §1 비용

> **결론 한 줄**: 트리거 하향이 원가를 줄인다는 **우리 환경의 근거가 아직 하나도 없다**.
> 마스터플랜이 정한 진입 조건("단계 0 데이터가 근거를 보여줄 때만")이 충족되지 않았다.
> 대신 **결정적 실험 1건**(dev 15분 통화 1통, 현행 16k 유지)의 승인을 요청한다.

## 0. 선결 조건 — B5 는 채웠다

마스터플랜은 단계 4 착수 전 `build_live_config` / `LIVE_CTX_*` 검증 0건(B5)을 메우라고 했다.
`tests/test_gemini_live_config.py` 13건으로 완료(커밋 `a1ddb8c`). 그중 단계 4 가 실제로
의존하는 것은 두 개다.

- `test_env_override_reaches_the_wire` — env 로 낮춘 값이 실제 config 까지 흘러간다.
  이게 없으면 "8k 로 낮췄다"고 믿으며 16k 로 도는 실험을 할 수 있다.
- `test_target_must_stay_below_trigger` — 잘못된 조합은 기동 시 막힌다(런타임에 조용히 이상하게 돌지 않게).

## 1. 데이터 현황 — 결정적 관측이 **아직 없다**

| 있는 것 | 없는 것 |
|---|---|
| 계기판 코드(단계 0)는 구현 완료 — `normalcall usage:` 요약 + `LIVE_USAGE_TRACE` 시계열 | **실통화 로그 수집이 미실시**(Phase 0 문서 §5-3 "남은 검증(배포 후)") |
| 2026-08-02 call 880 메모: 5분·22턴 / 입력 209,974 tok / 오디오 85% / 약 $0.58 | 계기판 이전 수치라 모달리티 분해·시계열이 없다 |
| — | **15분 통화의 usage 시계열 0건** |

### ⛔ 여기가 핵심이다

`core/config.py` 의 실측 메모대로, **5분 통화의 최대 컨텍스트는 약 11,000 토큰**이다
(지시문 1,428 + 오디오 ~9,300 + 주입 ~300). 현재 트리거는 16,000이다.

> **즉 지금까지의 모든 통화에서 압축은 한 번도 발동한 적이 없다.**
> 우리는 "이 API 의 압축이 실제로 컨텍스트를 자르는가"를 **한 번도 관측한 적이 없다.**

트리거 하향의 절감 효과는 전부 "압축이 발동하면 컨텍스트가 target 까지 실제로 내려간다"는
가정 위에 서 있는데, 그 가정이 우리 환경에서 미검증이다.

## 2. 모델 계산 — 가정이 맞다면 얼마인가

⚠ **아래는 실측이 아니라 모델이다.** 실측으로 읽지 마라. 가정을 명시한다.

| 기호 | 값 | 근거 |
|---|---|---|
| 컨텍스트 성장률 `g` | 32 tok/s | 5분에 오디오+전사로 ~9,600 누적(실측 메모 역산) |
| 턴 간격 `τ` | 13.6 s | 5분 22턴(실측) |
| 시작 컨텍스트 | 1,428 tok | 지시문(실측 메모) |
| 입력 단가(혼합) | $2.625 /1M | 오디오 85%×$3.00 + 텍스트 15%×$0.50 |
| 재과금 모델 | 매 모델 턴마다 컨텍스트 전체가 입력 | Live API 구조 |

압축 후 컨텍스트는 target↔trigger 사이를 톱니로 오간다(평균 `(T+G)/2`).

| 설정 | 압축 시작 | Σ 입력 토큰 | 입력 원가 | 비고 |
|---|---|---|---|---|
| 15분, 압축 없음 | — | 1,047,000 | $2.75 | 참고값 |
| **15분, 16k/12k (현행)** | 455s | **749,000** | **$1.97** | 압축이 이미 28% 깎고 있다(가정대로라면) |
| 15분, 8k/6k | 205s | 429,000 | $1.13 | 현행 대비 **-43%, 통화당 -$0.84** |
| **5분, 16k/12k (현행)** | **미발동** | **137,000** | **$0.36** | 트리거에 닿지 않는다 |
| 5분, 8k/6k | 205s | 120,000 | $0.31 | 현행 대비 **-13%, 통화당 -$0.05** |

*(5분 모델값 137k 는 실측 메모의 209,974 보다 작다. Phase 0 문서가 같은 통화를 재구성해
얻은 Σ 도 142,120 이었고 그 값으로 원가 $0.585 가 실측과 맞았다 — 209,974 의 출처가
무엇인지는 계기판 실측으로만 확정된다. 어느 쪽이든 **아래 결론의 방향은 바뀌지 않는다**.)*

### 2-1. 숫자가 말하는 것 — 전역 하향은 레버의 방향이 틀렸다

```
8k 하향의 이익:   15분 통화 -$0.84   /   5분 통화 -$0.05   (17배 차이)
8k 하향의 비용:   15분 통화 초반 망각  /   5분 통화도 3.4분부터 초반 망각
```

**이익은 장통화(Pro·Max)에 몰려 있는데, 품질 비용은 전 통화(Free 5분 포함)에 걸린다.**
5분 통화는 $0.05 를 아끼자고 통화 초반 2/3의 기억을 버리는 셈이다. 마스터플랜이 단계 4 를
"진짜 위험 지점"이라고 쓴 이유가 정확히 이것이다 — *"15분 기능"인 줄 알았던 변경이 전
일반 통화를 건드린다.*

☞ 설령 §3 실험이 "레버는 실재한다"로 나와도, **전역 env 하향은 채택하면 안 된다.**
  트리거를 **통화 길이(플랜)별로** 갈라야 한다. 구조상 어렵지 않다 —
  `build_live_config` 는 이미 인자를 받고, `call_session` 은 `state.call_duration_s` 를 안다.
  (이건 이번 범위 밖. 실험 결과가 긍정일 때 별도 플랜으로.)

## 3. 반증 — 이 모델이 통째로 틀릴 수 있는 경로

마스터플랜 §1 이 인용한 커뮤니티 실측: **`target_tokens` 를 512 vs 8,000(16배)으로 바꿔도
누적 과금이 거의 같았다**(작은 쪽이 오히려 9% 비쌌다). 추정 원인은 *슬라이딩 윈도우가
USER 턴 경계에서만 자르는데 오디오 턴 하나가 커서 작은 target 에 도달 자체가 불가능*.

그 가설이 맞다면 **trigger 도 같은 이유로 안 들을 수 있다.** 트리거를 낮추면 압축은 더 자주
발동하지만, 한 번에 버릴 수 있는 양이 턴 경계에 묶여 있어 컨텍스트가 target 까지 안 내려간다.
그러면 §2 표의 "톱니 평균 `(T+G)/2`" 전제가 무너지고, 실제 곡선은 **압축을 켜든 안 켜든
계속 자라는 모양**에 가까워진다 — 절감은 0 에 수렴하고, 남는 건 망각뿐이다.

우리 데이터로는 이 갈림길을 **판정할 수 없다.** 5분 통화가 트리거에 닿은 적이 없기 때문이다.

## 4. 결정적 실험 (승인 요청 대상)

**"트리거를 낮추자"가 아니라 "레버가 실재하는지 1통으로 확인하자"** 를 요청한다.

| 항목 | 값 |
|---|---|
| 무엇 | dev 실기기 **15분 통화 1건** |
| 설정 | `LIVE_CTX_TRIGGER_TOKENS=16000` **현행 유지**(하향 없음) + `LIVE_USAGE_TRACE=true` |
| 비용 | 통화 1건 ≈ $2.5~2.9 + 15분 |
| 위험 | 없음 — 설정을 바꾸지 않는다. 로그만 켠다 |

### 판정표 (trace 의 `t:prompt/total` 시계열 한 줄로 끝난다)

| 관측 | 해석 | 다음 행동 |
|---|---|---|
| prompt 가 16k 부근에서 **톱니**(12k 근처까지 낙하) | 압축이 실제로 자른다 = **레버 실재** | 8k A/B 2통으로 진행. 단 §2-1 대로 **플랜별 트리거**로 설계 |
| prompt 가 16k 를 **넘어 계속 증가** | 압축이 안 걸리거나 못 자른다 | **단계 4 폐기.** 절감은 다른 레버(전사 off·프롬프트 축소·캐스케이드)로 |
| 톱니는 있는데 낙차가 작다(예: 16k→15k) | 커뮤니티 관측과 같은 상황 | 하향해도 효과 미미 → **폐기** |

부수 확보(같은 로그 한 줄로): `usage_metadata` 가 증분인지 누적인지(`monotonic`), 15분 통화의
**실제** 원가, GoAway·재연결이 usage 에 어떻게 찍히는지.

### 실험이 곧 싸진다

작업 2(재접지 통합)가 들어가면 `_observe_compression` 이 **모든 통화에서** 압축 감지를
`normalcall: 컨텍스트 압축 감지 #n (prompt A → B)` 로 자동으로 남긴다. 그 뒤로는 이 판정이
전용 실험 없이 평소 로그에서 나온다 — 15분 통화가 dev 에서 돌기 시작하면 자동 축적된다.

## 5. 요약 — 사장님 결정이 필요한 것

1. **단계 4(트리거 하향)는 지금 진행하지 않는다.** 근거 데이터가 없다(마스터플랜의 진입 조건 미충족).
2. 승인 요청: **dev 15분 통화 1건 + `LIVE_USAGE_TRACE=true`**(설정 변경 없음, 위험 없음).
3. 실험이 긍정이어도 **전역 하향은 채택하지 않는다** — 플랜별 트리거로 가야 한다(별도 플랜).
4. 코드는 되돌릴 수 있는 상태로 유지된다: `LIVE_CTX_TRIGGER_TOKENS` 는 이미 env 이고,
   env 값이 실제로 반영되는지는 B5 테스트가 지킨다.
