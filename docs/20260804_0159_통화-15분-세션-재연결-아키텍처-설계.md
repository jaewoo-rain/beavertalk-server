# 통화 15분화 — Live 세션 재연결(session_resumption) 아키텍처 설계

> 2026-08-04. **설계 문서(구현 아님).** 대상: `domains/learning/realtime/call_session.py`,
> `core/gemini_live.py`. R4 대상(2펌프·절대 백스톱·barge-in off·종료 규약에 손을 댄다).
> 이 문서의 "사실"은 전부 코드/설치된 SDK/공식 문서에서 직접 확인한 것이고,
> 확인 못 한 것은 **[추측]** 또는 **[미검증]** 으로 표시했다.

## 0. 한 줄 요약

세션을 갈아끼우는 축을 **"세션 슬롯 간접 참조"가 아니라 "세대(generation) 루프 + 세대마다 TaskGroup 재생성"**
으로 잡는다. 세션 객체는 절대 공유·별칭되지 않고 각 세대의 지역 변수로만 존재하며,
통화 상태(`_CallState`)만 세대를 건너 살아남는다. 스왑은 **턴 경계에서만**, **종료 구간에서는 절대**
일어나지 않는다. 핸들이 없거나 재연결이 실패하면 **오늘의 우아한 종료 경로 그대로** 폴백한다.

## 1. 목표 / 비목표

### 목표
- normal 통화 길이 5분 → **15분**(`CALL_DURATION_S 300 → 900`).
- Gemini Live 연결 수명 ~10분을 **세션 재개(session_resumption)** 로 넘어, 통화 하나가 여러 연결에 걸치게 한다.
- 학습자에게 연결 교체가 **들리지 않게** 한다(문장 절단 0, 오디오 손실 0, 이중 인사 0).
- 재연결이 안 되면 통화가 **깨지지 않고 짧아지기만** 한다(R5).

### 비목표(이번 설계 범위 밖 — 별도 판단 필요)
- 15분 대화의 **내용 품질**(드리프트·재접지 주기·프롬프트 다이어트). 재접지 비율(0.5/0.8)은 그대로 스케일만 하고, 튜닝은 실측 후 별도.
- 레벨테스트(3분 하드캡)는 **손대지 않는다** — 8분 스왑 임계에 닿지 않아 코드 경로가 전혀 바뀌지 않는다(회귀 논거).
- 클라(Flutter) 프로토콜 변경. v1은 **무변경**.
- 통화후 분석 파이프라인의 3배 부하 대응(§9에 위험만 기록).

## 2. 현재 구조 분석 (코드 근거)

### 2.1 실행 토폴로지
```
run_call                                   # state = _CallState() 는 여기서 생성 — 세션 바깥
 └ asyncio.timeout(absolute_timeout)       # = max(540, call_duration_s + 22 + 30)
    └ _run_session
       └ async with live_session_factory(...) as session      # ← 세션 = 이 CM 의 수명
          └ async with asyncio.TaskGroup() as tg:
               ├ _pump_client_to_gemini(client_ws, session, state)
               ├ _pump_gemini_to_client(client_ws, session, state)
               ├ _watch_call_clock(state, session)
               ├ _watch_idle(session, state)
               ├ _reground_once(session, state)
               └ _periodic_flush(db_factory, state, call_id, member_id)
             await session.send_text_turn(seed_text)          # 선톡
          except* _CallFinished / except* _ClientDisconnect → 홑겹 재전파
 └ finally: 힌트·밴드 task 취소 → flush → 분석/업로드/국적 fire-and-forget → _finish_call
```

**핵심 사실 6가지**
1. `state` 는 `run_call` 지역 변수다(`call_session.py:677`). 즉 **세션 교체와 무관하게 이미 통화 전체를 산다** — 재연결 설계에서 가장 큰 선물이다.
2. 6개 태스크가 전부 `session` 객체를 **인자로 직접 잡는다**. 세션을 바꾸려면 (a) 태스크를 다시 만들거나 (b) 인자를 간접화해야 한다. 중간은 없다.
3. `_pump_gemini_to_client` 는 `session.events()` 소진 시 `_CallFinished` 를 던진다(`:1603-1604`). **연결이 끊기면 = 통화 끝**이 지금의 규약이다.
4. GoAway 는 이미 정규화돼 있고(`gemini_live.py:220-225`) 펌프가 **종료 파이프에 합류**시킨다(`:1536-1541`): `should_close=True` → idle 이면 즉시 시드, 발화중이면 다음 `turn_end` 에서. **스왑 트리거가 필요로 하는 "턴 경계 지연 실행" 패턴이 이미 검증된 채로 있다.**
5. 종료 규약의 단일 소유권 가드는 `close_seed_sent`(await 전 선점, `:1721-1726`). 종료 후보는 시계워처·펌프·무음 3단·밴드 사이드카 4곳인데 이 한 플래그로 직렬화된다.
6. 힌트/밴드 사이드카는 **TaskGroup 밖**에서 `create_task` 된다(`_analysis_tasks`/`state.hint_tasks`/`state.band_tasks`). 밴드 사이드카는 `session` 을 잡고 있고 `_inject_close_seed(session, ...)` 까지 호출한다(`:1449-1455`) — **세션 교체 시 죽은 세션을 참조할 유일한 경로**다.

### 2.2 지금 값들
| 상수 | 값 | 의미 |
|---|---|---|
| `CALL_DURATION_S` | 300 | 통화 시계(종료 시드 시점) |
| `LEVELTEST_MAX_S` | 180 | 레벨테스트 하드캡 |
| `ABSOLUTE_CALL_TIMEOUT_S` | 540 | 절대 백스톱 하한. **근거가 "연결 ~10분 선점"** |
| `SEED_TO_HANGUP_S` | 22 | 시드 후 강제 종료까지 |
| `FLUSH_INTERVAL_S` | 60 | 점진 저장 |
| `IDLE_NUDGE1/2/CLOSE_S` | 60/10/12 | 무음 3단 |
| `REGROUND_AT_FRACTION` / `_LATE_` | 0.5 / 0.8 | 재접지 시점(비율이라 자동 스케일) |

`absolute_timeout = max(540, duration + 22 + 30)` 이라 15분이면 **952초로 이미 자동 스케일**된다. 다만
`except TimeoutError` 로그가 `absolute_timeout` 이 아니라 상수 `ABSOLUTE_CALL_TIMEOUT_S` 를 찍는다(`:762`) —
**기존 경미 버그**(15분에선 "540s 초과"라고 거짓말한다). 이번에 같이 고친다.

### 2.3 지금 15분을 그냥 켜면 무슨 일이 나나 (예상 타임라인)
```
t=0     연결 open, 선톡 → 통화 시계 시작
t~540   asyncio.timeout(952) 아직 멀었음 → 통화 계속
t~480~540  Gemini: goAway(timeLeft≈60s)      [문서상 60초 전 예고 — 미검증]
        → 펌프: should_close=True → 종료 시드 → 비버 작별 → _CallFinished
결과: 15분으로 설정해도 통화는 ~9분에 "정상 작별"로 끝난다. (뚝 끊기진 않는다)
GoAway 없이 끊기면: events() 소진/ConnectionClosed → _CallFinished 또는 generic except
        → 작별 없이 종료(뒤처리는 정상). 사용자는 "갑자기 끊겼다"고 느낀다.
```
즉 **지금도 안 죽는다. 짧아질 뿐이다.** 이 사실이 이번 작업의 안전망 기준선이다 —
재연결 실패 시 언제나 이 상태로 되돌아가면 된다.

## 3. SDK·서버 사실 확인

### 3.1 검증됨 (설치된 google-genai 2.10.0 직접 조회)
- `types.SessionResumptionConfig(handle: str|None, transparent: bool|None)` 존재.
- `types.LiveConnectConfig.session_resumption` 존재(현재 미설정).
- `LiveServerMessage.session_resumption_update: LiveServerSessionResumptionUpdate(new_handle, resumable, last_consumed_client_message_index)` 존재, Vertex 응답 변환기에 매핑돼 있음(`_live_converters.py:1483,1542`).
- `LiveServerMessage.usage_metadata` 존재(현재 미사용).
- **`transparent=True` 는 Vertex(=Gemini Enterprise Agent Platform)에서만 허용**. mldev(API key) 경로는 SDK가 `ValueError` 로 막는다(`_live_converters.py:1821-1825`). 우리는 `genai.Client(vertexai=True)`(`main.py:104-109`) 라 **SDK 레벨에선 사용 가능**.
- Vertex 경로는 `session_resumption` 을 그대로 `setup.sessionResumption` 으로 흘린다(`_live_converters.py:1135-1140`).
- SDK 는 `websockets` 로 붙고 keepalive 는 라이브러리 기본값 `ping_interval=20 / ping_timeout=20` — **죽은 피어 감지 ~20~40초**(TCP 블랙홀 시 이 시간 후에야 스트림이 끊긴다).
- `starlette.WebSocket.receive()` 는 메시지를 받은 **뒤에만** 상태를 바꾼다 → 대기 중 취소해도 상태가 깨지지 않고 재진입 가능. uvicorn 의 `asgi_receive` → `websockets.recv()` 는 수신 메시지를 deque 에 쌓아두므로 **취소로 프레임이 유실되지 않는다**(TCP 백프레셔로 늦게 올 뿐).

### 3.2 공식 문서 (인용 — 우리 모델에서 재확인 필요)
- 연결 수명 "around 10 minutes", 압축 없으면 오디오 세션 15분 한계, 압축 켜면 세션 무제한. (ai.google.dev/gemini-api/docs/live-session)
- goAway 는 **종료 60초 전** 전송, `timeLeft` 포함. (Vertex 문서 요약)
- transparent 모드: `last_consumed_client_message_index` 로 미소비 메시지 재전송. **클라 인덱스는 1부터, 재개마다 1로 리셋**, 0은 "재개 불가" 의미.
- 핸들 유효기간: AI Studio 문서는 "24시간", 다른 요약본은 "마지막 세션 종료 후 2시간". **불일치** — 우리는 수 초 내 재개라 무관.

### 3.3 미검증 (이 설계의 최대 리스크)
1. **`gemini-live-2.5-flash-native-audio`(Vertex)가 sessionResumption 을 실제로 지원하는지.** 커뮤니티에 native-audio + resumption 조합에서 반복 `1011 Internal error` 보고가 있다.
2. `sessionResumptionUpdate` 가 **얼마나 자주** 오는지(턴 경계마다? N초마다?) → make-before-break 의 핸들 신선도를 좌우한다.
3. 재개 시 **새 setup 의 system_instruction 이 어떻게 합쳐지는지**. 우리 프롬프트는 "먼저 작별하지 마라 / 통화 길이를 모른다"를 포함하므로 **재주입 자체는 오히려 공짜 재접지**일 수 있다. 반대로 모델이 "새 대화 시작"으로 오해해 **다시 인사(이중 인사)** 하면 치명적.
4. **context_window_compression 과 resumption 의 상호작용**(압축된 컨텍스트가 핸들에 담기는가).
5. **재개가 컨텍스트를 재과금하는가.** 통화 원가의 81%가 입력 토큰인데(CLAUDE.md), 스왑마다 전체 컨텍스트를 다시 먹으면 원가 구조가 흔들린다.
6. 스왑 직후 **버스트 오디오(백프레셔로 밀린 0.5~1.5초치)** 를 한꺼번에 밀어 넣을 때 VAD 가 정상 분절하는지.

→ **§10 스파이크(반나절)로 1·2·3·5를 먼저 재는 것을 선결 조건으로 둔다.** 특히 1이 아니면 이 설계 전체가 무의미하다.

## 4. 설계

### 4.1 세션 참조 간접화 — 두 안 비교

#### 안 A. 세대 루프(TaskGroup 을 세션마다 재생성) ★추천
```
_run_session
 └ AsyncExitStack                      # 세대별 세션 CM 소유
    └ while True:                      # 세대 루프
         session = await 열기(handle)  # 세대 N
         try:  await _run_generation(session, state, ...)   # ← 오늘의 TaskGroup 본문 그대로
         except _SessionSwap: 세대 정리 → epoch += 1 → continue
```
- 세션은 **각 세대의 지역 변수**. 태스크는 인자로 받은 그 세션만 안다 → **별칭(aliasing) 0, 좀비 0**.
- 세대 경계에서 TaskGroup 이 모든 자식을 확실히 회수한 **뒤에** 다음 세션을 연다 → 두 세대가 겹치지 않는다(구조적 보장).
- 오늘의 `_run_session` 본문이 `_run_generation` 으로 **거의 그대로** 이동 → 코드 diff 가 작고 검증된 경로가 보존된다.
- 대가① 워처 4개가 재시작된다 → **재시작 멱등성 감사 필요**(§4.7 표).
- 대가② 클라→Gemini 펌프도 재시작 → 스왑 구간(수백 ms) 동안 `ping`/`playback_done` 응답이 지연되고, 클라 오디오는 ASGI/TCP 버퍼에 쌓였다가 재개 후 몰려서 전달된다(무손실, 지연만).

#### 안 B. 활성 세션 슬롯(단일 TaskGroup + 간접 참조)
```
link = _LiveLink()      # .current, .epoch, .swap_lock
TaskGroup 은 통화당 1회만 생성. 모든 send 는 link.current 를 그때그때 읽는다.
Gemini→클라 펌프만 내부에서 세대 루프를 돈다.
```
- 장점: 클라 펌프가 안 끊긴다(핑 응답·명시적 오디오 버퍼링·순서 제어를 우리가 100% 통제).
- 단점①: **송신 지점이 5곳 이상**(`send_audio`, `send_text_turn` ×4 용도, `send_reground`, `send_tool_response`) — 전부 "지금 슬롯이 교체 중인가"를 신경 써야 한다. 한 곳만 빠뜨리면 **죽은 세션에 주입** = 이 프로젝트가 반복해서 낸 사고 유형 그대로.
- 단점②: Gemini 펌프가 세션 종료를 내부에서 삼키므로 **"펌프 하나가 죽으면 전부 죽는다"** 는 TaskGroup 불변식이 약해진다(R4 의 핵심 근거가 흐려진다).
- 단점③: 스왑 중 상태(“교체 진행 중”)가 새 전역 상태로 추가되고, 종료 경로와 교차한다 → 상태 조합 폭발.

#### 안 C. 하이브리드(바깥 TaskGroup=통화 수명 태스크, 안쪽 TaskGroup=세대 태스크)
- UX 최적(클라 펌프 유지 + 세대 격리)이지만, **불변식이 2계층으로 쪼개지고** 통화 수명 태스크는 결국 안 B 의 간접 참조를 그대로 필요로 한다. 복잡도 대비 이득이 스왑 구간 수백 ms 뿐.

#### 결정: **안 A**
근거: 이 프로젝트가 실제로 데인 사고는 "핑이 늦어서"가 아니라 **좀비 세션·종료 레이스·클로징 중 상태 덮어쓰기**였다. 안 A는 그 세 종류를 *구조적으로* 불가능하게 만든다(세션이 공유되지 않으므로 별칭이 존재할 수 없다). 안 B/C가 사는 이득(스왑 구간 수백 ms의 매끄러움)은 §4.4의 make-before-break 로 대부분 회수할 수 있다.
**되돌아갈 길**: 안 A → 안 C 로의 이행은 `_run_generation` 을 쪼개는 리팩터라 가능하다. 실측에서 갭이 문제로 확인되면 그때 올라간다.

#### 좀비 방지 규칙(안 A에서 명문화)
- **R-Z1** 다음 세대의 세션은 **이전 세대의 TaskGroup 이 완전히 종료된 뒤에만** 연다(make-before-break의 사전 연결은 "세션을 미리 열어둘 뿐, 아무 태스크도 그것을 읽지 않는다" — 읽는 주체가 하나뿐이라는 불변식은 유지).
- **R-Z2** 이전 세션은 `AsyncExitStack` 의 콜백으로 **명시적으로 닫는다**. `asyncio.wait_for(aclose, 2.0)` + `suppress(Exception)` — 닫기가 멈춰도 통화를 못 붙잡게(닫기 타임아웃은 경고 로그).
- **R-Z3** `state.session_epoch` 를 모든 스왑 로그에 찍는다. 늦게 도착한 태스크는 epoch 비교로 no-op.
- **R-Z4** **사이드카는 세션을 잡지 않는다.** 밴드 사이드카(`_band_observe_sidecar`)에서 `_inject_close_seed(session, ...)` 를 제거하고 `should_close=True` 만 세우게 바꾼다 — 주입은 이미 그 일을 하는 시계워처가 한다(`_watch_call_clock` 의 seed-wait 루프). 레벨테스트 전용 경로라 15분과 무관하지만, **세션을 잡은 유일한 사이드카**이므로 이번에 정리한다.

### 4.2 핸들 생명주기

```python
# core/gemini_live.py
LiveEventKind = Literal[..., "resume_update"]

@dataclass(slots=True)
class LiveEvent:
    ...
    handle: Optional[str] = None            # kind=="resume_update": new_handle
    resumable: Optional[bool] = None

```

```python
# _CallState 추가 필드 (전부 통화 수명 — 세대를 건너 산다)
resume_handle: Optional[str]   # 최신 new_handle (resumable 일 때만 갱신)
resumable: bool = True         # 서버가 재개 불가라 하면 False → 스왑 영구 금지
swap_pending: bool = False     # 턴 경계에서 갈아끼우라는 arm
swap_reason: str = ""          # goaway | scheduled | stream_end | send_error
swap_count: int = 0
last_swap_ts: Optional[float]
session_epoch: int = 0
gen_started_ts: float          # 이 세대 연결 시각(예정 스왑 계산 기준)
```

수신 처리(펌프에서, forward 대상 아님 — 클라로 안 나간다):
```
event.kind == "resume_update":
    if event.resumable is False or not event.handle:
        state.resumable = False            # 서버가 "재개 불가" → 스왑 금지, 오늘 동작으로 폴백
        logger.warning(...)                # 알람 대상: 15분 기능이 조용히 죽은 것
    else:
        state.resume_handle = event.handle # 최신값으로 덮어씀(가장 신선한 것 1개만 보관)
```

**핸들 없음/거부 시 정책 — "새 세션"은 절대 만들지 않는다.**
핸들 없이 새 세션을 열면 컨텍스트가 통째로 날아가 비버가 **처음부터 다시 인사**한다.
그건 뚝 끊기는 것보다 나쁘다(사용자는 "AI가 미쳤다"고 느낀다).
따라서 폴백은 **항상 "오늘의 우아한 종료"** 다:
| 상황 | 처리 |
|---|---|
| 아직 핸들 못 받음 | 스왑 arm 자체를 안 함 → GoAway 오면 오늘 경로(작별 후 종료) |
| `resumable=False` | `state.resumable=False` → 이후 스왑 영구 금지 |
| 재연결 connect 실패/타임아웃 | 1회 재시도(0.5s 후) → 그래도 실패면 `_CallFinished`(세션이 이미 죽어 시드 주입 불가) |
| 재연결 직후 즉시 close(1008/1007/1011) | 실패로 계산 → 예산 소진 시 종료 |
| 예산·플래핑 가드 걸림 | 세션이 살아있으면 **종료 시드 → 정상 작별**, 죽었으면 `_CallFinished` |

### 4.3 전환 타이밍 (트리거 3종 + 턴 경계 게이트)

**트리거 우선순위: `_CallFinished`/`_ClientDisconnect` > 종료(should_close) > 스왑 > 무음 넛지 > 재접지.**

| 트리거 | 발원지 | 성격 |
|---|---|---|
| ① 예정 스왑(주) | `_watch_generation_clock`(신규 태스크) — `PER_SESSION_MAX_S=480` 경과 | **예측 가능·테스트 가능**. GoAway 의 문서화 안 된 타이밍에 의존하지 않는다 |
| ② GoAway(보조) | 펌프의 기존 `go_away` 분기 | 예상보다 빨리 끊길 때. `time_left` 는 **파싱하지 않는다**(형식 미검증) — "지금 곧"으로만 취급 |
| ③ 스트림 종료/송신 오류(폴백) | 펌프 `events()` 소진·예외, `send_audio` 예외 | §4.5 |

**턴 경계 게이트 — 기존 종료 패턴 그대로 재사용.**
```
_arm_swap(state, reason):
    ok, why = _may_swap(state)              # closing / no_handle / budget / flapping
    if not ok:
        if why != "closing": state.should_close = True   # 기존 종료 파이프에 합류
        return
    state.swap_pending = True; state.swap_reason = reason
    # 깨끗한 경계면 즉시, 아니면 펌프가 turn_end 에서
```
펌프의 `turn_end` 분기에 **종료 다음 순서로** 한 줄 추가:
```
if state.close_seed_sent: ...      # (1) 오늘 그대로
elif state.should_close: ...       # (2) 오늘 그대로 — 종료가 스왑보다 항상 우선
elif state.swap_pending: raise _SessionSwap(state.swap_reason)     # (3) 신규
elif state.tag_leak_seen: ...      # (4) 오늘 그대로
```
"깨끗한 경계" 정의는 종료 시드와 **같은 조건**을 쓴다: `state.turn_id is None and not state.user_turn_open`.
(= 비버도 안 말하고, 학습자 발화 응답 대기도 없음. `call 197` 종료 레이스에서 이미 값을 치른 조건이다.)

**스왑 직전에 반드시 하는 것 — 열린 턴 로컬 종결.**
더러운 경계(네트워크 끊김)에서 `state.turn_id` 가 남아 있으면:
- 클라는 `turn_end` 를 영영 못 받아 재생 상태기계가 열린 채로 남고,
- 서버는 `turn_id != None` 이라 **barge-in off 게이트가 마이크를 영구히 막는다** → 무음 통화.

따라서 스왑 처리 진입부에서:
```
_close_open_turn_locally(client_ws, state):
    if state.turn_id: send ServerTurnEnd(turn_id) ; state.turn_id = None
    _flush_beaver_segment(state)          # 잘린 발화도 전사에 남긴다
    state.last_activity_ts = now          # 스왑은 '무음'이 아니다
```

### 4.4 오디오 갭

#### 갭의 정체
스왑은 **턴 경계**에서 일어난다 = 비버 오디오는 이미 끝났고 학습자는 말하기 직전/직후다.
따라서 "비버 목소리가 잘리는 갭"은 원리적으로 없다. 남는 건 **학습자 오디오가 모델에 도달하는 지연**뿐이다.

#### 클라 오디오 처리 — 명시 버퍼가 필요 없다
안 A에서 클라 펌프가 잠시 멈추면, 클라 오디오는 **TCP → websockets deque → ASGI 큐**에 쌓였다가
펌프 재개 후 순서대로 읽힌다(§3.1 검증). 즉:
- **손실 0**(TCP), **순서 보존**, **중복 0**.
- 그리고 결정적으로: **옛 세션이 이미 소비한 오디오를 다시 보내는 일이 없다** — 우리가 보내기를 멈춘 시점 이후의 오디오만 새 세션으로 간다.
- → **`transparent=True` + `last_consumed_client_message_index` 가 v1에 필요 없다.** transparent 가 해결하는 문제(미소비분 재전송)를 "우리가 끊는 시점을 우리가 고른다"로 이미 푼 것이다. 인덱스 부기(오디오 청크마다 인덱스 + 미ack 링버퍼 + 재개 시 리플레이)는 실패 지점만 늘린다.
- transparent 는 **§4.5 예상치 못한 끊김**에서만 이득이 있고, 그때 잃는 건 마지막 0.5~2초 사용자 오디오다. **v2 후보로 보류**.

#### 갭 추정 [추측 — 실측 필요]
실측된 "세션 열기+첫 토큰 1.5초"를 분해하면:
```
TLS+WS 핸드셰이크(동일 리전)  ~100~300ms
setup 전송 + setup ack        ~100~300ms      → 여기까지 되면 오디오 송신 재개 가능
첫 토큰 생성                   ~900~1300ms     → 스왑에는 불필요(비버가 말할 차례가 아님)
```
- **break-then-make**: 오디오 재개까지 **0.3~0.8초** [추측]. 학습자가 그 사이 말하면 그 오디오는 버퍼링됐다가 몰려 들어가므로 **응답 지연 +0.3~0.8초**로 체감.
- **make-before-break**: 새 연결을 미리 열어두면 전환 순간은 "지역 변수 교체 + 태스크 재생성" 뿐 → **50~150ms** [추측].
- 정확한 신뢰 자격증명 갱신(`_ensure_fresh_credentials`)이 만료 토큰을 만나면 여기에 수백 ms 가 더 붙는다(스왑 전 미리 갱신해 두면 회피 가능).

#### make-before-break 설계(단계 2에서 추가)
```
_watch_generation_clock 이 PER_SESSION_PREOPEN_S(예: 450s) 에 도달하면:
    next_session = await stack.enter_async_context(factory(..., resume_handle=state.resume_handle))
    state.next_session_ready = True          # 아직 아무도 이 세션을 읽지 않는다
그 다음 깨끗한 턴 경계에서 _SessionSwap → 세대 루프가 next_session 을 그대로 채택
```
- 사전 연결은 **읽는 주체가 없다**(R-Z1 위반 아님). 세션을 읽는 태스크는 언제나 정확히 하나의 세대뿐.
- 사전 연결 세션의 ~10분 수명도 그때부터 흐른다 → 사전 연결은 **30초 이내**로 짧게(450s→480s).
- 사전 연결 후 스왑 전에 통화가 끝나면 `AsyncExitStack` 이 닫는다(누수 0).
- **핸들 신선도**: 사전 연결에 쓰는 핸들은 그 시점 최신값이고, 그 후 스왑까지 진행된 1턴 정도가 재개 컨텍스트에서 빠질 수 있다 [미검증 — §3.3(2)]. 그래서 사전 연결은 **가능한 한 스왑 직전**에.
- ⚠ **단계 2는 단계 1 실측 후에만.** 갭이 0.5초 이하로 나오면 make-before-break 은 복잡도만 늘리는 최적화다.

### 4.5 GoAway 없이 끊기는 경우 (네트워크)

세 경로가 있고, 셋 다 **같은 스왑 지점**으로 모은다.

| 경로 | 지금 동작 | 새 동작 |
|---|---|---|
| `events()` 가 조용히 소진(`received_any=False`) | `_CallFinished` | `_may_swap` 이면 `_SessionSwap("stream_end")`, 아니면 `_CallFinished` |
| `session.receive()` 가 `ConnectionClosed` 로 예외 | TaskGroup → `run_call` generic except → 통화 종료 | 동일 판정 |
| `send_audio`/`send_text_turn` 이 닫힌 소켓에 던짐 | 클라 펌프에서 미포착 예외 → 통화 종료 | 클라 펌프의 `send_audio` 를 좁게 감싸 `_SessionSwap("send_error")` 로 변환 |

주의점 3가지
- 이 경로는 **더러운 경계**다(비버가 말하는 도중일 수 있다) → `_close_open_turn_locally` 필수(§4.3).
- **감지 지연**: TCP 블랙홀이면 websockets keepalive(ping 20s/timeout 20s)까지 아무 일도 안 일어난다 → 최대 ~40초 침묵. 그 사이 `_watch_idle` 이 넛지를 주입하려다 실패(예외 흡수)하고 무음 단계만 전진한다. **완화**: 넛지 주입이 예외로 실패하면 그 자체를 `send_error` 스왑 트리거로 승격(핸들이 있을 때만).
- **더러운 스왑 후 데드락 방지**: 학습자가 말을 마쳤는데 그 응답이 옛 세션과 함께 증발했다면, 새 세션은 아무 자극이 없어 **최대 60초(1단 넛지)** 조용해진다. 완화(권장, 새 프롬프트 문구 0):
  ```
  더러운 스왑(user_turn_open 이었음) 직후:
      state.last_activity_ts = now - (state.idle_nudge1_s - RESUME_NUDGE_AFTER_S)   # 예: 8초 뒤 1단 넛지
  ```
  기존 무음 파이프를 그대로 쓰므로 새 종료·주입 경로가 생기지 않는다.
- **예외 삼키기 위험**: `send_error` 판정을 위해 광범위한 `except Exception` 을 쓰면 진짜 버그가 숨는다 → 반드시 예외 타입·epoch 를 로그에 남기고, **핸들이 있을 때만** 스왑으로 변환한다(없으면 오늘처럼 그대로 터뜨려 종료).

### 4.6 백스톱 재설계

3층으로 나눈다. **오늘 있는 층은 값만 바뀌고, 새 층이 하나 는다.**

| 층 | 상수(제안) | 소유자 | 역할 |
|---|---|---|---|
| ① 통화 시계 | `CALL_DURATION_S = 900` | `_watch_call_clock` | 정상 종료 시작(종료 시드) |
| ② 종료 백스톱 | `SEED_TO_HANGUP_S = 22`(유지) | `_watch_call_clock` | 작별이 안 오면 강제 종료 |
| ③ **세대 상한(신규)** | `PER_SESSION_MAX_S = 480` | `_watch_generation_clock` | 연결 ~10분 전에 **우리가 먼저** 갈아끼운다 |
| ④ 절대 백스톱 | `absolute_timeout = max(600, duration + SEED_TO_HANGUP_S + 60)` | `run_call` 의 `asyncio.timeout` | 최후의 수단(스왑 루프 고착 포함) |

- ③이 핵심 변화다. **GoAway 를 기다리지 않는다** — 문서상 60초 전 예고지만 미검증이고, 모델·리전마다 다를 수 있다. 480초면 ~10분 한계까지 2분 여유.
  15분 통화는 `0~480 / 480~922` 로 **스왑 1회**면 끝난다.
- ④의 `540` 하한을 없애고 **`600` 하한 + 여유 60초**로 바꾼다. 540 은 "연결 10분 선점"이 근거였는데, 재연결이 그 근거를 대체한다. 5분 통화면 `max(600, 300+22+60)=600` → **기존 540 보다 60초 길어진다**(회귀 아님: 5분 통화는 이 상한에 닿은 적이 없다. 닿았다면 그건 이미 병리 상태다).
  ⚠ `test_absolute_backstop_is_540s` 는 **의도적으로 갱신**해야 한다(R4 근거를 테스트 docstring 에 남긴다).
- 재연결 상한:
  ```
  MAX_SESSION_SWAPS = 3         # 15분에 필요한 건 1~2회. 나머지는 재시도 여유
  SWAP_CONNECT_TIMEOUT_S = 8.0  # 새 연결 열기 상한(asyncio.wait_for)
  SWAP_RETRY = 1                # 연결 실패 시 0.5s 후 1회 재시도
  SWAP_FLAP_GUARD_S = 30        # 직전 스왑 후 30초 안에 또 스왑 요구 = 병리 → 우아한 종료
  ```
  플래핑 가드가 무한 재연결 루프의 진짜 방어선이다(예산만으로는 "3번 빠르게 실패"를 못 막는다).

### 4.7 타이머 재정의 & 세대 재시작 멱등성

`_CallState` 는 세대를 건너 **그대로** 산다. 새 세대에서 `_CallState()` 를 다시 만들면 안 된다(명문화).

| 태스크 | 재시작 시 무슨 일이 나나 | 조치 |
|---|---|---|
| `_pump_client_to_gemini` | `client_ws.receive()` 재진입 안전(검증). 스왑 구간 `ping`/`playback_done` 지연 | 갭 최소화. 클라 ping 타임아웃 ≥ 5s 확인(Flutter 협업 항목) |
| `_pump_gemini_to_client` | 본래 세대 전용 — 재생성이 정상 | 스트림 종료를 `_CallFinished` → `_SessionSwap` 판정으로 |
| `_watch_call_clock` | `call_start_ts`·`should_close`·`close_seed_sent`·`seed_sent_ts` 가 전부 state 라 **재진입해도 같은 결론**에 도달(이미 지난 마감은 즉시 통과) | 그대로. 단 "스왑 중 종료 금지" 규칙과 함께 봐야 함 |
| `_watch_idle` | `silence_stage`·`last_activity_ts` 는 state 라 보존. **스왑 직후 넛지 즉발 위험** | 스왑 완료 시 `last_activity_ts = now`(§4.3). `silence_stage` 는 **보존**(무음한 사용자가 스왑으로 리셋되면 안 됨) |
| `_reground_once` | `fire_at` 이 이미 지났으면 다시 `reground_pending=True` 로 arm. 펌프가 `reground_injected` 로 막긴 하지만, `_arm_late_continue` 가 `reground_reminder` 슬롯을 덮어쓸 수 있다 | 진입부에 `if state.reground_injected and state.continue_injected: return` 추가. `fire_at` 은 state 에 1회 계산해 보관 |
| `_periodic_flush` | `sleep(60)` 이 리셋 → 저장이 최대 60초 밀림 | ① **스왑 완료 직후 1회 강제 flush**(스왑은 천연 체크포인트) ② `state.next_flush_at` 데드라인 기반으로 전환 |
| 힌트 사이드카 | 세션 무참조 → 무해. `client_ws` 만 쓴다 | 그대로 |
| 밴드 사이드카 | **세션 참조 + 종료 시드 주입** → 죽은 세션 참조 가능 | R-Z4: 플래그만 세우도록 변경(주입은 시계워처) |

**15분에서 값 자체를 다시 볼 것들**
- `IDLE_NUDGE1_S=60` : 15분 통화에서도 60초 무음은 길다. 값 변경은 이번 범위 밖이지만, **15분에서 무음 3단(60+10+12=82초)이 통화를 끝낸다**는 사실은 그대로다 → 정상.
- 재접지 0.5/0.8 → 7.5분/12분. 15분 대화에서 1회 재접지가 충분한지는 **실측 후 판단**(비목표).
- `FLUSH_INTERVAL_S=60` → 15분이면 최대 15회. 그대로 두되 §9의 메모리 이슈와 함께 본다.

## 6. 추천안 (단계별)

### 단계 0 — 스파이크(선결, 반나절). 코드 머지 없음
`scripts/` 에 일회성 스크립트로 §3.3의 1·2·3·5를 잰다.
- native-audio + `session_resumption` 으로 연결 → 핸들이 오는가, 얼마나 자주 오는가.
- 인위적으로 끊고 핸들로 재연결 → 컨텍스트가 이어지는가, **비버가 다시 인사하는가**.
- 재연결 후 `usage_metadata.prompt_token_count` 로 **재과금 여부** 확인.
- 연결 open→setup ack 실측(갭 추정 검증).
**이 단계에서 "핸들 미지원"이 나오면 15분화는 다른 길(예: 5분 통화 3회 UX)로 재설계해야 한다.**

### 단계 1 — 재연결 없는 준비(회귀 0, 단독 배포 가능)
1. `core/gemini_live.py`: `session_resumption` 설정을 `settings.LIVE_RESUMPTION_ENABLED`(기본 False) 로 게이트해 추가 + `session_resumption_update` 정규화(`resume_update` 이벤트) + `usage_metadata` 로깅.
   - **팩토리 시그니처를 건드리지 않는다**: 활성화 여부는 `open_session` 이 `settings` 에서 읽는다(팩토리 인자는 이미 받고 있다). `resume_handle=` 만 **값이 있을 때만** 넘긴다 — `tools` 에 쓴 것과 같은 패턴이라 **기존 테스트의 가짜 팩토리가 그대로 통과**한다.
2. 펌프에 `resume_update` 소비 추가(state 갱신만, 클라 미전송).
3. `_band_observe_sidecar` 의 세션 참조 제거(R-Z4).
4. `except TimeoutError` 로그를 실제 `absolute_timeout` 으로 수정.
→ 이 상태로 배포하면 **동작은 오늘과 100% 같고**(플래그 off), 켜면 핸들만 수집·로깅한다. dev 에서 켜서 §3.3(2) 를 실전 관측.

### 단계 2 — 세대 루프 + 스왑(핵심)
5. `_SessionSwap` + `_run_session` 세대 루프 + `_run_generation` 분리(오늘 본문 이동).
6. `except*` **우선순위 수집기**: 핸들러에서 바로 `raise` 하지 않고 `outcome` 에 모았다가 우선순위(`_ClientDisconnect` > `_CallFinished` > `_SessionSwap`)로 한 번만 던진다.
   > 오늘도 잠재 위험이다: `except* _CallFinished: raise` 와 `except* _ClientDisconnect: raise` 가 **둘 다** 매치되면 두 핸들러가 모두 실행돼 예외가 다시 그룹으로 묶인다. 절이 셋이 되면 실제로 밟을 확률이 오른다.
7. `_watch_generation_clock`(예정 스왑) + `_arm_swap`/`_may_swap` + 펌프 `turn_end` 게이트 + `_close_open_turn_locally`.
8. 스트림 종료/송신 오류 → 스왑 판정(§4.5), 더러운 스왑 후 넛지 앞당기기.
9. 백스톱 3층 재조정(§4.6) + 스왑 직후 강제 flush.
10. `CALL_DURATION_S 300 → 900`(**마지막 단계**. 그전까지는 5분 통화에서 예정 스왑을 강제 트리거해 스왑 경로만 검증할 수 있다 — `PER_SESSION_MAX_S` 를 테스트에서 낮추면 된다).

### 단계 3 — 실측 후 선택
11. make-before-break 사전 연결(갭이 크면).
12. `transparent=True`(예상치 못한 끊김에서 마지막 발화 손실이 실제 문제면).
13. 메모리 대책(§9-①).

## 9. 위험과 완화

① **메모리 — 15분화의 가장 과소평가된 위험(재연결과 무관)**
`state.segments[*]["pcm"]` 은 점진 flush 후에도 **비워지지 않는다**(`_periodic_flush` 는 저장만 하고, `_trigger_nationality` 가 종료 시점에 그 PCM 을 읽는다 — `call_session.py:806-809`).
즉 **통화 전체 오디오가 통화 내내 RAM 에 있다.** 대략 [추정]: 학습자 16k·16bit = 32KB/s, 비버 24k·16bit = 48KB/s → 5분 통화 ~10MB → **15분 통화 ~30MB/통화**. 동시 통화 N개면 Cloud Run 인스턴스 메모리에 그대로 곱해진다.
- 완화: 점진 flush(이미 GCS 업로드까지 끝난 세그먼트)에서 `seg["pcm"] = b""` 로 해제하고, 국적 추론용 PCM 은 **앞 60초 분량만** 따로 보관.
- **15분 전환 전에 실제 메모리 프로파일 1회 측정**을 조건으로 건다.

② **원가** — 통화 길이 3배 + 스왑마다 컨텍스트 재과금 가능성[미검증]. 15분 통화의 실제 토큰을 `usage_metadata` 로 세대별 기록해 먼저 재고, 필요하면 `LIVE_CTX_*` 를 다시 잡는다.

③ **native-audio + resumption 의 1011** — 커뮤니티 보고 존재. 완화: 플래그 게이트(단계 1) + 스왑 실패는 언제나 우아한 종료로 폴백 + 스왑 실패율 로그 알람.

④ **재개 후 이중 인사** — 있으면 치명적. 스파이크에서 최우선 확인. 만약 발생한다면 대안은 (a) 재개 setup 의 system_instruction 에 "이미 진행 중인 통화" 한 줄 추가(프롬프트 소유자와 협의), (b) 재개 직후 첫 비버 턴이 인사로 판정되면 되돌리기(자기낭독 안전망과 같은 계열) — 둘 다 v1 범위 밖으로 두고, 발생 시 **15분화를 보류**한다.

⑤ **버스트 오디오와 VAD** — 갭 동안 밀린 0.3~1.5초 오디오를 한 번에 밀어 넣을 때 VAD 가 발화 시작을 놓칠 가능성[추측]. 완화: 재개 후 첫 N 청크를 실시간 속도로 페이싱(간단한 sleep 페이서). 실측 전엔 넣지 않는다.

⑥ **클라 keepalive** — 스왑 구간에 `ping` 응답이 지연된다. Flutter 의 ping 타임아웃/재연결 정책 확인 필요(협업 항목). 값이 2초 같은 짧은 값이면 **클라가 먼저 끊어** 스왑이 무의미해진다.

⑦ **통화후 파이프라인 3배** — 전사 토큰·MP3 변환/업로드(현재 ~9초)·분석 지연이 모두 3배. 결과 화면 체감과 Cloud Run 요청 수명(fire-and-forget, throttling=false 필요)에 영향. 별도 점검 항목.

⑧ **R4 회귀 표면** — 이번 변경은 2펌프·백스톱·종료 규약 셋 다 만진다. 완화: ① 5분 통화의 **관측 가능한 동작은 그대로**(스왑 트리거가 5분 안에 발생하지 않음) ② 레벨테스트는 코드 경로가 동일 ③ 플래그 off = 오늘과 바이트 동등한 config ④ §8 테스트 통과 후에만 병합.
