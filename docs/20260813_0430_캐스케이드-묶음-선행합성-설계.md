# 묶음 사이 공백을 닫는다 — **묶음 선행 합성** (설계)

작성 2026-08-13 04:30 · 상태 **설계만**(배포 금지 기간이라 구현 전 검토 요청)

## 0. 증상과 기준선

클라 실측(에뮬 통화):
```
SERVER GAP 2435ms mid-utterance (mic was OPEN)
SERVER GAP  492ms mid-utterance
feed silence — queue empty WHILE beaver speaking (starved! #5)   ← 12.6초에 5회
```
⇒ 비버가 한 문장 말하고 **2.4초 침묵한 뒤** 다음 문장. 지금 사용자가 듣는 **가장 큰 결함**이다.

**기준선(성공 판정의 기준)** — 새로 넣은 `묶음공백=[…]` 의 값:
| 통화 | 값 |
|---|---|
| 에뮬 (2026-08-13) | `2.44s`, `0.49s` |
⇒ 목표: **중앙값이 내려간다.** 0 이 목표가 아니다(0.25초 미만은 애초에 안 찍는다).

## 1. 왜 생기나 — 코드가 근거

```
_run_reply:  async for piece in chat.chunks():        ← LLM 조각 소비
                 for sentence in buffer.push(piece):
                     pending.append(sentence)
                     if 묶음 기준 충족: await _flush_batch()   ← ⛔ 여기서 **막힌다**
```
`_flush_batch` 는 `await self._speak(...)` 로 **그 묶음을 다 보낼 때까지** 기다린다(페이서가
실시간으로 재우므로 오디오 길이만큼). 그동안:

1. **LLM 조각을 안 읽는다**(제너레이터가 멈춰 있다) — 다만 SDK/소켓이 버퍼링하므로 재개하면
   대개 **즉시** 다음 텍스트가 있다. ⇒ 공백의 주범은 LLM 이 아니다.
2. **다음 묶음의 TTS 를 안 건다.** 그래서 앞 묶음이 끝난 **뒤에야** 벤더 왕복이 시작되고,
   그 왕복(실측 **937~1098ms**)이 통째로 침묵이 된다.

⚠ 구간(언어) 단위 선행 합성은 **이미 있다**(`_speak_segments` 의 `prefetch_depth`) —
확인했다. **묶음과 묶음 사이에는 없다.** 그게 이 일이다.

⛔ 그리고 근본 배경: **페이서에 필러가 없다**(`_pace` 는 앞설 때 재우기만 한다). 보낼 것이
없으면 와이어가 그냥 조용하다 — 선행버퍼(1.5초)를 넘는 구멍은 곧바로 굶김이 된다.

## 2. 무엇을 바꾸나

**송출을 태스크로 돌리고, 다음 묶음의 합성을 그 사이에 시작한다.** 순서는 체인으로 지킨다.

```python
send_task: asyncio.Task | None = None

async def _flush_batch():
    nonlocal send_task
    text = " ".join(pending); pending.clear()
    opened = await self._open_batch(text)        # ⭐ 벤더 요청만 건다(빠르다). 오디오는 아직
    prev, send_task = send_task, None
    send_task = asyncio.create_task(_send_after(prev, opened))

async def _send_after(prev, opened):
    if prev is not None:
        await prev                                # ⛔ 순서 보장: 앞 묶음이 끝난 뒤에 보낸다
    return await self._send_batch(opened)
```
루프는 `send_task` 를 기다리지 않으므로 **LLM 을 계속 읽고**, 다음 묶음이 준비되면 그 시점에
**TTS 를 미리 건다**. 앞 묶음이 재생되는 동안 벤더 왕복이 끝나 있다.

### 2-1. 쪼갤 함수 (기존 `_speak` 을 둘로)
| 새 함수 | 하는 일 | 지금 어디 있나 |
|---|---|---|
| `_open_batch(text)` | 언어 분할 + `언어구간` 로그 + 구간 **열기**(합성 시작) | `_speak` 앞부분 + `_speak_segments` 의 여는 부분 |
| `_send_batch(opened)` | 열린 구간을 **순서대로** 송출 | `_speak_segments` 의 보내는 부분 |
⚠ `_speak`(단일 문장 경로·데모 훅·회귀가 쓴다)는 **그대로 남긴다** — 두 함수를 이어 부르는
얇은 껍데기가 된다. 지우면 회귀가 대거 깨진다(오늘 정리에서 배운 것).

## 3. ⛔ 지켜야 할 불변식

| # | 불변식 | 어떻게 지키나 |
|---|---|---|
| I1 | **순서** — 묶음은 만든 순서대로 나간다 | `_send_after` 가 앞 태스크를 `await` (체인) |
| I2 | **첫소리를 안 늦춘다** | 첫 묶음은 지금과 같은 경로. 선행은 **두 번째부터** |
| I3 | **취소하면 미리 만든 것도 버린다** | `_run_reply` 의 finally 에서 `send_task.cancel()` + 열린 구간 전량 `task.cancel()` (지금 `_speak_segments` 의 finally 가 하는 일을 상위로 올린다) |
| I4 | **동시 벤더 요청 상한** | 선행은 **깊이 1**(다음 묶음의 첫 구간만) ⇒ 최대 `prefetch_depth + 1`. 429 는 이미 겪은 자리라 늘리지 않는다 |
| I5 | I6(짝수 바이트)·마커 순서 | 송출 경로 자체는 안 바뀐다(같은 `_send_segment`) |

## 4. ⚠ 대가 — 정직하게

· **원가**: 미리 만든 묶음이 barge-in 으로 안 쓰이면 **돈만 나간다.** 지금도 구간 단위로 같은
  일이 있지만 창이 커진다. ⇒ `선행폐기=N자` 를 대답 줄에 남긴다. **얼마나 버려지는지 보이게.**
· **복잡도**: 대답 경로에 태스크가 하나 는다. 예외·취소 경로가 늘어난다 — 회귀로 덮는다.
· **효과 상한**: 벤더 왕복(0.94~1.10s)만 없앤다. 남는 공백은 **LLM 이 늦은 경우**이고 그건
  이 변경으로 안 줄어든다. ⇒ `묶음공백=` 이 0 이 되지는 않는다.

## 5. 회귀(구현과 같이)

1. 두 번째 묶음의 **합성이 첫 묶음 송출 중에 시작**된다(가짜 TTS 의 호출 시각으로 확인)
2. **순서**: 묶음 2개면 오디오가 1→2 순서로 나간다(뒤바뀌지 않는다)
3. **취소**: barge-in 이면 미리 연 묶음도 **소리가 안 난다**(오늘 고친 "끊었는데 더 나온다" 계열)
4. 첫 묶음은 **예전과 동일**(첫소리 경로 불변)
5. 실패(합성 예외)해도 **나머지 묶음은 나간다**(R5)
6. `선행폐기=` 가 버린 글자 수를 남긴다

## 6. 검증 — 배포 뒤 실통화

```
cascade 대답: … 묶음공백=[…] 선행폐기=N자
```
· `묶음공백=` **중앙값**을 기준선(2.44s·0.49s)과 비교. ⛔ 단발로 판정하지 마라.
· 클라의 `SERVER GAP … mid-utterance` 건수·크기를 같이 본다(같은 250ms 창이라 맞댈 수 있다).
· `선행폐기=` 가 크면 선행 깊이를 줄이거나 barge-in 정책과 같이 재검토한다.
