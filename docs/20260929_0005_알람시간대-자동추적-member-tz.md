# 알람 시간대 자동 추적 — member.tz (2026-09-29)

## 문제
§5(3cf7d0f)로 디스패치가 알람 존(`alarm.tz` → `tz_offset_min` → 서울)으로 시·분·요일을 계산하게 됐지만,
운영 활성 알람 11개 중 10개가 비한국어 회원인데 `alarm.tz` 가 NULL → **서울 기준으로 울린다.**
또 알람 만들 때의 tz 가 고정돼 여행 시 현지 시각을 따라가지 못한다.

## 전제(코드 확인 — bt-back)
앱은 이미 IANA tz 를 보낸다: `GET /calls/daily-status?tz=` · `GET /stats/calendar?tz=` · WS `start.tz`.
⇒ **앱 작업 0**, 위치 권한 불필요(기기 시간대 설정값).

## 결정
1. `member.tz` Text NULL 추가(기본값·백필 없음). 마이그레이션 `4cec70d04fc0`(down=`f737b32e72cf`).
2. `call_service.remember_device_tz(db, member_id, tz)` — 3곳에서 호출.
   - 유효성: `_resolve_zone` 재사용, 실패 시 경고 + **저장 안 함**. 64자 초과는 파싱도 안 한다. 저장값은 `zone.key`.
   - 값이 같으면 쓰기 없음(SELECT 1회 — 라우터는 CurrentMember 가 이미 세션에 있어 identity map 히트).
   - 예외를 밖으로 내지 않는다(R5). 라우터는 **응답을 다 만든 뒤** 호출 → 실패해도 200.
   - WS 는 한도·동시통화 거절 여부와 무관하게 start 직후 기록(“지금 기기 시간대”는 사실).
3. 디스패치 존: **member.tz → alarm.tz → tz_offset_min → Asia/Seoul** (`_alarm_zone`).
   - 이유: 「여행 가면 현지 시각에 울린다」. 알람 생성 시점 값이 이기면 존이 고정된다.
   - 둘 다 NULL 이면 지금과 바이트 동일한 서울 키(배포 경계 안전).

## 함정 — 존이 움직이면 멱등 키도 움직인다
키 = 그 존의 로컬 벽분 `"YYYY-MM-DD HH:MM"`(존 이름 미포함). 알람의 시·분은 고정이므로 **키가 달라지는 건 날짜뿐**이다.
- **같은 날짜로 끝나는 경우**(서울↔뉴욕 등 대부분): 키 문자열이 같아 UNIQUE 가 막는다.
  서울 「월 08:00」이 울린 뒤 뉴욕으로 가면 뉴욕 「월 08:00」은 안 울린다 = 로컬 발생당 1회.
  (로그 보존 2일 > 최대 벽시계 차 26h 라 항상 막힌다.)
- **다른 날짜 키가 짧은 시간 안에 생기는 경우**: 벽시계 차 22~26h 인 두 존(날짜변경선 양쪽, 예 +14 ↔ -10)은
  같은 순간이 「화 08:00」이자 「월 08:00」. 울린 직후 기기 tz 가 바뀌면 catchup 창에서 다른 키로 한 번 더 울린다.
  → **가드**: 같은 알람이 *다른 날짜·같은 HH:MM* 키로 `_REFIRE_GUARD`(3h) 안에 발송됐으면 건너뛴다.
  3h = 최악 간격 |24h−26h|=2h + 여유. 시·분이 다른 키(알람 시각 수정)는 막지 않는다(QA 흐름 보존).
  비원자적(SELECT 후 INSERT)이지만 서로 다른 키가 동시에 나오려면 tz 변경과 크론 2회가 겹쳐야 해 무시.

## 알려진 동작(의도)
- **배포 당일 1회 누락 가능**: 외국 회원의 알람이 배포 후 먼저 서울 시각(틀린 시각)에 울리고, 그 통화로 앱이
  member.tz 를 알려오면, 같은 날 현지 08:00 은 같은 키라 막힌다. 다음 날부터 정상. 회원이 그 전에 앱을 한 번이라도
  열면(홈의 daily-status) 누락 없음.
- 서쪽 여행 시 같은 로컬 날짜의 두 번째 울림은 막는다(위 규칙). 동쪽 여행으로 날짜가 넘어가면 정상 발송.
