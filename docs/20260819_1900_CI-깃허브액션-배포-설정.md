- **작성** 2026-08-19
- **상태** 워크플로 작성 완료 / ⚠ **GCP·GitHub 설정은 사장님이 1회 실행해야 한다**
- **결정** 마이그레이션은 **사람이 돌린다**(CI 에서 안 돌린다 — 2026-08-19 사장님)

---

## 0. ⛔ 먼저 알아야 할 것 — DB 는 분리돼 있지 않다

```
app-api · demo-api · test-api  →  전부 같은 Supabase(ppllscbfdvebsmdatpnc)
```

⇒ **dev 에 push 해서 demo-api 가 배포돼도 그 코드는 실서비스 DB 를 쓴다.**
지금까지는 사람이 매번 확인해서 안 터졌다. 자동 배포가 붙으면 그 안전장치가 사라진다.

⇒ 그래서 **마이그레이션은 CI 에서 절대 돌리지 않는다.** 코드 배포만 자동화하고,
스키마 변경은 사람 손에 남긴다 — 되돌리기 어려운 쪽이 그쪽이다.

⚠ 모델을 바꾼 PR 이 머지되면 **배포 전에** 사람이 `alembic upgrade head` 를 돌려야 한다.
안 그러면 새 코드가 없는 컬럼을 읽고 통화가 전부 죽는다(2026-08-19 실제로 겪었다).

## 1. WIF(Workload Identity Federation)를 쓰는 이유

| | |
|---|---|
| **WIF** | ⭐ **키 파일이 없다.** GitHub 이 GCP 에 직접 인증한다 |
| SA JSON 키 | 간단하지만 **키가 GitHub 에 저장**된다. 유출되면 GCP 전체가 열린다 |

후자는 이 프로젝트 규율(R6 — 서비스계정 키는 사장님 확인)과도 부딪힌다.

---

## 2. ⚠ 사장님이 한 번 실행할 것 (GCP)

⛔ 이 명령들은 **IAM 을 바꾼다.** 내가 임의로 돌리지 않는다(R6).

```bash
PROJECT=bt-dev-web-01
PROJECT_NUMBER=333511894671
REPO=jaewoo-rain/beavertalk-server
SA=github-deployer@$PROJECT.iam.gserviceaccount.com

# ① 배포 전용 서비스계정 (⚠ Cloud Run 이 실행에 쓰는 계정과 **다른** 계정이다)
gcloud iam service-accounts create github-deployer \
  --project=$PROJECT --display-name="GitHub Actions 배포용"

# ② 권한 — 배포에 필요한 최소만
#    run.admin        : Cloud Run 서비스 갱신
#    cloudbuild.builds.editor : 이미지 빌드
#    artifactregistry.writer  : 이미지 push
#    iam.serviceAccountUser   : 런타임 SA 를 서비스에 붙일 때 필요
for ROLE in roles/run.admin roles/cloudbuild.builds.editor \
            roles/artifactregistry.writer roles/iam.serviceAccountUser; do
  gcloud projects add-iam-policy-binding $PROJECT \
    --member="serviceAccount:$SA" --role="$ROLE"
done

# ③ WIF 풀 + 공급자
gcloud iam workload-identity-pools create github \
  --project=$PROJECT --location=global --display-name="GitHub Actions"

gcloud iam workload-identity-pools providers create-oidc github \
  --project=$PROJECT --location=global --workload-identity-pool=github \
  --display-name="GitHub" \
  --issuer-uri="https://token.actions.githubusercontent.com" \
  --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository" \
  --attribute-condition="assertion.repository=='$REPO'"
# ⛔ attribute-condition 을 반드시 건다. 없으면 **아무 GitHub 저장소나** 이 SA 를
#   빌릴 수 있다(WIF 의 대표적 사고 자리다).

# ④ 그 저장소만 이 SA 를 빌릴 수 있게
gcloud iam service-accounts add-iam-policy-binding $SA --project=$PROJECT \
  --role=roles/iam.workloadIdentityUser \
  --member="principalSet://iam.googleapis.com/projects/$PROJECT_NUMBER/locations/global/workloadIdentityPools/github/attribute.repository/$REPO"
```

## 3. ⚠ 사장님이 넣을 GitHub 시크릿

`Settings → Secrets and variables → Actions → New repository secret`

| 이름 | 값 |
|---|---|
| `GCP_WIF_PROVIDER` | `projects/333511894671/locations/global/workloadIdentityPools/github/providers/github` |
| `GCP_SERVICE_ACCOUNT` | `github-deployer@bt-dev-web-01.iam.gserviceaccount.com` |
| `GCP_PROJECT` | `bt-dev-web-01` |
| `GCP_REGION` | `asia-northeast3` |
| `SERVICE_DEV` | `beavertalk-app-demo-api` |
| `SERVICE_PROD` | `beavertalk-app-api` |

⚠ 서비스 이름·리전은 **비밀이 아니다**(공개 URL 에 다 드러난다). 사장님이 시크릿에 넣기로
하셔서 그렇게 쓴다 — 나중에 서비스가 늘거나 이름이 바뀌어도 코드를 안 고쳐도 된다는
실용적 이점은 있다.

## 4. 브랜치 규약

```
push → dev    →  테스트 → 빌드 → demo-api 배포
push → main   →  테스트 → 빌드 → app-api 배포   ⚠ 실서비스
PR            →  테스트만
```

⚠ **`main` 은 실서비스다.** GitHub `Environments` 에 `production` 을 만들고
`Required reviewers` 를 걸면 머지돼도 **사람이 승인해야** 배포된다. 권장한다.

---

## 5. ⛔ 남은 위험

1. **DB 공유** — §0. dev 배포가 실서비스 데이터에 닿는다.
2. **테스트 7건이 환경 의존으로 실패한다**(`.env` 의 GPT_API_KEY 유무). CI 에는 `.env` 가
   없으니 통과하겠지만, 반대로 **로컬에서만 깨지는** 상태가 계속 산다. 별건으로 고쳐야 한다.
3. **`ENV` 가 test 다** — 실서비스(app-api)도 `ENV='test'` 라 일일 한도가 안 돈다.
   CI 와 무관하지만, 자동 배포가 붙기 전에 정리하는 게 맞다.
