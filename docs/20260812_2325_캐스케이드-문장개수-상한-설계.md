# 캐스케이드 대답 길이 — **토큰이 아니라 문장 개수로** 센다 (설계)

작성 2026-08-12 23:25 · 상태 **설계만**(사장님이 "몇 문장"을 정하시면 바로 구현)

## 0. 왜 바꾸나 — 사장님 지적이 정확했다

> "애초에 지금 문장 단위로 잘라서 계속 TTS로 보내는 거 아니야?"

맞다. 우리는 **이미 문장 단위로** 흘린다(`cascade_reply.SentenceBuffer` → `_speak`).
그런데 길이는 **토큰**으로 자른다(`CASCADE_LLM_MAX_OUTPUT_TOKENS=40`). 단위가 둘이라
경계가 안 맞고, 그래서 **문장 중간에서 끊긴다**.

실측(2026-08-12):

| 근거 | 숫자 |
|---|---|
| 실통화 call 938 | b1 꼬리 59자 버림 · b2 85자 · b3 **99자**(말한 것의 4배) |
| 짝지은 측정 n=24쌍 | 잘림 **11/24**(46%) · 버린 글자 합 249~259자 |
| 평균 말한 길이 | 82~90자 (상한 40토큰 ≈ 90~126자) |

⇒ **상한이 대답 길이 분포의 한가운데 있다.** 그래서 절반이 걸린다. 프롬프트 문구로는 못 넘는다
(샘플링 분산이 지시보다 크다 — 3안 교차 비교에서 효과가 재현되지 않았다).

**문장 개수로 세면 버림이 구조적으로 0 이다.** 문장이 끝난 자리에서만 멈추기 때문이다.

## 1. 무엇을 바꾸나

```
지금   LLM 스트림 ──토큰 40에서 절단──> 미완성 꼬리 발생 ──> 서버가 꼬리를 버린다
바꾼뒤 LLM 스트림 ──문장 N개 채우면 스트림 종료──> 꼬리 없음(항상 문장 경계)
```

핵심은 **이미 있는 문장 분할기를 종료 조건으로도 쓴다**는 것뿐이다. 새 파서를 만들지 않는다.

### 1-1. 코드 자리 (한 곳)

`cascade_session._run_reply` 의 스트리밍 루프 — 지금은 문장이 나오면 `pending` 에 담고 계속
받는다. 여기에 **센 문장 수가 상한에 닿으면 스트림을 닫는다**를 더한다.

```python
sentences_done = 0
async for piece in chat.chunks():
    for sentence in buffer.push(piece):
        sentences_done += 1
        ...  # (지금 하던 그대로: 첫 문장 단독 / 배치 묶기)
    if _sentence_cap() and sentences_done >= _sentence_cap():
        await chat.aclose()        # ⭐ 남은 생성을 **받지 않는다**(원가·지연 절약)
        break
```

⚠ `buffer.flush()`(마지막 미완성 조각)는 상한에 닿아 끊은 경우 **버린다** — 그건 N+1번째
문장의 앞부분이고, N개는 이미 완결됐으므로 버려도 말이 안 잘린다. 지금의 `_drop_incomplete_tail`
과 같은 판단이되, **버릴 양이 훨씬 작다**(문장 시작 몇 글자).

### 1-2. 토큰 상한은 **안전망으로만** 남긴다

⛔ 지우지 않는다. 모델이 문장 종결부호를 영영 안 찍는 병리(외국어 나열·목록·이모지 폭주)에서
무한 생성을 막는 마지막 방어선이다. **훨씬 높게** 올린다(예: 40 → 200). 그 값에 걸리는 일이
정상 통화에서 0 이어야 하고, 걸리면 **경고 로그로 드러난다**(이미 `상한잘림` 이 그 자리다).

⚠ 상한을 올리는 것 자체가 대답을 늘리지 않는다 — 길이는 이제 **문장 수**가 정한다.

## 2. 정해야 할 값 — 사장님 결정 대기

`CASCADE_LLM_MAX_SENTENCES` (env, 기본값 미정)

| 후보 | 예상 길이 | 근거 |
|---|---|---|
| 2문장 | ≈ 55~70자 | 지금 평균(82~90자)보다 짧다 — "말이 너무 짧다"가 될 수 있다 |
| **3문장** | ≈ 85~100자 | **지금 실제로 말하는 길이와 가장 가깝다**(버림만 사라진다) |
| 4문장 | ≈ 110~130자 | 지금보다 길어진다 — 턴이 느려진다 |

⭐ 권고는 **3**이다. 근거: 지금 사장님이 듣고 계신 길이(평균 82~90자)를 **그대로 유지**하면서
버림만 없앤다 — 즉 "짧아졌다/길어졌다"는 변화 없이 **잘림만 사라진다**. 값 자체는 env 라
통화마다 바꿔 가며 들어 보실 수 있다.

⚠ 문장당 글자 수는 언어·내용에 따라 흔들린다(위 표는 실측 평균에서 역산한 근사다).
**정확한 값은 바꾼 뒤 실통화 로그의 `글자=` 로 확인한다** — 지금 재 둔 숫자로 단정하지 않는다.

## 3. 무엇이 좋아지고, 무엇을 내주나

**좋아지는 것**
- 꼬리 버림 **0**(구조적으로). 지금 통화당 249~259자를 버린다.
- 원가가 준다 — 상한에 닿으면 남은 생성을 **받지 않고 끊는다**(지금은 40토큰까지 다 받고 버린다).
- 로그가 정직해진다: `상한잘림` 이 뜨면 그건 **진짜 병리**다(지금은 절반이 그 표시라 신호가 죽었다).

**내주는 것 · 위험**
- ⚠ 문장 하나가 **아주 길면** 그 대답이 길어진다(문장 수만 세므로). 안전망 토큰 상한이 그 경우를
  잡지만, 그때는 예전처럼 중간에서 끊긴다 — **드물게 남는 결함**이다. 실측으로 빈도를 봐야 한다.
- ⚠ 스트림을 중간에 닫으면 **usage 집계가 끊긴 시점 기준**이 된다. 원가는 실제로 생성된 만큼만
  청구되므로 오히려 정확해지지만, `candidates_token_count` 를 못 받는 경우가 있는지 확인해야 한다
  (지금 코드가 마지막 청크에서 읽는다 — **구현 시 반드시 실측 확인**).
- ⚠ 프롬프트의 길이 규칙(`short_reply`)과 **겹친다**. 문장 수로 강제하면 프롬프트 문구는
  중복이다. 구현 시 둘 중 하나로 정리한다 — 지금 상태로 두면 "1~2문장" 문구와 상한 N 이 또
  어긋날 수 있다(이번 결함과 같은 계열의 실수다).

## 4. 회귀(구현 시 같이 넣는다)

1. 문장 N개를 받으면 **N+1번째를 기다리지 않는다**(스트림을 닫는다)
2. 상한에 닿아 끝난 대답은 **버린 꼬리가 0자**다 — 모든 발화가 문장 경계에서 끝난다
3. 상한보다 짧게 끝나는 대답은 **예전과 완전히 동일**(모델이 스스로 끝내면 아무 일도 안 한다)
4. 토큰 안전망에 걸리면 **로그에 남는다**(그 자리는 지금과 같다)
5. `CASCADE_LLM_MAX_SENTENCES=0`(또는 미설정)이면 **지금 동작 그대로** — 되돌릴 수 있어야 한다

## 5. 남은 질문 (사장님·bt-back)

- 몇 문장인가 (권고 **3**)
- 프롬프트의 길이 문구를 **문장 수와 같은 값으로 맞출지**, 아니면 문구를 **아예 뺄지**
  (서버가 강제하므로 프롬프트로 또 시킬 이유가 약하다 — 다만 모델이 "3문장 안에 할 말을
  마치도록" 계획하게 하려면 문구가 남는 편이 낫다. **실측으로 가른다**)
