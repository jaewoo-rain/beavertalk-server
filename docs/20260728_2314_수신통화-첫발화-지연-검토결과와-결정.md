## 1. 실측 (운영 로그 20건, 2026-07-27)

```
WS accept → "normalcall 시작"     0.35~0.78s  (중앙 0.55)   ← A·C의 전장
"normalcall 시작" → 첫 오디오      1.26~2.34s  (중앙 1.50)   ← 아무도 못 건드림 (68%)
──────────────────────────────────────────────
accept → 첫 오디오                1.8~3.0s    (중앙 2.2)
```

`0.55초` 구간 내역: `find_or_create_by_auth`(3q) + `start` 대기(≈0) + `load_call_setup`(~19q)
+ 프롬프트 조립(CPU) + `create_call`(~2q) ≈ **24 쿼리**.

`load_call_setup` 이하는 `start`의 `character_id`가 있어야 돌아서 **선행 불가**. 즉 A가 앞당길 수
있는 상한은 `verify_token` + `accept` + `find_or_create_by_auth` 뿐이다.

클라 실측 5초 vs 서버 2.2초 → 차이 2.8초는 클라·네트워크(CallKit, 오디오 세션, TLS, 프리버퍼 400ms).

### 콜드스타트 (진짜 병목)

```
12.78  Starting new instance

```

- `beavertalk-app-api` : `minScale` 미설정(=0), `cpu=1 / memory=2Gi`, `cpu-throttling=false`

## 2. 요청서 사실 검증

### 맞는 것 (코드 확인 완료)

| 주장 | 위치 | 결과 |
|---|---|---|
| `verify_token` = GoTrue HTTP 왕복, 캐시 없음 | `core/supabase_auth.py:37` | ✅ |
| `_read_initial_start` 2초 타임아웃 → 기본 캐릭터 진행 | `call_session.py` | ✅ |
| member 중복 조회(라우터에서 로드 후 버림 → 셋업에서 재조회) | `ws_router.py` / `normalcall_service.py:99` | ✅ |
| `reasons`·`owned_characters` = `selectin`, `Character.voice` = `select` | 모델 | ✅ |
| `create_call`·Live 세션 모두 `start` 이후 → 미수신 시 잔여물·Gemini 비용 0 | — | ✅ |

### 틀린 것 — A의 §3.2

> "6회 반복 제한은 유지해도 무방함"

**무방하지 않다.** 현재 구조가 **반복마다** `wait_for(timeout)`이라 타임아웃을 70초로 올리면
깨진 프레임 6개에 **최대 420초** 점유가 된다. 전체 대기에 단일 데드라인을 걸어야 한다.

```python
deadline = loop.time() + START_WAIT_TIMEOUT
for _ in range(6):
    remain = deadline - loop.time()
    if remain <= 0:
        raise _ClientDisconnect()
    message = await asyncio.wait_for(client_ws.receive(), timeout=remain)
```

### 요청서가 못 본 것 2가지

**① `NullPool` — C-3③ 병렬화가 손해일 수 있다**

`db/engine.py:28` `poolclass=NullPool` (pgbouncer가 풀링). 세션을 새로 만들 때마다 **새 접속**이다.
지금은 `load_call_setup`이 세션 하나로 19쿼리를 돌린다(접속 1회). 병렬화하면 접속이 1회 늘고,
두 갈래가 `_load_history` 2쿼리 vs `_load_study_materials` 11쿼리로 심하게 불균형이라
**2쿼리 아끼려고 접속 1회를 더 낸다.** 본전이거나 손해.

**② `ENV`가 `prod`가 아니다**

`app-api`·`demo-api`·`test-api` 모두 `ENV=test`. `duration_min`의 "prod 무시" 게이트가
실서비스에서 동작하지 않는다(별건 — 클라가 통화 길이를 마음대로 정할 수 있다).
언어 게이트에서 같은 함정을 겪고 `ENV` 조건을 제거했다
(`docs/20260728_0125_학습언어-DB-단일소스화와-모국어-정규화.md` §2-2).

## 3. 채택 항목 상세

### 3-1. 워밍 (1순위)

푸시를 **실제로 보내는 순간에만** `app-api /health`를 찔러, 벨이 울리는 5~10초 동안 인스턴스를
기동시킨다. `/health`는 인증 불요.

```python
# domains/push/... dispatch-calls 안, 푸시 발송 성공 직후
if pushed:
    with contextlib.suppress(Exception):
        httpx.get(f"{settings.APP_API_URL}/health", timeout=3)
```

- ⚠ **매분 무조건 찌르면 안 된다.** 인스턴스가 영영 안 자서 24/7 과금(`cpu-throttling=false`)
- 실패해도 안전(`suppress`) — 지금과 동일하게 동작
- **한계**: 홈에서 직접 거는 통화는 커버 못 함(서버가 언제 걸지 모름)

**대안 비교**

| | `min-instances=1` | 벨 워밍 |
|---|---|---|
| 콜드스타트 제거 | 항상(홈 발신 포함) | 예약전화만 |
| 비용 | 월 $40~60 상시 추정 | ≈0 |
| 작업 | 명령 한 줄 | 코드 3줄 |

지금처럼 하루 6번 자고 깨는 트래픽에선 **벨 워밍이 비용 대비 우월**. 사용자가 늘어 인스턴스가
상시 떠 있게 되면 그때 `min-instances`가 자연스러워진다.

**클라 측 보완(다음 릴리즈, 급하지 않음)**: 홈에서 통화 화면 진입 시 `/health` 1회 —
서버가 못 덮는 홈 발신을 커버. 토큰 불필요.

> 클라가 푸시 받고 `/health`를 쏘는 방식도 검토했으나, FCM 배달 + 앱 부팅만큼(1~3초) 늦게
> 출발해 6.4초를 다 태우지 못할 수 있고, iOS PushKit 창·Doze 제약이 붙는다. **서버가 더 이르고
> 확실하다.** 둘은 경쟁이 아니라 서로 다른 경우(예약 vs 홈발신)를 덮는다.

### 3-2. C-0 계측 (2순위)

경과 ms 로그를 5지점에. **속도 이득 0 — 다음 판단을 추측이 아니게 만드는 게 목적.**

`verify_token` / `find_or_create_by_auth` / `load_call_setup` / Live 세션 open / 첫 오디오 청크

쿼리 수는 `before_cursor_execute` 카운터 또는 `echo=True` 1회로 확정.
⚠ 토큰·이메일 등 PII를 로그에 넣지 말 것.

**C-2 착수 여부는 이 결과로 판단한다.** 왕복이 20ms면 C-2가 60ms, 2ms면 안 할 일.

### 3-3. C-3①② (3순위)

| 대상 | 관계 | 조치 | 절감 |
|---|---|---|---|
| `Character.voice` | **N:1** | `joinedload`(= JPA `JOIN FETCH`) | 1쿼리 |
| `Member.owned_characters` | 1:N | `noload` — 통화 셋업에서 **미사용 확인함** | 1쿼리 |
| `Member.reasons` | 1:N | `selectin` **유지**(joinedload 금지 — 곱집합) | — |
| 학습항목 존재 확인 | — | 첫 선별 쿼리에 병합 | 1쿼리 |

`db.get()` → `select().options(...)` 로 바꿔야 옵션을 걸 수 있다. 로직은 불변.
`raiseload`가 더 안전하지만 같은 헬퍼를 쓰는 다른 경로가 터질 수 있어 `noload`가 무난.

**총 3쿼리 제거 ≈ 0.05초 + 비용 감소.** 체감은 없다.

## 4. 제외 항목과 이유

**C-1 토큰 캐시** — ① 영향 범위가 `core/deps.py:45`를 통해 **REST 전체** ② 탈퇴·로그아웃이
최대 TTL 동안 안 먹음(앱에 회원 탈퇴 있음) ③ 프로세스 내 dict인데 `concurrency 80 × maxScale 5`라
**수신통화는 그날 첫 요청이라 대부분 미스**. 리스크는 확실하고 효과는 불확실.

**C-3③ 병렬화** — §2 ① 참조.

**A 선행 연결** — 클라 작업이 전제인데 앱팀은 여유 소진 상태. Cloud Run 비용 소폭 증가
(`cpu-throttling=false`). 좀비 연결 관리 필요. 그리고 **A의 숨은 가치(선행 연결이 인스턴스를
깨움)를 워밍이 더 싸게 가져간다.** `timeoutSeconds=3600`이라 벨 60초 추가 자체는 안전.
A를 하게 되면 §2의 6회 루프 함정을 반드시 같이 고칠 것. **A와 C-2는 궁합이 나쁘다**
(벨 구간에 member를 미리 읽으면 캐릭터 변경 반영이 어긋남).

**B Gemini 예열** — 미수신 통화도 Live 세션을 열어 과금. A/C 실측 후에도 부족할 때만.

## 5. 재개 시 첫 단계

1. `dispatch-calls`에서 푸시 발송 분기를 찾아 `/health` 핑 추가 (**알람 있는 분에만**)
2. 5지점 경과 ms 로그 추가 → 배포 → 통화 3~5건 → 로그로 구간별 ms 확정
3. 그 숫자로 C-2 착수 여부 결정
4. C-3①② 적용(계측과 독립적으로 안전)

**검증**: 클라 로그 `first-audio-in +Nms`를 변경 전후 비교(요청서 §7).
`connect/socket-open` 기준이라 서버 구간이 그대로 드러난다.

## 6. 곁가지 정리 대상 (발견만, 미착수)

- `normalcall_service._base_locale()`와 오늘 추가한 `core.languages.normalize_locale()`가
  **같은 일을 하는 중복 함수**다(빈 값 처리만 다름: `"en"` vs `None`). 하나로 합칠 것.
- `duration_min`의 "prod 무시" 게이트가 `ENV=test`라 실서비스에서 무력하다 — 클라가 통화 길이를
  임의 지정할 수 있는 상태. 언어 게이트와 같은 방식으로 손볼지 판단 필요.
