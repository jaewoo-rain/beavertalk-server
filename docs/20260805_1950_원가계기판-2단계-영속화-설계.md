## 0. 결정 요약

| # | 결정 | 한 줄 이유 |
|---|---|---|
| D1 | **하이브리드** — 집계 컬럼 7개 + 원본 `usage_json` 1개 | 제안서의 JSONB 단일 컬럼은 집계가 불편하다. 자주 쓰는 값만 컬럼으로 승격 |

## 1. D1 — 왜 JSONB 단일 컬럼이 아닌가

제안서(Phase 0 §3-3)는 `usage_json JSONB NULL` 1컬럼이었다. 목적이 **"원가 추이 집계"** 라면
그 형태는 쓰기엔 편하고 **읽기엔 불편하다**.

```sql
-- JSON 단일 컬럼이면 매번 이렇게 된다(캐스팅 + 인덱스 불가)
SELECT date_trunc('day', call_date),
       SUM((usage_json->>'in_audio')::bigint) * 3.00 / 1e6 + …
```

집계에 실제로 쓰는 값은 **소수(7개)** 이고, 그중 4개는 **단가가 서로 다른 4항**이라 반드시
따로 있어야 한다(오디오 입력 $3 / 텍스트 입력 $0.5 / 오디오 출력 $12 / 텍스트 출력 $2 —
**입출력 오디오만 4배 차이**). 그래서 그 값들만 정수 컬럼으로 승격한다.

### 승격하는 컬럼 (7)

| 컬럼 | 타입 | 왜 컬럼인가 |
|---|---|---|
| `usage_msgs` | INTEGER | 계측이 돌았는지(0 = 미수신) 판별. 표본 신뢰도 |
| `usage_in_audio` | BIGINT | 원가 산식 4항 — 단가 $3.00 |
| `usage_in_text` | BIGINT | 원가 산식 4항 — 단가 $0.50 |
| `usage_out_audio` | BIGINT | 원가 산식 4항 — 단가 $12.00 |
| `usage_out_text` | BIGINT | 원가 산식 4항 — 단가 $2.00 |
| `usage_total` | BIGINT | API 가 준 총합. **4항의 합이 아니다**(thoughts·cached 포함) → 파생 불가 |
| `usage_peak_prompt` | INTEGER | 이 통화가 도달한 **최대 컨텍스트**. 압축·트리거 튜닝의 핵심 지표이고, 단계 4 판정이 정확히 이 값의 분포다 |

### `usage_json` 에 남기는 것

스키마를 안 바꾸고 받아 두는 그릇이다: `dropped` · `monotonic` · `last_prompt`/`last_total` ·
`thoughts` · `cached` · `tool_in` · **위 4종 외의 모달리티**(VIDEO/IMAGE 등이 생겨도 컬럼
추가 없이 들어온다) · `epochs`/`reconnects`/`compressions`(재연결·압축 관측).

⛔ **시계열(turn-by-turn trace)은 넣지 않는다.** 통화당 최대 400엔트리 ≈ 48KB 라 1만 통화면
   약 480MB 다. 시계열이 필요한 건 조사 기간뿐이고 그건 로그(30일)로 충분하다.

### ⚠ 신 포맷 기준으로 잡는다

8/4 로그의 모달리티는 **입출력이 합쳐진 한 덩어리**였고, 2026-08-05 06:17 UTC 배포분부터
`sum_in=` / `sum_out=` 이 분리됐다. 위 4항은 **신 포맷 기준**이다 — 구 포맷 형태(합산 1덩어리)로
컬럼을 잡으면 만들자마자 낡는다.

## 2. D2 — 원가(달러)를 컬럼으로 저장하지 않는 이유

| | 저장한다 | 저장 안 한다(채택) |
|---|---|---|
| 장점 | 조회가 단순. 과거 청구액이 그 시점 단가로 고정 | 단가가 바뀌어도 **전 기간을 새 단가로 재계산** 가능. 단가 오타를 나중에 고칠 수 있다 |
| 단점 | 단가 변경 시 과거와 현재를 **같은 잣대로 못 본다**. 산식 버그가 행에 박제된다 | 조회할 때마다 단가표를 곱해야 한다 |

**토큰은 사실이고 원가는 파생 계산**이다. 이건 레벨 시스템의 관통 원칙 ②(*증거가 원본,
나머지는 파생 — 별도 플래그 금지*)와 같은 규율이다. 단가표는 코드 한 곳
(`normalcall_service.LIVE_TOKEN_PRICE_USD`)에 두고 `estimate_usage_cost_usd()` 가 곱한다.

☞ 나중에 **회계** 목적(실제 청구액 대사)이 생기면, 단가표에 적용일자를 붙여
  `price_at(call_date)` 로 확장하면 된다 — 그때도 토큰 원본은 그대로 쓸 수 있다.
  반대로 달러를 박아 두면 그 확장이 불가능하다.

## 3. 저장 지점과 안전성

```
run_call finally
  ├─ _flush_* (세그먼트 확정)
  ├─ _log_usage_summary(state, …)        ← ①로그 1줄(무손상)
  ├─ _persist_usage(…)                    ← ②신규. 예외 전량 흡수
  ├─ _persist_remaining(…)                (전사 저장 + finalize_call)
  └─ _trigger_* / _finish_call
```

- **R4 무영향**: 통화 루프(`_run_session`) 밖, 종료 후다. 2펌프·백스톱·barge-in·종료 규약 어디에도 안 닿는다.
- **R5**: `contextlib.suppress` 로 감싼다 — usage 저장이 실패해도 전사 저장·분석·통화 종료는 그대로 간다.
  `_persist_remaining` 과 **분리된 DB 트립**인 이유가 이것이다. 한 트랜잭션에 묶으면 usage 오류가 통화 기록을 같이 죽인다.
- **R3**: 쓰기는 service(`normalcall_service.save_call_usage`)가 `db.commit()`.
- **usage 0건이면 아무것도 쓰지 않는다**(모킹 세션·Live 실패) — NULL 로 남아 "계측 안 됨"과 "0 토큰"이 구별된다.

## 4. 계산의 단일 소스

지금 `_log_usage_summary` 안에 집계가 인라인으로 들어 있다. 이걸 `_usage_summary(state) -> dict|None`
로 뽑아 **로그와 DB 가 같은 값을 쓴다.** 로그 문자열은 한 글자도 바꾸지 않는다(D5).

## 5. 마이그레이션 (R2)

- `call` 테이블에 컬럼 8개 추가. 전부 **NULL 허용**(기존 행 무영향, 백필 없음).
- ⛔ **적용하지 않는다.** 생성·검토까지만 하고 보고한다(R6 — dev DB 포함).
- ⚠ 이 워크트리에 `.env` 가 없어 **`--autogenerate` 를 돌릴 수 없다**(DB 접속 불가).
  그래서 마이그레이션을 **손으로 작성**했다. autogenerate 결과와 대조하는 검토가 남아 있다.

## 6. 검증

| 테스트 | 무엇을 못 박나 |
|---|---|
| 요약 집계 정확성 | 모달리티 4항·total·peak 이 usage_log 로부터 정확히 나온다 |
| usage 0건 | 아무것도 저장하지 않고 통화는 정상 종료(NULL 유지) |
| dropped > 0 | 상한 초과 통화도 저장된다(요약은 과소지만 dropped 로 드러난다) |
| 저장 실패 | DB 가 던져도 통화는 정상 종료(R5) |
| 로그 무손상 | 기존 요약 줄 형식이 그대로다 |
| 원가 산식 | 4항 × 단가가 손계산과 일치 |
