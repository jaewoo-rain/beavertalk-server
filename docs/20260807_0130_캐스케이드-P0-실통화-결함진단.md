## §1 결함 B — 같은 발화가 턴 2개 (**원인 확정**)

### 관측
```
u16 speech_ms=1463 lag=79461 text='안녕하세요'   16:09:49.499
u17 speech_ms=0    lag=897   text='안녕하세요'   16:09:49.843
```
같은 쌍이 u2/u3, u4/u5, u18/u19, u20/u21, u22/u23. **둘째는 항상 `speech_ms=0`.**

### 원인 (산수로 확정)
`_arm_close_timer` 는 "이미 흘러간 침묵"을 오디오 시각으로 빼고 남은 만큼만 기다린다:

```
remain = 침묵임계(800ms) − (audio_ms − event.offset_ms)
```

이 뺄셈은 **파이프라인 지연 < 침묵 임계**일 때만 성립한다. 그런데 이 통화의 실측 지연은
**810·830·831·835·852·877·897·914ms** — 임계 800ms 를 **넘는다**. 그러면 `remain = 0` 이 되어
턴은 `speech_end` 를 처리하는 **바로 그 순간** 닫힌다. 그 발화의 최종 전사는 아직 오는 중이다.
0.02~0.9초 뒤 도착한 최종 전사는 상태가 IDLE 이라 `_on_transcript` 가 **새 턴을 연다.**
새 턴은 이미 지난 오프셋 때문에 `remain=0` 으로 즉시 닫힌다 → `speech_ms=0`.

**증거 3종이 서로 맞물린다**: ①둘째 턴의 lag 이 전부 800 초과(805·811·845·877·897·1029)
②둘째의 `speech_ms=0` ③중복이 안 난 u6~u11 은 최종 전사가 타이머보다 먼저 왔다.

> ⛔ P1 을 막는 이유가 이것이다 — LLM 이 붙으면 **비버가 같은 말에 두 번 대답한다.**

### 고친 것
1. **최소 대기 바닥** `CASCADE_TURN_MIN_WAIT_MS=250` — 지연이 임계를 넘어도 최종 전사를 기다릴
   시간을 항상 남긴다. 지연이 임계보다 작을 때의 동작은 예전과 동일.
2. **유령 턴 차단** `_is_stale_tail()` — 방금 닫은 턴의 끝(오디오 시각)을 넘지 못하는 최종
   전사는 새 턴을 열지 못한다(유예 `CASCADE_STALE_FINAL_MS=1500`). 바닥보다 더 늦게 오는
   전사(롤오버 재인식 등)까지 막는 2차 방어.
3. **롤오버 재생에서 이미 확정된 구간을 잘라낸다**(`RollingSttV2Stream._flush`) — 재인식되면
   같은 발화가 턴 2개가 되고 **그 구간이 이중 과금**된다(원가 설계 §2-2 위험의 실현 경로).

세 가지는 각각 독립된 원인 경로다. 테스트로 **하나씩 꺼서** 필요성을 확인했다
(`CASCADE_TURN_MIN_WAIT_MS=0` → ①번 테스트 실패, `CASCADE_STALE_FINAL_MS=0` → ②번 실패).

## §2 결함 C — 빈 턴 (`text=''`) — **B 의 부산물 + 판단**

`u13 u14 u15 u24` 가 빈 텍스트로 닫혔다. u15·u24 는 §1 과 같은 조기 종료(전사가 오기 전에
닫힘)라 위 수정으로 사라진다.

**판단(요청받은 근거)**: 빈 턴이라도 **닫기는 해야 한다.** 안 닫으면 상태가 `USER_SPEAKING`
으로 굳고 다음 발화가 같은 턴에 얹힌다(안전망 `reason=max` 가 있는 이유). 대신 **사용자 턴으로
취급하면 안 된다** — 빈 입력으로 LLM 을 부르면 원가만 나가고 비버가 헛대답을 한다.
그래서 닫되 `cascade 빈 턴: … (LLM 호출 금지)` 로 로그를 남기고, P1 은 `text==''` 이면
LLM 을 호출하지 않는다. 화면·프로토콜은 그대로 둔다(데모가 "턴이 열렸다 버려졌다"를 봐야 한다).

## §3 결함 A — pipeline_lag 79초 (⭐ **2026-08-07 판정 완료 · 수정됨**)

### 판정 — 후보 ② 확정
두 번째 실통화(104초)에서 결정적 증거가 나왔다:

```
u5  pipeline_lag_ms=79377        ← 오염값
stt_streams=1                    ← 롤오버가 아예 없었다
WARNING cascade 파이프라인 지연 이상: lag=72252ms kind=speech_begin offset_ms=860 audio_ms=73113
```

`[stt-v2] 스트림 교체` 줄이 25분치 로그에 **0건**이다. 롤오버가 없는데 79초가 튀었으므로
후보 ①(롤오버 기준점)은 배제된다. → **`speech_event_offset` 은 전역 오디오 타임라인이
아니다**(문서 표현은 'beginning of the audio' 인데 실측이 다르다).

### 고친 방식 — 의미를 가정하지 않고, 말이 안 되는 값을 거절한다
벤더가 그 기준을 무엇으로 정의하는지는 **여전히 모른다.** 우리가 확실히 아는 건 하나다 —
"우리가 흘려보낸 오디오보다 한참 과거를 가리키는 값은 침묵 계산에 쓸 수 없다".
`_sanitize_offset()` 한 곳에서 걸러 미상(-1)으로 만들고, 기존 폴백(전체 침묵 대기)으로 흘린다.

⚠ 한 곳에서 막는 이유는 오염값이 **세 곳을 동시에** 망가뜨리기 때문이다:
①계측(lag) ②침묵 타이머 remain(=0 → 결함 B 재발) ③**barge-in 최소 지속 게이트**
(`audio_ms − offset >= min_ms` 가 무조건 참 → 마이크 상시개방을 켜는 순간 잔여 에코 한 번에
비버가 끊긴다). ③은 지금까지 마이크 상시개방이 OFF 라 드러나지 않았을 뿐이다.

### 관측

### 확인한 것 / 배제한 것
- lag 값이 **자라지 않고 일정**하다 → 오프셋이 벽시계와 같은 속도로 전진한다.
  즉 "오프셋이 0/미상으로 온다"(그러면 lag 이 계속 자란다)는 **아니다.**
- 배제: 두 번째 WS 세션(그 시간대 accept 로그 1건뿐), 클라의 오디오 게이팅
  (`cascade_demo.html` 은 조건 없이 매 프레임 전송), 리베이스 코드 누락
  (`events()` 의 `offset_ms += self._base_ms` 는 **모든 이벤트에 무조건** 걸린다).
- 남은 후보 2개: ①롤오버 시 기준점(`_base_ms`)이 실제로 0 으로 잡힌 경우
  ②`speech_event_offset` 과 `result_end_offset` 의 기준이 서로 다른 경우
  (쌍의 **첫 턴**은 VAD 이벤트로, **둘째 턴**은 전사로 닫힌다 — 둘의 lag 이 79.4초 vs 0.9초로
  갈린 것이 이 후보와 맞물린다).

### 왜 못 정했나 — 그리고 무엇을 심었나
⛔ **롤오버가 서버 로그에 한 줄도 안 남고 있었다.** WS 이벤트로만 클라에 보냈다. 그래서
"그 시각에 롤오버가 있었는가"조차 로그로 확인할 수 없다. 원인을 모른 채 오프셋을 덮는 것은
증상 가리기라 하지 않았다. 대신 다음 통화 1건이면 판정되도록 계측을 심었다:

- `cascade stt 롤오버: reason=… gap_ms=… audio_ms=…` (세션)
- `[stt-v2] 스트림 교체: base_ms=… 재생=…ms 잘라냄=…ms audio_ms=…` (스트림 — **기준점 원본**)
- `cascade 파이프라인 지연 이상: lag=… kind=… offset_ms=… audio_ms=…` (3초 초과 시 1회 경고)

세 줄을 대조하면 ①이면 `base_ms` 가 0 으로 찍히고, ②면 롤오버 없이 `kind=speech_*` 에서만
튄다. **다음 실통화에서 확정한다.**

> 참고: A 는 B 를 **확실하게 만든다**(lag 79초 ⇒ remain 항상 0). B 의 수정은 A 가 남아 있어도
> 턴 중복을 막지만, A 자체는 계측값을 못 믿게 하므로 별도로 닫아야 한다.
