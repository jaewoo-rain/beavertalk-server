# 통화 마이크를 `flutter_sound` → `record` 로 바꾼다

작성 2026-09-06 13:00 · 상태 **계획 확정 / 미구현** · 저장소 `beavertalk-flutter`

---

## 0. ⭐ 원인은 실측으로 확정됐다 — 네 판의 대조

메인 스레드 지각(`main_late_ms`, 20ms 자기재게시 프로브)을 5초 창마다 잰 값:

| 실험 | 앞절반 → 뒷절반 | 최대 | 판정 |
|---|---|---|---|
| 평소 | 93 → 282ms | 698ms | ⛔ 자람 |
| AEC 끔(`MIC_NO_AEC`) | 86 → 243ms | 393ms | ⛔ 자람 → **AEC 무죄** |
| 업링크 차단(`MIC_ALWAYS_GATED`) | 33 → 330ms | 330ms | ⛔ 자람 → **소켓 전송 무죄** |
| **마이크 끔(`MIC_OFF`)** | **31 → 28ms** | **54ms** | ✅ **평평** |

⇒ **마이크를 여는 것 자체**가 메인 스레드를 막는다. 소켓으로 안 보내도, 에코 제거를 꺼도
  자란다. 마이크를 **아예 안 열 때만** 사라진다.

### 그래서 무엇이 끊기나

    오디오 재생  ✅ 멀쩡하다 — 2026-08-14 에 재생 채널을 백그라운드 큐로 뺐다
                    (`ping` 왕복이 네 판 내내 0~2ms 로 완전히 평평하다)
    영상        ⛔ 끊긴다 — `video_player` 는 아직 메인 스레드다

사장님 체감과 정확히 맞는다: *"음성 버벅임은 없는데 캐릭터 영상 버벅임은 그대로야."*

### ⛔ 배제된 것들 (다시 의심하지 마라)

- 오디오 재생 채널 · 표정/감정 클립(0건으로 만들어도 곡선 동일) · idle/talk 영상 교체
  (영상 이벤트 0건인 30초 구간에도 곡선이 자랐다) · AEC · 업링크 전송

## 1. 왜 `record` 인가 — 소스로 확인한 차이

```
flutter_sound   캡처 루프에 **전용 스레드가 없다.** 메인 루퍼에 자기를 계속 재게시한다
                (`FlautoRecorderEngine`, AAR). 채널도 TaskQueue 없이 메인이다
                (`FlutterSoundRecorderManager.java:49` — 2인자 생성자)
record          `RecordThread.kt:84`  mRecordThread = Thread { … }   ← 진짜 백그라운드
                `RecorderRecordStreamHandler.kt:23`  uiThreadHandler.post { … }
                ⇒ 메인으로는 **전달만** 한다
```

⭐ 그리고 **이미 의존성에 있다**(`pubspec.yaml:94  record: ^7.1.1`). 발음챌린지 STT 가
  쓰고 있어 **선례까지 있다**(`stt_service.dart:214` `startStream(RecordConfig(...))`).

## 2. 갈아끼울 자리는 한 곳이다

통화 마이크는 `normalcall_controller.dart` 하나뿐이다. 복습(`review/data/audio_recorder.dart`)·
재생(`review/data/audio_player.dart`)도 flutter_sound 를 쓰지만 **이 작업 범위가 아니다.**

### 2-1. ⭐ 소비 코드는 그대로 둔다

지금 배관:

```
FlutterSoundRecorder.startRecorder(toStream: controller.sink)   → StreamController<Uint8List>
                                                                 → _micSub = controller.stream.listen(...)
```

`record` 배관:

```
recorder.startStream(RecordConfig(...))  → Stream<Uint8List>
                                          → _micSub = stream.listen(...)   ← 같은 리스너
```

⇒ **타입이 같다**(`Uint8List`). 리스너 본문(계측·게이트·업링크)은 **한 줄도 안 바꾼다.**
  `StreamController` 를 우리가 만들 필요가 없어져 오히려 코드가 준다.

### 2-2. 옵션 대응표 (전부 있는 것을 확인했다)

| 지금(flutter_sound) | record |
|---|---|
| `codec: Codec.pcm16` | `encoder: AudioEncoder.pcm16bits` |
| `sampleRate: 16000` | `sampleRate: 16000` |
| `numChannels: 1` | `numChannels: 1` |
| `enableEchoCancellation` | `echoCancel` |
| `audioSource: voice_communication` | `androidConfig.audioSource: AndroidAudioSource.voiceCommunication` |
| `enableVoiceProcessing`(iOS) | `iosConfig` (아래 ⚠) |

### ⭐ 착수 결과 — **안드로이드만 바꿨다**

`enableVoiceProcessing` 이 1:1 대응이 아니어서(아래) iOS 는 `flutter_sound` 를 유지한다.
증상도 안드로이드에서 잰 것이라 안 아픈 쪽을 같이 수술할 이유가 없다.

⭐ 그리고 소스로 확인한 것 하나 — `record` 의 `audioManagerMode: modeNormal` 은
  «모드를 **건드리지 않는다**» 는 뜻이다(`AudioSessionManager.kt:58`
  `if (config.audioManagerMode != MODE_NORMAL)`). ⇒ 우리가 `MainActivity.kt:337` 에서
  세운 `MODE_IN_COMMUNICATION` 이 그대로 남는다. 같은 이유로 `speakerphone: false`·
  `manageBluetooth: false` 로 두어 **라우팅은 오늘과 한 글자도 다르지 않다.**

⚠ **`enableVoiceProcessing` 이 1:1 대응이 아니다.** iOS 의 VoiceProcessingIO 를 켜는
  플래그인데 `record` 는 `iosConfig` 로 다르게 노출한다. iOS 동작이 바뀔 수 있으므로
  **안드로이드부터 바꾸고 iOS 는 별도로 확인**한다(지금 증상도 안드로이드다).

⭐ `record` 에만 있는 것도 있다 — `androidConfig.speakerphone`·`audioManagerMode`.
  지금은 우리가 손으로 스피커폰을 강제하는데(`normalcall_controller.dart:2002` 근처),
  그 자리를 대체할 수 있는지 착수 때 본다(범위 밖이면 그대로 둔다).

## 3. ⚠ 위험과 미결

1. **⛔ 이 교체는 ①②를 더 가르지 않고 통째로 바꾸는 것이다.**
   MIC_OFF 가 뺀 넷 중 ③④는 배제됐고 ①(프레임 전달)②(AudioRecord 스레드)가 남았는데,
   `record` 는 **둘 다** 바꾼다. 효과가 나오면 «어느 쪽이었나» 는 영영 모른다.
   ⇒ 그래도 괜찮다 — 우리가 원하는 건 원인 규명이 아니라 **버벅임 제거**다.

2. **AEC 실험 토글 3종이 이 배관에 물려 있다**(`MIC_OFF`·`MIC_NO_AEC`·`MIC_ALWAYS_GATED`).
   갈아끼우면 그 토글들도 새 배관에 다시 물려야 한다. ⛔ 안 하면 다음에 재보려 할 때
   «토글을 켰는데 아무 일도 안 일어난다» 가 된다 — 2026-08-14 에 반나절 태운 그 함정이다.

3. **에코**. 지금은 `voice_communication` + `enableEchoCancellation` 으로 막는다.
   `record` 에서 같은 조합이 실제로 같은 효과를 내는지는 **실기기로만 확인된다.**
   ⚠ 실패하면 비버가 자기 목소리에 끊긴다 — barge-in 이 off 라도 STT 가 오염된다.

4. **권한 흐름**. `permission_handler` 로 받는 마이크 권한은 공유되지만, `record` 는
   자체 `hasPermission()` 을 갖는다. 두 경로가 어긋나면 «권한은 있는데 녹음이 안 열린다».

5. **되돌리기**. flutter_sound 는 복습·재생이 계속 쓰므로 **의존성을 지우지 않는다.**
   ⇒ 통화 배관만 바꾸므로 되돌리기가 쉽다(한 파일).
