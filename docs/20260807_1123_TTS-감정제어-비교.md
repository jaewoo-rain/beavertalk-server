## 결론 먼저: **Gemini-TTS 로 간다.** 같은 구글, 같은 목소리 이름, 감정 제어 있음

1차 조사 결론("원가로는 바꿀 이유 없다")은 그대로 유효하다. **이번엔 답이 다르게 나온다** —
축이 원가가 아니라 감정이기 때문이다. 그리고 운 좋게도 **가장 좋은 후보가 가장 싸다.**

| | 현행 Chirp3-HD | **Gemini-TTS** |
| --- | --- | --- |
| 감정 제어 | ❌ **없다**(운율·발음만) | ✅ 자연어 지시 + `[sigh]` `[laughing]` 류 태그 |
| 음색 이름 | Fenrir·Leda·… 30종 | **같은 이름 체계**(우리가 쓰는 5종 전부 있다) |
| 벤더·키·SDK | Cloud TTS | **같은 Cloud TTS**(신원·키 그대로) |
| 15분 통화 TTS | $0.180 | **$0.07~$0.23**(토큰 과금, ⚠단가 미확정) |
| 스트리밍 | ✅ | ✅ (공식 문서 확인 — §2) |

⭐ **결정적 이유는 가격이 아니라 음색이다.** Gemini-TTS 의 프리빌트 보이스 목록이
`core/tts.py` 의 `_CHIRP3_HD_VOICES` 와 **같은 이름 체계**다. 우리가 실제로 쓰는 5종
(Fenrir·Leda·Sadachbia·Sulafat·Vindemiatrix)이 **전부 들어 있다.**
→ 1차 조사에서 가장 크다고 봤던 **이전 비용(음색 재매핑 5~30종)이 사실상 0 이 된다.**
다른 벤더는 전부 이 비용을 문다. Gemini-TTS 만 안 문다.

**2순위는 Cartesia Sonic 3**(§5) — 지연이 진짜 병목으로 밝혀졌을 때만.

⛔ 단, **실사격 전에는 확정이 아니다.** §7 의 미확인 3개(단가 원문·스트리밍 실동작·한국어 감정 품질)가
남아 있고, 오늘 `LINEAR16` 도 문서로는 몰랐다가 400 을 맞고서야 알았다.

## 1. ⭐ 1순위 질문의 답: **Chirp3-HD 는 감정 제어가 없다**

bt-back 이 SDK 로 못 갈랐던 부분을 문서에서 확인했다.

| 시점 | Chirp3-HD 가 받는 것 |
| --- | --- |
| 2025-05 | **pace(속도)·pause(멈춤)** 제어 추가 — 전 로케일 |
| 2025-10 | **SSML 입력 지원** — 단 태그가 `<phoneme> <p> <s> <sub> <say-as>` 뿐 |
| **스트리밍** | ⛔ **SSML 태그 미지원**(비스트리밍 요청에만 적용) |

⭐ **저 SSML 태그들은 감정이 아니다.** 발음(`phoneme`), 문단·문장 경계(`p`/`s`), 치환(`sub`),
읽는 방식(`say-as`) — 전부 **무엇을 어떻게 발음하나**이지 **어떤 감정으로 말하나**가 아니다.
`<mstts:express-as>` 같은 스타일 태그도, ElevenLabs `[excited]` 같은 인라인 태그도 없다.

**그리고 우리 캐스케이드는 스트리밍 경로다 → SSML 자체가 안 먹는다.**
즉 현행 구성에서 비버 목소리가 평평한 건 **설정 문제가 아니라 모델의 한계**다.
Chirp3-HD 에서 감정을 짜내는 방법은 **없다.** 이건 튜닝으로 못 푼다.

## 2. ⛔ bt-back 이 지적한 모순 — 풀렸다. 답은 **(a) 문서가 좁게 쓰인 것**

- 1차 조사 인용: *"Streaming Cloud Text-to-Speech is only compatible with Chirp 3: HD voices."*
- SDK 실물: `StreamingSynthesisInput.prompt` 가 존재하고 원문이 "we pass the unedited text to
  **Gemini-TTS**" 라고 말한다.

**공식 Gemini-TTS 문서를 직접 열어 확인했다**(검색 요약이 아니라 문서 본문 추출 성공):

> "Streaming synthesis is suitable for real-time applications where fast response is critical."
> Cloud Text-to-Speech API 는 **multiple request multiple response** 스트리밍,
> Vertex AI API 는 단방향 스트리밍(단일 요청·다중 응답)을 지원한다.

→ **Gemini-TTS 는 스트리밍이 된다.** 1차 조사에서 인용한 문장은 **Chirp 계열 페이지의 서술**이고,
Gemini-TTS 에는 적용되지 않는다. `prompt` 필드가 스트리밍 입력에 달려 있는 것도 이것과 일관된다.

⚠ 다만 **"문서가 된다고 했다"와 "우리 SDK 버전·우리 코드 경로에서 실제로 된다"는 다르다.**
오늘 `LINEAR16` → 400 이 정확히 그 격차였다. **실사격 필요**(§7-1).

## 4. ElevenLabs 의 함정 — **감정과 실시간을 동시에 못 준다**

ElevenLabs 가 감정 태그로는 가장 유명하지만, 우리 용도에는 **구조적으로 안 맞는다**:

- **v3**(오디오 태그 있음) → ElevenLabs 자신이 *"higher latency, not suitable for real-time or
  conversational use cases"* 라고 명시한다. 사전 렌더링용이다.
- **Flash v2.5**(~75ms, 실시간용) → **오디오 태그가 없다.**

즉 "ElevenLabs 로 감정을 되찾자"는 **실시간 통화에서는 성립하지 않는다.** 게다가 v3 는 $0.60/15분 —
현행의 3.3배다. **탈락.**

같은 이유로 **Hume Octave** 는 감정이 제품 자체이고 지연도 좋지만(~100~200ms), 지원 11개 언어에
**한국어가 안 보인다.** 어학 앱의 주력 언어가 빠지면 1차 필터에서 탈락이다(1차 조사의 Deepgram 과 같다).

## 6. 이전 비용 — 음색 이름이 쓰이는 **세 곳**

| 쓰이는 곳 | Gemini-TTS 로 갈 때 | 타 벤더로 갈 때 |
| --- | --- | --- |
| Gemini **Live 통화** | 그대로 | 그대로(Live 는 안 바꾸므로) |
| **캐스케이드 TTS** | **이름 그대로**(같은 프리빌트 목록) | 새 벤더 음색 선정·매핑 |
| **표현 TTS**(복습 오디오) | 그대로 두거나 같이 이전 | **불일치 발생** — 같은 캐릭터가 통화와 복습에서 다른 목소리 |

DB 실측(SELECT 집계): `character` **5개**, 실사용 음색 **5종**(Fenrir·Leda·Sadachbia·Sulafat·
Vindemiatrix), `voice` 카탈로그 **30행**. **5종 전부 Gemini-TTS 목록에 있다.**

→ Gemini-TTS 이전 비용 = **음색 재매핑 0** + 모델 ID·요청 형식 변경 + `prompt`(감정 지시) 조립.
   타 벤더 이전 비용 = 위 전부 + **30종 재선정(사람이 듣고 고르는 일)** + 세 곳 불일치 관리.

### 감정 지시를 무엇으로 채우나 (구현 시)
이미 재료가 있다 — 캐릭터의 `role`/`personality`(`persona_prompt`)와 `call_mode`(공부/대화).
`prompt` 에 "따뜻하고 격려하는 선생님 톤" 같은 **한 줄**을 조립해 넣으면 된다.
⚠ 단 **LLM 이 생성한 문장을 그대로 넣지 마라** — 프롬프트 규율(문자열 조립, 생성 0)과 같은 이유다.

## 7. ⛔ 미확인 — 채우지 않고 비워둔다

1. **스트리밍 실동작.** 문서는 된다고 하지만 우리 SDK 버전·`StreamingSynthesizeRequest` 경로에서
   Gemini-TTS 모델이 실제로 도는지 **안 쏴봤다.** `LINEAR16` 전례가 있어 이건 반드시 실사격이다.
   확인 항목: 모델 지정 방법, `prompt` 가 스트리밍에서 먹는지, 출력이 **raw PCM 24k** 인지.
2. **Gemini-TTS 단가 원문.** 토큰 과금(오디오 1초 = 25 토큰)이라는 것까지는 잡았으나,
   $6/1M 과 $20/1M 두 숫자가 **검색 요약 기준**이고 **모델명이 공식 모델 ID 목록과 어긋난다**
   (문서상 ID: `gemini-3.1-flash-tts-preview`, `gemini-2.5-flash-tts`,
   `gemini-2.5-flash-lite-preview-tts`, `gemini-2.5-pro-tts` — 검색 요약이 말한 "3.5 Flash TTS" 는 없다).
   ⛔ **이 숫자로 플랜 가격을 정하지 마라.** 콘솔 청구서로 재확인해야 한다.
3. **한국어 감정 품질.** 1차 조사와 같다 — **한 문장도 안 들어봤다.** 크레덴셜·계정이 없다.
   "감정 제어 파라미터가 있다"와 "한국어에서 자연스럽게 들린다"는 다른 얘기다.
   (Azure 는 실제로 *"zh-CN 음성에서 style 값을 바꿔도 출력이 동일하다"* 는 사용자 보고가 있다 —
   파라미터 존재가 동작 보장이 아니라는 증거다.)
4. **Azure ko-KR 음성의 style 목록.** 스타일은 음성별로 다른데 한국어 목록을 못 찾았다.
5. **Gemini-TTS 의 중국어 지원 등급**, 베트남어는 preview 라는 것까지만 확인.
6. **Journey/Polyglot/Chirp/ChirpHD** 레거시 계열, **PlayHT**, **CLOVA·Typecast 단가** — 미확인.
7. **지연.** 1차 조사와 같은 구멍 — 첫소리 2.7초 중 TTS 몫을 아직 안 갈랐다.
   Gemini-TTS 는 생성형이라 **Chirp3-HD 보다 느릴 가능성**이 있고, 그게 이 안의 최대 리스크다.

4. 지연이 문제로 확정되면 그때 **Cartesia**(더 비싸지만 최저 지연)를 본다.

pro 를 쓰면 $0.225(현행의 1.25배). **감정을 얻고도 원가가 내려간다는 §5 의 결론이 원문으로 확인됐다.**

### ⛔ 단위가 다르다 — 문자 수로는 못 잰다

클래식 TTS 는 **문자 수** 과금인데 Gemini-TTS 는 **출력 오디오 토큰** 과금이다.
같은 문장이라도 **천천히 읽으면 더 비싸다.** 그래서 `tts.chars` 로는 계산이 불가능하고,
문자→초 환산은 말하는 속도에 따라 배로 틀린다(그럴듯한 거짓 숫자가 된다).

→ 산식은 **`tts.audio_s`(합성된 오디오 초)를 요구**하고, 없으면 추정하지 않고
**미상으로 드러낸다**(`tts:<모델>(audio_s 없음 …)`). 0 원으로 먹으면 캐스케이드가 공짜로 보인다.
⭐ **cascade-impl 이 수집해야 할 값: `vendors.tts.audio_s`.** PCM16/24k 라
`보낸 바이트 / (24000 × 2)` 로 정확히 나온다(추정이 아니라 실측이다).

`gemini-2.5-flash-lite-preview-tts` 는 가격표에 행이 없어 **flash 단가를 보수적으로 차용**하고
코드 주석에 미확인이라고 박았다 — 과소 계상(캐스케이드가 싸 보임)이 과대 계상보다 위험해서다.
