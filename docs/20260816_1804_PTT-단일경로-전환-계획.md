## 1. ⭐⭐ 벤더 계약이 바뀌면서 **자동으로 죽는 것**들 (여기가 판단의 뿌리)

`turn_detection: null` 을 보내는 순간, 지금 코드가 의존하는 **입력 두 종류가 사라진다.**
이건 우리가 지우는 게 아니라 **벤더가 안 보내는 것**이다.

### ① VAD 이벤트가 안 온다
`input_audio_buffer.speech_started` / `speech_stopped` 는 **server VAD 이벤트**다.
turn_detection 이 null 이면 발생 자체가 없다 — 스파이크 §2 본시험 응답에 그 둘이 **없다**
(`committed → item.added → item.done → transcription.completed` 만 왔다).

⇒ `core/openai_stt.py:270-273` 의 두 분기가 영영 안 탄다
⇒ `SPEECH_BEGIN` / `SPEECH_END` 이벤트가 세션에 **한 건도 안 들어온다**

### ② 오디오 시각(offset)이 **전부 −1** 이 된다
`SttV2Event.offset_ms` 기본값은 −1(`core/stt.py:234`). 그리고 OpenAI 어댑터는
**전사 이벤트에 offset 을 안 싣는다**(`openai_stt.py:278,283` — `offset_ms` 미지정).
지금 offset 은 **VAD 이벤트에서만** 온다(`:271,273`). ①이 사라지면 **오디오 타임라인이 통째로 없다.**

⇒ 아래가 전부 **입력이 없어 무력화**된다(지우지 않아도 이미 아무것도 안 지킨다):

| 코드 | 파일:행 | null 에서의 실제 동작 |
|---|---|---|
| `_sanitize_offset` | `cascade_session.py:1663-1693` | 검사 대상이 없다 |
| `_is_same_utterance` | `:1820-1837` | `:1834` 가드에 걸려 **항상 False** |
| `_arm_close_timer` 의 `already_ms` | `:2057-2068` | 항상 0 ⇒ 앵커 절약 0 |
| `_stt_profile` VAD 앵커 | `:289-398, 2061-2066` | `_turn_end_offset_ms` 가 영영 −1 |
| `pipeline_lag_ms` | `:1910` | 영영 0 ⇒ `cascade turn:` 계기 한 칸이 거짓 |

⭐ **이게 ⓐ 를 정당화하는 가장 강한 근거다.** ⓑ(모드 분기)로 남겨도 PTT 모드에서 이 코드는
**살아 있으면서 아무것도 안 지킨다** — 사장님이 못 박은 "제일 나쁜 상태" 그 자체다.
⇒ 남기느냐 지우느냐가 아니라, **지우지 않으면 거짓말하는 계기판이 7개 생긴다.**

### ③ ⚠ 그리고 **hold 중에는 부분 전사가 안 온다**
Realtime 은 **item 단위로 전사**하고 item 은 commit 으로 생긴다. commit 이 없으면 item 이
없고, 따라서 `transcription.delta` 도 없다.
⇒ **버튼을 누르고 있는 동안 사용자 자막(`input_transcript`)이 화면에 안 뜬다.**
· 확신도: **구조상 확실 + 스파이크 이벤트 순서와 일치.** 다만 delta 유무를 직접 재지는 않았다.
· ⛔ 제품 결정이 필요하다(§7-①). 그리고 **투기적 실행의 전제를 무너뜨린다**(§6).

## 2. 무엇이 실제로 얼마나 빨라지는가 (숫자)

기준: 앱 실측 `말끝 → 들림` 중앙 **2,354ms**(전수조사 §1, 앱 6턴).

| 구간 | 현재 ms | PTT 후 | 근거 |
|---|---:|---:|---|
| 벤더 침묵창(server_vad) | 300 | **0** | `OPENAI_STT_SILENCE_MS=300` 실적용 확정(스파이크 §3) |
| 서버 침묵 타이머 잔여 | ~340 | **0** | 800 − 앵커절약 실측 442~550(`_close_turn` 로그) |
| 최종 전사 대기 | **0**(위 두 구간에 가려짐) | **+320** (p95 430) | 전사확정 실측 중앙 320/p95 430(`config.py:2045-2048` 주석) |
| 사람 릴리즈 지연 **R** | 0 | **+R** | ⛔ **미측정**(플랜 §11-3) |
| 릴리즈 그레이스 **G** | 0 | **+G** | 정책값. 플랜 §4 L1 잠정 300 |
| LLM 첫조각 | 844 | 844 | **못 건드린다** |
| 문장 완성 | 206 | 206 | 못 건드린다 |
| 묶음 대기 | 82 | 82 | 우리 정책이나 PTT 와 무관 |
| TTS 첫 바이트 | 819 | 819 | **못 건드린다** |
| 송출 | 16 | 16 | |
| 클라 쿠션(앱) | 520 | 520 | PTT 무관(별건 수정으로 −200 예정) |

⭐ **가리기(hiding)가 핵심이다.** 지금 최종 전사(320ms)는 벤더 침묵창 300 + 서버 대기 340 =
640ms 창 **안에서** 도착해 사용자를 기다리게 하지 않는다. PTT 는 그 창을 없애므로
**전사 대기가 통째로 노출된다.**

```
순변화 = (R + G + 320) − 640 = R + G − 320
  R=0,   G=0    →  −320ms  (2,354 대비 13.6%)
  R=150, G=0    →  −170ms  (7.2%)
  R=150, G=300  →  +130ms  ← 더 느려진다
  R=200, G=300  →  +180ms  ← 더 느려진다
```

⇒ 🔴 **"응답시간 최대한 빠르게"라는 목표만 놓고 보면, PTT 는 R+G < 320ms 일 때만 목표를
   달성한다.** 그리고 R 은 안 잰 값이고 G 는 잘림 방지에 필요한 값이다.

### 못 줄이는 것 — 명시
**1,663ms(전체 71%)는 PTT 로 1ms 도 안 줄어든다.** LLM 첫 토큰 844 + TTS 첫 바이트 819 는
벤더 왕복이고, 사장님 지시("모델은 기존에 쓰던거 그대로")가 교체를 배제한다. 지연 개선의
**상한이 640ms(27%)** 이며, 실현치는 그보다 R+G 만큼 작다.

### ⭐ 그런데 지연 표에 안 잡히는 **진짜 이득**이 하나 있다 — 끊기 지연
지금 사용자가 비버 말을 끊으려면 **판정 사다리 3층**을 통과해야 한다:
`_bargein_allowed`(`:2201`) ⓪들린 300ms 이상 → ①에너지 임계 → ②전사 확인 **보류 최대
3,500ms**(`CASCADE_BARGEIN_PENDING_MS`, `config.py:514`).
PTT 는 **버튼 다운 = 확정**이다 ⇒ 끊기 지연이 `보류 0~3,500ms + 전사 왕복` → **0ms**.
⛔ 이 값은 `말끝→소리` 지표에 안 잡히지만 **체감으로는 가장 큰 항**일 수 있다.
⚠ 다만 지금 `CASCADE_MIC_ALWAYS_OPEN=False`(`config.py:488`)면 barge-in 은 아예 기각된다
(`:2249`) — 즉 **현재 운영값에 따라 이 이득은 "3.5초 → 0" 이 아니라 "불가 → 가능"** 이다.
운영 실값 확인이 필요하다(내가 못 봤다).

## 4. ⚠ 지우기 과정에서 밟을 지뢰 3개 (내가 코드에서 찾은 것)

### A. `_close_turn` 의 `speech_ms` 가 조용히 0 이 된다
`:2130` 은 `_last_voice_at − _turn_began_at` 인데 `_last_voice_at` 은 STT 이벤트로만
갱신된다(`:1905`). 이벤트가 사라지면 **에러 없이 0** 이 나온다.
⇒ 플랜 §8 이 요구한 A/B 기준선(`turn 당 speech_ms 분포`)이 **PTT 쪽에서 통째로 0** 이 되어
비교가 불가능해진다. R5 치환이 없으면 **PTT 도입 효과를 영영 측정 못 한다.**

### B. `빈 턴` 로그와 `_resume_interrupted` 의 트리거가 훨씬 자주 온다
`:2173-2198`. PTT 는 오조작(눌렀다 바로 뗌)이 **정상 조작 안에** 있다(스파이크 §4).
⇒ `_resume_interrupted`(K3)가 지금보다 자주 돈다 — 살려야 하는 이유가 강해졌다.
⚠ 동시에 `input_audio_buffer_commit_empty` 도 그때 난다 — 이미 비치명 처리됨(`openai_stt.py:48`).

### C. D11(꼬리 무음)은 **조건부**다
릴리즈마다 commit 하므로 통화 중엔 필요 없다. ⛔ 그런데 **버튼을 누른 채 종료 버튼을 누르는**
경우(`_pump_in:1548` stop 경로)엔 커밋 안 된 오디오가 남는다.
⇒ 꼬리 무음이 아니라 **stop 처리에서 commit 1회**로 대체한다. 무음 1.5초 + `sleep` 이
사라지므로 **통화 종료가 1.5초 빨라지는 덤**이 있다.

## 5. ⭐ `_discard_unheard_reply` 가 PTT 에서 핵심이 되는 이유 (인수인계 확인)

인수인계 주장에 동의하고, 코드로 근거를 붙인다.

지금은 사용자가 말을 시작해도 **비버를 끊을지**가 3층 판정에 달려 있다(`_bargein_allowed`).
PTT 는 그 판정을 없애지만, **THINKING 구간**(LLM 생성 중, 오디오 0바이트)은 그대로 남는다 —
실측 첫소리 2,026ms 동안 비버는 소리가 없다.
그 사이 사용자가 버튼을 누르면:
· `_audible_ms()` = 0 ⇒ `_beaver_unheard()` = True(`:2434`)
· ⇒ `_start_reply` 가 `_discard_unheard_reply` 로 간다(`:2452`)
· ⇒ **아무도 안 들은 대답을 버리고 새 발화에 답한다**

⛔ 이걸 지우면 "멈칫한 학습자"가 **2초 전 자기 말에 대한 답**을 듣는다. 그리고 PTT 는
버튼이 있어서 **사용자가 더 자주 다시 시작한다** ⇒ 발생 빈도가 지금보다 는다.
⇒ K2·K4 는 **지우면 안 되는 것 1순위**다.

## 6. 투기적 실행(릴리즈 전 LLM 선행 시작) — **내 판단: v1 에서는 안 한다**

사장님·bt-back 이 "남은 유일한 큰 레버"로 보신 것에 대한 답이다.

### 근거 4개

**① 전제가 성립하지 않는다.** 투기 실행은 "릴리즈 전에 텍스트가 있다"를 전제하는데,
`turn_detection: null` 에서는 **commit 전에 전사가 한 글자도 안 온다**(§1-③).
⇒ 릴리즈 전에 투기할 **재료 자체가 없다.** 재료를 만들려면 hold 중 주기적 commit 이
필요한데, 그건 **단어 중간에서 오디오를 자르는** 것이라 전사 정확도 손실이 미측정이다.
⚠ 우리가 OpenAI 를 고른 **유일한 이유가 code-switching 정확도**다(`openai_stt.py:3-11`) —
정확도를 지연과 바꾸는 건 이 벤더를 고른 이유를 되돌리는 것이다.

**② 이득의 상한이 미측정 항보다 작다.** 투기로 벌 수 있는 최대치는 전사 대기
**320ms**(p95 430)다. 그런데 우리가 아직 안 잰 R 은 그보다 클 수 있다(플랜 §2 가 "200ms 면
이득이 마이너스"라고 경고한 그 값).
⇒ **더 큰 미측정 항을 두고 더 작은 항을 최적화하는 순서**가 된다.

**③ PTT 의 존재 이유와 정면 충돌한다.** 플랜 §3-① 이 말한 PTT 의 최대 이득은
**추측 제거**다(추측 코드 430줄·노브 10개를 버튼 신호로 치환). 투기적 실행은 정의상
**"사용자가 말을 끝내기 전에 뭘 말할지 추측하는 것"** 이고, 오판 시 취소·재실행 배관이
필요하다 — 방금 지운 것과 **같은 종류의 복잡도를 새 자리에 다시 만든다.**

**④ 원가.** 오판마다 LLM 호출이 하나 더 나간다. 사장님 지시가 "모델은 기존 그대로"라
모델 다운그레이드로 상쇄할 수도 없다.

### ⇒ 대신 이걸 한다 (추측 0, 대가 0)

| 대안 | 예상 | 확신 |
|---|---:|---|
| ⓐ **버튼 다운 = 즉시 취소** — 판정 3층 생략 | 끊기 지연 **0~3,500ms → 0** | 확정(§2) |
| ⓑ **stop 경로 commit 로 꼬리무음 1.5초 제거** | 통화 종료 −1,500ms | 코드 확인(`openai_stt.py:215`) |
| ⓒ **LLM keepalive 30s** — 전수조사 §5-#2, 이미 승인·A/B 8/8 | −185ms | 교차확인 |

### ⇒ 조건부 YES 로 다시 올릴 자리
**R 을 재고 나서**, `R + G > 320` 으로 나오면 그때 투기가 **유일한 탈출구**가 된다.
그때는 이 순서로 검토한다:
1. `completed` 가 아니라 **마지막 `delta` 로 LLM 을 건다**(가장 싸고 취소 배관이 필요 없다.
   위험: 꼬리 잘린 텍스트로 답한다)
2. hold 중 주기 commit (전사 정확도 실측이 선행 조건)
⛔ 지금 이 순서를 뒤집어 2번부터 하면 벤더 선택 근거를 잃는다.
