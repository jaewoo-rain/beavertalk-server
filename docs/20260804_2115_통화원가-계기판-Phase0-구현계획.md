## 1. 코드 검증 결과 — 제안서 대비 정정 2건

착수 전 제안서 주장을 실제 코드·설치 SDK(`google-genai==2.10.0`)로 확인했다.

### 1-1. 확인된 사실 (제안서 그대로 맞음)

- `core/gemini_live.py:202` `events()` 루프는 `response.usage_metadata` 를 **한 번도 읽지 않는다.**
- SDK `types.LiveServerMessage.usage_metadata: Optional[UsageMetadata]` 실재(`types.py:19701`).
  `UsageMetadata`(`types.py:19475`) 필드 확인 —
  `prompt_token_count` · `cached_content_token_count` · `response_token_count` ·
  `tool_use_prompt_token_count` · `thoughts_token_count` · `total_token_count` ·
  `prompt_tokens_details` / `cache_tokens_details` / `response_tokens_details`
  (`list[ModalityTokenCount]`) · `traffic_type`.
- `domains/learning/service/normalcall_service.py:1193` `analyze_call` → `generate_structured(...)`
  호출에 `thinking_budget` **미전달** → `core/gemini_analysis.py:54` 계약상 `thinking_config`
  자체를 넣지 않음 → 모델 기본 동적 thinking. 제안서 주장대로다.
- 대조군 확인: 사이드카는 이미 전부 `thinking_budget=0` —
  힌트(`call_session.py:1302`), 레벨테스트 턴판정(`normalcall_service.py:1966`, `:2084`),
  발음 팁(`pronunciation_service.py:199`).

### 1-2. ⚠ 정정 ① — `LiveEventKind` 는 6종이 아니라 **7종**이다

제안서 §3-1(a)의 리터럴을 그대로 붙이면 **`tool_call` 이 사라진다.** 현행(`gemini_live.py:50`):

```python
LiveEventKind = Literal[
    "audio", "in_tr", "out_tr", "interrupted", "turn_end", "go_away", "tool_call"
]
```

`tool_call` 은 레벨테스트 조기종료 function-call(`LEVELTEST_DONE_TOOL`) 신호 경로다.
→ **`usage` 를 기존 7종 뒤에 덧붙인다**(제거 0).

### 1-3. ⚠ 정정 ② — 비용 산식의 전제가 미검증이다

제안서 §3-1(d)는 "턴별 `prompt_token_count` 의 **합** = 재과금 항"으로 산식을 세웠다.
그런데 Live API 의 `usage_metadata` 가 **메시지별 증분**인지 **세션 누적**인지 확정할 근거가 없다.

- SDK `_live_converters.py:1477` 은 서버의 `usageMetadata` 를 **그대로 통과**시킬 뿐,
  누적/차분 로직이 없다. 즉 의미는 전적으로 서버가 정한다.
- 누적인데 합산하면 원가가 **턴 수 배로 부풀려진다**(15턴이면 최대 15배). 반대로 증분인데
  마지막 값만 쓰면 과소 추정한다. 어느 쪽이든 계기판이 거짓말을 한다.

**대응**: 판별을 코드가 아니라 **첫 실통화 1건의 데이터**로 한다.
- 원시 메시지 단위로 `(경과초, prompt, resp, total)` 시계열을 남기고,
- 종료 로그에 **Σ(합)과 last(마지막 값)를 둘 다** 찍는다.
- `total_token_count` 가 단조증가 → **누적**(last 채택). 오르내림/톱니 → **증분**(Σ 채택).

이 판별은 제안서 §4의 "압축이 실제로 도는가"(톱니면 발동, 단조증가면 미발동)와
**같은 시계열 하나로 동시에 해결**된다. 별도 작업 없음.

- 어댑터 규율 유지: 여기서 원가 계산·집계를 하지 않는다. 원본을 그대로 넘긴다.

## 3. 로그 스키마 (분석 시 그대로 파싱)

실제 출력(구현 후 확인). 단일 라인, `logger.info`, 전부 `key=value`:

```
normalcall usage: call_id=880 type=normal msgs=22 dropped=0 t=[13.6..299.2]
sum_prompt=142120 sum_resp=18040 sum_thoughts=0 sum_total=160160
last_prompt=11080 last_total=11900 monotonic=True
sum_in=AUDIO=120802,TEXT=21318 sum_out=AUDIO=17600,TEXT=440
```

`LIVE_USAGE_TRACE=true` 일 때 1줄 추가:

```
normalcall usage trace: call_id=880 t:prompt/total 13.6:1840/2660 27.2:2280/3100 …
```

### 판별표 (첫 실통화 1건으로 확정)

| 관측 | 해석 | 원가 산식 |
|---|---|---|
| `monotonic=True` + trace 가 매끈한 단조증가 | **누적** 의심 + **압축 미발동** | `last_*` 채택 |
| `monotonic=False` (trace 가 톱니) | **증분** 확정 + **압축 발동** | `sum_*` 채택 |
| `monotonic=True` 인데 `sum_total` 이 청구서와 맞음 | **증분**(압축만 미발동) | `sum_*` 채택 |

원가 산식(택일 후 동일 형태):

```
cost = in_AUDIO×$3.00 + in_TEXT×$0.50 + out_AUDIO×$12.00 + out_TEXT×$2.00   (per 1M tok)
```

**모달리티는 detail 에서 그대로 나오므로 오디오 토큰율 25 vs 32 가정이 불요하다** —
제안서 §1-2 의 ±25% 불확실성이 이 필드 하나로 사라진다.

### 사전 교차검증 (구현 직후, 시뮬레이션)

`core/config.py:93` 에 이미 남아 있던 실측 메모 —
**2026-08-02, call 880, 5분/22턴, 입력 209,974 tok(오디오 85%), 원가 ~$0.58** — 를
같은 형태로 재현해 보면 산식이 맞아떨어진다:

- 컨텍스트가 1.4k → 11k 로 자라는 22턴을 넣으면 `sum_in=AUDIO 120,802 / TEXT 21,318`,
  `sum_out=AUDIO 17,600 / TEXT 440`.
- 위 산식 적용 → **$0.585**. `config.py` 메모의 "~$0.58" 과 일치한다.

☞ 시사점 2개.
1. **`usage_metadata` 는 증분일 가능성이 높다.** 209,974 라는 실측 입력 토큰은 5분 통화의
   최대 컨텍스트(≈11,000)의 19배라, 턴별 prompt 의 **합**이어야만 나오는 수다.
2. **제안서의 추정 $0.35 는 약 40% 낮다.** 실제 기준선은 $0.58 쪽으로 보이며, 그렇다면
   절감의 기대 효과(절대액)는 제안서 표보다 크다. **단, 확정은 실통화 로그로 한다.**
