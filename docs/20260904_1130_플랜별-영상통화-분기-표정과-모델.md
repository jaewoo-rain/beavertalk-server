# 플랜별 통화 분기 — 영상(표정)·모델을 구독 등급으로 가른다

작성 2026-09-04 11:30 · 상태 **계획 확정 / 미구현** · 브랜치 `merge/dev-prompt-work`
관련 `domains/learning/service/call_service.py` · `domains/learning/realtime/call_session.py`
     · `core/config.py` · `core/gemini_live.py`

## 0. 사장님 지시 (2026-09-04)

```
max 만 영상통화. free·pro 는 모두 음성통화.
pro·max 는 5분씩 최대 15분.
모델을 가르는 이유는 원가 절감.
free 는 한 조각으로만.
2.5 로 내리더라도 일단 동일한 프롬프트 규칙으로 — 품질이 달라지면 그때 수정.
```

## 1. 목표 표

| | Free | Pro | Max |
|---|---|---|---|
| 통화 | 음성 | 음성 | **영상** |
| 표정 `set_face` | ✗ | ✗ | ✓ |
| Live 모델 | 2.5 | 2.5 | 3.1 |
| 조각 수 | 1 | 3 | 3 |

## 2. ⭐ 이미 있는 것 — 새로 만들 필요가 없다

```python
# call_service.py:110
CALL_FRAGMENT_S = 360.0                      # 조각 하나 = 6분
CALL_FRAGMENTS_BY_PLAN = {None: 1, "pro": 3, "max": 3}
effective_plan(db, member_id)                # 상태 8종 → 플랜 판정
```

⇒ **조각 요구(free 1 / pro·max 3)는 이미 코드가 그대로다.** 손댈 것이 없다.

⚠ **"5분씩 15분"과 코드의 "6분씩 18분"은 어긋난 것이 아니다.** 조각 경계는 프론트가
  정한다(5분에 "이어서 하시겠습니까?" → 소켓 닫기). 서버 6분은 그 뒤에 오는 **백스톱**이라
  넉넉해야 한다 — 5분에 딱 맞추면 클라 왕복 한 번에 서버가 먼저 끊어 비버 말이 잘린다.
  사용자가 겪는 값은 5분×3=15분이 맞다.

## 3. 새로 만들 것 — 표 두 개와 배선

지금은 두 축이 **전역 env** 하나씩이다. 사용자별로 갈라지는 배선이 아예 없다.

```
표정  face_tool = bool(settings.LIVE_FACE_SPIKE)   # call_session.py:1351
모델  settings.GEMINI_LIVE_MODEL                   # gemini_live.py:623
```

⇒ `CALL_FRAGMENTS_BY_PLAN` **옆에 같은 모양의 표 두 개**를 세우고, 통화 시작 지점에서
  이미 읽고 있는 `member_id` 로 플랜을 물어 넘긴다.

```python
CALL_VIDEO_BY_PLAN:  dict[str | None, bool] = {None: False, "pro": False, "max": True}
CALL_LIVE_MODEL_BY_PLAN: dict[str | None, str | None] = {
    None: LIVE_MODEL_VOICE, "pro": LIVE_MODEL_VOICE, "max": LIVE_MODEL_VIDEO,
}
```

⛔ **빈 dict 금지 · 모르는 플랜은 Free 로 떨어뜨린다**(R5, 기존 표와 같은 규율).
  "모르면 짧게·싸게 준다"가 안전하다 — 길게 줬다 원가가 새는 것보다 낫다.

⛔ **상태(state)와 플랜(plan)은 다른 축이다.** `grace`·`on_hold`·`ending` 은 "직전에 무슨
  플랜이었나"를 유지하므로 상태만 보고 정하면 안 된다. 판정은 반드시 `effective_plan` 하나로
  간다 — 앱도 같은 구조라(`subscription_state.dart` 의 `impliedTier`) 어긋나면 앱·서버가
  다르게 판정한다.

## 4. 원가 근거 — 무엇이 확실하고 무엇이 아닌가

### ✅ 확실한 것 — 표정 도구를 빼면 지시문이 준다 (실측)

```
지시문 face_tool=True   6,877자
지시문 face_tool=False  5,819자
차이                    1,058자 ≈ 423 토큰
```

그리고 이 몫은 **매 턴 전액 재과금된다**(Live 는 프리필을 매번 다시 센다).
실측 통화 1289(5분40초, 20 usage 메시지): `sum_in TEXT=138,523` 토큰.
423 × 20 ≈ **8,460 토큰**이 지시문 몫만으로 빠진다.

여기에 더해 (미계량):
- `set_face` **tool 스키마**가 매 턴 컨텍스트에 실린다
- tool 호출·응답이 대화 이력에 쌓인다 (통화 1289 에서 10회)

### ⭐ 단가 확인은 건너뛴다 — 대신 **실측이 가능하게** 만든다 (사장님 결정 2026-09-04)

> "단가 당연히 줄어드니까 확인은 필요없고, 실측을 위한거면 작성해도 괜찮을듯."

⇒ 벤더 단가표를 뒤지는 대신, **나중에 DB 로 답할 수 있게** 만든다.

⛔ **지금은 그게 불가능하다.** 통화 행의 엔진 문자열이 모델을 안 담는다:

```python
ENGINE_LIVE_GEMINI = "live:gemini-native-audio"   # normalcall_service.py:1155
```

2.5 통화와 3.1 통화가 **같은 문자열로 섞인다.** 플랜 분기를 넣어 놓고도
"2.5 로 내린 게 얼마 아꼈나"를 못 묻는다.

⇒ 모델을 실어 `live:gemini-2.5-native-audio` / `live:gemini-3.1-native-audio` 로 남긴다.
  컬럼 계약이 이미 `'<모드>:<구성요소>'` 라 **스키마 변경이 필요 없다**(call.py:126 주석).
  그러면 한 줄로 답이 나온다:

```sql
select usage_engine, count(*), avg(usage_in_text), avg(usage_out_audio),
       avg(total_time)
from call where usage_engine like 'live:%' group by 1;
```

⚠ 단가표(`LIVE_TOKEN_PRICE_USD`)는 모델별로 **쪼개 두되 값은 양쪽 동일**로 시작한다.
  추측한 숫자를 넣으면 계기판이 조용히 거짓말한다 — 벤더 단가를 알게 되는 날 한 곳만
  고치면 되도록 **자리만** 만들어 둔다.

### (참고) 원래 적었던 미확인 사항

`LIVE_TOKEN_PRICE_USD`(normalcall_service.py:1105)는 **모델별로 안 갈라져 있다.**
in_audio $3 / in_text $0.5 / out_audio $12 / out_text $2 — 하나뿐이다.
⇒ **"2.5 가 싸다"는 코드에 근거가 없다.** 구현 전 벤더 단가표로 확인하고, 다르면 이 표를
  모델별로 쪼개야 한다(그래야 계기판이 거짓말을 안 한다).

⚠ 확인 전까지 이 변경의 **입증된 절감은 「표정 도구 제거」뿐**이다. 모델 교체는 그와 별개다.

## 5. ⚠ 위험과 미결

1. **2.5 는 우리 프롬프트로 튜닝된 적이 없다.** 지금 지시문·재접지는 3.1 기준이다
   (재접지 통로 `send_realtime_input` 도 3.1 규약). 사장님 지시대로 **같은 프롬프트로 먼저
   내보내고**, 품질이 달라지면 그때 고친다. ⇒ 통화 1건 실측이 착수 직후 필요하다.
2. **벙어리 인사는 3.1 전환(8/23)부터 시작됐다.** 2.5 로 내리는 free·pro 에서는
   **사라질 수도 있다** — 그러면 그 자체가 원인 규명의 단서다. 통화 후 로그를 볼 것.
3. **표정을 끄면 프론트가 무엇을 보나.** 마커가 안 오는 것은 계약상 정상이지만
   (`ServerSentenceMarker` 는 선택적), 앱이 "영상통화 화면"을 띄운 채 표정만 없으면
   어색하다. ⇒ 프론트가 플랜을 알아야 한다. `call_meta`/`call_started` 에 실을지 별건.
4. **앱 문구가 옛 계약이다** — `app_en.arb` Pro "Unlimited calls. 15 minutes each."
   는 6분×3 과 어긋난다(call_service.py 주석이 이미 지적). 프론트 몫.
5. **`LIVE_FACE_SPIKE` 의 위치가 바뀐다.** 지금은 "표정 기능 자체의 on/off"인데, 플랜 표가
   들어오면 **비상 차단기**로 격하된다(켜져 있어도 플랜이 아니면 안 준다). 주석으로 못박을 것.

## 7. 수용 기준

- Free·Pro 통화에서 `set_face` tool 이 **아예 안 실린다**(로그에 표정 0건)
- Max 통화는 지금과 **동일**하게 동작한다(표정·모델 3.1)
- 모르는/없는 플랜은 Free 취급 — 예외가 아니라 조용한 강등
- `effective_plan` 이 유일한 판정기 — 상태 문자열을 직접 보는 코드가 없다
