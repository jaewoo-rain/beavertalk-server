# 02. Event Loop — 한 스레드로 수천 연결을 다루는 마법

> **한 줄 요약**: 이벤트 루프는 **한 스레드**가 여러 작업 사이를 "기다림이 생길 때마다 다른 일로 갈아타며" 관리하는 방식이다. 대기(I/O)가 많은 서버가 스레드 수천 개 없이도 수천 연결을 다룰 수 있는 비결.

**이 챕터의 키워드**: Event Loop, Non-blocking I/O, Cooperative Multitasking

---

## 1. 왜 중요한가

FastAPI 가 "빠르다"는 말의 절반은 이 이벤트 루프 덕이다. 우리 서버는 통화 하나가 5분 내내 열려 있는 **장수명 WebSocket** 이 여러 개 동시에 떠 있다. 각 통화마다 OS 스레드를 하나씩 붙이면 금세 수백 스레드가 되어 메모리·문맥전환 비용이 폭발한다. 대신 **한 스레드 + 이벤트 루프**가 "지금 데이터 온 통화"만 골라 처리하면, 놀고 있는(대기 중인) 수많은 연결이 거의 공짜가 된다. 단, 이 마법에는 **깨지는 조건**이 있고(블로킹), 그걸 모르면 서버가 통째로 멈춘다.

## 2. 개념 — 비유로 시작

**비유**: 라면집 요리사(=스레드)가 딱 한 명인데 냄비(=연결)는 여러 개다. 서툰 요리사는 1번 냄비 앞에 서서 **물이 끓을 때까지 멍하니 지켜본다(=블로킹)**. 그동안 2·3·4번 냄비는 방치된다. 능숙한 요리사는 1번에 물을 올리고 **끓는 동안 2번으로 가서** 스프를 넣고, 3번 면을 넣고... "기다림이 필요한 순간마다" 다른 냄비로 옮겨 다닌다. 냄비가 100개여도 요리사는 한 명으로 충분하다 — **일이 대부분 '기다림'이기 때문**이다.

- **이벤트 루프** = 그 능숙한 요리사의 머릿속 순회 규칙: "지금 준비된(=데이터 도착/타이머 만료된) 냄비로 간다."
- **Non-blocking I/O** = "이 냄비 지금 끓었나?"를 묻고 **안 끓었으면 바로 돌아서는** 조리법. 서서 기다리지 않는다.
- **Cooperative Multitasking(협력적 멀티태스킹)** = 각 냄비 작업이 "나 지금 기다려야 해, 다른 냄비 보고 와"라고 **스스로 양보**해야 순회가 돈다. 아무도 안 뺏는다(비선점).

**정확한 정의**: 이벤트 루프는 "실행 가능한 작업들의 큐를 돌며 하나씩 실행하고, 각 작업이 `await`(양보)하면 잠시 제쳐 뒀다가, 그 작업이 기다리던 이벤트(소켓 읽기 가능, 타이머 만료 등)가 준비되면 다시 큐에 넣는" 단일 스레드 루프다. OS 의 `epoll`/`kqueue`/`IOCP`(11장) 에게 "이 소켓들 중 하나라도 준비되면 알려줘"라고 위임하고, 준비된 것만 깨워 처리한다.

## 3. 그림

```
[이벤트 루프 = 한 스레드]

  준비된 작업 큐:  (A) (C)            대기 중(기다림 등록):  B(소켓), D(타이머)
      │
      ├─ A 실행 → A 가 await(소켓 read) → "준비되면 알려줘" 등록하고 물러남
      ├─ C 실행 → C 가 await(sleep 1s)  → 타이머 등록하고 물러남
      │
   (OS epoll/IOCP 에게) "B 소켓, D 타이머, A 소켓 중 준비된 거?"
      │  B 준비됨! ↓
      └─ B 를 큐에 넣고 다시 실행 ...

  => 한 스레드가 '준비된 것'만 돌린다. 대기는 OS 에 맡긴다(공짜에 가까움).

블로킹이 끼면 (치명적):
  ├─ A 실행 → time.sleep(1)  ← 양보 안 함! 루프 스레드가 1초간 정지
  │                            그동안 B·C·D 전부 못 돎 (전 냄비 방치)
```

## 4. 직접 돌려보자

### (a) gather 로 100개의 await 를 동시에 → 총 ~1초

파일: [`examples/02_event_loop_gather.py`](examples/02_event_loop_gather.py)

```python
async def one(i):
    await asyncio.sleep(1.0)   # 여기서 루프에 양보
    return i

await asyncio.gather(*(one(i) for i in range(100)))
```

실행:
```bash
python examples/02_event_loop_gather.py
```

실제 출력:
```
asyncio.sleep(1.0) x100 동시 실행
  총 시간   : 1.004 s   <- 합(100초)이 아님
  결과 개수 : 100
```

**어디를 보라**: `1.0초 × 100 = 100초`가 **아니다**. 총 `1.004초`. 코루틴 100개가 각자 `asyncio.sleep` 에서 루프에 제어를 넘기고, 루프는 그 100개의 타이머를 **한꺼번에** OS 에 걸어 둔 뒤 함께 기다린다. 100개의 "1초 대기"가 완전히 겹쳤다. 스레드는 **한 개**뿐인데 100개 연결을 동시에 다룬 셈 — 이것이 서버가 스레드 폭발 없이 대량 연결을 감당하는 원리다.

### (b) 함정 데모 — async 안의 time.sleep 은 동시성을 죽인다

파일: [`examples/02_event_loop_blocking.py`](examples/02_event_loop_blocking.py)

한 줄(sleep 종류)만 다르다:
```python
async def blocking_task():
    time.sleep(1.0)          # ❌ 블로킹: 루프 스레드를 통째로 멈춤

async def async_task():
    await asyncio.sleep(1.0) # ✅ 논블로킹: await 에서 양보
```

실행:
```bash
python examples/02_event_loop_blocking.py
```

실제 출력:
```
같은 '1초 일' 5개를 gather 로 동시에 시도

BEFORE  time.sleep(1)  x5 (블로킹)   : 5.001 s
AFTER   asyncio.sleep(1) x5 (논블로킹): 1.003 s
```

**어디를 보라**: **똑같이 `gather` 로 5개를 동시에** 시켰는데, `time.sleep` 버전은 **5.001초**(= 1초씩 줄서서 순차), `asyncio.sleep` 버전은 **1.003초**(= 겹침). 차이는 `await` 한 줄뿐이다. `time.sleep` 은 루프에게 양보하지 않고 스레드 자체를 1초간 재우므로, 그 1초 동안 **다른 코루틴이 단 하나도 못 돈다**. `gather` 로 감쌌어도 소용없다 — 동시성은 "동시에 시작했느냐"가 아니라 "**대기 중에 양보하느냐**"에서 나온다.

## 5. 우리 코드와 연결

- **한 이벤트 루프에서 통화 한 건의 모든 것이 돈다**: [`call_session.py`](../../domains/learning/realtime/call_session.py#L292) 의 `_run_session` 은 하나의 이벤트 루프 위에서 **2개의 펌프 + 시계 워처 + 점진 flush** 를 동시에 굴린다([call_session.py:311-317](../../domains/learning/realtime/call_session.py#L311)). 이들은 대부분 `await client_ws.receive()`, `async for event in session.events()` 처럼 **대기 지점에서 양보**한다. 그래서 요리사(한 스레드)가 "마이크 데이터 왔다 / Gemini 오디오 왔다 / 1분 지났다"를 번갈아 처리할 수 있다.
- **블로킹을 절대 루프에 두지 않는다**: 우리 DB 는 **동기** SQLAlchemy(psycopg2)다. 동기 쿼리는 (b)의 `time.sleep` 처럼 루프를 멈춘다. 그래서 [`normalcall_service.py`](../../domains/learning/service/normalcall_service.py#L50) 의 `run_db` 가 그 호출을 `run_in_threadpool` 로 **별도 스레드**에 던진다. 그 스레드가 DB 응답을 기다리는 동안(그 스레드는 GIL 을 놓는다, 1장 참고) **이벤트 루프는 계속 다른 통화의 오디오를 나른다.** 만약 루프 스레드에서 직접 `db.execute(...)` 를 했다면, 그 통화만이 아니라 **같은 워커의 모든 통화가 함께 멈춘다.**
- **FastAPI 의 `def` vs `async def`**: [`core/deps.py`](../../core/deps.py#L34) 의 `get_current_member` 같은 **동기 `def` 의존성/핸들러는 FastAPI 가 알아서 스레드풀에서** 돌린다(그 안의 동기 DB 조회가 루프를 막지 않도록). 반대로 `async def` 핸들러는 **이벤트 루프에서 직접** 돈다 — 그래서 `async def` 안에서 실수로 동기 블로킹(무거운 `requests.get`, `time.sleep`, 동기 DB)을 호출하면 (b)처럼 서버 전체가 굶는다. "async 로 만들었으니 빠르다"가 아니라, **async 안에서는 반드시 논블로킹이거나 오프로드해야** 빠르다.

## 6. 흔한 오해 / 함정

- ❌ **"`async def` 로 바꾸면 무조건 빨라진다."** → 그 안이 블로킹이면 오히려 **더 위험**하다. 동기 함수는 FastAPI 가 스레드풀로 빼주지만, `async def` 안의 블로킹은 루프를 직접 막는다.
- ❌ **"`gather` 로 감싸면 동시에 돈다."** → 각 코루틴이 `await` 로 양보해야 동시다. (b)의 `time.sleep` 버전이 5초 걸린 게 증거.
- ❌ **"CPU 계산도 async 면 동시에 처리된다."** → 아니다. 이벤트 루프는 **비선점(cooperative)** 이라, CPU 를 오래 잡고 `await` 안 하는 코루틴이 있으면 그 시간만큼 루프 전체가 멈춘다(= 다른 통화 굶음). CPU 는 오프로드(스레드/프로세스)해야 한다.
- ⚠️ **`asyncio.sleep(0)`** 은 "지금 한 번 양보하고 바로 돌아와" 라는 관용구다(긴 루프 중간 양보용).

## 7. 요약

- 이벤트 루프 = **한 스레드**가 "준비된 작업"만 골라 돌리는 순회. 대기는 OS(epoll/IOCP)에 위임.
- 동시성의 원천은 "동시에 시작"이 아니라 **대기 중 `await` 양보**다.
- **협력적(비선점)** 이라 아무도 안 뺏는다 → CPU 를 오래 잡거나 블로킹하면 루프가 굶는다.
- `async def` 안에서는 논블로킹이거나 스레드풀로 **오프로드**해야 한다(우리 `run_db`).
- FastAPI 는 동기 `def` 핸들러를 자동으로 스레드풀에 태워 준다.

## 8. 연습문제

1. `02_event_loop_gather.py` 의 개수를 100 → 1000 으로 늘리면 총 시간은 대략 얼마가 될까? 왜 여전히 ~1초 근처일까?
2. `02_event_loop_blocking.py` 의 `blocking_task` 를 `await asyncio.to_thread(time.sleep, 1.0)` 로 바꾸면 결과가 어떻게 될까? 왜?
3. 우리 `async def` WebSocket 핸들러 안에서 실수로 동기 `db.query(...)` 를 직접 호출하면 어떤 장애가 생길지, 이 챕터 용어로 설명하라.

1. 여전히 **약 1초**. 코루틴이 1000개여도 각 `asyncio.sleep` 은 타이머 하나만 등록하고 즉시 양보하므로, 1000개의 1초 대기가 모두 겹친다. (실제로는 스케줄링 오버헤드로 아주 조금 늘 수 있지만 100초 근처엔 절대 안 간다.)

3. 동기 쿼리가 완료될 때까지 **이벤트 루프 스레드가 통째로 멈춘다**. 그 순간 같은 워커가 담당하는 **모든 통화의 오디오 펌프·시계·flush 가 함께 정지**해 오디오가 끊기고 응답이 밀린다. 협력적 스케줄링에서 한 작업이 양보 없이 블로킹하면 전원이 굶기 때문. 해결은 `run_db`/`to_thread` 로 오프로드.
