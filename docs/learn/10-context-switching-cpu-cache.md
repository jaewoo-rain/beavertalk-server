# 10. Context Switching & CPU Cache — 밑바닥에서 무슨 일이

> **한 줄 요약**: 코어는 하나뿐인데 실행할 게 많으면 OS 스케줄러가 스레드를 번갈아 올린다(**문맥교환** — 싸지 않다). 그리고 CPU 는 느린 RAM 앞에 **캐시(L1/L2/L3)** 를 두는데, 메모리를 **연속으로(지역성 있게)** 훑으면 빠르고 뜀뛰기하면 느리다. 이 둘이 "왜 스레드를 무작정 늘리면 안 되나", "왜 async 인가"의 하드웨어적 이유다.

**이 챕터의 키워드**: Context Switching, Scheduler, Cache Line, Cache Locality, False Sharing, Branch Prediction, Lock Contention

> 이전 챕터([09. Load Test](09-load-test.md))까지는 "무엇이 느린지 재는 법"이었다. 이 장부터(모듈 5)는 **왜 하드웨어 레벨에서 느린지** 한 겹 더 내려간다. ⚠️ 이 모듈은 제일 조심스럽다 — 파이썬은 GIL·객체모델·인터프리터 오버헤드 때문에 C 처럼 캐시/분기 효과가 선명히 안 나온다. **그래서 파이썬에서 실측되는 것만 실측하고, C 레벨에서만 의미 있는 것은 개념·그림으로 정직하게** 설명한다.

## 1. 왜 중요한가

우리 서버는 통화 1건이 5분간 오디오를 실시간 중계한다(2펌프). 동시 통화가 100건이면 "스레드를 100개, 아니 넉넉히 1000개 만들면 되지"라는 직관이 든다. **그런데 왜 uvicorn·asyncio 는 스레드 1000개 대신 이벤트 루프 하나에 코루틴 수천 개를 얹을까?** 답은 이 장의 두 하드웨어 사실에 있다.

- 스레드를 많이 만들면 OS 가 코어 위에서 스레드를 **끊임없이 갈아 끼워야** 한다(문맥교환). 갈아 끼울 때마다 레지스터·스택을 저장/복원하고 캐시가 식는다. 스레드 수가 늘수록 이 오버헤드가 쌓인다.
- 통화 오디오 버퍼(`bytearray` 누적)를 다룰 때, 데이터를 어떻게 배치·접근하느냐에 따라 CPU 캐시 히트율이 달라진다. 같은 계산도 메모리 접근 순서만으로 몇 배 차이가 난다.

이 장을 모르면 "스레드만 늘리면 동시성이 는다"거나 "코드는 같은데 왜 어떤 건 빠르고 어떤 건 느리지?"에서 헤맨다.

## 2. 개념 — 비유로 시작

**비유 1 (문맥교환)**: 요리사(코어)는 한 명인데 주문(스레드)이 여러 개다. 요리사는 한 요리만 붙잡고 끝내지 않고, 공평하게 하려고 5분마다 다른 냄비로 옮겨간다. 옮길 때마다 **지금 냄비 상태를 메모하고(레지스터 저장), 다음 냄비의 메모를 다시 읽고(복원), 도마 위 재료도 새로 깔아야(캐시 오염)** 한다. 냄비가 3개면 이 "옮기는 비용"이 사소하지만, 냄비가 500개면 요리사가 **옮겨 다니느라** 정작 요리할 시간을 까먹는다.

**비유 2 (CPU 캐시와 지역성)**: 책상(L1 캐시)은 좁고, 책장(L2/L3)은 조금 멀고, 창고(RAM)는 아주 멀다. 창고에서 물건을 가져올 땐 **한 개만 집어오지 않고 상자째(캐시라인, 보통 64바이트)** 가져온다. 그러니 상자 안 물건을 **연달아 다 쓰면**(연속 접근) 창고를 한 번만 다녀와도 되지만, 물건을 **여기저기 흩어 쓰면** 매번 창고를 다녀와야 한다(캐시 미스). 데이터도 똑같다 — **가까이 있는 걸 연달아 쓰는 게(locality)** 빠르다.

**정확한 정의**:
- **Context Switching(문맥교환)**: OS 스케줄러가 코어에서 실행 중인 스레드/프로세스를 내리고 다른 것을 올리는 것. 레지스터·프로그램카운터·스택포인터를 저장/복원하고, TLB·캐시가 새 문맥으로 오염된다. **직접비용(수 µs)** 보다 **간접비용(식은 캐시를 다시 데우는 것)** 이 클 때가 많다.
- **Scheduler(스케줄러)**: 누구를 언제 얼마나 코어에 올릴지 정하는 OS 부품. 타임슬라이스가 끝나거나(선점) I/O 로 블로킹되면 다른 스레드로 넘긴다.
- **Cache Line(캐시라인)**: 캐시가 RAM 을 읽어오는 **최소 단위**. 보통 64바이트. 1바이트만 필요해도 그 바이트가 든 64바이트를 통째로 읽는다.
- **Cache Locality(지역성)**: 방금 쓴 데이터 근처를 곧 다시 쓰는 성질. **공간 지역성**(옆 주소) + **시간 지역성**(방금 그 주소). 지역성이 높으면 캐시 히트율이 오른다.
- **Lock Contention(락 경합)**: 여러 스레드가 같은 자물쇠를 동시에 원해 줄 서는 상황. 대기 + 문맥교환 + (파이썬이면) GIL 핸드오프 비용이 붙는다.
- **False Sharing(거짓 공유)**: 서로 다른 스레드가 **서로 다른 변수**를 쓰는데 그 두 변수가 **같은 캐시라인**에 들어 있어, 한쪽이 쓸 때마다 다른 코어의 캐시라인이 통째로 무효화되는 것(캐시 핑퐁). → 뒤에서 "파이썬에선 재현이 어렵다"고 정직히 다룬다.
- **Branch Prediction(분기 예측)**: CPU 가 `if` 결과를 미리 찍어 파이프라인을 채워두는 것. 잘 맞으면 빠르고, 틀리면(misprediction) 채운 걸 버려 느려진다.

## 3. 그림

```
[문맥교환] 코어 1개, 스레드 3개 — 스케줄러가 번갈아 올림
  코어: [T1..][T2..][T3..][T1..][T2..] ...
              ↑     ↑     ↑
           갈아끼울 때마다: 레지스터 저장/복원 + 캐시 식음
  스레드가 3개면 갈아끼움 비용이 사소, 500개면 그게 일의 절반이 됨

[메모리 계층] 아래로 갈수록 느리고 크다 (대략적인 감)
  레지스터  <1ns
  L1 캐시   ~1ns     (수십 KB)
  L2 캐시   ~4ns     (수백 KB)
  L3 캐시   ~15ns    (수 MB, 코어들이 공유)
  RAM       ~80ns    (수 GB)          <- L1 보다 ~수십 배 느림
  → RAM 을 덜 다녀오게 '연속 접근'하는 게 곧 최적화

[캐시라인 64B] 1바이트 요청해도 64바이트가 통째로 올라온다
  RAM:  [ .. a0 a1 a2 ... a7 (연속 8개 double=64B) .. ]
  연속 접근 a0→a1→...→a7 : 창고 1번 다녀와 8개 다 씀 (히트 7번)
  뜀뛰기  a0→(N칸)→a1→... : 매번 새 라인 (미스 8번)

[False Sharing] 코어 A는 x만, 코어 B는 y만 쓰는데 x,y가 같은 라인
  라인:[ x | y | .. ]  A가 x 쓰면 → B의 라인 무효화 → B가 y 읽으려 다시 로드
  서로 안 겹치는 변수인데 캐시라인 때문에 '거짓으로' 공유돼 핑퐁
  ⚠️ CPython 은 GIL 로 진짜 동시쓰기가 없어 이 효과를 재현하기 어렵다(6절)
```

## 4. 직접 돌려보자

> 환경: Windows, Python 3.13, numpy 는 `uv run --with numpy` 로. 숫자는 필자 기기 기준이라 **여러분 기기에선 배수가 다르다** — 중요한 건 **방향과 배수의 크기 감**이다.

### (a) Cache Locality — 같은 데이터, 접근 순서만 바꿔도 3배

파일: [`examples/10_cache_locality.py`](examples/10_cache_locality.py)

numpy 는 C 로 짠 **연속 메모리**라 파이썬 for 루프보다 캐시 효과가 선명하다. 같은 원소를 두 방식으로 복사한다 — `copyto(dst, a)`(메모리 순서대로 읽기) vs `copyto(dst, a.T)`(전치 뷰라 세로로 뜀뛰며 읽기). **총 바이트·원소·연산은 완전히 같고, 오직 접근 순서만 다르다.**

```bash
uv run --with numpy python examples/10_cache_locality.py
```

실제 출력:
```
배열 4000x4000 float64 (128 MB), 원소 16,000,000개
연속 복사  copyto(dst, a)    :    6.78 ms  (메모리 순서대로 = 캐시 히트)
전치 복사  copyto(dst, a.T)  :   20.50 ms  (세로 뜀뛰기 = 캐시 미스)
느려진 배수                  :  3.02x

같은 원소, 같은 총 바이트, 같은 연산 — 오직 '접근 순서'만 달랐다.
```

**어디를 보라**: `a.T` 는 데이터를 복사한 게 아니라 **같은 버퍼를 전치로 보는 뷰**다. 그래서 원소를 하나 읽을 때마다 메모리를 `N*8`바이트씩 건너뛴다 → 매번 새 캐시라인을 로드 → **캐시 미스 폭증**. 같은 16M 개 원소인데 접근 순서만으로 **3배** 차이. 이게 "지역성 있게 짜라"의 실체다.

> ⚠️ 왜 numpy 로 하냐면, **순수 파이썬 리스트론 이 효과가 거의 안 보인다.** 파이썬 리스트는 값이 아니라 **포인터 배열**이고, 각 원소 접근마다 포인터 역참조 + 인터프리터 디스패치(수십 ns)가 붙어 캐시 미스(수십 ns)를 **덮어버린다**. C 연속 배열(numpy)에서만 캐시가 병목으로 드러난다. 이게 이 장 전체의 핵심 정직성이다.

### (b) Lock Contention — 하나의 자물쇠를 넷이 다투면 6배 느리다

파일: [`examples/10_lock_contention.py`](examples/10_lock_contention.py)

스레드 4개가 **공유 카운터 하나**를 `Lock` 으로 보호하며 400만 번 올리기 vs, **스레드별 로컬 카운터**로 세고 마지막에 합산. 결과 합계(4,000,000)는 같다.

```bash
python examples/10_lock_contention.py
```

실제 출력:
```
스레드 4개, 각 1,000,000회 증가 (합계 목표 4,000,000)
공유 Lock 경합   :    449.3 ms   결과=4,000,000
스레드로컬 합산  :     72.0 ms   결과=4,000,000
경합이 느린 배수 :    6.2x
```

**어디를 보라**: 같은 400만 번 증가인데 공유 락 버전이 **6배** 느리다. 매 증가마다 `lock.acquire()`/`release()` + **GIL 핸드오프** + 대기 스레드의 **문맥교환**이 끼어들어 사실상 직렬화된다. 파이썬은 GIL 때문에 어차피 한 번에 한 스레드만 도는데, 여기에 락 경합까지 더하면 "느리게 직렬화"가 된다. **결론: 공유 상태 락은 최대한 짧게, 아니면 아예 스레드 로컬로 모아서 마지막에 합쳐라.**

### (c) Context Switch 비용 감 — 같은 일을 잘게 쪼갤수록 느려진다

파일: [`examples/10_context_switch.py`](examples/10_context_switch.py)

총 작업량(600만 회 루프)은 **고정**. 이걸 T개 스레드로 나눠 돌린다. 일의 양은 늘 같으니, 시간이 늘면 그건 순수 **오버헤드**(스레드 생성 + 문맥교환)다.

```bash
python examples/10_context_switch.py
```

실제 출력:
```
총작업 6,000,000회를 T개 스레드로 분할 (일은 항상 같은 양)
  threads=   1 :     94.6 ms   (1스레드 대비 1.00x)
  threads=   2 :     90.7 ms   (1스레드 대비 0.96x)
  threads=   4 :     92.1 ms   (1스레드 대비 0.97x)
  threads=   8 :     92.8 ms   (1스레드 대비 0.98x)
  threads=  32 :     98.1 ms   (1스레드 대비 1.04x)
  threads= 128 :    105.9 ms   (1스레드 대비 1.12x)
  threads= 512 :    145.8 ms   (1스레드 대비 1.54x)
```

**어디를 보라**: 1~8 스레드는 시간이 거의 같다 — GIL 때문에 어차피 직렬 실행이라 스레드를 더 만들어도 병렬 이득이 없다(1장). 그런데 128, 512 로 가면 시간이 **뚜렷이 는다**(512개는 54% 더 느림). 일은 그대로인데 느려진 만큼이 **스레드 생성 + OS 문맥교환** 오버헤드다. "스레드를 많이 만들면 손해"라는 추세가 눈에 보인다.

> 정밀한 "문맥교환 1회 = 몇 µs"는 파이썬에서 못 잰다(OS 스케줄러·`perf` 같은 커널 도구 영역). 여기선 **추세**만 정직하게 보였다.

### (d) Branch Prediction — C 에선 극적, 파이썬에선 흐릿한 이유

파일: [`examples/10_branch_prediction.py`](examples/10_branch_prediction.py)

C 에선 "정렬된 배열이 안 정렬된 것보다 몇 배 빠르다"가 유명하다(분기 예측이 잘 맞아서). 파이썬에선 어떤지 **정직하게** 본다. 노이즈에 묻히기 쉬워 `best-of-9` × `trial 3회` 로 재현성까지 확인한다.

```bash
uv run --with numpy python examples/10_branch_prediction.py
```

실제 출력:
```
원소 2,000,000개 (0~255), 조건: v >= 128  |  best-of-9, trial 3회
       | if:비정렬  정렬   gap  | 브랜치리스:비정렬  정렬   gap
trial0 |    29.9   21.5   8.4 ms |      44.3   33.1  11.2 ms
trial1 |    30.2   21.8   8.4 ms |      44.4   33.2  11.1 ms
trial2 |    31.7   24.4   7.3 ms |      47.9   33.5  14.3 ms
(if 비정렬 반복당 약 15.9 ns — 디스패치 오버헤드가 지배적)
→ '정렬이 빠르다'는 재현된다. 하지만 브랜치리스 gap 이 if gap 보다
  크기도/작기도 해서, 파이썬에선 '분기예측 몫'을 깨끗이 못 떼어낸다.

=== numpy 마스크합 (분기 없음 = 벡터화) ===
  비정렬   9.307 ms   정렬   2.976 ms
  → 이 차이는 '분기예측'이 아니라 흩어진 gather = 캐시 미스다.
```

**어디를 보라 (정직 3단계)**:
1. **재현되는 것**: `if` 버전은 정렬(약 21ms)이 비정렬(약 30ms)보다 **확실히 빠르다**(~28%). trial 3번 다 일관.
2. **재현 안 되는 것**: "그 차이가 다 분기예측이냐"를 확인하려고 **데이터 의존 분기를 제거한 브랜치리스 버전**을 대조군으로 뒀는데, 그 gap 이 실행마다 `if` gap 보다 크기도/작기도 하다. → **파이썬에선 분기예측 몫을 깨끗이 분리 못 한다.** 이것 자체가 정직한 결론이다.
3. **왜 C 처럼 극적이지 않나**: 반복당 약 **16ns** 인데 이건 대부분 **바이트코드 디스패치 오버헤드**다(`FOR_ITER`, `COMPARE_OP`, `POP_JUMP_IF_FALSE`, `BINARY_OP`… 매 원소마다). CPU 분기 mispredict 페널티(수 ns)는 이 16ns 안에 **묻힌다**. C 의 타이트한 루프는 반복당 ~1ns 라 mispredict 가 상대적으로 커서 몇 배 차이가 난다.

**보너스 정직**: numpy 버전은 정렬/비정렬이 **3배** 넘게 차이 나서 "거봐 분기예측!" 하기 쉽다. **틀렸다.** numpy 는 벡터화라 데이터 의존 분기가 **없다**. 그 차이는 `arr[arr>=128]` 의 gather 가 정렬 데이터에선 연속 구간, 비정렬에선 흩어진 접근이라 생기는 **캐시 미스**다(=(a)와 같은 원리). 순진한 해석은 원인을 이렇게 오인한다.

## 5. 우리 코드와 연결

- **"왜 스레드 수천 개 대신 async 인가"의 하드웨어적 답**: (c)가 그 답이다. 동시 통화 100건을 스레드 100개(+각 통화의 여러 대기마다 스레드 더)로 처리하면 OS 가 문맥교환에 시간을 쏟는다. 대신 asyncio 는 **단일 스레드 이벤트 루프**에서 코루틴으로 처리해 **문맥교환을 통째로 피한다**([2장](02-event-loop.md)). 코루틴 전환은 OS 스케줄러가 아니라 파이썬 함수 호출 수준이라 문맥교환보다 훨씬 싸다. normalcall 의 2펌프도 스레드 2개가 아니라 **한 루프 안의 태스크 2개**다([`call_session.py`](../../domains/learning/realtime/call_session.py)).
- **동기 DB 를 스레드풀로 — 하지만 '조금만'**: [`normalcall_service.py`](../../domains/learning/service/normalcall_service.py#L50) 의 `run_db` 는 동기 psycopg2 호출을 `run_in_threadpool` 로 넘긴다. 이건 DB **대기**(I/O)를 겹치려는 것([1장](01-gil.md))이지, 스레드를 무한정 늘리자는 게 아니다. 스레드풀 크기가 유한한 이유가 (c)다 — 너무 크면 문맥교환으로 손해. "짧게 열고 닫는 단위로만"이라는 `run_db` 주석도 스레드·세션 점유를 줄이려는 것.
- **락은 짧게**: (b)의 교훈은 공유 상태 접근을 최소화하라는 것. 우리 통화 상태 [`_CallState`](../../domains/learning/realtime/call_session.py#L84) 는 **각 통화가 자기 것만** 쓰고(펌프끼리 공유하지만 단일 루프라 진짜 동시쓰기 없음), 전역 공유는 `_analysis_tasks: set` 정도로 최소화돼 있다.
- **`__slots__` = 메모리 지역성/객체 크기 절감**: [`_CallState.__slots__`](../../domains/learning/realtime/call_session.py#L87) 는 인스턴스마다 `__dict__`(해시테이블)를 없애고 필드를 **고정 슬롯**에 담는다. 효과는 (1) 인스턴스당 메모리가 작아지고, (2) 필드가 dict 해싱 없이 **고정 오프셋**으로 배치돼 접근·지역성이 좋아진다. 통화 상태처럼 필드가 고정된 객체에 딱 맞는 관용구다. (`bytearray` 버퍼를 새로 할당하지 않고 **누적/재사용**하는 것도 같은 결 — 작은 할당 폭증과 캐시 오염을 줄인다.)

## 6. 흔한 오해 / 함정

- ❌ **"스레드를 많이 만들면 동시성이 는다."** → (c)처럼 어느 선을 넘으면 문맥교환·생성 비용이 이득을 잡아먹는다. I/O 동시성은 **스레드 대량생성이 아니라 async**(또는 유한한 스레드풀)로.
- ❌ **"순수 파이썬 리스트로 캐시 최적화를 실측하겠다."** → 거의 안 보인다. 파이썬 리스트는 포인터 배열이고 인터프리터 오버헤드가 캐시 미스를 덮는다. 캐시 효과는 **numpy/C 연속 배열**에서만 선명하다((a)의 경고).
- ❌ **"정렬 데이터가 빠르면 분기예측 덕이다."** → (d)처럼 파이썬에선 못 단정한다. numpy 사례는 아예 **캐시 미스**가 원인이다. 원인 귀속은 대조군 없이 하지 마라.
- ⚠️ **False Sharing 을 파이썬으로 재현하려 하지 마라**: False Sharing 은 **여러 코어가 진짜 동시에** 서로 다른 변수를 쓸 때 같은 캐시라인이 핑퐁하는 현상이다. 그런데 **CPython 은 GIL 때문에 한 번에 한 스레드만 바이트코드를 돌아 진짜 동시쓰기가 없다.** 게다가 파이썬 객체는 값이 아니라 힙에 흩어진 객체라 "두 변수가 같은 64B 라인에" 얹히도록 통제하기도 어렵다. → False Sharing 은 **C/C++/Rust 멀티스레드, 또는 3.13 free-threaded 빌드**에서나 실측 대상이다. 이 장에선 **그림(3절)으로 원리만** 이해하고 넘어간다. (해법 개념: 코어별 변수를 캐시라인 크기로 패딩해 분리 — "cache line padding".)
- ⚠️ **문맥교환 1회 비용을 파이썬으로 정밀 측정하려 하지 마라**: 커널 스케줄러 영역이라 `perf`(리눅스) 같은 도구가 필요하다. 파이썬에선 (c)처럼 **추세**만 본다.

## 7. 요약

- **문맥교환**: 코어에서 스레드를 갈아 끼우는 비용(레지스터 저장/복원 + 캐시 오염). 스레드가 많을수록 커진다 → (c)에서 512스레드가 1.5배 느림.
- **CPU 캐시**: RAM 은 느려서 L1/L2/L3 캐시가 앞을 막는다. **캐시라인(64B) 단위**로 올라오니 **연속 접근(지역성)** 이 빠르다 → (a)에서 접근 순서만으로 3배.
- **Lock Contention**: 공유 락을 다투면 대기+문맥교환+GIL 핸드오프로 느려진다 → (b)에서 6배. 락은 짧게, 스레드 로컬로.
- **Branch Prediction / False Sharing**: C·멀티코어에선 크지만, **파이썬은 인터프리터 오버헤드·GIL 로 재현이 흐릿하거나 불가**하다. 정직하게 개념·그림으로.
- 우리 코드: async(문맥교환 회피)·유한 스레드풀·`__slots__`·버퍼 재사용이 모두 이 하드웨어 사실의 실무적 대응이다.

## 8. 연습문제

1. (a)에서 `a.T`(전치 뷰) 대신 `np.ascontiguousarray(a.T)` 를 먼저 만들어 두고 그걸 복사하면 시간이 어떻게 될까? 왜?
2. (b)에서 `Lock` 을 `RLock` 으로 바꾸면 경합 시간이 더 빨라질까 느려질까? 근본 원인(직렬화)은 바뀌나?
3. (c)에서 `spin`(CPU 루프) 대신 각 스레드가 `time.sleep(0.001)` 을 여러 번 하도록 바꾸면, 스레드를 512개로 늘릴 때 (c)와 추세가 같을까 다를까? ([1장](01-gil.md) I/O 실험과 연결해) 이유는?
4. False Sharing 을 "파이썬 순수 스레드로 실측하겠다"는 동료를 어떻게 말릴 것인가? 두 가지 이유를 대라.

<details>
<summary>답</summary>

1. **더 빨라진다** — `ascontiguousarray` 로 **한 번** 뜀뛰기하며 연속 버퍼로 만들어 두면, 그 뒤 복사는 연속→연속이라 (a)의 `copyto(dst, a)` 처럼 빠르다. 즉 "여러 번 접근할 데이터라면 미리 연속으로 정렬해두는" 최적화. 단, 정렬 자체에 한 번의 비용과 메모리가 든다(공간-시간 트레이드오프).
2. **더 느려지거나 비슷하다.** `RLock`(재진입 락)은 "지금 이 스레드가 이미 잡았나"를 추가로 확인하므로 `Lock` 보다 획득/해제가 조금 더 무겁다. 그리고 **근본 원인인 직렬화는 그대로다** — 여전히 한 번에 한 스레드만 카운터를 만진다. 락 종류를 바꾸는 건 해법이 아니고, **락을 아예 없애는 것(스레드 로컬 합산)** 이 해법이다.
3. **추세가 달라진다(덜 나빠진다).** `time.sleep` 은 I/O 대기라 진입 시 GIL 을 놓아([1장](01-gil.md) (b)) 대기들이 겹친다. 스레드가 많아도 대부분 자고 있어 코어를 다투지 않으니, CPU 루프(c)만큼 문맥교환이 심하지 않다. 다만 스레드 **생성·스택 메모리** 비용은 여전해서 수천 개로 가면 결국 한계가 온다 — 그래서 "자는 스레드 수천 개"보다 **async 코루틴 수천 개**가 낫다.
4. (1) **GIL**: CPython 은 한 번에 한 스레드만 바이트코드를 실행해 **진짜 동시쓰기가 없다** → 캐시라인 핑퐁이 애초에 안 일어난다. (2) **객체모델**: 파이썬 변수는 힙에 흩어진 객체 포인터라 "두 변수를 같은 64B 캐시라인에" 의도적으로 배치·통제하기 어렵다. → False Sharing 은 C/Rust 나 free-threaded 빌드에서 재현·측정할 문제다.
