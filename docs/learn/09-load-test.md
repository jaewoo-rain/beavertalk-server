# 09. Load Test — 터지기 전에 터뜨려봐라

> **한 줄 요약**: 부하 테스트는 **운영 트래픽이 오기 전에, 통제된 환경에서 일부러 부하를 걸어** 한계 RPS·꼬리지연·무너지는 지점을 미리 아는 일이다. 8장에서 정의만 했던 **RPS·P95/P99 를 실제로 생성**하는 행위이며, 종류(Load·Stress·Spike·Soak)에 따라 알아내는 것이 다르다.

**이 챕터의 키워드**: Load Test, Stress Test, Spike Test, Soak/Endurance Test, Chaos(언급), k6, Locust, wrk, ApacheBench(ab)

> 이전 챕터([08. Profiling & 성능 지표](08-profiling.md))에서 **Latency·P95/P99·Throughput(RPS)** 이 무엇인지 정의하고, 손으로 만든 분포에서 계산해 봤다. 그런데 그 숫자는 어디서 오나? **실제 서버에 실제 부하를 걸어야** 나온다. 이 장이 그 부하를 만드는 도구다.

---

## 1. 왜 중요한가

우리 서버는 언젠가 "동시 통화 200건이 몰리면 버티나?", "예약전화 디스패처가 1분마다 도는데 알람이 한꺼번에 터지는 자정에 괜찮나?" 같은 질문을 받는다. 이 질문에 **"아마 될 거예요"** 라고 답하면 안 된다. 부하 테스트의 목적은 세 가지다.

- **한계 RPS 를 안다**: 이 인스턴스 1대가 초당 몇 요청까지 P99 를 지키며 처리하나. 이 숫자가 있어야 "인스턴스 몇 대가 필요한지" 용량 계획(capacity planning)을 한다.
- **무너지는 지점(breaking point)을 안다**: 부하를 계속 올리면 어디서 P99 가 폭발하고, 어디서 에러(타임아웃·5xx)가 나기 시작하나. 그 앞에 알람을 걸어야 새벽 3시에 안 깬다.
- **숨어 있던 병목이 부하에서만 드러난다**: 5장의 "블로킹이 루프를 막는다", 7장의 "N+1" 은 **동시성이 낮을 땐 안 보인다**. 요청 1개일 땐 50ms 인 엔드포인트가, 동시 100개일 때 갑자기 P99 2초로 튄다. 부하를 걸어야 이게 보인다.

> ⛔ **철칙: 프로덕션/원격 서버(Cloud Run·Supabase)에 부하를 걸지 마라.** 실제 사용자에게 장애를 주고, 클라우드 비용이 폭증하고, DDoS 로 오인돼 IP 가 차단될 수 있다. 부하 대상은 **내가 통제하는 로컬 서버**여야 한다. 이 장의 모든 실습은 `127.0.0.1` 에서 잠깐 띄운 장난감 앱을 때린다.

## 2. 개념 — 비유로 시작

**비유 1 (자동차 충돌 시험)**: 자동차 회사는 신차를 **일부러 벽에 처박는다**. 사고가 나길 바라서가 아니라, **어떤 속도에서 어디가 먼저 찌그러지는지** 통제된 환경에서 미리 알기 위해서다. 부하 테스트가 서버의 충돌 시험이다. 진짜 사고(운영 장애) 전에, 내 실험실(로컬)에서 먼저 부딪혀 본다.

**비유 2 (테스트 종류 = 부딪히는 방식이 다르다)**: 같은 충돌 시험이라도 "정속 주행 내구(Soak)", "정면 충돌(Stress)", "갑자기 튀어나온 장애물(Spike)"은 알아내는 게 다르다. 서버도 마찬가지다 — **부하를 어떻게 거느냐에 따라 드러나는 결함이 다르다**.

| 종류 | 어떻게 거나 | 무엇을 알아내나 | 우리 예시 질문 |
|---|---|---|---|
| **Load**(부하) | 예상되는 **정상 최대치**로 꾸준히 | 정상 트래픽에서 P95/P99·RPS 가 SLA 안인가 | "피크 시간 동시 통화 150건, P99 괜찮나?" |
| **Stress** | 무너질 때까지 **계속 올림** | 한계 RPS, 어디서 에러/폭발이 시작되나 | "몇 건부터 타임아웃이 나기 시작하나?" |
| **Spike**(급증) | 평소→**갑자기 확** 튀었다 내림 | 급증을 흡수하나, 회복하나(오토스케일 반응) | "자정에 알람 1만 개가 동시에 깨면?" |
| **Soak/Endurance**(지속) | 보통 부하를 **오래(수시간)** 유지 | 시간이 지나며 새는 것 — 메모리 누수, 커넥션 고갈, FD 누수 | "5분 통화를 몇 시간 반복하면 메모리가 새나?" |
| **Chaos**(장애 주입) | 일부러 **장애를 넣음**(DB 끊기, 지연 주입) | 장애 상황에서의 복원력(graceful degradation) | (언급만 — 5장 폴백과 연결) |

**정확한 정의**: 부하 테스트는 **부하 생성기(load generator)** 가 다수의 가상 유저(virtual user)를 흉내 내 대상 서버에 요청을 쏟아붓고, 응답시간을 모아 **처리량(RPS)·지연 분포(P50/P95/P99)·에러율**을 집계하는 실험이다. 8장의 지표를 "손으로 만든 분포"가 아니라 **진짜 서버가 만든 분포**로 뽑는다.

> ⚠️ **Benchmark ≠ Load Test.** 벤치마크는 "이 코드/이 서버가 최선의 조건에서 얼마나 빠른가"(마이크로, 8장). 부하 테스트는 "현실적 동시성에서 어떻게 무너지나"(시스템, 이 장). 둘 다 필요하지만 답하는 질문이 다르다.

## 4. 직접 돌려보자

우리 환경은 **Windows + 파이썬**이다. 도구 지형을 먼저 보자.

| 도구 | 정체 | 스크립트 언어 | 강점 | 우리 환경 적합도 |
|---|---|---|---|---|
| **Locust** | 파이썬 라이브러리 | **파이썬** | 코드로 시나리오, 웹 UI, 분산 워커, 파이썬 생태계 | ⭐ **바로 돈다**(pip/uv) |
| **k6** | Go 단일 바이너리 | JavaScript | CI 친화, 가볍고 빠름, 임계값(threshold) | 설치 필요(바이너리) |
| **wrk** | C 프로그램 | Lua | 초경량·초고성능(적은 자원으로 큰 부하) | Linux/mac 중심, Windows 빌드 번거로움 |
| **ab**(ApacheBench) | C 프로그램 | (없음, 플래그) | 가장 단순, 한 줄로 즉석 확인 | Apache 동봉, Windows 별도 설치 |

이 장은 **Locust 를 메인 실습**으로 하고(파이썬이라 `uv run` 한 줄로 돈다), 8장 스타일의 **자체 부하 생성기(asyncio+httpx)** 로 교차검증한다. k6·ab 는 이 머신에 설치돼 있지 않아 **스크립트 형태만** 정직하게 보여준다(아래 (d)).

### (a) 부하 대상 — 로컬 장난감 앱

파일: [`examples/09_target_app.py`](examples/09_target_app.py)

8장 지표가 **서로 다르게** 나오도록 성격이 다른 4개 엔드포인트를 뒀다.

```python
@app.get("/fast")            # 즉답: 지연 하한, RPS 상한
async def fast(): ...
@app.get("/slow")            # await asyncio.sleep(0.05): I/O 대기(2·8장)
async def slow(): await asyncio.sleep(0.05); ...
@app.get("/work")            # 파이썬 루프로 CPU 살짝: GIL 병목(1장)
async def work(): ...
@app.get("/block")           # 동기 def + time.sleep: 스레드풀 오프로드(5장)
def block(): ...
```

로컬에서 백그라운드로 띄운다(⚠️ 반드시 `127.0.0.1`):

```bash
uv run --with fastapi --with uvicorn uvicorn 09_target_app:app \
    --host 127.0.0.1 --port 8009 --log-level warning
```

### (b) Locust 헤드리스 — 메인 실습(진짜 통계표)

파일: [`examples/09_locustfile.py`](examples/09_locustfile.py)

가상 유저가 `wait_time`(0.1~0.5초 think-time)만큼 쉬었다가, `@task` 가중치대로 `/fast`(3) `/slow`(2) `/work`(1)을 골라 때린다. 헤드리스(웹 UI 없이 콘솔 통계)로 실행:

```bash
uv run --with locust --with fastapi --with uvicorn locust \
    -f 09_locustfile.py --headless -u 50 -r 10 -t 15s \
    --host http://127.0.0.1:8009
#   -u 50  가상 유저 50명 / -r 10 초당 10명 램프업 / -t 15s 15초 동안
```

**실제 출력**(15초, 유저 50, 대상 로컬 8009):

```
Type     Name       # reqs      # fails |    Avg     Min     Max    Med |   req/s  failures/s
--------|----------|-------|-------------|-------|-------|-------|-------|--------|-----------
GET      /fast        1008     0(0.00%) |      2       0      53      1 |   68.19        0.00
GET      /slow         629     0(0.00%) |     60      51      78     62 |   42.55        0.00
GET      /work         335     0(0.00%) |      6       3      53      5 |   22.66        0.00
--------|----------|-------|-------------|-------|-------|-------|-------|--------|-----------
         Aggregated   1972     0(0.00%) |     21       0      78      5 |  133.41        0.00

Response time percentiles (approximated)
Type     Name             50%    66%    75%    80%    90%    95%    98%    99%  99.9% 99.99%   100% # reqs
--------|----------|--------|------|------|------|------|------|------|------|------|------|------|------
GET      /fast              1      2      2      4      5      6      9     12     22     54     54   1008
GET      /slow             62     63     63     63     64     64     65     69     79     79     79    629
GET      /work              5      6      7      8      9     13     22     23     54     54     54    335
--------|----------|--------|------|------|------|------|------|------|------|------|------|------|------
         Aggregated         5     10     58     62     63     63     64     65     76     79     79   1972
```

**어디를 보라**:
- **이게 8장의 지표다, 실물로.** `req/s`(=RPS), `50%`(=P50/median), `95%`(=P95), `99%`(=P99). 8장에서 `statistics` 로 손계산하던 값을 **Locust 가 실제 응답에서 뽑아 줬다**.
- **엔드포인트마다 지연 분포가 다르다**: `/slow` 는 P50 62ms(서버의 `sleep 0.05` + 오버헤드), 꼬리 P99 도 69ms 로 **좁다**(대기 시간이 일정하니까). `/fast` 는 P50 1ms 지만 P99 12ms, 최대 53ms 로 **꼬리가 상대적으로 길다** — 순수 오버헤드는 스케줄링 요동에 더 민감하다.
- **실패 0%.** 이 부하(유저 50, think-time 있음)는 아직 이 서버에 여유 부하다. 무너지는 지점을 보려면 `-u` 를 올려야 한다(= Stress).
- **Aggregated P50 이 5ms 인데 P80 이 62ms 인 이유**: 요청의 다수가 빠른 `/fast`(가중치 3)라 중앙값은 낮지만, 느린 `/slow` 섞임이 상위 백분위를 끌어올린다. **혼합 워크로드의 백분위는 이렇게 계단이 진다** — 엔드포인트별로도 꼭 나눠 보라.

> Locust 는 파이썬 코드로 시나리오를 쓰므로(로그인→통화시작→종료 같은 **상태 있는 흐름**도 표현 가능), 우리처럼 파이썬 팀엔 진입장벽이 가장 낮다. 웹 UI 가 필요하면 `--headless` 를 빼고 `http://localhost:8089` 를 연다.

### (c) 자체 부하 생성기 — 8장 스타일로 교차검증

파일: [`examples/09_mini_loadgen.py`](examples/09_mini_loadgen.py)

Locust 없이 **asyncio + httpx** 로 부하를 만든다(8장 `08_latency_vs_throughput` 을 실제 HTTP 서버에 대고 돌리는 버전). `Semaphore` 로 동시성 50 을 고정하고, `AsyncClient` **하나를 재사용**(keep-alive)하며, 워밍업 50건을 버린다. **think-time 없이 계속 쏘아** 서버를 포화(saturate)시킨다.

```bash
uv run --with httpx python 09_mini_loadgen.py http://127.0.0.1:8009/slow
```

**실제 출력**(세 엔드포인트, 동시성 50, 각 3000요청):

```
=== /fast ===
RPS(처리량)   :    313.7      median(P50): 96.76 ms   P95: 486.35 ms   P99: 771.67 ms   실패: 0
=== /slow ===
RPS(처리량)   :    204.8      median(P50):187.78 ms   P95: 580.87 ms   P99: 880.07 ms   실패: 0
=== /work ===
RPS(처리량)   :    207.2      median(P50):219.28 ms   P95: 506.62 ms   P99:1010.90 ms   실패: 1
```

**어디를 보라 — 여기서 진짜 교훈이 나온다**:
- **`/fast` 마저 RPS 313 에서 막힌다.** 서버가 사실상 아무 일도 안 하는 `/fast`(Locust 에선 P50 1ms 였다)가, 포화 부하에선 P50 이 **96ms** 로 뛰고 RPS 는 313 이 천장이다. 서버가 느려서가 아니다 — **부하 생성기(단일 프로세스 asyncio+httpx)와 단일 uvicorn 워커가 천장**이다. 이것이 6절 첫 번째 함정 "**클라(부하생성기)가 먼저 병목**"의 실물 증거다. `/fast`/`/slow`/`/work` 가 성격이 판이한데 RPS 가 200~310 으로 뭉치는 건 서버 특성이 아니라 **파이프의 좁은 목(단일 이벤트 루프)** 이 공통 원인이라는 신호다.
- **Locust(133 RPS)와 mini(200~310 RPS)가 다른 이유**: Locust 는 think-time 이 있는 **closed-loop**(유저가 쉬었다 친다 — 현실적), mini 는 쉬지 않고 쏘는 **포화**다. 같은 서버라도 **부하 모델이 다르면 숫자가 다르다.** "RPS 133" 하나만 들고 "우리 서버는 133 RPS 짜리"라고 못 박으면 안 된다 — 어떤 부하 모델의 숫자인지 항상 같이 적어라.
- **포화의 대가는 지연으로 나타난다**: mini 의 `/slow` P50 187ms 는 Locust 의 62ms 보다 3배다. 요청이 세마포어/큐에서 **기다린 시간**이 지연에 얹혔다(대기행렬). 8장 (c)의 "지연 vs 처리량"이 반대로 작동하는 장면 — 포화에선 처리량이 천장에 닿고 **초과분은 지연 폭증으로 샌다**.
- 이 실습은 "최소 하나는 진짜 부하 통계"라는 요구를 (b) Locust 와 (c) mini **둘 다** 실제 실행으로 충족한다. 프로덕션엔 단 한 발도 쏘지 않았다(대상은 로컬 8009).

### (d) k6 · ab — 설치 시 이렇게 (이 머신엔 미설치, 안 돌림)

이 머신에서 확인한 결과 `k6`·`wrk`·`ab` 는 **설치돼 있지 않다**(`command -v` 전부 미검출). 그래서 **돌리지 않았다.** 설치돼 있다면 형태는 이렇다(아래는 예시 스크립트/전형적 출력 모양이지 실측 아님):

**ab(ApacheBench)** — 가장 단순, 한 줄:
```bash
# 총 3000요청, 동시 50 (⚠️ 로컬만)
ab -n 3000 -c 50 http://127.0.0.1:8009/slow
# 전형적 출력에 다음이 담긴다:
#   Requests per second:    XXX [#/sec]        <- RPS
#   Percentage of the requests served within a certain time (ms)
#     50%     62
#     95%    ...
#     99%    ...                               <- 8장의 P95/P99
```

**k6** — JS 시나리오 + CI 임계값:
```javascript
// script.js
import http from 'k6/http';
export const options = {
  vus: 50, duration: '15s',
  thresholds: { http_req_duration: ['p(99)<200'] },  // P99<200ms 아니면 CI 실패
};
export default function () { http.get('http://127.0.0.1:8009/slow'); }
```
```bash
k6 run script.js   # http_req_duration 의 p(95)/p(99) 를 표로 뽑고 threshold 로 통과/실패 판정
```

k6 의 강점은 저 `thresholds` 다 — **부하 테스트를 CI 게이트로** 만들어 "P99 가 회귀하면 빌드 실패"를 자동화한다. 우리도 나중에 도입한다면 이 방향이다.

## 5. 우리 코드와 연결 (실제 코드 기준)

- **부하 걸기 좋은 순수 엔드포인트 — `/health`**: [`main.py`](../../main.py#L160) 의 `@app.get("/health")` 는 `{"status": "ok", "env": ...}` 만 반환한다(주석에 "DB 연결은 확인하지 않음"). DB·외부 의존이 없어 **(a)의 `/fast` 에 대응**하는, 서버/프레임워크 자체 오버헤드 하한을 재기 좋은 표적이다. 부하 테스트의 "워밍업/스모크" 대상으로 흔히 이걸 쓴다.
- **`POST /api/v1/internal/dispatch-calls` — 개념만, 로컬에서만**: [`push/routers/internal.py`](../../domains/push/routers/internal.py#L20) 의 디스패처는 크론이 **1분마다** 호출해 예약전화를 흘려보낸다. 이건 부하 관점에서 **Spike 후보**다 — 자정처럼 예약이 몰리는 순간 이 한 번의 호출이 `DispatchService(db).run()` 으로 DB 를 크게 훑는다. 다만 `INTERNAL_DISPATCH_SECRET` 과 실제 DB 가 필요하니, 부하로 때리려면 **로컬 DB + 로컬 서버**에서 개념 검증만 하고, 절대 운영 Supabase 로 쏘지 않는다(R5·비용·차단).
- **부하에서만 드러나는 5장·7장의 병목**: 8장에서 예고한 그대로다. [`normalcall_service.run_db`](../../domains/learning/service/normalcall_service.py#L50) 가 동기 psycopg2 쿼리를 `run_in_threadpool` 로 넘기지 않고 **루프에서 직접** 했다고 가정해 보자. 요청 1개(낮은 동시성)일 땐 티가 안 난다. 그런데 부하로 동시 50건을 걸면, 블로킹 쿼리 하나가 이벤트 루프를 잡는 동안 **나머지 49건의 P99 가 함께 폭발**한다. 마찬가지로 [`analyze_call`](../../domains/learning/service/normalcall_service.py#L324) 의 표현별 직렬 TTS 루프(7장 N+1 사촌)는 표현이 많은 통화가 몰릴 때 **부하 시 P99 로 튄다**. **낮은 동시성 개발 환경에선 안 보이던 게 부하에서 드러난다** — 그래서 부하 테스트를 한다.
- **WebSocket 통화는 부하 테스트가 특수하다**: [`ws_router`](../../domains/learning/realtime/ws_router.py) 의 통화는 짧은 요청-응답이 아니라 **5분간 오디오를 양방향 스트리밍**하는 장수명 연결이다. Locust 로도 WS 부하가 가능하지만(`gevent` 기반 커스텀 클라이언트), "RPS" 대신 **동시 연결 수·연결당 대역폭·연결 유지시간**이 지표가 되고, Gemini Live 라는 외부 의존이 물려 있어 **로컬 부하로 재현하기가 까다롭다**(스텁 세션 주입이 필요 — 회귀 테스트 `test_normalcall_ws.py` 의 가짜 세션 접근과 같은 결). 이건 일반 HTTP 부하와 **분리해서** 다뤄야 한다.
- **Cloud Run 오토스케일 예고(12·15장)**: 로컬에선 uvicorn 1워커가 천장이라 (c)처럼 RPS 가 막혔다. 운영에서 부하를 올리면 Cloud Run 이 **인스턴스를 수평으로 늘려**(scale-out) RPS 를 받아낸다 — 부하 테스트는 이 오토스케일이 **제때·충분히** 반응하는지(콜드스타트 지연 포함)를 검증하는 자리이기도 하다. 프로세스 매니저(12장)와 Keep-Alive/로드밸런서(15장)에서 이어진다.

## 6. 흔한 오해 / 함정

- ❌ **프로덕션에 무단 부하.** 실사용자 장애·클라우드 비용 폭증·DDoS 오인 차단. **항상 로컬/스테이징의 통제된 대상에만.** 이 장 전체가 이 규칙을 지켰다(대상 = 로컬 8009).
- ⚠️ **부하 생성기(클라)가 먼저 병목.** (c)에서 `/fast` 조차 RPS 313 에 막힌 게 실물 증거다 — 서버가 아니라 **단일 프로세스 부하 생성기**가 천장이었다. 서버를 재기 전에 **부하 생성기가 서버보다 빠른지** 먼저 확인하라. 부족하면 Locust 분산 워커(`--worker`)를 여러 개 띄우거나 여러 머신에서 건다.
- ⚠️ **Keep-Alive 없이 매 요청 새 연결.** 요청마다 TCP·TLS 를 새로 맺으면 클라 측 **로컬 포트가 고갈**(`TIME_WAIT` 누적)돼 부하 생성기가 먼저 죽는다. (c)가 `AsyncClient` **하나를 재사용**한 이유다. 이건 15장(HTTP Keep-Alive)의 예고편.
- ⚠️ **워밍업 없이 첫 요청 포함.** 첫 요청은 연결 수립·임포트·JIT·콜드스타트로 느리다. (c)는 워밍업 50건을 **버렸다**. 안 버리면 P99 가 콜드스타트 이상치에 오염된다(8장 micro-benchmark 함정의 시스템판).
- ❌ **평균만 보고 P99 무시.** (b)에서 `/fast` 는 Avg 2ms 지만 Max 53ms 다. 8장의 교훈 그대로 — **평균은 꼬리를 숨긴다.** 부하 테스트 리포트는 반드시 P95/P99(가능하면 엔드포인트별로)를 본다.
- ❌ **너무 짧은 테스트.** 15초짜리로는 **메모리 누수·커넥션/FD 고갈**이 안 보인다. 그런 건 **Soak(수시간 지속)** 으로만 드러난다. 짧은 Load 테스트가 "이상 없음"이라고 Soak 문제까지 없다고 말하지 마라.
- ⚠️ **하나의 RPS 숫자로 서버를 규정.** (c)에서 봤듯 think-time 있는 closed-loop(Locust 133)와 포화(mini 200~310)는 다른 숫자를 준다. **"어떤 부하 모델·어떤 동시성의 숫자인지"를 항상 함께** 기록하라.

## 7. 요약

- **부하 테스트 = 통제된 환경에서 일부러 부하를 걸어 한계 RPS·꼬리지연·무너지는 지점을 미리 아는 일.** 8장의 P95/P99·RPS 를 **실제 서버로 생성**한다.
- **종류마다 알아내는 게 다르다**: Load(정상 SLA), Stress(한계·breaking point), Spike(급증 흡수), Soak(장시간 누수), Chaos(장애 복원력·언급).
- **도구 지형**: 우리 환경(Windows·파이썬)엔 **Locust 가 바로 돈다**. k6(CI 임계값), wrk(초경량), ab(즉석 한 줄)는 상황별. 이 장은 Locust + 자체 asyncio 생성기를 **실제로 돌려** 통계를 뽑았다.
- **부하에서만 드러나는 병목이 있다**: 5장 블로킹·7장 N+1 은 낮은 동시성에선 숨어 있다가 **부하 시 P99 로 폭발**한다.
- **함정**: 프로덕션 무단 부하 금지, 클라가 먼저 병목, keep-alive/워밍업, 평균 함정, 너무 짧은 테스트, 부하 모델 명시.

## 8. 연습문제

1. (b) Locust 를 `-u 50` 대신 `-u 500 -r 100` 으로 올리면(=Stress) 어느 엔드포인트의 P99 가 먼저 폭발할까? `/fast` `/slow` `/work` 중 짐작하고 이유를 1·8장으로 설명하라.
2. (c) mini 생성기에서 `/fast` 가 서버 부담이 거의 없는데도 RPS 313 에 막혔다. 이 천장을 올리려면 **부하 생성기 쪽**에서 무엇을 바꿔야 하나? (힌트: 6절 첫 함정)
3. "우리 서버는 133 RPS 를 처리한다"는 문장이 왜 불완전한가? 무엇을 함께 적어야 하나?
4. 15초 Load 테스트가 전부 통과(실패 0%)했다. 그런데도 **Soak 테스트를 따로 해야 하는 이유**를 하나 대라. 우리 코드에서 그 위험이 있을 만한 곳은?

<summary>답</summary>

1. **`/work` 의 P99 가 먼저 폭발**할 가능성이 크다. `/work` 는 CPU 파이썬 루프라 `await` 양보 지점이 없어 **GIL 을 붙잡는다**(1장). 동시성을 크게 올리면 단일 이벤트 루프가 `/work` 계산에 묶여 다른 요청까지 굶기고, `/work` 자신도 큐에서 밀려 꼬리가 급증한다. `/slow` 는 `await sleep` 이라 잘 겹쳐서(2장) 상대적으로 버틴다. (실제로 확인하려면 로컬에서 `-u` 를 올려가며 재 보라 — 단, 로컬만.)
2. 부하 생성기의 병렬성을 늘린다: Locust **분산 워커**(`--master` + 여러 `--worker` 프로세스)로 여러 코어/여러 머신에서 부하를 나눠 만든다. 단일 파이썬 프로세스(단일 이벤트 루프)가 천장이었으니, 프로세스를 늘려야(6·13장의 논리) 클라 천장이 올라간다. 대상 서버도 uvicorn 워커를 늘려야 함께 올라간다.
3. **부하 모델과 조건이 빠졌다.** think-time 있는 closed-loop 인지 포화인지, 동시 유저 몇 명인지, 어떤 엔드포인트 혼합인지, P99 는 얼마였는지에 따라 같은 서버가 다른 RPS 를 낸다. "동시 유저 50(think-time 0.1~0.5s), 혼합 fast:slow:work=3:2:1 에서 aggregate 133 RPS, P99 65ms"처럼 **조건을 붙여야** 재현·비교가 된다.
4. **누수는 시간에 비례해 쌓이므로 짧은 테스트엔 안 보인다** — 메모리 누수, DB 커넥션/FD 누수, 무한 증가하는 캐시 등. 우리 코드에선 통화가 반복될 때 [`call_session.py`](../../domains/learning/realtime/call_session.py) 의 오디오 버퍼(`bytearray` 누적)나 `_analysis_tasks: set` 이 **끝난 뒤 제대로 비워지는지**, 커넥션 풀(7장)이 반환되는지가 Soak 로만 확실히 검증된다. 5분 통화를 수백 회 반복 걸어 메모리 그래프가 우상향하는지 봐야 한다(로컬에서).
