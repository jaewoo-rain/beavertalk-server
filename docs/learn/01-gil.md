# 01. GIL — 왜 파이썬 스레드는 CPU를 한 번에 하나만 쓰나

> **한 줄 요약**: CPython 에는 "한 번에 하나의 스레드만 파이썬 바이트코드를 실행"하게 하는 자물쇠(GIL)가 있다. 그래서 **CPU 바운드는 스레드로 병렬화가 안 되고**, **I/O 바운드는 대기 중 GIL 을 놓아주므로 스레드가 효과 있다**.

**이 챕터의 키워드**: GIL, CPython, Reference Counting, Garbage Collection, Bytecode, pymalloc

---

## 1. 왜 중요한가

우리 서버는 통화 1건이 5분 동안 마이크·스피커 오디오를 실시간으로 중계하고(I/O), 동시에 통화후 분석은 무겁게 계산·외부호출을 한다. "스레드를 늘리면 빨라지겠지"라는 직관은 파이썬에서 **절반만 맞다**. CPU 계산은 스레드를 아무리 늘려도 안 빨라지고(오히려 느려질 수 있고), 반대로 네트워크·DB 대기는 스레드가 확실히 도움이 된다. 이 경계를 모르면 엉뚱한 곳에 스레드를 쏟아붓고 "왜 안 빨라지지?" 하게 된다.

## 2. 개념 — 비유로 시작

**비유**: 도서관에 책이 딱 한 권 있고, 그 책이 있어야만 글을 쓸 수 있다고 하자. 사람(스레드)이 열 명이어도 **책을 든 한 명만** 글을 쓸 수 있다. 나머지는 기다린다. 이 "한 권짜리 책"이 GIL(Global Interpreter Lock)이다.

- 단, 글을 쓰다 **화장실에 가는(=I/O 대기)** 사람은 책을 내려놓고 간다. 그동안 다른 사람이 책을 집어 글을 쓴다. → I/O 가 겹치면 여러 명이 번갈아 진도를 뺀다.
- 하지만 모두가 **쉬지 않고 글만 쓰려 하면(=CPU 계산)**, 책은 계속 한 명 손에만 있으므로 열 명이든 한 명이든 총 진도는 똑같다.

**정확한 정의**: GIL 은 CPython(우리가 그냥 "파이썬"이라 부르는 표준 구현) 인터프리터가 가진 하나의 뮤텍스다. 파이썬 바이트코드를 실행하려면 그 스레드가 GIL 을 쥐고 있어야 한다. 그래서 **한 순간에 파이썬 바이트코드를 실행하는 스레드는 정확히 하나**다. 스레드는 일정 간격(기본 5ms, `sys.getswitchinterval()`)마다, 그리고 블로킹 I/O 에 들어갈 때 GIL 을 놓아 다른 스레드에 넘긴다.

> ⚠️ GIL 은 "파이썬"의 문제가 아니라 **CPython 구현**의 특성이다. Jython, PyPy(STM 실험), 그리고 3.13 의 실험적 free-threaded 빌드(`python3.13t`)는 다르다. 이 교과서는 표준 CPython(GIL 있음) 기준이다.

**왜 이런 게 있나?** CPython 은 메모리를 **레퍼런스 카운팅(reference counting)** 으로 관리한다. 객체마다 "지금 몇 군데서 참조 중인지" 세는 정수 카운터가 있고, 0 이 되는 순간 즉시 해제한다. 여러 스레드가 이 카운터를 **동시에 ++/--** 하면 값이 깨져(경합) 메모리가 이르게 해제되거나 영영 안 풀린다. 모든 객체마다 잠금을 거는 대신, **인터프리터 전체에 하나의 큰 자물쇠**를 두는 것이 (단일스레드 성능·구현 단순성 면에서) 싸고 확실했다. 그 대가가 멀티코어 CPU 병렬성의 포기다.

## 3. 그림

```
CPU 바운드 (계산만) — 스레드 2개라도:
  코어1: [T1][T2][T1][T2][T1][T2] ...   <- GIL 을 번갈아 쥠. 실제로 도는 건 항상 1개
  코어2: (놀고 있음)                     <- 두 번째 코어를 못 씀
  => 총 시간 = 순차와 비슷 (문맥전환 오버헤드로 더 느릴 때도)

I/O 바운드 (sleep/네트워크 대기) — 스레드 2개:
  T1: [실행]---(sleep, GIL 놓음)------------[깨어남]
  T2:         [실행]---(sleep, GIL 놓음)----[깨어남]
  => 대기가 겹침(overlap). 총 시간 ~= 한 번의 대기 시간

멀티프로세스 (계산) — 프로세스는 각자 GIL 을 가짐:
  코어1: [P1 계산 쭉]
  코어2: [P2 계산 쭉]                     <- 진짜 동시. 코어 다 씀
  => 총 시간 ~= 절반
```

## 4. 직접 돌려보자

### (a) CPU 바운드 — 스레드는 안 빨라지고, 프로세스는 빨라진다

파일: [`examples/01_gil_cpu_bound.py`](examples/01_gil_cpu_bound.py)

```python
def countdown(n):        # 순수 파이썬 루프 = 바이트코드 실행 = GIL 필요
    while n > 0:
        n -= 1

# 같은 계산을: 순차 2번 / 스레드 2개 / 프로세스 2개
```

실행:
```bash
python examples/01_gil_cpu_bound.py
```

실제 출력:
```
작업: countdown(50,000,000) 를 총 2번
순차 (2번)   :  1.582 s
스레드 2개   :  1.599 s   <- GIL: 안 빨라짐
프로세스 2개 :  0.899 s   <- 진짜 병렬
```

**어디를 보라**: `스레드 2개`(1.599s)가 `순차`(1.582s)와 **사실상 같다** — 오히려 문맥전환 탓에 아주 살짝 느리다. GIL 때문에 두 스레드가 동시에 계산을 못 했기 때문이다. 반면 `프로세스 2개`(0.899s)는 거의 **절반**이다. 프로세스는 각자 자기 인터프리터·자기 GIL 을 가져 두 코어를 진짜로 나눠 썼다.

### (b) I/O 바운드 — 스레드가 확실히 빨라진다

파일: [`examples/01_gil_io_bound.py`](examples/01_gil_io_bound.py)

```python
def io_task():
    time.sleep(1.0)   # "기다림". 파이썬은 sleep 동안 GIL 을 놓는다
```

실행:
```bash
python examples/01_gil_io_bound.py
```

실제 출력:
```
작업: time.sleep(1.0) 를 4번
순차       :  4.001 s   <- 4번 = 약 4초
스레드 4개 :  1.001 s   <- 겹침 = 약 1초
```

**어디를 보라**: 순차는 1초 × 4 = 4초. 스레드 4개는 약 **1초**. `time.sleep` 은 "기다리는" 작업이라 진입 시 GIL 을 놓아주고, 그 틈에 다른 스레드가 GIL 을 잡아 자기 sleep 에 들어간다. 네 개의 기다림이 **겹쳐서(overlap)** 총 시간이 확 준다. (실제 네트워크·DB·파일 I/O 도 같은 원리다.)

> 정리: **계산 → 프로세스(또는 async 오프로드), 대기 → 스레드/async.** 이 한 줄이 GIL 챕터의 실무 결론이다.

### (c) 바이트코드 · refcount · GC 를 눈으로

파일: [`examples/01_gil_bytecode_refcount.py`](examples/01_gil_bytecode_refcount.py)

실행:
```bash
python examples/01_gil_bytecode_refcount.py
```

실제 출력:
```
=== 1) dis.dis(add): 파이썬 → 바이트코드 ===
 17           RESUME                   0

 18           LOAD_FAST_LOAD_FAST      1 (a, b)
              BINARY_OP                0 (+)
              RETURN_VALUE

=== 2) reference counting (sys.getrefcount) ===
refcount 처음        : 2 (임시참조 +1 포함)
refcount alias=obj 뒤 : 3
refcount del alias 뒤 : 2

=== 3) 순환참조는 refcount 만으론 못 지운다 → gc 필요 ===
gc.collect() 가 회수한 순환 객체 수: 2000 (refcount 로는 절대 0이 안 됐다)
```

**어디를 보라**:
- **1) 바이트코드**: `def add(a, b): return a + b` 는 `LOAD_FAST_LOAD_FAST`(변수 두 개 적재) → `BINARY_OP 0 (+)`(더하기) → `RETURN_VALUE` 라는 **명령 목록**으로 컴파일된다. 파이썬 인터프리터는 이 명령들을 하나씩 실행하는데, **이 실행 루프를 동시에 여럿이 못 돌게** 막는 것이 GIL 이다. "파이썬은 인터프리트된다"의 실체가 이 목록이다. (명령 이름은 파이썬 버전마다 조금씩 다르다 — 위는 3.13.)
- **2) refcount**: `sys.getrefcount(obj)` 가 처음에 `2` 로 나온 건, 변수 `obj` 의 참조 1 + **함수에 인자로 넘기는 순간의 임시 참조 1** 이다(그래서 항상 실제보다 1 크게 보인다). `alias = obj` 로 참조가 하나 늘면 `3`, `del alias` 로 다시 `2`. 이 카운터가 0 이 되면 객체는 **즉시** 해제된다. 이 ++/-- 를 스레드 안전하게 만드는 싼 방법이 GIL 이었다.
- **3) 순환참조**: 서로를 가리키는 두 dict 는 함수를 벗어나도 refcount 가 서로 1 로 남아 **영영 0 이 안 된다**. 이런 순환(cycle)은 별도의 **순환 수집기(gc)** 가 찾아 회수한다. 여기선 1000쌍 = 2000개를 `gc.collect()` 가 회수했다.

## 5. 우리 코드와 연결

- **왜 우리는 CPU 계산을 스레드 대신 프로세스/async 오프로드로 미룰까**: 위 실험이 답이다. 통화 오디오 브리지는 대부분 **대기(WebSocket recv, Gemini 스트림 수신)** 라서 async/스레드가 잘 맞지만, 무거운 계산을 이벤트 루프 스레드에서 하면 GIL 을 붙잡아 통화가 끊긴다.
- **동기 DB 를 스레드풀로 미루는 이유(다음 챕터로 이어짐)**: [`normalcall_service.py`](../../domains/learning/service/normalcall_service.py#L50) 의 `run_db` 는 동기 SQLAlchemy(psycopg2) 호출을 `run_in_threadpool` 로 넘긴다. DB 대기는 **I/O** 라서(위 (b)처럼) 스레드로 넘기면 그 스레드가 GIL 을 놓고 기다리는 동안 이벤트 루프가 다른 일을 계속한다. 만약 이벤트 루프 스레드에서 직접 동기 쿼리를 하면, 그 대기 동안 GIL+루프가 통째로 멈춰 **모든 통화가 함께 멈춘다**.
- **GC 방지 강참조**: [`call_session.py`](../../domains/learning/realtime/call_session.py#L60) 의 `_analysis_tasks: set[asyncio.Task]` 는 refcount 를 일부러 붙잡아 두는 장치다. `create_task` 결과를 어디서도 안 붙잡으면 refcount 가 0 이 돼 **분석 태스크가 중간에 GC 될 수 있다**(3장에서 자세히). refcount 를 이해해야 이 코드가 왜 필요한지 보인다.
- **pymalloc 한 문단**: CPython 은 512바이트 이하의 작은 객체(우리가 통화중 쉴 새 없이 만드는 dict·bytes 조각들)를 위해 **pymalloc** 이라는 전용 고속 할당자를 쓴다. OS 에 매번 `malloc` 하지 않고 미리 받아둔 메모리 풀(arena)에서 잘라 준다. `_CallState.cur_user_pcm = bytearray()` 처럼 **버퍼를 재사용/누적**하는 우리 관용구는 이 작은 할당의 폭증을 줄이려는 것과 결이 같다.

## 6. 흔한 오해 / 함정

- ❌ **"스레드를 늘리면 CPU 계산이 빨라진다."** → (a) 실험대로 GIL 때문에 안 빨라진다. CPU 병렬은 **멀티프로세싱**(13장) 또는 C 확장/NumPy(GIL 밖에서 계산)로.
- ❌ **"GIL 때문에 파이썬은 동시성이 안 된다."** → 틀렸다. **I/O 동시성**은 (b)처럼 스레드로, 더 나아가 async 로 매우 잘 된다. GIL 이 막는 건 **CPU 병렬성**뿐.
- ❌ **"refcount 가 있으니 메모리 누수는 없다."** → 순환참조는 refcount 로 안 풀린다. gc 가 돌아야 한다. gc 를 껐다면(`gc.disable()`) 순환은 쌓인다.
- ⚠️ **`sys.getrefcount` 값이 1 크게 나오는 건 버그가 아니다** — 인자로 넘기는 임시 참조 때문이다.

## 7. 요약

- CPython 은 **GIL** 로 "한 번에 한 스레드만 바이트코드 실행"을 강제한다.
- **CPU 바운드**: 스레드 무의미(안 빨라짐) → 프로세스/네이티브 계산.
- **I/O 바운드**: 대기 중 GIL 을 놓으므로 **스레드/async 가 효과적**.
- GIL 이 존재하는 이유는 **refcount 기반 메모리 관리**를 싸게 스레드 안전화하기 위해서.
- 순환참조는 refcount 로 못 풀어 **gc** 가 필요하다. 작은 객체는 **pymalloc** 이 빠르게 준다.
