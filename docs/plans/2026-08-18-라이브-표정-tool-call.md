## 1. 목표 & 범위

### 목표
라이브(Gemini Live) 통화에서 **비버의 표정을 서버가 판정해 프론트에 보낸다.**
프론트는 그 값으로 감정 영상(`emo_happy.mp4` 등)을 재생한다.

### ⛔ 이건 "없는 걸 만드는 것"이 아니다 — **추측을 사실로 바꾸는 것**이다
프론트는 **지금도 표정을 바꾸고 있다.** 서버가 안 주니 **자막 키워드로 추측**한다
(`avatar_emotion.dart`):
```dart
happy: ['하하','ㅋㅋ','좋아','최고','잘했','great'...]
sad:   ['슬프','아쉽','ㅠ','sad'...]
```
그리고 그게 실패한 기록이 그 파일에 남아 있다 —
*"실기기에서 **'표정이 대사와 전혀 안 맞는다'**로 나타났다(2026-08-02)"*.
오탐이 심해 `'진짜?' '뭐야' '미안'` 같은 흔한 말을 사전에서 **빼야** 했다.

### MVP 범위
- Live 세션에 `set_face(emotion)` NON_BLOCKING tool 선언
- 프롬프트에 **타이밍 지시 한 줄**(구조 지시 아님)
- `tool_call` → 클라로 `sentence{text:"", emotion}` 프레임 **인밴드** 전송
- 직전 값과 같으면 **안 보낸다**(중복 억제)
- env 스위치로 on/off. 꺼지면 **바이트 동일**

### 비범위
- 프론트 수정 (**0줄** — 아래 §2 근거)
- 캐스케이드 (이미 되어 있다. 그리고 사장님 결정: **라이브만 쓴다**)
- 서버 깜빡임 억제 damper (**실측이 불필요하다고 답했다** — §4)
- 말 구조 고정("반응 먼저, 설명 나중") — **일부러 안 한다**(§5 D3)
- 감정 종류 확장 (5종 고정)

## 2. 아키텍처 & 데이터 흐름

### 왜 텍스트 태그가 아니라 tool-call 인가
native-audio 는 **모델 출력이 곧 소리**다. `<happy>` 를 시키면 **"꺾쇠 해피"라고 읽는다.**
`persona_prompt.py:647` 이 `emotion_tags` 를 Live 에 금지한 이유가 정확히 그것이다:
> ⛔ **Live 에는 절대 붙이지 마라** — 태그를 그대로 읽어 버린다(서버가 걷어낼 자리가 없다).

캐스케이드는 `LLM → 텍스트 → (서버가 태그 제거) → TTS` 라 중간 자리가 있지만,
라이브는 그 자리가 없다. **tool-call 이 소리가 아닌 유일한 통로다.**

### 흐름
```
Gemini Live ──┬─ tool_call(set_face="happy")   ← 소리 아님. 서버만 받는다
              └─ audio ─ audio ─ audio ...

서버(Gemini→클라 펌프 하나) — 받은 순서 그대로 흘린다
   {"type":"sentence","emotion":"happy","text":""}
   [PCM24k][PCM24k][PCM24k]

프론트  마커를 봉투 위치(at:_envAdded)에 꽂아 둔다 → 화면 안 바꿈
        재생이 그 위치에 닿음 → avatarEmotion.value = happy → emo_happy.mp4 크로스페이드
```

### ⭐ 프론트가 이미 다 해놨다 — 그래서 수정 0
| 프론트 사실 | 근거 |
|---|---|
| 서버 값이 오면 **추측기를 끈다** | `normalcall_controller.dart:3828` `if (next != null && !_serverEmotionSeen)` — *"명시적인 값이 추측을 이긴다"* |
| 감정을 **도착 시점에 반영 안 한다** | `_onSentenceMarker`: *"이 구간의 오디오는 아직 안 들린다(최대 1.2초 앞당겨 넣는다). 도착 시점에 바꾸면 소리보다 앞서 간다"* → `at:_envAdded` 로 꽂고 `_envPlayed` 가 닿을 때 터뜨린다 |
| **`text:""` 면 자막을 안 건드린다** | `_fireDueMarkers`: `if (m.text.isNotEmpty) {…자막…}` / `avatarEmotion.value = m.emotion` 은 **무조건** |
| 모르는 값이 와도 **안 죽는다** | `knownLabel` 은 로그용. 표정만 안 바꾼다 ⇒ 서버가 어휘를 늘려도 앱 배포 불필요 |
| 값 5종이 **아바타 어휘와 같은 축** | 커밋 `d1139d8` *"클라 표정 5종으로 축을 맞춘다 — 매핑 계층을 만들지 않는다"* |

### ⛔ 서버는 **바이트를 세지 않는다**
프론트가 `at:_envAdded`(자기가 받은 위치)로 **스스로** 도장을 찍는다.
`server_bytes` 는 **자막 타자기 속도 계산 전용**이고, 프로토콜 주석이 못박아 뒀다:
> ⚠ `server_bytes` 는 **주 키가 아니다 — 순서가 주 키다.**

⇒ 서버가 지킬 것은 **순서 하나**다. Live 는 Gemini→클라 펌프가 하나라 자동으로 지켜진다.

### 영상 자산 (실측 2026-08-18)
```
캐릭터 5종  baba · bibi · dudu · popo · rara   (각 11클립, 18~21MB)
감정 클립   emo_happy · emo_surprised · emo_sad · emo_angry   ← neutral 은 클립 없음(= 기본 상태)
길이        전부 2.25초 · loop:true 로 연다 ⇒ **길이는 제약이 아니다**
전환 비용   fadeIn 80ms · fadeOut 220ms · hangover 180ms
⛔ 하드 디코더 2~3개 한계 — idle + talk + 감정으로 **이미 셋**(sync_avatar.dart:21)
```
⇒ 클립이 짧아도 루프라 안 잘린다. 진짜 제약은 **전환 비용(~300ms)** 이고,
  실측 최소 간격이 0.5초라 **닿지 않는다**(§4).

### 2단계 — 회귀 (서버, 1~2시간)

## 4. 수용 기준 & 실측 데이터

### ⭐ 스파이크 실측 (2026-08-18, 5세션 28호출, call 1070~1075)

| 미지수 | 답 | 판정 |
|---|---|---|
| ① 모델이 부르는가 | **28회 / 5세션** | ✅ 시키면 부른다 |
| ② 말보다 먼저 오는가 | **27/28 (96%) 턴누적오디오 0.00초** | ✅ **설계 성립 조건** |
| ③ 얼마나 자주 | 간격 **최소 0.5s / 중앙 10.0s** · 0.4초 내 변경 **0건** | ✅ 깜빡임 없음 |

**감정 분포 — 캐스케이드보다 훨씬 풍부하다**
```
라이브     neutral 43% · happy 32% · sad 11% · angry 7% · surprised 7%   ← 5종 다 씀
캐스케이드  neutral 82%  (턴당 1개 고정)
```
턴당 하나가 아니라 **감정이 움직이는 지점마다** 부르기 때문이다. 영상통화에 이게 낫다.

**⚠ 예외 1건** — `set_face(neutral) 턴누적오디오=3.99초`
직전전사 `'Almost! It's "안녕히 가세요." One more time!'` ⇒ 말을 끝내고 중립으로 **복귀**한 것.
그 위치에 꽂히면 "이후 중립"이 되어 **오히려 맞다.** 무해.

**⚠ 중복 7건(25%)** — `surprised → surprised` 처럼 같은 값 연달아. 1단계에서 억제.

### 완료 판정
- 스위치 off → 프레임 집합·config·지시문이 **기존과 동일**
- 스위치 on → 감정 영상이 **대사와 같은 시점에** 바뀐다(사장님 눈)
- 통화 품질(목소리·말투) 무변화 — ✅ **이미 확인**("목소리 괜찮았어", 로그 경고·에러 0건,
  발화 속도 ko 6.5~8.1 / en 13~17자per초로 평소 범위)

### 엣지 케이스
| 케이스 | 처리 |
|---|---|
| 모델이 한 턴에 안 부름 | **안 바뀐다**(직전 표정 유지). 프론트 자료구조의 기본 동작 — 폴백 불필요 |
| 같은 값 연속 | 서버가 억제 |
| 모르는 값 | 그대로 보냄 → 클라가 neutral |
| barge-in 취소 | 프론트가 `_cancelledResidual` 로 오디오와 **같이** 버린다(이미 있음) |
| tool 응답 실패 | 로그만, 통화 유지(R5) |

## 5. 리스크 & 결정 사항

### 결정
- **D1. tool-call 이다.** 텍스트 태그는 낭독된다. 출력 전사 사이드카는 **소리보다 늦어**
  영상통화에서 못 쓴다. 오디오 프로소디는 늦고 크고 정확도 미지수.
- **D2. "바뀔 때만" 부른다.** 턴당 1개도, 문장마다도 아니다.
  프론트 `_pendingMarkers` 가 **변화 지점 목록**이라 자료구조와 일치하고,
  "안 부르는 턴" 문제가 **문제 자체로 성립하지 않는다.**
- **D3. ⛔ 말 구조를 고정하지 않는다.** "반응 먼저, 설명 나중"을 프롬프트로 강제하지 않는다.
  바이트 위치 못박기가 이미 그 문제를 풀었고, 고정하면 대사가 틀에 박히며
  문장상한 3(반응1+설명1+질문1)과 부딪힌다. 프롬프트가 정하는 건 **타이밍뿐**이다.
- **D4. 값 5종 고정.** `neutral happy surprised sad angry` = 영상 자산과 정확히 일치.
- **D5. 서버 damper 없음.** 실측이 불필요하다고 답했다(0.4초 내 변경 0건).
  ⚠ n=28 이라 본편 배포 후 재확인. 필요해지면 그때 넣는다.
- **D6. `WHEN_IDLE`.** `SILENT` 는 "생성하지 마"라 비버가 입을 닫는다(실측·수정 완료).
  `INTERRUPT` 는 하던 말을 자른다.

### 리스크
- **R1. Live 세션 config 가 바뀐다.** 이 프로젝트에서 제일 조심하는 자리.
  ⇒ env 게이트 + "꺼지면 바이트 동일" 회귀. 실측상 품질 영향은 **관측되지 않았다.**
- **R2. ⚠ 앱은 `app-api` 를 본다.** 사장님이 앱으로 걸면 스파이크가 없는 서버로 간다
  (실제로 한 번 그래서 로그가 0건이었다). 3단계 검증은 **웹 데모**나
  **앱의 서버 주소 전환**이 전제다.
- **R3. n=28.** ②96% · ③깜빡임 0 은 표본이 작다. 본편 후 같은 계기판으로 재확인.
- **R4. 하드 디코더 2~3개 한계.** 감정이 자주 바뀌면 디코더 교체가 잦다.
  실측 간격(중앙 10초)에서는 안전하나, 모델이 수다스러워지면 프론트에서 볼 문제.

### 가정
- 프론트는 `feat/multilang` 기준. 위 5개 사실은 **직접 읽어 확인**했다.
- 캐스케이드 감정은 이미 동작 중이며 이 계획으로 **바뀌지 않는다.**
