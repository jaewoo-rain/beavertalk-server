## 0. 한 줄

통화가 끝난 뒤 도는 작업 4개를 **app-api 밖으로** 빼서, app-api·demo-api 의 `cpu-throttling` 을 켠다.
⇒ **월 약 $21 절감(95%)** + **분석 유실 제거** + **재시도 확보**.

## 1. 왜 하나 — 실측 숫자

### 1-1. 지금 돈이 새는 구조

| 최근 7일 | app-api | demo-api | 합계 |
|---|---|---|---|
| 과금된 인스턴스 시간 | 14.5h | 51.3h | **65.8h** |
| 실제 HTTP 요청 시간 | 0.15h | 1.06h | 1.21h |
| 실제 통화(WS) 시간 | — | — | 0.61h (40건 · 평균 55초) |
| **⇒ 유휴(그냥 켜져 있던 시간)** | | | **≈ 64h (97%)** |

통화 40건에 총 37분, HTTP 요청 다 합쳐 73분인데 **과금은 65.8시간**이다.

원인: `cpu-throttling=false`(CPU 상시 할당). 이 설정이면 **인스턴스가 살아 있는 내내** CPU 요금이 붙는다 —
요청이 없어도 붙는다. `min=0` 이라 결국 회수되지만, 회수까지의 유휴 꼬리가 저 64시간이다.

⇒ 월 약 282h × $0.079(1 vCPU + 2 GiB · 서울 · 상시할당) ≈ **월 $22**

### 1-2. 왜 상시 할당을 켰나 — 그게 문제의 뿌리

통화가 끝나면 무거운 작업을 **fire-and-forget**(`asyncio.create_task`)로 띄운다. WS 요청은 그 전에 닫힌다.
`cpu-throttling=true` 면 요청이 끝난 순간 CPU 가 거의 0으로 조여져 **그 작업이 멈춘다.**
그래서 상시 할당을 켰다 — 즉 **「요청 밖에서 일을 시키려고」 24시간 CPU 를 산 것**이다.

### 1-3. 그런데 유실도 일어나고 있다 (더 중요)

`min=0` + fire-and-forget 이라, WS 가 닫힌 뒤 인스턴스가 회수되면 **작업이 그냥 사라진다.** 재시도가 없다.

운영 실측(최근 30일 통화 461건):

| | |
|---|---|
| 60초 이상인데 요약·문장이 **아예 없는** 통화 | **2건** |
| `call=1713` m=169 · 09-28 12:16 · 89초 | 문장 0 |
| `call=1386` m=85 · 09-09 12:52 · 69초 | 문장 0 |

0.4% 다. 그 회원은 통화를 했는데 복습 재료도, 체크판 증거도 못 받았다.
⛔ **트래픽이 늘면 이 비율은 나빠진다** — 인스턴스 회수가 더 자주 일어난다.

## 2. 어떻게 하나 — 구조

### 2-1. 지금

```
앱 ──WS(5분)──▶ app-api ──통화 종료──▶ create_task 4개를 띄우고 WS 닫음
                    │                   (분석 · 재개요약 · 오디오 업로드 · 국적)
                    └── 이 작업들이 돌 때까지 CPU 가 필요하다
                        ⇒ cpu-throttling=false (24시간 CPU 구매)
                        ⇒ 인스턴스가 회수되면 작업 유실 · 재시도 없음
```

### 2-2. 바꾼 뒤

```
앱 ──WS(5분)──▶ app-api ──통화 종료──▶ Cloud Tasks 에 «작업 등록» 1줄 (즉시 반환)
                                              │
                                              ▼
                                   Cloud Tasks 큐  ← 재시도 · 속도제한 · 중복제거
                                              │  (HTTP push · OIDC 인증)
                                              ▼
                                   worker 서비스 ──▶ 분석 · 오디오 업로드 · 국적 추론
                                   (cpu-throttling=true)

app-api·demo-api : cpu-throttling=true  ⇒ 요청·통화가 도는 동안만 과금
worker           : cpu-throttling=true  ⇒ 태스크가 곧 요청이므로 도는 동안만 과금
```

⭐ **핵심은 「작업을 요청으로 바꾸는 것」이다.** Cloud Tasks 가 워커를 HTTP 로 찔러 주면 그건 정식 요청이라,
CPU 가 정상 할당되고 요청형 과금이 적용된다. 요청 밖에서 일할 필요가 없어지므로 상시 할당을 끌 수 있다.

### 2-3. 워커는 **test-api 를 쓴다** (새 서비스를 만들지 않는다)

`beavertalk-app-test-api` 가 이미:
- **같은 이미지**를 돌린다(deploy.yml 이 main 푸시 때 app-api 와 같은 이미지를 배포한다)
- **`cpu-throttling=true`** 다
- env 27개 · 시크릿 마운트가 이미 다 있다
- `X-Internal-Secret` 내부 인증 패턴이 이미 있다(`/internal/dispatch-calls` · `/internal/refresh-subscriptions`)
- 이미 스케줄러 전담이다 — 알람 발송(매분) · 구독 스윕(매시 20분)

⇒ **역할 이름만 「스케줄러 전담」 → 「워커」로 넓힌다.** 새 Cloud Run 서비스·새 시크릿·새 배포 경로가 필요 없다.

## 3. 사장님 질문 2개에 대한 답

### Q1. 「app-api 에서 알람까지 한 번에 처리하고 test-api 를 없애도 되지 않나?」

**기술적으로는 가능하지만, 이득이 없다. 권고하지 않는다.**

| | |
|---|---|
| test-api 지금 비용 | 7일 0.5h → **월 약 $0.2** |
| 없애서 아끼는 돈 | **거의 0** |
| 알람을 app-api 로 옮기면 | 매분 요청이 들어온다 → 월 약 43,200 요청 · 12h ≈ **$1.25** (throttling ON 이면 감당 가능) |

⛔ 그런데 **잃는 게 있다**:
1. **격리가 사라진다.** `app-api` 는 `maxScale=5` 다. 알람 발송이 느려지거나 막히면 **통화가 쓸 인스턴스를 잡아먹는다.** 지금은 test-api 가 `maxScale=20` 으로 따로 받는다.
2. **배포 사고 범위가 합쳐진다.** 지금은 통화가 깨져도 알람은 살고, 반대도 된다.
3. ⚠ **매분 요청은 인스턴스를 24시간 깨워 둔다.** throttling ON 이면 과금은 요청 시간만이지만, 만약 나중에 누군가 app-api 의 throttling 을 다시 끄면 **그 순간 월 $57(720h)로 튄다.** 지금 상시 할당을 켠 이유를 생각하면 그런 날이 또 올 수 있다.

### Q2. 「test-api 를 worker 로 쓰면 되는 거지?」

**그렇다. 이게 맞는 답이다.** §2-3 그대로 — test-api 를 워커로 쓰고, 알람·구독 스윕도 거기 그대로 둔다.
서비스 3개 구성이 유지된다: **app-api(운영 통화) · demo-api(데모 통화) · test-api→worker(스케줄러 + 태스크)**.

⚠ 이름이 헷갈린다는 건 사실이다(`test-api` 인데 운영 알람을 쏜다). 이름 변경은 **별건으로 미룬다** —
Cloud Run 서비스 이름을 바꾸면 URL 이 바뀌고 스케줄러 2개·deploy.yml 을 같이 고쳐야 한다. 이번 변경에 끼우면 실패 지점이 늘어난다.

- [ ] **6. 스케줄러 잡 추가 없음** — 알람·스윕은 그대로 test-api
- [ ] **7. ⚠ 마지막에** `app-api`·`demo-api` **`--cpu-throttling` 켜기**. ⛔ 4·5 가 실제로 도는 걸 확인한 **뒤에** 켠다. 순서를 뒤집으면 분석이 전부 죽는다
- [ ] **8. 유실 백필(선택)** — `call=1713`·`1386` 처럼 분석이 안 돈 통화를 태스크로 다시 돌릴 수 있다. 전사가 남아 있으면 가능

## 6. 수용 기준

- [ ] 통화 종료 응답 시간이 지금과 같거나 빠르다(등록은 1줄이다)
- [ ] 통화 1건 → 태스크 4개 등록 → 워커가 다 처리 → `call.summary`·`sentence`·오디오·국적이 지금과 동일하게 채워진다
- [ ] **같은 태스크를 2번 보내도 결과가 한 번만 생긴다**(멱등 — 회귀로 고정)
- [ ] 워커가 500 을 돌려주면 Cloud Tasks 가 재시도하고, 재시도로 성공한다
- [ ] 등록 자체가 실패해도 **통화는 정상 종료**된다(폴백 경고 로그 1줄)
- [ ] `app-api`·`demo-api` throttling ON 이후에도 분석이 100% 돈다(24시간 관찰)
- [ ] 통화 중 태스크 8개는 **건드리지 않았다**(§4) — 통화 회귀 `tests/test_normalcall_ws.py` 통과
