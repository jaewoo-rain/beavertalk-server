## 3. S2 — 계정 삭제를 하드 삭제로 (가장 큼)

### 실측 — DB 는 한 방에 끝난다
`member` 를 참조하는 FK 가 **전부 `ON DELETE CASCADE`** 다.
⇒ **`DELETE FROM member` 하나로 DB 가 끝난다. 테이블을 하나씩 지우는 코드를 쓰지 마라.**

> ⚠ **개수가 두 출처에서 다르다.** bt-back 이 운영 DB `information_schema` 로 센 값은
> **22개**, 빌더가 `domains/` 에서 `ForeignKey("member.member_id"` 로 센 값은 **18개**다.
> 차이는 컬럼명이 다른 것(`classroom.teacher_member_id`)과 `domains/` 밖 테이블로 보인다.
> **cascade 동작의 권위 있는 출처는 DB(22개)** 다 — 구현 전에 그 22개 목록으로 다시 맞춘다.

### 걸림돌 ① 결제 보존
`payment`·`subscribe`·`iap_receipt` 의 `member_id` 가 **NOT NULL** 이라 「연결만 끊기」가
안 되고 cascade 로 같이 지워진다.

> 📌 **「5년」의 출처는 코드가 아니다.** 빌더가 전수 확인했으나 코드·설정에 근거가 없다 —
> 요청서(법무)가 「전자상거래법 5년」이라고 적은 것이다. **1차 자료가 아니므로 법무
> 확인이 필요하다**(§7).

### ⭐ 결정(2026-09-26 사장님) — **`member_id` 를 비운다.** 아카이브 테이블 안 만든다

사장님: **「멤버지우면 fk member_id칸 비우면 안되나?」**
bt-back·빌더는 처음에 아카이브 테이블을 추천했는데 **사장님 안이 더 낫다.** 뒤집는다.

| | **(가) `member_id` → NULL** ⭐채택 | (나) 아카이브 테이블 (기각) |
|---|---|---|
| 스키마 | 3표에 `DROP NOT NULL` + FK `ON DELETE SET NULL` — **1회 마이그레이션** | **3표를 복제** — 영구히 늘어난 스키마 |
| 코드 | **없음** — DB 가 알아서 비운다 | 삭제마다 스냅샷 복사 로직 |
| 조회 | 결제 행이 **원래 자리에 그대로** | 「과거 결제」를 보려면 두 표를 합쳐야 한다 |

⇒ bt-back 이 (나)를 밀었던 근거는 「운영 FK 변경이 위험」이었는데, 그건 **일회성**이고
아카이브는 **중복 스키마를 영구히 남긴다** — 그쪽이 더 비싸다. 판단을 바꾼다.

### 구현 시 주의
- 마이그레이션: `payment`·`subscribe`·`iap_receipt` 3표에 대해
  ① `ALTER COLUMN member_id DROP NOT NULL` ② FK 를 `ON DELETE CASCADE` → **`SET NULL`**
  ⛔ ②를 빼면 여전히 cascade 로 **지워진다.** 둘을 같이 해야 한다
- ⛔ **모델(`Mapped[]`)의 `nullable`·`ondelete` 도 같은 커밋에서 바꾼다**(R2 — 모델과
  마이그레이션은 같은 커밋). 모델만 바꾸고 마이그레이션을 빼면 2026-09-23 알람 500 이 재현된다
- ⚠ 빌더 지적: 기존에 `payment ⋈ member` 로 조회하는 코드가 탈퇴 회원을 걸러내는지
  **감사하지 않았다** — 구현 전에 grep 한다. `member_id IS NULL` 행이 생기므로
  **INNER JOIN 은 그 행을 조용히 떨어뜨린다**(그게 맞는 동작인지 확인)
- ⚠ **신원이 사라진다**: 금액·일시·상품은 남지만 「누가 낸 돈인지」가 없다.
  법이 「거래 기록」만 요구하면 충분하고 「거래자 정보」까지 요구하면 이메일 같은 걸
  스냅샷 컬럼으로 박아야 한다 → **§7 (2) 법무 확정 대기.**
  ⇒ 그때까지는 **스냅샷 컬럼 없이 `member_id` 만 비우는 쪽**으로 짠다. 필요해지면
  컬럼 하나 더 붙이면 되므로 되돌릴 수 없는 선택이 아니다

### 걸림돌 ② GCS 음성 — ⭐ **사장님 결정(2026-09-26): 지우지 않는다**

> **「음성 놔둬. 지우지마」** — 탈퇴해도 GCS 음성은 **보존한다.**
> bt-back 이 Play 요건과의 충돌을 한 번 제기했고 사장님이 재확인했다. 그대로 간다.

⇒ **S2 의 GCS 단계가 통째로 빠진다.** `core/storage.py` 에 삭제 함수를 새로 쓸 필요도
없고(없는 걸 확인했다), 「GCS 먼저, DB 나중」 순서 고민도 사라진다.
설계가 **DB 하드 삭제 + 결제 아카이브** 둘로 단순해진다.

⭐ **재사용 위험 없음(확인)** — 음성 경로에 `member_id` 가 박혀 있어서 「지운 회원의
번호가 새 회원에게 다시 나가면 남의 음성을 가리킨다」가 걱정거리였는데,
`member.member_id` 는 `GENERATED BY DEFAULT AS IDENTITY`(시퀀스 `member_member_id_seq`,
현재 162 > 최대 158)다. **시퀀스는 값을 재사용하지 않는다.** 남는 객체는 영구히
「그 번호의 탈퇴 회원 것」으로만 남는다.

⛔ **법무 후속(서버 아님)**: 처리방침과 Play 「데이터 삭제」 답변에 **「계정 삭제 후에도
통화 음성은 보존한다 + 그 사유 + 보존 기간」** 을 명시해야 한다. 앱 문구
(「permanently deletes your account and data」)도 실제와 어긋나므로 앱팀·법무가 조정한다.
S4 폐기로 생긴 「90일」 문구 불일치와 **같이 처리하면 된다.**

- ⭐ **`subscribe` 에 필요한 5칸이 전부 이미 있다**(`subscribe.py:27-83`) —
  `billing_state`·`is_trial`·`end_date`·`product_id`·`source`. 마이그레이션 불필요
- **acknowledge 호출 코드는 저장소 전체에 0건**(docstring 언급뿐)

### 설계
- **구글**: `subscriptionState == ACTIVE` + `lineItems[].expiryTime` 로 유효성 판단.
  ⚠ acknowledge API 는 **v2 가 아니라 v1** `purchases.subscriptions.acknowledge` (빌더 확인)
  ⛔ **순서가 곧 환불 방지 설계다 — 「검증 → 지급 → acknowledge」.**
  지급 전에 acknowledge 하면 지급이 실패해도 환불 창구가 닫힌다.
  acknowledge 가 없으면 **3일** 안에 자동 환불+revoke(공식 문서 확인됨)
- **애플**: App Store Server API 「Get All Subscription Statuses」
  (`GET /inApps/v1/subscriptions/{transactionId}`).
  ⚠ 애플엔 acknowledge 류 절차가 **없는 것으로 보인다** — 웹 검색 기반이고 Apple 원문의
  명시적 부정문은 확인하지 못했다. **구현 전에 재확인**한다
- **키 없이 짤 수 있는 범위**: `subscribe` 대응표 · `IapReceipt` 저장 · 라우터·서비스
  뼈대 · acknowledge 호출 **위치** · 가짜 응답으로 도는 시험
- **키가 있어야만 되는 범위**: `_verify_google`·`_verify_apple` 의 실제 HTTP 검증
- 켠 뒤 운영 env `IAP_VERIFY_ENABLED=true`

### ⛔ GCS 버킷에 접두어가 둘이다

버킷 **전체**에 lifecycle 이나 일괄 삭제를 걸면 **취약발음 미리 구운 음성 233건 ·
숙제 예문 3건 · TTS 가 같이 지워진다.** 반드시 `voice-recordings/` 로 좁힌다.

### ⛔⛔ 전사를 지우면 달력·하루한도가 깨진다 — 「행 삭제 vs NULL」 둘 다 못 피한다
bt-back 이 「`call` 행을 지우면 달력이 깨진다」고 적었는데 **불완전했다**(빌더 정정).
`call_repository.py:17-29` `_spoke_exists()` 는 **`call` 행 존재가 아니라
`call_raw_data.role=='user' AND content IS NOT NULL AND content != ''`** 를 직접 본다.
그리고 달력(:275)뿐 아니라 **하루 한도·이어하기 판정(`has_call_in_window`, :113)도
같이 쓴다.**
⇒ **행을 지켜도 `content` 만 비우면 똑같이 깨진다.** 파기를 하려면 `_spoke_exists()` 를
`content` 의존에서 **분리하는 것이 선행조건**이다(예: 통화 종료 시 `call.was_spoken`
같은 불변 플래그를 한 번 기록). 부수 작업이 아니다.

> 📌 이 발견은 지금도 유효한 사실을 설명한다 — 운영에 **user 전사가 전부 빈 통화가
> 398건**(평균 17초)인데, 그 통화들은 달력·하루한도에서도 「말한 통화」로 세지지 않는다.

### ⛔ `item_evidence` 와 하드 삭제
`item_evidence` 는 레벨업 근거인 **append-only 로그**(「증거가 원본·UPDATE 금지」 불변식)이고
`learner_quote` 에 전사를 **그대로 복사한 발췌**를 담는다(`item_evidence.py:87-89`).
`call` 행을 하드 삭제하면 cascade 로 **같이 사라진다** — 파기를 행 삭제로 하면 이 불변식과
정면충돌한다. (탈퇴 회원의 하드 삭제에서는 사라지는 게 **맞다** — 그 회원의 데이터다.)
⭐ 참고: `mastery_service`·`mastery_repository` 는 `CallRawData` 를 **한 곳도 안 읽는다**
(grep 0건) — 승급 판정은 `item_evidence` 만 본다.

### 앱은 통화 원음을 재생하지 않는다 (확인함)
`GET /calls/{id}/raw` 가 서명 URL 을 싣지만 **앱은 그 엔드포인트를 부르지 않고**
`voiceUrl` 을 소비하지 않는다(`beavertalk-flutter` `origin/dev` 전수 검색).

### 소프트 삭제된 계정에 이상 데이터 — ⛔ **「중간에 죽은 삭제」가 아니다(정정)**
`member 93` = `pregen-tmp-20260921@beavertalk.im` — `deleted_at` 이 찍혔는데 **email 이
남아 있고 `auth_user_id` 도 있다.**

bt-back 이 처음에 「§3 걸림돌 ③(멱등 아님)의 실제 증거일 수 있다」고 적었는데 **틀렸다.**
확인한 사실:
- `member_service.delete()`(`:225-235`)는 `deleted_at`·`email=None`·`auth_user_id=None` 을
  **한 번에 커밋**한다 — 이 경로에서는 그 조합이 **나올 수 없다**
- `deleted_at` 에 값을 쓰는 코드는 저장소 전체에 **2곳뿐**이다
  (`member_service.py:225` 회원 · `sentence_service.py:235` 문장)
- 부활 경로도 아니다 — `find_or_create_by_auth`(`:97`)는 `auth_user_id`(삭제 후 NULL)로만
  찾으므로 소프트 삭제된 행을 다시 채우지 않는다. `get_by_email` 폴백은 IntegrityError
  분기 안에만 있고 그 행은 `email` 이 NULL 이라 거기서도 안 걸린다

⇒ **원인 미상.** 수동 SQL 이나 저장소 밖 스크립트로 보인다(pregen 임시 계정이다).
⛔ **쫓지 마라** — S2 하드 삭제가 어차피 정리한다. 멱등화의 근거는 이 계정이 아니라
`supabase_auth.py` 의 except 통짜 처리 자체였고, 그건 그대로 유효하다.
