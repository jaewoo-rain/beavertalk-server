## 0. ⭐ 한 줄

`flutter_sound` 의 안드로이드 캡처 루프가 **자기 자신을 메인 루퍼에 계속 불려 넣는다.**
대기 러너블이 **초당 ~45개씩 선형으로 늘고**, 그 줄 뒤에 선 **영상 프레임 콜백이 굶어서** 버려진다.
오디오는 2026-08-14 에 백그라운드 큐로 빼 뒀기 때문에 혼자 멀쩡했다.

⇒ **처방은 `record` 로의 교체가 맞다.** 다만 근거는 「전용 스레드라서」가 아니라 **「증식항이 0이라서」** 다.

## 1. 근본원인 — 바이트코드로 확인했다

소스가 AAR 안이라(`com.github.canardoux:flutter_sound_core:9.30.0`) `javap -c` 로 읽었다.
AAR: `~/.gradle/caches/modules-2/files-2.1/com.github.canardoux/flutter_sound_core/9.30.0/…/flutter_sound_core-9.30.0.aar`

### 1-1. `FlautoRecorderEngine.writeData` — ⭐ 자기증식 루프

```
  3: if (!isRecording) → return
 30: ret = writeData16(...)          ← 여기서 AudioRecord.read
 70: if (!isRecording) → skip
 77: mainHandler.post(p)             ★ 매 회전마다 자기(p)를 다시 심는다
 89: if (ret != 0) → goto 3          ← 데이터가 있으면 계속 돈다
 94: → return
```

`p` 한 번 실행이 소비하는 것은 **자기 1개**인데, 회전마다 **1개씩 새로 심는다.**
비어 있지 않은 read 가 k 번이면 posts = k+1, 소비 = 1 ⇒ **순증 +k.**

⇒ 초당 캡처 청크 수(실측 ~45)만큼 **큐 깊이가 초당 45씩 자란다.**

### 1-2. 폴링이다 — 블로킹이 아니다

`writeData16` offset 22-23:
```
 22: iconst_1
 23: invokevirtual android/media/AudioRecord.read:([BIII)I
```
4번째 인자 `1` = **`READ_NON_BLOCKING`**. 그래서 메인이 통째로 멈추지는 않고(ANR 안 남),
대신 **큐가 깊어지는** 형태로 나타난다 — 우리가 잰 93~698ms 가 정확히 그 모습이다.

offset 5 `ByteBuffer.allocate(bufLn)` — **빈 폴링 1회마다 새로 할당한다.**
`bufLn` 기본 8192B(`flutter_sound_recorder.dart:754`) ⇒ N개가 떠 있으면 한 바퀴에 8KB × N 가비지.

### 1-3. 모델이 실측과 맞는다

`main_late_ms ≈ N × (폴링 1회 비용)`, `N ≈ 45·t`

| | 창 중앙 | 예측 N | 관측 |
|---|---|---|---|
| 앞절반 | ~75s | ~3,400 | **93ms** |
| 뒷절반 | ~225s | ~10,100 | **282ms** |

**관측 비 282/93 = 3.03 · 시간 비 225/75 = 3.00.** 원점을 지나는 직선이다.
역산한 폴링 1회 비용 27µs 는 8KB 할당 + JNI read 1회의 자릿수와 맞는다.
`MIC_NO_AEC`(86→243, 비 2.8)도 같은 직선. `MIC_OFF`(31→28)는 평평 — `p` 가 아예 없다.

⭐ **네 판이 전부 이 한 모델로 설명된다.** 그리고 「채널 부하라면 처음부터 높고 평평해야 한다」는
직관이 옳았다 — 자라는 것은 부하가 아니라 **큐의 깊이** 다.

### 1-4. 왜 하필 «영상» 만 죽는가

```java
FlutterRenderer.java:546-547   reader.setOnImageAvailableListener(…, new Handler(Looper.getMainLooper()));
FlutterRenderer.java:461-462   MAX_IMAGES = 5 + 2 = 7
FlutterRenderer.java:556-557   while (imageQueue.size() > 2) { …image.close(); }   ← 밀리면 버린다
```

영상 프레임 수신 콜백이 **메인 루퍼에 하드코딩** 돼 있다. 적체된 `p` 뒤에 줄을 서고,
못 따라가면 프레임이 버려지고 풀(7장)이 마르며 디코더까지 역압이 걸린다.

```java
FlutterPcmSoundPlugin.java:355-358   new MethodChannel(…, messenger.makeBackgroundTaskQueue());
```
오디오 재생은 2026-08-14 에 여기로 뺐다 ⇒ 메인 적체와 **완전히 격리** ⇒ `ping` 0~2ms 평평.

⇒ **「소리는 멀쩡한데 영상만 끊긴다」가 정확히 설명된다.** 두 관측이 일관된다.

## 2. 처방 — `record` 가 맞는 이유 (수정된 근거)

```kotlin
RecordThread.kt:84        mRecordThread = Thread { … }        ← 전용 스레드
PCMReader.kt:45           reader.read(readBuffer, 0, size)    ← 3인자 = 블로킹. 폴링 아님
RecordThread.kt:109-111   read → encode   (한 바퀴에 청크 1개)
RecorderRecordStreamHandler.kt:23   uiThreadHandler.post { eventSink.success(buffer) }   ← 청크당 정확히 1회
```

| | flutter_sound | record |
|---|---|---|
| read | **비블로킹 폴링** | 블로킹(커널에서 잔다) |
| 청크당 메인 post | **1~2개 (증식)** | **정확히 1개 (고정)** |
| 큐 깊이 | 초당 +45 | 상수 |
| 빈 폴링 할당 | 8KB/회 | 없음 |

### ⛔ 「record 도 메인에 post 하니 똑같다」는 기각

사실이다 — `record` 도 메인에 post 한다. 그리고 **어떤 플러그인도 그걸 못 없앤다**
(플랫폼→Dart 메시지는 메인 강제). 하지만 문제는 **«메인을 쓰느냐»가 아니라 «메인 큐가 자라느냐»** 였다.
`record` 는 그 증식항이 **0** 이다. 덤으로 프레임 크기가 704B/45회 → 1280~3200B/10~25회로
**건수까지 준다**(`PCMReader.kt:106,118` `minBufferSize*2`).

### 기각한 대안

| 대안 | 왜 기각인가 |
|---|---|
| **flutter_sound 채널에 TaskQueue** | ⛔ **효과 0.** TaskQueue 는 *Dart→네이티브* 방향만 바꾼다. 폭풍은 채널 밖 AAR 안에서 `Looper.getMainLooper()` 로 직접 post 한다 |
| **ExoPlayer 를 다른 Looper 로** | 뺄 손잡이가 없다. 프레임 콜백 스레드는 플러그인이 아니라 **엔진** 이 `FlutterRenderer.java:547` 에서 못 박는다. ExoPlayer 는 원인이 아니라 **피해자** |
| **`VideoViewType.platformView`(SurfaceView)** | 영상만 면역이고 원인은 남는다. 그리고 아바타는 idle/talk/emo **3층을 opacity 로 크로스페이드** 한다(`sync_avatar.dart:255-266`) — 플랫폼뷰로는 이 합성이 사실상 불가능 |
| **스프라이트로 회귀** | 사장님이 2026-08-31 에 폐기(`avatar_assets.dart:6-11`), 자산 147장·53MB 를 `5d4043a` 에서 삭제 |

## 3. ⛔ 머지 전에 반드시 고칠 것 — 전부 실측 확인함

이미 만든 교체본(미커밋)에 **조용히 실패하는 결함이 3개** 있다. 셋 다 예외도 로그도 안 남는다.

### D1 ⛔ iOS 통화가 영구 정지한다 (내가 만든 결함)

`_closeMicRecorders` 가 **리스너 없는** `StreamController` 를 `await close()` 한다.

> `dart-sdk/lib/async/stream_controller.dart:272-274` —
> *"If no one listens to a non-broadcast stream … this future will never complete."*

경로: `_openWithFlutterSound` 가 `_micController` 를 **리스너 없이** 세운다 → `startRecorder` 가
던진다 → 재시도 catch 의 `_closeMicRecorders()` → **여기서 멈춘다.** 통화가 「연결 중」에 박힌다.
⚠ 옛 코드는 안전했다 — 컨트롤러 생성 **직후 동기로** 리스너를 붙였다.

**고칠 방향**: 실패 시 컨트롤러를 `close()` 하지 말고 참조만 떼거나, `hasListener` 를 보고 닫는다.

### D2 ⛔ 안드로이드 재시도 6회가 사문화됐다

```kotlin
RecordThread.kt:113-115   } catch (ex: Exception) { recorderListener.onFailure(ex) }
                 finally { startLatch.countDown() }
```
`record` 는 캡처 실패를 **스레드 안에서 삼킨다.** `startRecording()` 은 정상 리턴한다
⇒ `"AudioFlinger could not create record track"` 류가 **예외 0건** ⇒ 재시도가 한 번도 안 걸린다.
⚠ 그 재시도는 「잠금화면 accept 직후 실패」를 겪고 만든 것이다(`:2282-2286` 주석).

**고칠 방향**: 스트림에 `handleError` 를 붙여 최소한 **보이게** 하고, 워치독 one-shot 을 안드로이드에서 2~3회로.

### D3 ⛔ 알림음 하나에 마이크가 죽고 안 돌아온다 (신규 회귀)

```kotlin
AudioRecorder.kt:53   audioSession.apply(config, requestFocus = true)
AudioSessionManager.kt:52   if (requestFocus && config.audioInterruption != NONE) requestAudioFocus(...)
AudioRecorder.kt:37-40   onFocusLoss = { pauseRecording() }
                         onFocusGain = { if (interruption == PAUSE_RESUME) resumeRecording() }
```
`audioInterruption` 기본값이 **`pause`** 라 **재개 분기를 안 탄다.** 포커스를 잠깐 뺏기면
**남은 통화 내내 벙어리** 가 되고, 워치독은 6초 1회라 못 잡는다.
⚠ `flutter_sound` 는 오디오 포커스를 **한 번도 안 만졌다** — 순수 신규 경로다.

**고칠 방향**: `audioInterruption: rec.AudioInterruptionMode.none` 한 줄. 포커스 요청 자체가 안 나가
옛 거동과 같아진다.

### D4 ✅ 이미 고침 — `MIC_NO_AEC` 가 캡처 소스까지 물었던 것

옛 코드는 `audioSource` 를 토글과 **무관하게** 늘 `voice_communication` 으로 뒀다
(`HEAD:normalcall_controller.dart:2310-2313` — 직접 확인). 교체본이 그걸 토글에 물려서
그 실험이 「AEC 를 뺐다」가 아니라 「AEC+NS+캡처소스를 뺐다」가 됐다 ⇒ **되돌렸다.**

### D5 계측 눈금 갱신 (반나절을 태우는 종류)

프레임이 704B/22ms → 1280~3200B/40~100ms 로 바뀐다. 이걸 안 따라간 주석들:
`:2214-2227`(「건당 704B」「22ms 가 기준자」) · `:2232`(`gapUs < 2000` 짝도착 임계) ·
`:2935`(「마이크는 다른 채널(flutter_sound)」) · `:2940-2942`(판정표).
⇒ **실기기 첫 판의 `MIC:` 로그로 실제 값을 확인한 뒤** 주석을 고친다(추측으로 쓰지 않는다).

## 6. ⛔ 아직 안 풀린 것 하나 — 결정을 막지는 않는다

Flutter 3.44 는 UI 스레드를 플랫폼(메인)에 **병합** 한다:
```
settings.h:382-383                merged_platform_ui_thread = kEnabled   (기본)
android_shell_holder.cc:143-145   ui_runner = platform_runner
```
그렇다면 「메인 2.3초 정지 창에서 Dart 지연 `_elLagMax` 는 17ms」(`통화로그.txt:3134`)가
**성립할 수 없다.** 둘 중 하나가 거짓말을 하고 있다.

⚠ 그리고 그 관측 위에 세운 판정 규칙이 코드에 남아 있는데, **그 규칙도 성립 불가** 다 —
`normalcall_controller.dart:2853-2859` 는 `ping`(빈채널왕복)과 `main_late_ms` 를 대조하라고 하지만
`ping` 은 백그라운드 큐라 **메인 루퍼를 안 탄다**(`FlutterPcmSoundPlugin.java:355-358`).

⇒ **읽어서는 못 가른다. 30분짜리 실측이다** — 네이티브에서 메인을 1초 일부러 막고
두 값을 나란히 찍는다. 같이 튀면 병합이 맞고, 지금까지의 「Dart 는 무죄」 전제가 무효다.
⭐ 다만 **이번 결정은 이것과 무관하다** — `MIC_OFF` 판(31→28ms 평평)은 저 대조 규칙을 안 썼다.

### 계측 자체는 검증했다

| 의심 | 판정 |
|---|---|
| 93→282 이 누적 최댓값인가 | **아니다.** `FlutterPcmSoundPlugin.java:495-496` 이 창마다 0으로 비운다(창 5초) |
| 28 vs 31ms 차이 | **무의미.** 20ms 표본 ⇒ ±20ms 양자화. 93 vs 282 는 잡음 밖이라 유효 |
| `MIC_OFF` 가 다른 것도 끄나 | 워치독(6초 1회 타이머) 하나뿐 — **오염 없음** |
| `main_late_ms` 가 부하인가 | **아니다. 최댓값이다.** p50·p95·초과횟수가 없다. 「평균 3배 바빠졌다」로 읽으면 과대해석 |
