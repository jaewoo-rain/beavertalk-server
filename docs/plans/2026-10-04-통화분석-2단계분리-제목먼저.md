# 통화 분석 2단계 분리 — 제목 먼저 (PM-DEC-362)

> 작성 2026-10-04 15:18 KST · 기준 `origin/main` = `3f54ec5` · 브랜치 `feat/title-first-analysis`
> 요청: 앱 PM-DEC-362. 승인: 사장님 「a로 먼저 하고 푸쉬」.

## 0. 무엇을 고치나

통화가 끝나면 앱 대기 화면이 날짜·통화시간을 먼저 띄운다(앱 반영 완료). 그런데
**제목(`call.summary`)은 분석 LLM 1회(실측 5초+)를 기다린다** — 표현·현지인표현·격려와
**한 커밋**이기 때문이다(`normalcall_service.py:2863`, `_save_analysis`).

⇒ 제목만 **별도 경량 LLM 1회**로 먼저 만들어 `call.summary` 에 선저장한다.
분석(2단계)은 현행 그대로 돌고, **이미 제목이 있으면 덮지 않는다.**

⛔ **상태값(`status`)은 추가·변경하지 않는다.** `analyzing` 그대로다 —
앱은 「`summary` 필드가 차 있나」로 판단한다. 스키마(테이블·열)도 **무변화**.

## 1. 자리 — 어디에 띄우나

실제 코드를 눈으로 확인한 결과 **분석 태스크와 이어하기 요약 태스크는 둘 다
`call_session._trigger_analysis`(:4483) 안에서 떠 있다**:

| 줄 | 무엇 |
|---|---|
| `call_session.py:4456` | `_trigger_chat_memory`(자유대화 기억, fire-and-forget) |
| `call_session.py:4459~4468` | `_trigger_analysis(...)` 호출 — finally 블록 |
| `call_session.py:4535` | 그 안에서 `normalcall-analysis-{id}` 태스크 생성 |
| `call_session.py:4548~4554` | 그 **바로 옆**에서 `normalcall-resume-summary-{id}` 태스크 생성 |

⇒ 제목 태스크도 `_trigger_analysis` 안, 이어하기 요약 **바로 앞**에 나란히 띄운다.
`trigger_reanalysis`(:4591)도 이 함수를 타므로 수동 재분석에도 자동으로 붙는다.

> ⚠ 요청서·지시문의 `:4455~4483` / `:4429~4466` 은 둘 다 실제와 어긋난다
> (오늘 PR #20·#21 이 이 파일을 건드렸다). 위 표가 `3f54ec5` 기준 실측이다.

## 2. 1단계 — 제목 생성기

| 항목 | 결정 |
|---|---|
| 재료 | `_resume_transcript(db, call_id)` — 이어하기 요약이 쓰는 **같은 읽기**(`normalcall_service.py:1075`). 역할 접두 + 마지막 4,000자 |
| 호출 | 경량 LLM **1회** · `thinking_budget=0` · `temperature=0.0` · 출력 **1필드** |
| 모델 | `settings.TITLE_MODEL`(신설, 기본 **`""` = `JUDGE_MODEL`**) — §9 실측 참조 |
| 출력 규칙 | ⭐ **일반 분석(`_analysis_instruction`)의 summary 규칙을 공유**(복제 금지) |
| 저장 | `call.summary` + `call.summary_lang`(`display_i18n_service.summary_lang_for`) |
| status | ⛔ **안 건드린다** |
| 실패 | 경고 로그만. 2단계가 현행대로 채운다(R5) |
| 조기 탈출 | 전사가 비었거나 **`status=done`** 이면 LLM 을 아예 안 부른다(§5) |

### 2-1. 출력 규칙을 공유하는 방법

요청서는 「출력 규칙은 `:3556` 과 같다」고 했으나 **그 줄은 분석 지시문이 아니라
`_leveltest_instruction`(:3503) 안**이다. 일반 분석의 규칙은 `:2444` 에 따로 있고
**예시 3개를 품고 있다**(경량 모델일수록 예시가 규칙이다 — prompts/README §3 원칙 4).

⇒ `:2444` 의 세 줄을 `_summary_field_rule(label)` 헬퍼로 뽑아
`_analysis_instruction` 과 새 `_title_instruction` 이 **같은 객체**를 쓴다.
⛔ 리팩터 결과는 **바이트 동일**이어야 한다(`test_native_expression_pair.py` 가 이 지시문을 읽는다).

⛔ `_leveltest_instruction` 의 summary 규칙은 **안 건드린다**(판정관 프롬프트 — 범위 밖).
1단계가 이기므로 레벨테스트 화면 제목도 `:2444` 톤으로 통일된다.

## 3. 2단계 — 현행 분석 (덮어쓰기 금지)

`call.summary = result.summary` 두 자리에 **「비어 있을 때만」** 가드를 넣는다.
`summary_lang` 도 **같이** 묶는다(한쪽만 바뀌면 목록이 언어 판정을 틀린다).

| 파일:행 | 함수 |
|---|---|
| `normalcall_service.py:2863,2865` | `_save_analysis`(:2833) — 일반·표현·프리토킹 |
| `normalcall_service.py:3709,3711` | `_save_level_assessment`(:3663) — 레벨테스트 |

**부수 효과(좋은 쪽)**: 레벨테스트 표본 미달 경로는 지금 `summary=""`·`summary_lang=NULL`
을 **덮어쓴다**(`analyze_level_test_call` 의 `sparse`). 가드가 들어가면 1단계 제목이 살아남는다.

## 4. 레벨테스트도 1단계 대상이다 (서버 판단)

둘 다 **같은 전사**를 보고 둘 다 **「핵심 소재 명사구」**를 요구한다. 레벨 판정은
`band`·`feedback_for_learner` 가 따로 담으므로 `summary` 는 판정과 무관한 칸이다.
앱이 통화 종류로 갈라지지 않으므로(`call_finish.dart:241`) 빼면 레벨테스트만 제목이 늦는다.
⇒ **콜타입 분기 없이** 전부 1단계를 돌린다(`_trigger_analysis` 는 콜타입을 안 본다).

## 5. 경합 — ⛔ QA 에서 설계를 한 번 뒤집었다

### 처음 쓴 것 (first-writer-wins = 「제목이 이미 있으면 안 쓴다」) — **틀렸다**

`_trigger_analysis` 는 통화 1건에 **조각마다** 다시 돈다(이어하기 — `resume_call`
(`:1011`)이 `status` 를 ongoing 으로 되돌리고, 조각이 끝나면 `_persist_remaining`
(`call_session.py:4642`)이 `finalize_call(status="analyzing")` 으로 되돌린다). 그래서:

```
조각1 끝 → 1단계가 **조각1 전사만** 보고 제목을 박는다
조각2 끝 → 1단계는 「있다」고 건너뛰고, 2단계도 「있다」고 건너뛴다
⇒ 15분 통화의 제목이 처음 5분만 설명한다
   (종전엔 조각2 분석이 전사 **전체**로 다시 썼다 — 조용한 품질 하락)
```

### 고친 것 — 1단계의 게이트는 **`status == "done"`**

2단계는 제목과 `status="done"` 을 **한 커밋**으로 쓴다 ⇒ `done` = 「2단계가 끝났고
결과 화면이 열렸다」. 그걸 기준으로 삼으면 두 요구가 **동시에** 만족된다:

| 경우 | 결과 |
|---|---|
| 1단계가 먼저(정상) | 1단계 제목이 뜨고 2단계가 건너뜀 → **화면에서 안 바뀜** |
| 2단계가 먼저(아주 짧은 통화) | `done` 이 찍혀 1단계가 **LLM 도 안 부르고** 건너뜀 |
| 조각2 (이어하기) | status 가 analyzing 으로 돌아왔으니 1단계가 **통화 전체 전사**로 다시 씀 |
| 수동 재분석 | `failed`→`analyzing` 이라 다시 돈다(제목도 갱신) |

2단계 쪽 가드는 요청서대로 **「이미 있으면 안 쓴다」** 그대로다(두 함수 모두).

- `call_session.py:299` 의 선례(이어하기 요약 경합, 최악 간격 3초)가 가리키는 함정은
  **「늦은 쪽이 옛 값을 쓴다」**였다. 여기는 늦은 쪽이 **아무것도 안 쓴다**.
- ⚠ 남는 틈(수 ms): 2단계가 `summary` 를 읽은 뒤 커밋하기 전에 1단계가 끼어들면 2단계가
  이긴다. 값은 같은 종류의 명사구 한 줄이라 데이터 깨짐이 아니다 — 제목 하나 때문에
  분석 트랜잭션을 행 잠금으로 직렬화할 가치는 없다.

## 6. 원가 기록

`usage_json` 에 **곁가지 키 `title`** 로 얹는다 — `add_call_usage_extra`(:2228) 선례 그대로.
`SIDE_LLM_KEYS`(:2025)에 `"title"` 을 등록해 `estimate_side_cost_usd` → `estimate_call_cost_usd`
가 자동으로 더하게 한다. ⛔ **새 산식을 만들지 않는다** — 원가 입구는 계속 그 한 함수다.

⚠ 키를 `analysis` 에 합치지 않는다 — `add_call_usage_extra` 는 같은 키를 **덮어쓰므로**
분석 몫과 제목 몫이 서로를 지운다.

## 7. 시험 (`tests/test_title_first_analysis.py` 신설)

1. 1단계가 `summary`·`summary_lang` 를 채운다 · `status` 는 `analyzing` 그대로

### Q6 상세 — 프로덕션 버그가 아니다

시험 DB 는 `sqlite:///:memory:` + `StaticPool` ⇒ **전 세션이 DBAPI 연결 하나를 공유**한다.
통화 종료 후 백그라운드 태스크 4개(분석·이어하기 요약·기억·**제목**)가 각자 `run_db` 로
세션을 열면 그 한 연결에서 트랜잭션이 겹쳐
`(sqlite3.DatabaseError) cannot start a transaction within a transaction` 가 난다.
실측: 전 스위트 부하에서 `test_run_call_persists_segments_and_status` 1건 실패
(그 파일 단독 6/6 통과 — 부하 의존).
⭐ 프로덕션은 세션마다 pgbouncer 풀에서 **자기 연결**을 받으므로 동시 실행이 정상 경로다
(분석·요약·기억이 이미 그렇게 돈다). ⇒ 고칠 자리는 **시험 하네스**.
⛔ 태스크를 끄지 않았다(끄면 그 시험들이 통화 종료 배관을 안 본다). 순서는 그대로 두고
겹침만 막는다(FIFO 락, 이벤트 루프별).

## 12. 못 한 것 · 미확인

- ⚠ **실통화 미검증.** 모든 지연·제목 품질 수치는 **합성 전사**로 재고 시험으로 못질한 것이다.
  배포 후 로그 `normalcall 제목 선생성: 저장 NNNms 제목='...'` 로 확인한다.
- ⚠ **usage 잃는 좁은 틈**: 제목·분석 두 태스크가 각자 `add_call_usage_extra`(읽고-합치고-쓰기)를
  하므로 같은 순간이면 한쪽 키가 덮일 수 있다. 계기판만의 손실(R5)이고 기존 `analysis`/`tts` 도
  같은 패턴이다 — 제목 쓰기(≈1.3s)와 분석 쓰기(≈6s)가 5초쯤 떨어져 있어 실제 확률은 낮다.
- ⚠ `vi` 제목은 베트남어 틀 + 한국어 인용 혼합이 남는다(`Học cấu trúc -고 싶어요 ...`).
  뜻은 맞아서 그대로 뒀다 — 실통화로 판단한다.
- ⛔ `_leveltest_instruction` 의 summary 규칙은 안 건드렸다(판정관 프롬프트 — 범위 밖).
  1단계가 실패한 레벨테스트만 예시 없는 옛 규칙으로 제목을 만든다.
