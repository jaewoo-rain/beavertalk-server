# §5 알람 시간대

## 0. ⭐ 지금 **활성 알람 10/11 이 잘못된 시각에 울릴 수 있다**
| | |
|---|---|
| `alarm` 행 | **17개**(요청서는 14 라고 적었다) · 활성 **11개** · `time` NULL 0 |
| `time` 저장 모양 | 17행 전부 `'2000-01-01 HH:MM:00+00'` — 앱이 시간대 없이 보낸 값이 세션 TZ(UTC)로 박힌다 |
| 활성 알람의 회원 언어 | **en 9(회원 7명) · ja 1 · ko 1** |

⇒ **활성 알람의 10/11 이 한국어가 아닌 회원 것이다.**
⛔ 다만 그들의 **실제 시간대는 서버 어디에도 저장돼 있지 않다**(`call` 표에도 `tz` 칸이 없다)
⇒ **지금 실제로 틀린 시각에 울리고 있는지는 확인할 수 없다.** 언어 ≠ 시간대다.

## 1. ⛔ 핵심은 시·분이 아니라 **요일**이다
`dispatch_service.py` 실측:
- `:29` `APP_TZ = ZoneInfo("Asia/Seoul")` · `:46` `now = datetime.now(APP_TZ)`
- `:33-37` `_wall_hm` 이 `alarm.time` 을 UTC 로 바꿔 **시·분만** 뽑는다(= 앱이 고른 벽시각)
- `:75` `b.hour/b.minute == 알람 시·분`
- `:77` 요일 = `_DAY_CODES[b.weekday()]` ← ⛔ **서울 벽시각의 요일**을 `day_of_week` 와 대조

⇒ 뉴욕 사용자가 고른 「**월** 08:00」은 **서울 월요일 08:00**(= 뉴욕 **일요일** 19:00)에 울린다.
**시·분만 옮기면 안 된다** — 알람 시간대의 `now` 에서 **시·분·요일을 같이** 계산해야 한다.

## 2. 설계

### 컬럼 (추가형)
`alarm.tz` Text NULL · `alarm.tz_offset_min` Integer NULL. ⛔ **기본값 없음.**

### ⭐ 폴백은 **디스패치 한 곳**에만 둔다
```python
zone = _resolve_zone(a.tz) or offset_zone(a.tz_offset_min) or ZoneInfo("Asia/Seoul")
now  = datetime.now(zone)          # 이 zone 의 시·분·요일로 비교
```
⛔ **쓰기 때 서울을 채워 넣지 마라.** 그러면 「앱이 안 보냈다」와 「진짜 서울이다」가
**구분이 안 된다.** 읽기(`AlarmOut`)도 저장값 그대로 — **없는 시간대를 응답에 지어내지 않는다.**
⭐ 디스패치가 시간대를 쓰는 **유일한 곳**이고 호출부가 하나다(`internal.py:29`).

### 우선순위는 있는 코드를 재사용한다
`call_service.py:329-337` `_resolve_zone` — tz(ZoneInfo) → 실패·없음이면 **경고 로그** →
`tz_offset_min`. 달력(`stats.py:16-38`)·daily-status(`call.py:140-189`)·WS start
(`call_session.py:3225-3264`)가 **이미 그 규율**이다.
⚠ 단 **마지막 폴백이 셋 다 UTC** 다. 알람은 **Asia/Seoul** 이어야 한다(기존 17행이 서울
가정으로 만들어졌다) ⇒ `_resolve_zone` 은 재사용하고 **폴백만 알람 쪽에서 서울로** 둔다.

### ⭐ 멱등 키 — **알람 시간대의 로컬 벽분**으로
지금: `bucket_key = "YYYY-MM-DD HH:MM"`(서울 벽분), 유니크 `(alarm_id, intended_fire_minute)`
(운영 인덱스 `uq_push_dispatch_alarm_minute`. 표본 `'2026-09-28 16:39'` 의 `created_at`
07:39 UTC = 16:39 KST 로 확인).

⇒ 알람 시간대의 로컬 벽분으로 바꾼다. **NULL(서울) 알람은 지금과 같은 문자열**이 나와
**배포 직후 같은 분에 이중 발송이 없다.**
⛔ **UTC 키로 바꾸지 마라** — 배포 경계의 catchup 창에서 같은 알람이 **다른 키로 한 번 더**
울린다.

## 3. ✅ 결정 — 서머타임
| | |
|---|---|
| 가을 되돌림(로컬 01:30 이 두 번) | 같은 키라 **두 번째가 막힌다 → 한 번만 울린다** ⭐ 바람직 |
| 봄 건너뜀(로컬 02:30 이 없는 날) | **그날 안 울린다** |

⇒ **봄 건너뜀은 받아들인다.** 대안(가까운 유효 시각으로 밀어 울림)은 **사용자가 예상 못 한
시각에 전화를 받게** 된다 — 그게 더 나쁘다. 1년에 한 번, DST 지역에서만이다.
⛔ **그 사실을 디스패치 주석에 적어라** — 다음 사람이 「버그」로 보고 밀어 울리게 고친다.

## 4. 기존 17행
컬럼 추가 후 전부 NULL → **서울로 동작(지금과 동일)**. ⛔ **백필하지 않는다** —
그들의 실제 시간대를 모른다(추측으로 채우면 엉뚱한 시각에 울린다).
⇒ 앱이 알람을 **수정할 때** 새 `tz` 로 덮인다(요청서 규칙).
⚠ 앱이 수정 없이도 한 번 재전송하게 할지는 **앱 쪽 결정** — 프론트에 알린다.

## 5. 📌 구서버 호환은 확인됐다
`AlarmCreate`·`AlarmUpdate` 가 평범한 `BaseModel` 이고 `domains/alarm` 에 `model_config`·
`extra` 설정이 없다 ⇒ pydantic v2 기본 `extra="ignore"` ⇒ **구서버는 `tz`·`tz_offset_min` 을
422 없이 무시한다.** 요청서의 「먼저 확인」에 대한 답이다 — 앱이 먼저 보내도 안전하다.

# §17 해지 사유 수집

## 0. 확인된 사실
- 사유 enum(flutter `winback_survey.dart:12`):
  **`enum WinbackReason { expensive, unused, missing, otherApp, other }`** — 이 순서
- ⛔ **와이어 코드가 아직 없다.** Dart 이름은 `otherApp`(카멜)인데 요청서는 `other_app` 이다
- 보내는 코드가 없다: `:124` `// TODO(server): submit the reason once an endpoint exists.`
  Send 는 `Navigator.pop(reason)` 만 한다
- 앱의 「어느 만료」 키: `winback_trigger.dart:78`·`:123-124` `winbackMark(status.expiresAt)`
  = `expiresAt` UTC ISO 문자열, ⚠ **null 이면 `'-'`**
- ⭐ **앱 DTO 가 `subscribe_id` 도 이미 파싱한다**(`subscription_status_dto.dart:17`·`:31`·`:42`)
- 붙일 만한 기존 표 **없음**(churn/winback 표 0개. `survey_*` 는 B2B 기관 설문용, 무관)
- ⚠ 컬럼 이름이 `expires_at` 이 아니라 **`end_date`** 다
- 운영 `subscribe` 11행 전부 `is_activate=true` · `end_date` NULL 3행(무기한 — 내가 만든
  `welcome@`·`playstore@` 포함) · 만료된 행 6개/회원 6명(그중 store 3건은 09-28 에 3~5분
  만에 끝나 **샌드박스 테스트로 보인다**)
- `subscribe.member_id` FK = **`ON DELETE SET NULL`**(S2 에서 내가 바꿨다)
- PG 17.6 ⇒ `UNIQUE ... NULLS NOT DISTINCT` 사용 가능

## 1. ⚠ 유니크 키 — 조사자 안 2 를 **한 칸 바꿔서** 채택
조사자 추천: `(member_id, subscribe_id)` + **서버가 `resolve_status` 로 스스로 정한다.**
⭐ 「어느 만료」 = 「어느 구독 행이 끝났나」라는 통찰이 정확하다. 시각 문자열을 키로 믿지
않는 것도 맞다(ISO 정밀도 차이).

⛔ 다만 **서버가 스스로 정하면 구멍이 하나 생긴다**: 회원이 설문에 답하기 **전에 재구독**하면
`resolve_status` 가 `expired` 가 아니어서 **거절하거나 엉뚱한 행을 고른다.** 그런데 그 답은
**직전 만료에 대한 것**이라 버리면 안 된다(윈백이 성공한 경우의 데이터다).

### ⇒ 채택: **앱이 `subscribe_id` 를 보내고 서버가 소유를 검증한다**
- 앱은 이미 그 값을 갖고 있다(`subscription_status_dto.dart:17`) — 새로 만들 게 없다
- 서버는 **그 행이 이 회원 것인지만** 확인한다 ⇒ 위조 불가
- ⇒ 시각 문자열 문제도 없고, 재구독 엣지도 없다
- 유니크 **`(member_id, subscribe_id)`**. ⛔ `NULLS NOT DISTINCT` 는 **필요 없다**(둘 다 NOT NULL)
- 두 번 오면 **`ON CONFLICT DO UPDATE`(마지막 값)** — 재설치 후 다른 답을 고르면 그게 최신 의사다

## 2. 표 — 새 표 `churn_reason`
```
member_id     FK → member  ON DELETE SET NULL   (§3 참조)
subscribe_id  FK → subscribe                    NOT NULL
reason        Text  CHECK (5종)                  NOT NULL
offer_shown   Boolean                            NOT NULL
end_date_snapshot  timestamptz NULL              (그때의 만료 시각 — 참고용)
created_at / updated_at
UNIQUE (member_id, subscribe_id)
```
⛔ **`subscribe` 에 칸을 붙이지 마라.** 조사자 판단이 맞다 — 구독 행은 **결제 상태 기계**이고
`subscription_status` 가 읽는 표다. 설문 값을 섞으면 그 표가 넓어진다.

## 3. ✅ 결정 — 탈퇴 시 `ON DELETE SET NULL`
S2 에서 회원 삭제는 하드 삭제이고 결제 3표만 `SET NULL` 로 보존한다.
해지 사유는 **법적 보존 의무가 없다.** 그런데:
| | |
|---|---|
| CASCADE(같이 지움) | 이탈 분석이 탈퇴마다 사라진다 |
| **SET NULL** ⭐ | `reason`·`offer_shown`·`created_at` 은 남고 **사람과의 연결만 끊긴다** |

⇒ **`SET NULL` 채택.** 개인을 특정할 수 없게 되므로 프라이버시상 CASCADE 와 같고,
집계는 살아남는다. 결제 3표와 **같은 패턴**이라 일관된다.
⚠ `subscribe_id` 도 그 회원 삭제 시 `SET NULL` 이 되므로(S2) `NOT NULL` 이면 삭제가 막힌다
⇒ **`subscribe_id` 도 nullable 로** 둬야 한다. ⛔ 유니크 키가 `(NULL, NULL)` 행을 허용하게
되니 **`NULLS NOT DISTINCT` 를 여기서 쓴다**(탈퇴 회원 행이 여러 개면 하나로 뭉치는 게 맞다).

## 4. ✅ 결정 — `offer_shown` 은 **앱이 보낸다**
조사자 지적이 맞다: 서버는 `reason == 'expensive'` 로 추론할 수 있지만 **오퍼 시트가 실제로
떴는지는 앱만 안다**(할인 이벤트가 없어 안 떴을 수도 있다). ⇒ 앱이 보낸 값을 저장한다.

## 5. ✅ 결정 — 관리자 집계 API 는 **만들지 않는다**
조사자 추천대로. 근거: 설문 대상(만료 회원)이 **6명**이고 그중 3명은 샌드박스로 보인다.
집계는 `SELECT reason, count(*) GROUP BY 1` 한 줄이다. 표에 `reason`·`offer_shown`·
`created_at` 이 있으면 나중에 API 를 붙일 때 **스키마 변경이 없다**(YAGNI).
