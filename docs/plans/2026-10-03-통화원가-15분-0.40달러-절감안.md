## 0. 결론 다섯 줄

1. **재청구는 공식 사실**이다(§1.1). 원가 동인은 통화 길이가 아니라 **턴 수 × 턴당 컨텍스트**.
2. ⭐ **윈도는 포화돼 있다.** 운영값 `trigger 8000 / target 7000`, 지시문 바닥 5,294 ⇒ 대화 여유 **2,206**. 실측 상주 오디오 **2,392** — **여유를 오디오가 전부 채운다.** 그래서 **지시문만 줄이면 그 자리를 4배 비싼 오디오가 채워 원가가 오른다**($0.92 → $1.31, **+43%**). ⛔ 제 앞선 버전의 「지시문 다이어트 단독」 권고는 **틀렸다.**
3. ⭐ **돈으로 줄 세우면 1위는 프롬프트에 재청구되는 대화 오디오다**(50%), 지시문은 2위(28%). 토큰 수로는 지시문이 69%지만 **단가가 4배($3.00 vs $0.75) 다르다.**
4. ⭐ **1위를 깎는 수단은 압축이 아니라 조각 분할이다.** 압축 추가 하향은 금지됐지만 **조각 경계에서 이력이 0으로 리셋되는 것은 금지 대상이 아니고, 메커니즘이 이미 운영 중이다**(끊김 없는 전환 S6 · 실측 조각당 123초 · 서버 강제 전환 `reason="loop"`).
5. **$0.40 은 도달 가능하다 — 조각 75~90초 + 지시문 다이어트 + 비버 발화 45% + VAD 로 $0.39~0.42.** 압축 설정은 손대지 않는다(금지 우회). 조각 60초까지 가면 $0.37.

## 1. 미지수 규명 — 압축이 `in_audio` 를 깎는가

### 1.1 재청구: 공식 명시

`ai.google.dev/gemini-api/docs/live-api/best-practices` §Pricing and billing (2026-09-15):

> "The API charges you **per turn for all tokens present in the session context window**."
> "**Re-billing**: Past tokens are re-processed and accounted for in each new turn, up to your configured context window size."
> "It retains conversational history as **raw audio tokens**… The API bills you for the accumulated native audio tokens at the standard audio input rate **on every turn**."

`ai.google.dev/api/live` §SlidingWindow:
> "operates by **discarding content at the beginning of the context window**. … **System instructions** and any `prefixTurns` **will always remain**."

Google 스태프(discuss.ai.google.dev/t/.../181691):
> "**Caching is not supported on Live API native audio models.** The entire active context (**including instructions and active tools**) is re-billed on every subsequent turn."

⇒ 압축은 축출분의 재청구를 멈추므로 **깎는다**. 단 **지시문은 영구 고정세이고 캐시 할인 경로가 없다**. 교차검증: 60건 전부 `usage_json.sum_cached = None`(벤더가 필드를 한 번도 주지 않음).

### 1.2 `peak_prompt` 역전의 정체 — peak 는 2× 로 찍힌 값이었다

| call | peak_prompt | 턴당 상주 오디오(보고) | `residual` | set_face 수 |
|---|---|---|---|---|
| 1602 | 4,506 | 3,409 | — | — |
| 1631 | 20,050 | 3,004 | 132 | 11 |

peak 가 4.4배 다른데 상주 오디오는 같다. ⇒ **peak 는 순간값, 청구는 적분값**이다. 그리고 `trigger=8000` 인데 peak 가 20,050 인 것은 **3.1 이 blocking 함수콜(`set_face`) 턴을 2회 추론하고 두 요청의 prompt 를 한 usage 에 합산 보고**하기 때문이다(`docs/20260912_1630_3.1-압축-연구.md` §4.1, `docs/ctxlab/20260912_1700_fable-분석1-툴콜-2배-과금.md:34-48`).

**판독 지표 실측** (`residual = sum_resp − out_audio − out_text`, `÷12 = set_face 수`), 표현학습 30건:

| 군 | n | peak | residual | out_text | 해석 |
|---|---|---|---|---|---|
| A | 14 | **18,000~20,800** | 96~277 | **0** | set_face **8~23회** → 2× 보고 섞임. 실제 peak ≈ 9,500 |
| B | 16 | **7,836~7,905** | **0** | >0 | set_face 0회 → 1× 보고. **peak ≈ trigger 8,000 과 일치 ✅** |

⇒ **B군이 운영 압축값을 교차검증한다.** 그리고 A군의 peak 20,000 은 **실제 10,000 의 2배 표기**다.

⚠ **`usage_peak_prompt` 는 원가 예측 지표가 아니다.** 쓸 수 있는 건 `usage_msgs` 와 `usage_in_*/usage_msgs` 다.

### 1.3 환산율은 25 tok/s (32 아님)

Live: "approximately **25 tokens per sec of audio**" (best-practices) / Vertex "Token Conversion Rates: **Audio: 25 tokens/second**". **32 tok/s 는 비(非)Live `generateContent` 값**(`docs/audio`)이다 — 섞으면 28% 틀린다. 교차검증 `$0.005/min ÷ $3/1M = 27.8 tok/s`.

**모델 검증**: 실측 출력 오디오 16.2 tok/s ÷ 25 = **비버 발화비율 65%**.

### 2.2 턴당 컨텍스트 분해 (보고값 → 실제)

보고 상주 텍스트/턴 = **7,097**. 지시문+툴 실측 = **5,294 tok**(지시문 6,434자 + `set_face` 선언 447자, 1.30 자/tok). 압축이 trigger 8,000 에서 바로 자르므로 주입 텍스트는 오래 남지 못한다 ⇒ 차액은 2× 보고분이다.

```
f = (7,097 − 5,294) / 5,294 = 0.34        ← 턴의 약 34% 가 2× 로 보고됨
실제 상주 오디오 = 3,207 / 1.34 = 2,392
실제 턴당 컨텍스트 = 5,294 + 2,392 = 7,686   ← trigger 8,000 바로 밑 ✅
지시문 비중 = 5,294 / 7,686 = 69%
```

⭐ **이 69% 는 독립 수렴이다** — `docs/20260906_1820_재접지-상시발동-원인과-처방.md:57-60` 이 다른 통화·다른 방법으로 "턴당 prompt 10,476 중 바닥 7,194 ⇒ **69% 가 지시문**"을 이미 냈다. 같은 숫자가 두 경로에서 나왔다.

## 3. 원가 모델 (검증됨)

```
원가 = 턴수 × (상주텍스트 × $0.75 + 상주오디오 × $3.00) / 1M     ← 입력, 매 턴 재청구
     + 비버발화초 × 25 × $12.00 / 1M                             ← 출력, 1회
     + 곁가지(사이드카 + 통화후 분석 + 복습 TTS)                    ← 실측 15분환산 $0.02~0.08
```

### 3.1 ⭐ 윈도 포화 — 이 기획의 핵심 메커니즘

```
대화 여유 = (trigger + target)/2 − 지시문바닥 = (8000+7000)/2 − 5294 = 2,206 tok
실측 턴당 상주 오디오(2× 보정)                                     = 2,392 tok
⇒ 포화. 압축이 비운 자리를 오디오가 즉시 다시 채운다.
```

누적률 `r = 25×비버발화비율 + 25×마이크열림비율 = 25×0.65 + 25×0.35 = 25 tok/s`
(마이크가 비버 idle 중 **상시** 열려 있으므로 두 항의 합은 비버 비율과 무관하게 25다.)
⇒ 포화 시간 `2,206 / 25 = 88초`. **5분 통화도 1분 반이면 포화에 든다.**

**따르는 결론 3개:**
1. **지시문만 줄이면 역효과다.** 여유 2,206 → 5,556 이 되고 그 자리를 오디오($3.00/1M)가 채운다. 텍스트($0.75/1M)를 오디오로 바꾸는 거래다. 실측 모델: **$0.915 → $1.311 (+43%)**.
2. **지시문 다이어트는 ①trigger 동반 하향 또는 ②조각 분할과 반드시 세트**여야 한다. 전자는 금지 구간에 닿을 수 있으니(§4.1) **후자가 안전하다.**
3. **조각 길이가 1위 변수다.** 조각 안에서 오디오는 0에서 다시 쌓이므로, 평균 상주 오디오는
   `F ≤ 포화시간` 이면 `r·F/2`, 아니면 `여유 − 여유²/(2·r·F)`.

## 4. 지렛대 비교 — **돈 순서**

⛔ 토큰 수로 줄 세우면 틀린다. **입력 오디오 $3.00/1M vs 입력 텍스트 $0.75/1M — 4배다.**

### 4.0 현재 원가의 돈 비중 (15분 · 68턴 · 1× 세계 · 실측 상주량)

| 항목 | 금액 | 비중 | 무엇이 결정하나 |
|---|---|---|---|
| **`in_audio`** — 프롬프트에 재청구되는 대화 오디오 | **$0.488** | **50%** | **조각 길이** · 윈도 여유 · 누적률 |

### 4.1 지렛대 — 달러 절감 순

기준선 모델값 $0.915(포화 모델). 각 지렛대를 **단독**으로 적용.

| 순위 | 지렛대 | 깎는 항목 | 결과 | **단독 절감** |
|---|---|---|---|---|
| **1** | **조각 60초**(현행 1조각 → 15조각) | `in_audio` | $0.601 | **−$0.314** |
| **2** | **조각 120초** | `in_audio` | $0.772 | **−$0.143** |
| **3** | **비버 발화 65%→45%** | `out_audio` | $0.861 | **−$0.054** |

| 5 | **VAD 무음 미전송** | `in_audio` 누적률 | $0.913 | **−$0.002** ⚠ |
| ⛔ | **지시문 다이어트 단독** | `in_text` ↓ / `in_audio` ↑↑ | **$1.311** | **+$0.396 (역효과)** |
| ⛔ | 압축 추가 하향 | — | 금지(§4.2) | — |
| ⛔ | 상품을 5분×3 | — | 역효과 | +$0.3 |
| ⛔ | `gemini-3.8-live` | — | 폭증 | 공식: proactive audio **영구 켜짐** → "charges for input tokens **the entire time** the Live API is listening" |

⚠⚠ **VAD 가 단독으로는 거의 쓸모없다 — 제 앞선 평가를 정정한다.** 윈도가 포화라 무음을 안 보내도 그 자리를 비버 발화 오디오가 채운다. VAD 가 바꾸는 건 **누적률**(25 → 17.5 tok/s)뿐이고, 포화 상태에서 누적률은 상주량을 바꾸지 않는다. **조각이 짧아져 「포화 전」 구간이 생길 때만 VAD 가 값을 낸다**(조각 60초: VAD 있으면 평균 오디오 525, 없으면 750 — **−$0.046**).
⚠ **`out_audio` $0.175 는 유일하게 못 깎는 바닥이다**(압축·다이어트·조각·VAD 전부 무효). $0.40 목표의 **44%**.
⚠ **지시문 다이어트는 조각 분할의 「승수」다** — 단독으론 역효과지만 조각 60초와 함께 쓰면 상주 오디오가 조각 길이에만 묶이므로 `in_text` 절감($0.172)이 그대로 남는다.

### 4.2 ⛔ 압축 하향은 금지됐다 (그리고 조각 리셋은 금지가 아니다)

`origin/main:core/config.py:197-200`:
> ⛔ 3.1 Live 실측(2026-09-12 ctx-lab): target 은 **턴 단위로 거칠게 양자화**된다 — target 4000 은 매 압축이 «마지막 유저 턴 1개» 착지(쪽지·큐 전부 퇴출), target 5000 도 5분에 1회 전면 퇴출(A→259). **7000/5000·6000/4000 은 사장님 결정으로 금지**(옵션으로도 안 연다). 운영은 8000/7000.

⭐ **금지된 것은 「압축 설정값」이고, 「조각 경계에서 이력이 0 으로 리셋되는 것」은 금지 대상이 아니다.** 둘의 차이:

| | 압축 하향 | 조각 분할 |
|---|---|---|
| 언제 이력이 사라지나 | **통화 중 예고 없이**, 턴 경계에서 뚝 | **조각 경계에서만**, 서버가 아는 시점에 |
| 비버가 받는 승계 | 없음(쪽지·큐까지 퇴출) | **종이**(`system_instruction` 에 박힘) |
| 지연 | 압축마다 증가(공식 경고) | 조각 전환 1회 |
| 상태 | **금지** | **이미 운영 중** |

⇒ **사장님 아이디어 「2턴마다 압축 0」의 올바른 구현은 압축 설정이 아니라 조각 분할이다.** 종이가 그 승계 수단이다.

⚠ 참고로 **「지시문 다이어트 + trigger 동반 하향」은 금지 해석을 다시 열 여지가 있다** — 금지는 **바닥 5,294 에서 측정**됐고(target 5000 이면 대화 여유 ≈ 0), 바닥이 1,944 라면 `trigger 4000/target 3000` 도 대화 여유 1,556 로 **현행 2,206 과 비슷**하다. 모델값 **$0.622**(−32%). 다만 **이것은 제 해석이고 금지는 사장님 지시다** — §7 질문으로 올린다. **조각 경로만으로 목표에 닿으므로 굳이 열 필요는 없다.**

## 5. 사장님 설계안의 구체화 — 「JSON 종이」

> "비버가 아무것도 몰라도 **지금 당장 내가 사용자에게 뭘 물어봐야하는지만** 기억할수있는 종이"

**이 아이디어의 진짜 값은 「압축 리셋」이 아니라 「지시문 69% 를 줄이는 수단」이다.** 압축은 이미 한계고, 바닥만 남았다.

### 5.1 종이는 이미 서버 메모리에 있다

| 맞음 | `expr_quiz_pass: set[int]` | `:988` |

| 다룸/없음 | `covered_nums` / `expr_quizzed` | `:977 / :995` |

### 5.2 종이 스키마 (제안)

```
[종이]  3신규 | 3복습 | 항목당 최대 3회
#1 신규 "밥 먹었어요?"    상태:맞음  횟수:2
#2 신규 "어디 가세요?"    상태:포기  횟수:3
#3 신규 "조금만 주세요"   상태:없음  횟수:0   ← 지금 이것을 물어라
#4 복습 "늦어서 미안해요" 상태:없음  횟수:0
#5 복습 "자리 있나요?"    상태:맞음  횟수:1
#6 복습 "이거 얼마예요?"  상태:없음  횟수:0
```

- 항목 1줄 ≈ 40자 × 6 + 머리글 = **≈300자 ≈ 230 토큰.** 현재 `[오늘의 표현]` 1,191자 + `[진행 절차]` 1,480자 = **2,671자를 대체**한다.
- **"지금 이것을 물어라" 화살표 1개가 핵심.** 절차를 설명하는 대신 **결과를 지목**한다 — 1,480자가 하는 일을 한 줄이 한다.
- 상태 어휘 4개 고정: `없음 / 맞음 / 틀림 / 포기`. 자유 서술 금지(= 드리프트 여지).
- 표면형을 남긴다 — 맥락을 잃어도 **물을 문장 자체는 있어야** 한다.
- ⛔ **종이는 서버가 쓰고 비버는 읽기만 한다.** 서버 퀴즈 상태기계가 큐를 열고 닫는 규약(`locked/expression.py:3`) 유지.
- **항목 수 18 → 6**: 현재 `CUR_ITEMS_PER_CALL=18`(`core/config.py:273`)이라 18줄(893자)이 실린다. 종이는 「3신규+3복습」만 들므로 사장님 설계와 그대로 맞는다.

## 7. 사장님께 — 결정이 필요한 것 **3개**

1. **`set_face`(영상통화 표정)를 끄거나 줄일 수 있습니까?**
   `LIVE_FACE_SPIKE=true` 로 운영 중이고 통화당 **8~23회** 불립니다. 3.1 은 함수콜 턴을 2회 추론해 prompt 를 2× 로 올립니다. **2× 가 실제 청구라면 이것 하나가 $0.26(27%)** 이고, 그러면 조각을 75초까지 줄이지 않고 **180초(5조각)로도 목표에 듭니다** — 설계 난이도가 절반이 됩니다. Max 플랜 상품 가치와의 교환이라 제가 못 정합니다.

2. **비버 발화를 65%→45% 로 줄여도 표현학습이 버팁니까?**
   출력 오디오 $0.175 는 압축·다이어트·조각·VAD **어느 것으로도 1원도 안 깎이는 유일한 바닥**이고 목표 $0.40 의 **44%** 입니다. 예시 2회→1회, 리액션 한 마디로 줄이는 수준입니다.

3. **조각을 「항목 전환 직후 + 60초 경과」로 서버가 끊어도 됩니까? (15분에 9~11회)**
   메커니즘은 이미 있고(S6 끊김 없는 전환, 실측 조각당 123초) 종이가 들어갈 자리도 있습니다(`:3840`). 대가는 **`FRAGMENT_DRAIN_S` 2초 × 10회 = 수업 시간 18~22초 손실**과 예산·동시통화 경합 창이 10배가 되는 것입니다. 시간 고정이 아니라 **항목 경계**에 맞추면 드릴이 중간에 끊기지는 않습니다.

**추가로 승인만 필요한 것 1건 (질문 아님)** — **OpenAI `gpt-realtime-2.1-mini` 4시간 단가 스파이크**(§8). 오디오 전용 cached 단가 **$0.30/1M** 가 공식 가격표에 실재함을 확인했습니다(Gemini Live 는 캐시 자체가 공식 미지원). 적중하면 **비버 발화 축소 하나만으로 $0.41** 이고, 우리가 Gemini 에서 네 개를 다 해야 닿는 선입니다. ⛔ **전면 교체는 반대합니다**(§8.5 — Baba 목소리 변경·16kHz 미지원·엔진 2개 부채). 기존 코드 무변경·`scripts/` 독립 클라이언트로 **적중률 하나만 재고, 80% 미달이면 즉시 기각**합니다.

(부수 확인 2건 — 결정 아님) **①1일분 결제 콘솔 대조**: 2× 세계인지 1× 세계인지. 압축 연구가 남긴 미완 과제이고, 위 1번의 가치를 6배 바꿉니다. **②잠금 프롬프트 수정 권한**: 4단계는 `core/prompts/locked/expression.py` 를 건드려 해시 재기준 + README §8 결정 로그가 필요합니다.

## 8. OpenAI Realtime — **전면 교체가 아니라 「4시간 단가 스파이크」**

### 8.1 ⛔ 먼저 확정해야 했던 전제 — **cached 가 오디오에도 붙는다 (확인 완료)**

`developers.openai.com/api/docs/models/gpt-realtime-2.1-mini` 가격표는 Text / **Audio** / Image 를 각각 `Input` · `Cached input` · `Output` 3행으로 갖는다(**내가 직접 fetch 해 확인**):

| | Text | **Audio** | Image |
|---|---|---|---|
| Input | $0.60 | **$10.00** | $0.80 |
| **Cached input** | $0.06 | **$0.30** | $0.08 |
| Output | $2.40 | **$20.00** | — |

`gpt-realtime-2.1`(full): Text $4/$0.40/$24 · **Audio $32/$0.40/$64** · 128k ctx.
⇒ **오디오 누적 재청구분이 `$10 → $0.30` 으로 33배 할인된다.** Gemini Live 는 공식적으로 **캐시가 없다**("Caching is not supported on Live API native audio models") — **여기가 두 벤더의 구조적 갈림길이다.**

보조 근거: prompt caching 가이드가 "the model's full rendered context including … **conversation history containing text, images, documents, and supported audio**" 를 캐시 대상으로 적는다. ⚠ 단 비용 가이드 본문에는 "오디오가 캐시된다"는 **명시 문장이 없다** — 근거는 **가격표의 오디오 cached 행**과 이 가이드 한 줄이다. ⇒ **실측 1통으로 못 박아야 한다**(§8.4).

### 8.2 환산율·과금 구조 (공식)

| | Gemini Live 3.1 | OpenAI Realtime |
|---|---|---|
| 입력 오디오 환산 | 25 tok/s | **10 tok/s** (1 tok/100ms) |
| 출력 오디오 환산 | 25 tok/s | **20 tok/s** (1 tok/50ms) |
| 누적 재청구 | **있음** | **있음** ("The entire conversation is sent to the model for each Response") |
| 누적분 캐시 할인 | **없음(공식 미지원)** | **있음** ($0.30/1M, best-effort) |
| 컨텍스트 관리 | sliding window 압축 | `truncation`(auto / retention_ratio / disabled) + **전사 있으면 오디오 토큰 자동 폐기** |
| 컨텍스트 한도 | 128k(native audio) | 128k (2.1 계열) |
| **연결 수명** | **~10분** ⇒ 15분 통화에 **재연결/조각 필수** | **60분** ⇒ 15분 통화에 곡예 불필요 |

⭐ **연결 수명이 숨은 승부처다.** 우리가 15분 상품에서 조각·재연결·백스톱으로 싸우는 이유의 절반이 Gemini 의 ~10분 연결 선점이다. OpenAI 는 그 문제가 없다.

### 8.3 산술 (15분 · 68턴 · 캐시 적중 전제)

| 안 | out_audio | in_audio fresh | in_audio **cached** | text | 곁가지 | **합** |
|---|---|---|---|---|---|---|
| **mini · 현행 그대로**(지시문 5,294 · 비버 65% · 조각 0 · VAD 0) | 0.234 | 0.032 | 0.152 | 0.025 | 0.04 | **$0.48** |
| **mini · 비버 45% 만** | 0.162 | 0.050 | 0.133 | 0.025 | 0.04 | **$0.41** |
| mini · 비버 45% + VAD | 0.162 | 0.023 | 0.106 | 0.025 | 0.04 | **$0.36** |
| ⛔ **full · 비버 45%** | **0.518** | 0.072 | 0.177 | 0.030 | 0.04 | **$0.84** |

⇒ **`full` 은 출력 오디오 하나($0.518)로 목표를 깨뜨린다.** 후보는 **mini 뿐이다.**
⇒ **mini 는 「비버 발화 축소」 한 가지만으로 $0.41** — Gemini 쪽에서 조각 75초 + 다이어트 + 발화축소 + VAD **네 개를 다 해야 닿는 $0.395** 와 같은 자리다.

⚠⚠ **그러나 캐시가 안 붙으면 재앙이다**: 적중률 0% 면 누적 오디오가 정가 $10/1M 로 청구돼 **$4.6**(현재 Gemini 의 4.7배). 그리고 공식 문서가 "**best-effort and not guaranteed**" 라고 못박았고, "**Truncation busts the cache … if truncation occurs on every turn then cache rate will be very low**" 라 **긴 통화에서 truncation 이 매 턴 돌면 캐시가 무력화된다**. ⇒ **적중률 하나에 10배가 걸려 있다.**

### 8.4 스파이크 설계 (4시간, 구현 아님 — 측정만)

**목표: 숫자 3개만 들고 나온다.**
1. **오디오 캐시 적중률** — `response.done` → `usage.input_token_details.cached_tokens_details` 를 5분 통화 전 구간 로깅.
2. **전사로 인한 오디오 토큰 폐기량** — "The GA service will automatically drop some audio tokens when a transcript is available" 의 실제 효과(문서에 정량 규칙 없음).
3. **턴당 누적 입력 실측** — Gemini 와 같은 축으로 비교.

**범위**: 기존 코드 **무변경**. `scripts/` 에 독립 WS 클라이언트 1개(`scripts/spike_openai_realtime.py`)를 두고, `gpt-realtime-2.1-mini` 에 5분 드릴 1통을 돌려 usage 를 파일로 떨어뜨린다. `core/`·`domains/` 는 **한 줄도 건드리지 않는다.**
**합격선**: 오디오 캐시 적중률 **≥ 80%** 이고 5분 통화 환산 원가 ≤ $0.15. 미달이면 **즉시 기각**하고 Gemini 경로(§6)로 돌아간다.

### 8.5 교체 비용 — **전면 교체에 반대하는 근거**

| 항목 | 상태 |
|---|---|
| **16kHz 입력** | ⚠ Realtime API 세션 오디오 포맷 enum 은 `audio/pcm rate 24000` 만 열거. 우리는 PCM16/**16k** 입력(`core/audio.py:18,20,21`) ⇒ **서버 업샘플 필요**(클라 변경은 불필요) |
| **음색** | ⛔ **Baba 목소리가 바뀐다.** `character.voice_id` 가 Gemini 음색이고 OpenAI 는 10종(`marin`/`cedar` 권장) + 커스텀. **제품 결정이지 기술 결정이 아니다.** 세션 중 오디오가 한 번 나오면 음색 변경 불가 |
| **2펌프·턴 상태기계** | `call_session.py` 의 턴 열림/닫힘·barge-in off·무음 3단 넛지·GoAway·세션재개가 **전부 Gemini 이벤트 스키마에 묶여 있다**(R4 불변식 영역) |
| **`set_face` 툴콜** | function_calling 은 있음. ⚠ 그러나 **「툴콜 턴 2× 과금」이 OpenAI 에도 있는지는 미확인** |
| **입력 전사** | 있음(`gpt-live-transcribe` 등). 우리 covered/퀴즈 판정·무음 넛지가 전사 의존이라 **필수 요건 충족** |
| **세션 재개** | 문서에 없음(확인 불가). 드롭 시 히스토리 재주입이 필요하고 **그 재주입이 캐시를 처음부터 다시 쌓는다** |
| **엔진 2개 떠안기** | ⛔ **전례가 있다** — 캐스케이드 엔진을 C14(`70e20e2`, 2026-09-23)에서 **지웠다**. 과거 통화 70여 건이 `usage_engine='cascade:*'` 로 남아 원가 계산이 `0 + «미상»` 폴백이 됐다. 엔진을 또 둘로 늘리면 같은 부채를 다시 진다 |

⇒ **권고: 전면 교체 금지. §8.4 스파이크로 「오디오 캐시 적중률」 하나만 측정한다.** 합격이면 그때 「엔진 추상화 vs 전면 이관」을 별도 기획으로 올린다. 불합격이면 4시간에 끝난다.

⚠ **참고로 과금 모델이 하나 더 있다**: `gpt-live-1` 이 **$0.05/분(초당 과금)** + 백엔드 모델 토큰 별도다. 15분 음성 = $0.75 + 백엔드 ⇒ **목표 초과**. 토큰 누적 리스크가 없는 대신 음성 레이어가 비싸다. 우리 옛 캐스케이드와 성격이 같아 **후보에서 뺀다.**
