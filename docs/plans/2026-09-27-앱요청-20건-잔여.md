## 0. ⛔ 먼저 — DB 확인으로 **요청 2건이 무효**가 됐다

요청서가 「DB 확인 필요」로 남긴 3건을 조회했다. 결과가 설계를 바꾼다.

### §4 「네 지표 평균 대상 통일」 — **고칠 게 없다**
```
evaluation 총 2,956행 · 네 칸 전부 있음 86 · 일부만 있음 0 · 전부 NULL 2,870
```
⇒ **일부만 찬 행이 0건**이다. 지표별로 따로 평균해도 **대상 집합이 같다**.
「게이지 총점과 세부 점수가 서로 다른 행 집합의 평균」이라는 증상은 **일어날 수 없다**.
⛔ **§4 는 닫는다.** 코드를 바꾸면 동작은 같고 위험만 생긴다.

> ⚠ 대신 훨씬 큰 사실이 나왔다 — **2,956건 중 채점된 건 86건(2.9%)뿐**이다.
> 나머지 2,870건은 네 칸이 전부 NULL 이다. 그게 §2(0점 대신 null)가 실제로 다루는 규모다.
> 지금은 그 2,870건이 앱에 **0점으로** 나가고 있다.

### §16 「`is_activate IS NULL` 행」 — **0건이다**
```
is_activate IS NULL 행: 0 · 그런 회원: 0
```
⇒ (필수)로 올린 두 항목 중 하나가 **대상이 없다**. `resolve_status` 에 방어를 넣는 건
값어치가 있지만 **지금 새는 회원은 없다**. 앱이 이미 선반영한 우회
(`winback_trigger.dart` `shouldOfferWinback`)로 현상은 막혀 있다.
⇒ **우선순위를 낮춘다**(코드 방어는 §16-A 로 남긴다, 데이터 정리는 불필요).

### §12 「연속일」 — ⛔ **요청서가 지목한 원인이 틀렸다**
요청: 「`calendar_calls` 의 status 조건을 `done` 하나로(분석 완료만)」

```
call.status 전체 분포:  done 1,601 · failed 13 · ongoing 1
```
⇒ **`analyzing` 상태 행이 DB 에 0건이다.** status 조건을 좁혀도 **아무것도 바뀌지 않는다.**

QA 가 본 「통화 2건인데 연속일 0」의 진짜 원인은 이것이다 — 09-26 member 30 통화:
| call | 길이 | status | `spoke` |
|---|---|---|---|
| 1697 | 10초 | done | **False** |
| 1698 | **82초** | done | **False** |
| 1701 | 59초 | done | True |
| 1703 | 74초 | done | True |

`_spoke_exists()`(`call_repository.py:17-29`)가 **`call_raw_data.role='user' AND content
IS NOT NULL AND content <> ''`** 를 본다. 1698 은 **82초짜리인데 user 전사가 비어 있다.**

⭐ 이건 2026-09-24 에 찾은 사실과 같은 현상이다 — 운영에 **user 전사가 전량 빈 통화가
398건**(평균 17초)이고, 그 통화들은 달력·하루한도에서 「말한 통화」로 세지지 않는다.
`docs/plans/2026-09-26-play심사-서버4건.md` §6 에 함정으로 적어 뒀다.

⇒ **§12 의 실제 과제는 「`_spoke_exists` 를 전사 내용 의존에서 떼어내는 것」이다.**
자세한 설계는 아래 §3.

## 2. 1순위 — 채점 계약(2·3) + `ios_fcm`(1)

### §1 `ios_fcm` 허용 (가장 작다)
`domains/push/schemas/device.py:12` `platform: Literal["android_fcm", "ios_voip"]` 에
**`"ios_fcm"` 추가**. ⛔ 착신 디스패치 대상은 **`ios_voip` 만** 유지한다 —
일반 알림 토큰으로 착신을 보내면 안 된다.
⭐ B2B 가 이미 `PUSHABLE_PLATFORMS = {android_fcm, ios_fcm}` 로 이 행을 기다린다.
시험: `ios_fcm` 등록이 201, 착신 선별에는 안 들어감.

### §2 점수 없음을 `null` 로
- `core/speechsuper.py:258` `_to_int(value, default=0)` → **기본값 `None`**
- `review_service.py:160-161` evaluation 부재 시 네 칸 0 → **`null`**
- `PronScoreOut` 네 칸 · `SoundResultOut.after` → `Optional[int]`

⛔ **키를 빼지 말고 `null` 로 보내라.** 이 저장소의 「키 생략」 규약(진행규칙 5)은
「그 속성이 이 행과 무관하다」는 뜻이고, 여기는 **「채점을 못 했다」는 사실 자체를 앱에
알려야** 한다. Q9(발음 리포트 `score`)에서 같은 판단을 이미 했다 — **그 선례를 따르라.**

⭐ 앱은 **이미 선반영**했다(`979093c` — null → 「-%」·「채점하지 못했어요」).

### §3 스텁 점수 구분
`core/speechsuper.py:89-120` 이 키 없음·로드 실패·**어떤 예외든** `_stub_assess` 로
떨어진다. 스텁은 `60 + ord % 41` 의 결정적 점수(60~100)라 **대부분 통과**로 찍힌다.

요청서가 둘 중 하나를 택하라 했다:
| 안 | 내용 |
|---|---|
| **(가)** ⭐ | 응답에 `is_stub: true` 를 싣고 **복습 기록·평균에 저장하지 않는다** |
| (나) | 운영 경로에서 스텁 폴백 대신 **503** |

⭐ **(가) 채택.** 근거: `iap_receipt.is_stub` 이 **같은 문제를 이미 그렇게 풀었다**
(「스텁 검증(실검증 아님) — 운영 집계 제외」). 같은 저장소에서 같은 문제에 두 가지
해법을 두지 않는다. 그리고 (나)는 키가 없는 개발 환경에서 QA 를 통째로 막는다.
⛔ 다만 **「저장하지 않는다」를 시험으로 못박아라** — 스텁 점수가 평균에 섞이면
학습자에게 가짜 실력이 보인다.

## 3. 2순위 — 연속일(§12) · 레벨 초기화(§9)

### §12 — `_spoke_exists` 를 전사 의존에서 뗀다
⛔ **요청서의 「status 를 done 으로」는 아무 효과가 없다**(§0). 진짜 설계는 이것이다.

```
지금:  「말한 통화인가」 = call_raw_data 에 내용 있는 user 행이 있나  (파생·불안정)
바꿈:  통화 종료 시점에 call 에 불변 플래그를 한 번 기록            (원본·안정)
```

- `call` 에 `was_spoken: bool`(또는 `spoke_at`) 추가 · 통화 종료(finalize) 때 확정
- `_spoke_exists()` 가 그 플래그를 본다
- ⛔ **기존 1,601행 백필이 필요하다** — 지금 기준(`content` 유무)으로 한 번 채운다.
  백필 없이 플래그를 보면 **모든 과거 통화가 「말 안 함」이 되어 달력이 통째로 빈다**
- ⚠ 이 함수는 **달력(`:275`)과 하루 한도·이어하기 판정(`has_call_in_window`, `:113`)이
  같이 쓴다.** 한쪽만 생각하고 바꾸면 예산 판정이 틀어진다
- ⛔ 마이그레이션 + 백필 + 두 소비처 → **「마이그레이션 적용 → 푸시」** 순서 필수

📌 부수 효과: 이 플래그가 생기면 나중에 「음성·전사 90일 파기」(폐기된 S4)를 되살릴 때
**선행조건이 이미 충족된다**. 그때 막혔던 지점이 정확히 이것이었다.

### §9 레벨 초기화를 통화 성립 뒤로
`mastery_service.py:819` 가 retake 요청 **즉시** `member_language_level` 행을 지운다.
통화가 성립하지 않으면(연결 중 취소 · `ALREADY_IN_CALL`) **레벨만 사라진 채 남는다.**

- `member_language_level` 에 **`retest_requested_at`** 추가 — retake 는 이 값만 찍는다
- 라우팅(D11)이 「레벨 미확정 **또는** 재측정 대기」를 `level_test` 로 본다
- 실제 삭제는 **레벨테스트 통화가 성립한 뒤**(`call_started` 전송 시점)
- ⛔ 통화가 안 되면 **기존 레벨이 그대로** 남는다

⚠ **L2 와 부딪치는지 확인하라** — 재측정으로 레벨이 바뀌면 진도를 그 레벨 첫 차시로
옮기는 로직이 있다(`normalcall_service._move_progress_to_new_level`). 삭제 시점이
바뀌면 그 호출 시점도 봐야 한다.
⚠ 「재측정 대기 취소 경로」는 **만들지 않는다**(앱에 버튼이 없다 · YAGNI). 필요해지면 그때.

## 4. 3·4순위 — 개요만 (착수 전 다시 상세화)

### §11 Free 분석 깊이 잠금 (출시 게이트)
`GET /calls/{id}/result` 에 `analysis_depth: "full" | "score_only" | "locked"`.
⛔ **잠긴 필드는 서버가 비워 보낸다** — 앱이 가리기만 하면 우회된다.
⚠ 「누적 3회」의 **회 정의**(통화 단위 vs 열람 단위)를 먼저 확정해야 한다 — 기획 확인 필요.
tz 는 `daily-status` 와 **같은 값**을 쓴다(어긋나면 「앱은 된다는데 서버는 거절」).

### §5 알람 시간대
`AlarmCreate`·`AlarmUpdate` 에 `tz`·`tz_offset_min` 추가 · 알람 행에 저장 ·
`dispatch_service.py:29` 의 `APP_TZ = Asia/Seoul` 고정을 알람별 시간대로.
우선순위는 다른 API 와 같게 **tz → tz_offset_min → Asia/Seoul**(기존 알람 호환).

### §16-A · §17
- `resolve_status` 에서 **NULL 만 있는 회원 → `free`**(대상 0건이지만 방어)
- `POST /members/me/churn-reasons` — 사유 코드 5종 · `expires_at` · `offer_shown` ·
  같은 회원·같은 만료는 **덮어쓰기**

### §6 · §10 · §13 — 다국어 3건을 **한 덩이로**
셋 다 「회원 `member.language` 로 서버가 골라 준다」는 같은 문제다:
| | 대상 |
|---|---|
| §6 | 차시 제목 `situation` |
| §10 | 통화 제목 `summary`(LLM 생성물) |
| §13 | 캐릭터 태그·설명·스토리 |

⭐ **취약 발음 번역(`sound_lesson_i18n`)이 이미 그 패턴의 선례다** — 별 표에 언어별 행을
두고 읽는 시점에 고른다. 같은 구조를 쓴다.
⛔ **§10 은 성격이 다르다** — `summary` 는 LLM 이 통화마다 새로 만드는 값이라 미리 번역표를
둘 수 없다. 요청서의 안 A(`summary_lang` 저장 + 조회 시 번역·캐시)가 맞다.
⚠ 번역 비용이 생긴다 — 통화마다 언어를 바꾼 회원 수만큼. **캐시가 필수**다.
