# 전사 중복 저장 — 원인·정리·재발 방지 (2026-09-18~19)

## 무슨 일이 있었나
사장님 통화 1644(ko·3.1·2조각)에서 `call_raw_data` 가 **75행인데 고유 turn_index 는 65개**였다 — turn 45~54 열 개가 두 벌.
판정·진도에는 영향이 없었지만 통화 기록·통화후 분석·이어하기 발췌가 겹친다.

## 원인 (코드 행)
`domains/learning/realtime/call_session.py` `_periodic_flush` 가 커서 `state.persisted_count` 를 **저장이 끝난 뒤에** 올렸다.
`svc.run_db` 는 `run_in_threadpool`(`normalcall_service.py`) 이라 **await 가 취소돼도 그 스레드의 commit 은 끝난다** ⇒
`fragment_end` 로 TaskGroup 이 내려가는 순간 «썼는데 안 썼다» 가 되고, `finally` 의 `_persist_remaining` 이 같은 구간을 다시 썼다.
조각 경계가 아니라 **조각 내부**에 중복이 생기는 이유가 이것이다(1644 의 45~54 = 조각1 마지막 flush 구간).
⚠ 새로 생긴 결함이 아니다 — 운영 DB 전수 조회에서 **통화 39건 · 잉여 400행**이 나왔다(가장 이른 것이 call_id=18).

## 고침
- 12차 A(2026-09-18): 커서를 **쓰기 전에** 올린다(되돌리는 건 진짜 실패뿐 — 취소는 되돌리지 않는다) ·
  `save_segments` 를 `(call_id, turn_index)` **멱등**으로 · `next_turn_index` 를 **max(turn_index)+1** 로(옛 코드는 행 수를 셌다).
- 13차 A(2026-09-19): **옛 중복 400행 삭제 완료** — bt-back 이 `scripts/dev_dedupe_raw_data.py --all --apply` 로 지웠다
  (각 `(call_id, turn_index)` 의 **가장 이른 행**만 남긴다 — 그 행이 점진 flush 가 쓴 것이라 `voice_url` 을 갖는다).
  1644 는 75→65행, 남은 중복 통화 0.
- 13차 B(2026-09-19): `(call_id, turn_index)` **유니크 제약**(`uq_call_raw_data_call_turn`) — 모델 + Alembic 리비전 `d4e5f6a7b8c9`.
  코드 멱등(사전 조회)은 그대로 두고, 경합으로 제약에 걸리면 **그 행만 SAVEPOINT 로 되돌려 건너뛴다**(R5 — 저장 전체를 죽이지 않는다).
  ⛔ 운영 적용은 사장님 «적용» 뒤 bt-back 이 한다 — 워크트리에서 `alembic upgrade` 를 돌리지 않는다.
