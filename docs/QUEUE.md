옮긴다 — 표현학습에서는 그 칸이 빈다. 퀴즈 결과로 대체한다(기획 §5).

### 정리할 때 순서
1. 새 모델이 실사용으로 자리 잡았는지 확인(표현학습 통화 N건 · 레벨업 1건 이상)
2. `normal` 통화를 남길지 폐기할지 결정 — 남기면 사슬도 남는다
3. 그 뒤에 컬럼·테이블 정리(Alembic, 파괴적이라 prod 백업 필요)

## Q24. 일일 한도를 «통화 횟수» 에서 «시간 예산» 으로 바꾼다 (2026-09-10 사장님 설계)

⛔ **지금 당장은 아니다.** `ENV='test'` 라 한도가 아예 안 돈다(`call_service.py:342`
`if not (settings.DAILY_LIMIT_ENFORCED or settings.ENV == "prod"): return False`).
켜는 날 이 설계로 간다.

### 사장님 설계
```
Free 5분 / Pro 15분 / Max 15분      ← 코스 둘이 예산을 **공유**한다
                                      (표현학습이든 프리토킹이든 쓰면 깎인다)
5분마다 재연결은 그대로

Free 가 2분 쓰고 끊으면 → 다음 통화는 화면이 2:00 부터 시작 (남은 3분)
⛔ 맥락은 안 이어진다 — 대화는 처음부터 새로
⭐ 진도는 이어진다 — quiz_passed_at·drilled_at 이 DB(회원×항목 행)라 자동
```
그리고 `normal` 통화는 없앨 예정이므로 한도 표에서도 빠진다.

### ⭐ 이 설계가 이번 구조와 맞는 이유
«맥락은 끊고 진도는 잇는다» 가 핵심인데, 진도를 DB 행에 두기로 이미 정했다
(기획 §2-3). ⇒ 새 통화든 조각이든 **진도는 저절로 이어진다.** 추가 작업이 없다.

⚠ 다만 «조각» 과 «새 통화» 가 **다른 축**이 된다:
```
조각(fragment)   맥락 이어짐 · 같은 call_id · 5분 경계에서 자동
새 통화          맥락 끊김   · 새 call_id  · 끊고 다시 걸기
```

### 착수 전에 확인할 것
1. **`total_time` 이 갑자기 끊었을 때도 기록되나.** `finalize_call`(normalcall_service.py:1090)
   이 총 시간을 쓰는데, 클라가 소켓을 죽이거나 앱이 크래시한 경로에서도 불리는지 확인해야
   한다. ⛔ 안 불리면 «2분 썼는데 0분으로 기록» 되어 예산이 안 깎인다 — 무제한과 같다.
2. **집계 단위.** `sum(total_time)` 을 당일 창(클라 로컬 자정, `daily_window_utc`)으로 묶는다.
   ⚠ `has_call_in_window` 는 EXISTS 라 «횟수» 용이다 — 합계 쿼리를 따로 만들어야 한다.
3. **남은 시간이 5분보다 짧으면.** Free 가 3분 남았을 때 조각을 3분으로 열지, 5분으로 열고
   3분에 끊을지. ⚠ 시계(`CALL_DURATION_S`)가 조각 길이를 소유하므로 그 값을 통화별로
   받게 해야 한다.
4. **클라 표시.** «화면이 2:00 부터 시작» 은 클라가 **당일 누적 사용량**을 알아야 한다
   ⇒ `GET /calls/daily-status` 에 남은 초를 실어 내리는 계약 추가(프론트 변경 동반).
5. **한도 UI.** 지금은 «오늘 통화했다/안 했다» 불린인데 «남은 시간» 으로 바뀐다.

### ⚠ 그동안의 안전한 임시 상태
`DAILY_CALL_LIMIT` 에 `expression: 1 · freetalk: 1` 을 **넣어 둔다.**
⛔ 빼면 안 된다 — `call_service.py:352` 가 «정의되지 않은 콜타입은 막지 않는다» 로 떨어져
**무제한**이 된다. Live 는 통화당 원가가 나가므로 «무제한» 이 «값 미확정» 보다 위험하다.
`tests/test_daily_call_limit.py::test_limits_are_one_each` 가 그 누락을 막는다.
