# 5. 서버가 한 일 — 요약

### S5 — dev 라우트를 `ENV` 와 분리
⛔ 요청서는 「운영 `ENV=prod` 전환」을 요청했는데 **그렇게 하지 않았습니다.**
`ENV` 하나가 세 축을 움직여, 바꾸면 `DAILY_LIMIT_ENFORCED` 게이트가 같이 켜지고
**플랜이 없는 사장님 계정이 하루 1통화에서 잠깁니다**(`config.py:41-44` 가 경고).
⇒ `DEV_ROUTES_ENABLED` 축을 따로 뺐습니다. 기본 False = **env 를 안 넣으면 닫힘.**

실측 근거(운영에 직접 요청): `POST /__dev/signup` → **400**(404 가 아니라 살아 있었음).
그 라우트는 service key 로 Supabase 계정을 만들고(`email_confirm=True`) **토큰까지** 줍니다.

### S3 — 탈퇴자 푸시
발송 선별 SELECT **한 곳**에 `Member.deleted_at IS NULL` 을 넣었습니다(호출부가 1개).
⭐ 운영 실측: 탈퇴 회원 1명이 알람 2개를 갖고 있었고 **그중 1개가 `is_activate=True`**
였습니다 — 「탈퇴자에게 전화가 온다」가 가설이 아니라 사실이었습니다. 정리했습니다(백업 보관).

### S2 — 하드 삭제
`DELETE FROM member` 하나로 끝납니다(FK 가 전부 CASCADE). 결제 3표만 **`SET NULL`** 로
바꿔 보존합니다. ⭐ 사장님 안(「FK `member_id` 칸 비우면 안 되나?」)이 아카이브 테이블보다
나았습니다 — 복사 로직이 없어 **반쪽 상태가 구조적으로 불가능**해졌습니다.
선행으로 `delete_auth_user` 를 **멱등화**했습니다(「이미 없음(404)」을 성공으로 접음) —
전엔 중간에 죽으면 재시도로 고칠 수 없었습니다.

### S1 — 영수증 검증
「**검증 → 지급 → acknowledge**」 순서를 코드와 시험으로 못박았습니다. 지급 전에
acknowledge 하면 지급이 실패해도 환불 창구가 닫힙니다. acknowledge 실패는 지급을
되돌리지 않습니다(구글이 3일 여유를 줍니다).
⭐ 이미 있던 것을 다시 만들지 않았습니다 — `subscribe` 5칸 · `IapReceipt`
`UNIQUE(platform, transaction_id)`(중복 지급 방지). **마이그레이션 없습니다.**
