# 통화 끊김·응답지연 원인 규명 — 하루 종합 (2026-08-13)

⛔ **먼저 읽을 것**: 「핑 곡선」 수사는 **종결**됐다. 미해결 숙제가 아니다. §3 을 보고 다시 파지 마라.

## 0. 한 줄

사장님이 듣는 **끊김은 전부 서버가 만든다.** 클라는 그것을 그대로 겪을 뿐이고,
클라/서버 로그가 **밀리초까지 일치**한다.

## 1. 확정된 사실 (전부 실측)

### 1-1. 발화 중 끊김 = 서버 와이어공백. 1:1 일치
```
클라 관측   735ms · 1356ms · 1221ms · 1246ms
서버 기록   0.73s · 1.36s  · 1.22s  · 1.24s     (call 970 b2)
```
⇒ **클라 무죄.** 처방은 전부 서버에 있다.

### 1-2. 끊김은 **두 종류**다 (한 덩이로 세면 안 된다)
| | 크기 | 정체 | 몫 |
|---|---|---|---|
| A. 턴 시작 지연 | 919~1040ms | 서버 첫 묶음이 늦음 + 클라 쿠션(450~900ms) | 서버+클라 |
| B. 발화 중 공백 | 730~1360ms | 묶음 사이 와이어공백 | **전부 서버** |

⚠ A 는 **매 턴** 걸린다(초반 한정 아님). 8/13 통화는 턴이 양끝뿐이라 양끝처럼 보였을 뿐이다.
⛔ A 의 클라 쿠션을 먼저 낮추지 마라 — 쿠션은 **굶어서** 자란 결과다. 서버부터 고친다.

### 1-3. ⛔ 선행합성이 먹었다는 증거는 **없다**(내가 틀렸다, 2026-08-13 정정)

처음에 나는 이렇게 읽었다 — ⛔ **틀렸다**:
```
전  묶음공백  [2.44s, 0.49s]
후  와이어공백 [0.73s, 1.36s, 1.22s, 1.24s]
"2.44 → 1.40 으로 줄었다"
```

**두 숫자는 다른 자로 잰 값이다.** 같은 커밋(82416be)에서 지표를 바꿨다:
- `묶음공백` = 앞 묶음을 다 보낸 뒤 **다음 묶음을 기다린 시간**(배치 경계)
- `와이어공백` = **프레임과 프레임 사이**가 빈 시간(송출 지점)

⇒ 2.44 시절에도 와이어는 이미 조용했을 수 있다. **두 값의 차를 개선폭으로 읽지 마라.**

🔴 그리고 더 큰 것 — **선행합성이 아예 안 돌고 있을 가능성이 높다**(코드 근거):
- `_flush_batch` 는 `pending 글자수 >= _batch_chars()` 일 때만 중간에 터진다
- gemini-tts 의 그 값은 **400자**(`CASCADE_TTS_BATCH_CHARS_GEMINI`)
- 그런데 대답은 3문장 = **실측 평균 82~90자**(길어야 250자)

⇒ **400 에 영원히 못 닿는다** ⇒ 중간 flush 가 한 번도 안 일어난다 ⇒ **대답 하나 = 묶음 하나**
⇒ `_send_chain` 의 `prev` 가 항상 None ⇒ **묶음 선행합성이 도는 자리가 없다.**

⚠ `선행폐기=-` 를 나는 "버린 게 없다 = 공짜로 먹었다"로 읽었는데, **"안 돌았다"** 가 더
그럴듯하다. 같은 관측을 두 가지로 읽을 수 있으면 **더 값싼 설명을 먼저 의심해야 했다.**

⇒ 그러면 남은 1.2~1.4초는 **묶음 사이가 아니라 묶음 안, 언어 구간 사이**다.
한국어 구간은 짧고(실측 5자 ≈ 0.4~0.5초) gemini TTFB 는 0.8~1.27초 ⇒ **차액이 그대로 공백**.

**판정 방법(배포 후 첫 질문)**: 새 로그의 `선행여유=` 가 값을 갖는가, `-` 인가.
`-` 면 선행합성은 안 돌고 있었던 것이고, 다음 칸은 `prefetch_depth` 가 아니라 **묶음 임계**다.
⚠ demo-api env 가 `CASCADE_TTS_BATCH_CHARS_GEMINI` 를 덮었으면 위 결론이 바뀐다 — 새 로그가 답한다.

### 1-4. 응답시간 분해 (서버 실측)
```
침묵대기 800ms  +  STT확정 ~190ms  +  첫소리 2300~2700ms  +  클라 쿠션 300~1200ms
첫소리 = LLM첫조각 1066~2079 + 문장완성 65~386 + TTS벤더 932~1143 + 송출 179~375
```
· LLM: `thinking_budget=0` 이미 바닥, 서울 리전 적용됨(1455→937ms). **벤더 옵션 없음.**
· prefill 실측: system_instruction 3,897자 ≈ 1,300~1,750토큰 = 턴당 3,100토큰의 **절반**.
  ⇒ 이력 상한 40,000자는 **범인이 아니다.** 남은 칸은 모델 교체뿐.
· 침묵대기 800ms 는 지금 **통째로** 붙는다(OpenAI 전사에 offset 이 없어 뺄셈이 안 돈다).

### 1-5. 서버 지연은 통화 내내 평평하다
통화 8건·턴 167개, 전반↔후반 중앙값 차 **최대 196ms**, 2건은 오히려 하락.
⚠ 단 서버는 **자기가 늦었는지 알 계기가 없다**(클라 재생 완료 회신을 안 받는다).
"서버 무죄"가 아니라 **"서버는 자기 시계만 본다"** 로 읽어라.

## 2. 이름 정정 — 「6분 곡선」은 없었다

무료 플랜 통화 상한이 **300초**다(`call_service.py:73-78`). 8/13 관측 통화 길이는
308~342초 = **전부 상한에 부딪힌 것**이다. 실기기 최대 관측도 246초 지점이었다.
⇒ **우리는 6분을 한 번도 측정한 적이 없다.** 전부 5분 관측이다.
탈출구: `NORMAL_CALL_DURATION_S=900`(config.py:123, dev/demo 전용).

## 3. ⛔ 핑 곡선 — 종결. 다시 파지 마라

**원인 확정**: AudioRecord 가 **열려 있다는 사실 자체**. 6판 표(전부 310~315초, 같은 조건):

| 판 | 레코더 | 업링크 | 핑 |
|---|---|---|---|
| MIC_OFF | 안 엶 | 없음 | **310초 내내 0ms** |
| MIC_TO_FILE | 열림 | 0바이트 | 12 → 511ms |
| 1단계 ×2 | 열림 | 정상 | 4~5 → 441~510ms |
| 2단계(아바타 ON) ×2 | 열림 | 정상 | 3~5 → 370~436ms |
| VOICE_AUDIO=false | 열림 | 게이팅 | 5 → 413ms |

**배제 목록**: 업링크 소켓 · Dart 프레임 수신 · 오디오 소스 종류(VoIP/일반) ·
아바타 영상 · 힌트 · AEC · 쿠션 · 서버.

⇒ **제거 불가**(통화 앱이 마이크를 안 열 수는 없다).
⇒ **그리고 어떤 사용자 증상과도 연결되지 않았다**:
  · MIC_OFF 는 핑 0ms 인데 구멍이 오늘 최악(2.2초)
  · 발화 중 공백은 서버와 밀리초 일치
  · 핑은 0→500ms 자랐는데 **구멍 크기는 초반·후반이 같다**(919 vs 640~1040ms)
⇒ 「곡선이 있어도 안 밀리게 한다」류 수술도 **지금 할 일이 아니다** — 밀린다는 증거가 없다.
⭐ 나중에 **어떤 증상이 곡선과 붙으면** 그때 되살려라.

## 4. 오늘 죽은 가설 (되살리려면 새 증거가 필요하다)

| 가설 | 무엇이 죽였나 |
|---|---|
| LDPlayer 가상 마이크 2배 | HAL 직접계측 1.002배 · MIC 계량기 31.2KB/s(기준 31.3) |
| 프레임당 채널 메시지 14,200건이 기제 | MIC_TO_FILE 은 Dart 수신 **0건**인데 곡선 동일 |
| 재생 플러그인 TaskQueue 한 줄 | 위와 같은 근거(채널 적체)가 죽어서 근거 소멸 |
| 클라가 sampleRate 를 틀리게 선언 | 정규통화 클라는 그 키를 **안 보낸다**(발음챌린지 전용) |
| 초반 굶주림은 통화 초반 한정 | **매 턴** 시작에 걸린다 |
| 아바타 영상(ExoPlayer) | OFF 로 두 판 연속 우상향 · ON 이어도 같은 띠 |

⚠ **미해명 1건**: 8/12 call 962·964 의 서버 `stt_audio_s/dur_s` = 1.94~2.00배.
8/13 재현 안 됨. "없었다"가 아니라 **"오늘 조건에서 재현되지 않는다"** 까지만 기록한다.

## 5. 계측이 거짓말한 자리 (같은 함정을 세 번 밟았다)

1. `fed/elapsed` — 조용한 통화에선 **의미 없다**(비버가 말을 안 하니 당연히 낮다).
   교차확인: `engine min` 이 안 말랐으면 그 값으로 「이상」 판정을 내지 마라.
2. `와이어공백` — **유휴 시간을 공백으로 센다**(조용한 판에서 293초가 찍힌다).
3. `발화중구멍` — **턴 시작 대기와 발화 중 끊김을 한 이름**으로 불렀다.
   (프론트가 `_turnFirstAudioFed` 로 분리 완료. **기존 수치를 새 지표와 같은 표에 놓지 마라.**)

⭐ 교훈: **지표가 두 가지를 한 이름으로 부르면, 그 지표로 낸 결론은 전부 다시 읽어야 한다.**
