# 힌트 예시를 책갈피에 담는다 — 기획

작성 2026-09-05 · 상태 **기획 / 미구현** · 요청: 사장님 + 프론트 문서

> 통화 중 힌트로 나오는 문장도 즐겨찾기(책갈피) 등록할 수 있게.

---

## 0. 프론트 주장 검증 — **3개 다 사실이다** (직접 확인)

프론트가 준 문서의 전제를 코드로 대조했다. 하나라도 틀리면 기획이 통째로 달라진다.

| 주장 | 확인 | 근거 |
|---|---|---|
| `source_type` 컬럼이 이미 있다 ⇒ Alembic 불필요 | ✅ 사실 | `models/sentence.py:33` |
| `call_repository` 가 문장을 **필터 없이** 싣는다 | ✅ 사실 | `call_repository.py:29` `selectinload(Call.sentences)` |
| `HintExample` 에 `id` 가 없다 | ✅ 사실 | `protocol.py:389-394` (korean/roman/native 뿐) |

⭐ 그리고 프론트가 **앱 수정을 이미 끝냈다.** 책갈피 UI 는 `sentence_id` 만 있으면 도므로
  (`PATCH /sentences/{id}/bookmark` 가 이미 있다), 서버가 id 를 실어 주면 앱 수정 0줄이다.

---

## 1. ⛔ 이 기획의 진짜 위험 — 안 하면 사고다

지금 힌트는 **DB 에 안 남고 WS 로만 나간다**(`_hint_sidecar` → `ServerHint`).
책갈피를 걸려면 `Sentence` 행이 있어야 하는데, 그냥 저장하면:

```
call_repository.py:29   selectinload(Call.sentences)   ← 필터가 없다
        ↓
통화 결과 화면에 힌트 문장이 «사용자가 새로 배운 표현» 으로 섞인다
        ↓
⛔ 사용자는 그 문장을 말한 적이 없다
```

⚠ 그리고 조용히 틀린다 — 에러가 안 난다. 결과 화면이 그럴듯하게 더 많은 문장을 보여줄 뿐이다.

⇒ **저장과 필터는 반드시 같은 커밋에 간다.** 저장만 먼저 내보내면 그 사이 통화의 결과가
  오염되고, 그건 이미 저장된 데이터라 되돌려도 남는다.

⛔ 그리고 필터를 걸 곳이 **거기 하나가 아닐 수 있다.** `Call.sentences` 를 읽는 자리를
  전수로 찾아야 한다(결과·복습·발음·증거 추출 등). 착수 첫 단계가 그 조사다.

## 2. 설계

### 2-1. 흐름

```
힌트 사이드카가 예시 3개를 만든다
   ↓
⭐ WS 로 쏘기 **전에** Sentence 로 저장 (source_type="hint")
   ↓ flush() 로 sentence_id 확보
ServerHint(examples=[{korean, roman, native, id}]) 로 전송
   ↓
앱이 id 로 PATCH /sentences/{id}/bookmark  ← 기존 API, 앱 수정 0줄
```

### 2-2. 손댈 곳 3

| 파일 | 무엇 |
|---|---|
| `realtime/call_session.py` `_hint_sidecar` | 전송 전에 저장 + `flush()` 로 id 확보 |
| `realtime/protocol.py` `HintExample` | `id: int \| None = None` 추가 |
| `repository/call_repository.py` (+ 전수 조사 결과) | `source_type != "hint"` 제외 |

⚠ `id` 를 **선택 필드**로 둔다. 저장이 실패해도 힌트는 나가야 한다(R5) — 그때 `id=None`
  이면 앱이 책갈피 버튼만 안 보여주면 된다. 힌트 자체가 사라지는 것보다 낫다.

## 3. ⚠ 아직 안 정한 것 (착수 전 결정 필요)

### ① 힌트 3개를 **다 저장하나, 담을 때 저장하나**

```
A. 다 저장   힌트 뜰 때마다 3행. 5분 통화에 힌트 5회면 15행이 쌓인다
             ⇒ 대부분 아무도 안 담는 문장이다. DB 가 힌트로 불어난다
B. 담을 때   앱이 «담기» 를 누른 순간 저장. 그런데 그때는 sentence_id 가 없다
             ⇒ 새 API 가 필요하다(POST /sentences 같은). 앱 수정도 생긴다
```
⭐ 프론트는 **A** 를 전제로 이미 구현했다(앱 수정 0줄이 그 대가다).
⚠ B 가 데이터는 깨끗하지만 **앱을 다시 고쳐야 한다.** 사장님 판단이 필요하다.

### ② 저장한 힌트 문장이 **다른 기능에 섞이나**

`Sentence` 를 읽는 곳이 결과 화면만이 아니다. 최소한 이것들을 봐야 한다:
- 복습(review) · 발음 평가 · 문장 목록 · 레벨 시스템 증거 추출(`item_evidence`)
- ⛔ 특히 **증거 추출**: 힌트 문장이 «학습자가 말했다» 로 잡히면 레벨이 잘못 오른다.
  `item_evidence` 는 append-only 라 **지울 수 없다**(CLAUDE.md 규율).

⇒ 착수 1단계가 **`Sentence`/`Call.sentences` 를 읽는 자리 전수 조사**다. 필터를 빠뜨린
  곳이 하나라도 있으면 그 기능이 조용히 오염된다.

### ⛔ (2026-09-05 추가) 증거 오염이 이제 **사용자 화면에 직접 뜬다**

기획서를 쓴 직후 dev 에 `f502780 feat(call): 통화 결과에 「이번 통화에서 쓴 표현」을 낸다`
가 들어왔다. 이게 판을 바꾼다:

```
call_service._used_items()   select(ItemEvidence.item_id, ItemEvidence.learner_quote, ...)
```

⇒ **증거(`item_evidence`)를 읽어 결과 화면에 「이번 통화에서 쓴 표현」으로 보여준다.**
  전에는 증거가 오염돼도 레벨 계산에만 영향을 줬는데, 이제 **사용자가 직접 본다.**
  힌트 문장이 증거로 잡히면 «당신이 이 표현을 썼습니다» 라고 화면에 뜬다 — 말한 적이 없는데.

⚠ 그리고 `item_evidence` 는 **append-only 라 지울 수 없다**(CLAUDE.md). 한 번 섞이면 끝이다.

⇒ §4 의 0번(전수 조사)에 이 경로를 **반드시 포함**한다. 그리고 §5 의 3번 회귀가
  이제 «레벨이 잘못 오른다» 가 아니라 «사용자에게 거짓말을 한다» 를 막는 시험이다.

### ③ 통화 없이 힌트만 있는 경우

`Sentence.call_id` 가 필수인지 확인해야 한다. 힌트는 통화 중에만 나오므로 문제없어 보이나,
레벨테스트 통화에서도 힌트가 나오는지(그러면 그 통화 결과에도 섞이는지) 확인이 필요하다.

## 6. 함께 온 것 — TTS 는 서버 쪽이 끝났다

프론트가 같은 문서에서 `POST /api/v1/tts/speech` 를 이미 붙였다고 알려 왔다.
서버 구현은 **완료·커밋됨**(`8c875a4`), 배포만 남았다.

⚠ 프론트가 `character_id` 를 요청에서 뺐는데, 우리 구현은 그 필드가 **선택**이라
  `{"text": "..."}` 만 보내도 대표 캐릭터로 동작한다. 계약이 맞는다.
⭐ 프론트가 «캐시 키에는 character_id 를 남겼다» 고 했는데, 옳은 판단이다 — 서버 ETag 도
  같은 이유로 `voice` 를 키에 넣었다(캐릭터가 바뀌면 다른 소리다).
